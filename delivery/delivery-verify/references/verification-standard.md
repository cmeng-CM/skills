# 交付验证记录内容规范

状态：现行规范；输入输出语义契约版本：1。

验证记录把“要求—方法—实际结果—判断”连起来，让人评估证据是否充分，让模型能够补验和识别失效。它证明特定对象在特定条件下的行为，不能单凭工具退出成功宣布整个任务完成。

## 总体规则

五块语义均必备，允许合并表达。开头用简短概览说明验证对象、结果分布、主要失败和缺口。覆盖矩阵适合表格，异常原因和方法局限用文字解释；原始日志、截图、产物清单独立保存并引用，不把报告变成日志堆积。

正文前记录报告 ID、目标与范围、验证者、时间、skill 名称与实际修订、契约版本、报告版本、产品/交付物版本及验收依据版本。完整交付规则见 [delivery-contract.md](delivery-contract.md)。

## 1. 验证依据与对象

**核心问题：在什么依据下，验证哪个实际交付物？**

最低内容：

- 验收要求、已确认需求或约束来源；无正式文件时明确此次检查项由哪些已明确要求推导，不伪造确认。
- 实际对象及版本：代码、生成文档、安装包、已安装应用、部署实例或其他交付物；需要时记录内容指纹与可恢复位置。
- 环境、依赖、账号权限、输入数据及必要前置条件；包含会影响结论的配置和版本差异。
- 本次范围、排除范围及依据，实际可执行与受阻部分。
- 操作授权；测试名义不自动授权外发消息、生产写入或发布。

**完成判据：** 读者能判断证据对应的实际产品，而不是误将生成器、源码或另一个安装版本作为交付物。

## 2. 验证方法与覆盖

**核心问题：每项要求怎样取得足够的证据？**

按验收项组织，不按任务机械分配一条命令。每项给出稳定 ID、要求、方法、预期结果、环境、证据类型及限制；一组有效证据可以覆盖多项要求，明确映射即可。

| 对象/要求特点 | 适合的方法 | 不能替代什么 |
| --- | --- | --- |
| 纯逻辑、边界处理 | 自动化测试、定向探针 | 真实安装或环境交互 |
| 跨模块行为 | 集成测试、可控端到端操作 | 未参与测试的外部系统状态 |
| 构建交付物 | 实际文件内容、签名、架构、安装检查 | 仅阅读构建脚本 |
| 文档/图表 | 内容核对、实际渲染检查 | 只检查生成代码或源格式 |
| 外部状态 | 实际状态读取与前后比对 | 只看本地请求返回成功 |
| 人工体验要求 | 指定对象上的真实人工操作记录 | 自动点击、离屏渲染或模型主观猜测 |

规定方法不能被更容易通过的方法静默替换。环境不具备时，补充方法说明能够证明的子范围，原要求仍保留未验证。方法选择中的重大歧义记录并按已有授权处理，不自行降低验收标准。

用一个反例检查方法是否足够：实际入口未接入、目标状态未改变或消费者没有收到结果时，该方法还会不会通过？若会，说明只能覆盖子范围，补足实际对象证据。mock、组件或构建检查可以复用，但不自动升级为端到端结论。

**完成判据：** 范围内没有无归属的验收项；验证方法能够观察该要求的核心结果，而非只检查一个无关代理指标。

## 3. 执行过程与证据

**核心问题：到底做了什么，看到了什么？**

每次相关检查记录：

- 时间、验证者、实际对象版本和环境；
- 输入、前置条件、准确命令或可复现操作步骤；
- 预期结果与实际结果，退出码只是实际结果的一部分；
- 原始输出、截图、状态快照或产物位置，以及对应的验收项；
- 中断、失败、重试和已知测量限制。

保存证据时保留可审阅内容，必要敏感信息脱敏并注明删减及可核实的受控来源。不得为满足留存而暴露秘密，也不能把已脱敏摘要冒充完整原始记录。

执行前后核对对象与有关环境是否变化。测试生成的正常缓存可以说明后排除；若产品在验证期间发生实质改变，该批证据是否有效必须重新判断。禁止将旧版本通过结果和新版本失败结果拼成新版本全部通过。

人工证据记录谁、何时、在哪个对象上、做了哪些操作、观察到什么。用户对方案说“可以”不构成运行验收；已有授权不需要重复询问，但授权和实际观察不能混淆。

**完成判据：** 另一位检查者可复核判断路径，关键证据可定位；不能只有“测试通过”或没有原始结果的命令列表。

## 4. 逐项判断与限制

采用以下语义，不要求固定英文状态码：

| 结果 | 使用条件 | 必须保留的说明 |
| --- | --- | --- |
| 符合 | 当前有效证据满足该要求 | 证据、对象、覆盖边界 |
| 不符合 | 有证据表明未满足要求 | 预期与实际差异、影响、关联问题 |
| 未验证 | 未执行、被阻塞或证据不足以判断 | 原因、缺少什么、解除条件 |
| 不适用 | 明确范围依据排除该项 | 排除依据及其有效性，不能自行删要求 |

若一项包含多个可分别判断的行为，应拆成子项或记录部分结果；不能因部分符合就把整体标符合。发生失败和未验证时同时保留，不能用“未完成”掩盖确认失败。

验收项的结论受其前置约束。前置指设计/计划为该验收项声明的适用时点或依赖场景（如「删列后」「部署后」）。前置未满足或无法确认时，结果只能取「未验证」，并在说明中注明前置状态；不得取「符合」。前置判定为「不适用」需给范围依据。逐项表以「前置满足」列记录该判断。

用户明确接受某个缺陷，不把结果改为符合。若用户正式修改要求，引用新版本，说明重评范围；历史记录仍对应旧要求。未经用户或项目规则允许，不能把关键证据缺失包装成可接受风险。

复用证据逐项核对：对象及内容是否相同、要求是否变化、相关环境是否相容、后续修改是否可能影响结果。写明复用理由；无法确定时补验，禁止只根据“同一提交”或“之前通过”推断有效。

**完成判据：** 每项要求有可辩护的判断及限制，读者不会把未知、不适用或风险接受理解为技术达标。

## 5. 验证结论与后续

分别汇总符合项、不符合项、未验证项和有依据不适用项，并列出阻断范围。只在所有当前必需项都有有效符合或不适用依据时，声明本次范围验证通过；存在失败或缺口则如实交付验证活动结果。

建议后续按原因反馈：

- 实际产品或正式测试需要修改：反馈实施；
- 任务遗漏或依赖安排问题：反馈规划；
- 要求矛盾或机制不可成立：反馈设计；
- 证据不足且对象未变：安排补验；
- 缺少环境、权限或人员：列出具体条件，不能自动归因产品失败。

本 skill 不自动调用这些能力，也不改变编排状态。带限制交付由调用方基于明确接受记录和项目不可豁免约束判断，验证报告保留事实。

补验或修复后验证生成关联记录，保留原失败、修复对象版本、检查范围和新证据。新证据只替代其实际覆盖的旧结论，不自动使整个目标通过。

**完成判据：** 调用方知道实际达标程度、未解决事项和恢复路径；“本次验证活动结束”不会被误读为完整交付已经完成。

## 独立性与 first-pass

所有功能任务（小/中/大）的 acceptance 必须有独立 verifier；未声明 acceptance 的机械/文档维护才可自检。逐项记录 attempt、first-pass、回退和 unknown；unknown 不写成 pass。独立验收在 final whole review 之前完成，final 读取验收证据；验收后修改代码，重跑受影响验收并重做 final。环境依赖项在 plan 中前置。
