# Delivery Verify

对实际交付物取得与验收要求相对应的证据，说明哪些满足、哪些不满足、哪些尚不能判断。验证结论与交付决定分开；本 skill 不批准风险例外，也不把局部通过写成整体完成。

## Working Protocol

### 1. 确定对象、要求与条件

用户要求交付验证、验收检查或补验时即可使用，无需点名；也可承接编排委派。识别实际要求的结果，普通问答不启动正式验证；已有任务按真实归属续接，只验证不授权产品修改或完整编排。独立使用不要求先完成其他 skill，也不依赖 `.workflow` 或编排脚本。

读[交付约定](references/delivery-contract.md)和[验证工作规则](references/work-rules.md)。识别实际交付物、需求与验收依据、产品版本、环境、授权操作及已存在证据。没有正式验收文件时从明确需求形成可观察的检查项，不私自改变要求；关键含义不清时保留未验证与阻塞范围。

### 2. 执行与取证

按风险和验收目标选择方法，先确定预期，再记录实际结果。覆盖由验收要求组织，不机械按实施任务逐个重复运行。用户或项目要求的方法必须执行；替代方法只能在适用范围内提供补充证据，不能静默取代。

- 验证真实交付物：构建代码正确不能证明安装包正确，离屏检查不能证明实际人工操作成功。
- 可使用隔离探针和测试数据；不修改业务代码、正式测试、设计或验收标准。需要修复时记录问题并反馈调用方。
- 命令退出码为 0、测试数量或截图存在都不是达标结论；逐项比较预期与实际。
- 核对必要场景实际执行、mock 的证明边界和真实消费者结果；空跑、全部 skip 或读错交付版本不能构成通过。
- 记录环境、输入、动作、时间、版本、原始输出和判断。遇到版本或环境变化评估影响；无法绑定时保留缺口，不能拼接出虚假的一次成功。
- 真实人工验收记录具体人、对象、动作与结论；用户笼统“可以”“继续”不是人工验收证据。

复杂修复的报告可提供原故障条件和诊断证据。验证仍对照既定要求检查实际修复版本、原失败条件和受影响行为；诊断探针、缓解效果及修复者自检不能自动替代规定验收。无法稳定复现时说明所用证据及其证明边界，不能补造“修复前失败、修复后通过”。已有有效证据可按实际影响复用，不为使用 fix 重跑全部检查。

编排内多项验收可以用 `verify-batch` 一次登记：每项有自己的唯一 `op` 和 `config_operation`（必须等于当前配置），其余字段同单条 verify；任一项不满足则整批拒绝、不写半批，全部已存在且请求一致并绑定当前配置时幂等返回。批次不改变验收标准；manual pending、缺少人工确认证据或最新 run 不匹配的项目不能借批量假通过。报告时间引用实际 run 事件时间，不手写成功时间；批量记录使用[批量验收模板](assets/verification-record-template.md)，逐项写 run op、command、exit code、证据对象 hash 与未验证范围。

### 3. 汇总、补验与交接

读[验证记录规范](references/verification-standard.md)，使用[记录骨架](assets/verification-template.md)，必要时查看[完整示例](references/example-verification.md)。逐项使用符合、不符合、未验证、有依据的不适用；失败和缺证据可以同时存在，均须列出。

补验链接原记录，原失败不删改；修复后重新验证受影响项并评估相关影响。复用证据必须核对对象、要求、环境和变化，说明仍有效的依据。用户接受缺陷时保留“不符合”；带限制交付由调用方依据明确授权和不可豁免约束决定。要求正式变更时引用新依据，不能倒改旧验证记录。

## Exit Criteria

- [ ] 实际交付物、版本、验收依据、环境与验证授权可识别。
- [ ] 范围内每项验收要求都有结果，证据不足明确未验证，不用已通过项掩盖遗漏。
- [ ] 结论能回溯到预期、动作、实际结果和原始证据，未将命令成功或作者报告直接当成验收通过。
- [ ] 失败、未验证、不适用分别处理；复用和补验说明适用性并保留历史。
- [ ] 没有越权修产品或正式测试，没有伪造人工验收、用户确认或交付例外。
- [ ] 报告与证据已保存，未完成范围、原因和下一步条件明确；整体交付决定留给调用方。

## Exit Protocol

交付报告路径、逐项结论摘要、失败与缺口、重要限制及建议后续。所有必需项有效符合或有依据不适用时，才可说“本次范围内验证通过”；不扩展为完整流程已收尾。验证活动结束可以带失败或阻塞，不能因此改写结论。

默认报告为 `.delivery/YYYY-MM-DD-主题/verification/001.md`，原始证据放在同目标目录 `evidence/` 下。用户明确仅对话时遵从并说明没有落盘记录。维护本 skill 时使用[行为案例](tests/behavior-cases.json)实际检验行为；仅检查文件结构不能证明验收判断可靠。
