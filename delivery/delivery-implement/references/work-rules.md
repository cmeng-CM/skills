# 实施工作与自检规则

## 开始前

1. 从用户当前目标和明确授权判断工作范围，读取关联项目规则、需求及必要代码，不从计划文件存在与否推断执行授权。
2. 检查实际工作区，识别既有修改、未跟踪文件和本任务改动边界。记录相关基线，不清理不属于本任务的工作。
3. 判断前置条件是产物可接入、验证门禁、设计决定还是环境资源。不能把这些统一降成“代码已提交”。
4. 缺少关键机制或存在矛盾时给出证据和影响。按已授予的自主权作范围内选择，重大未决记录后处理不受影响部分；不凭“质量优先”扩大功能或越权操作。

## 执行中

按真实交付链实施必要代码、正式测试、配置、调用接线和文档。局部实现细节自行合理选择，重大改变需要依据。已有用户授权覆盖时无需重复询问；授权不清且无法安全限定范围时停住受影响操作。

对依赖组区分已实现、可接入与已验证。前置产物达到计划声明的可接入条件可以继续，但明确的提前审查/验收门禁不可跳过。独立调用没有编排计划时，记录自己的客观产物条件，不制造整个任务的全局状态。

共享工作树、Git index、测试数据库或生成目录需要写入时，先核对调用方的持有者、隔离位置和交接条件。只读调查可并行；不能因任务没有产品依赖就假定可以同时写同一资源。遇到冲突记录具体资源与影响，暂停相关写入或采用已授权的隔离方式，不重置暂存区、不覆盖他人文件。普通独立调用不需要编排锁文件或专用 JSON。

针对风险运行必要检查。先用定向检查定位，相关测试通过后不要无依据反复重跑；有新的改动、失败或未解决风险时扩大验证。测试覆盖异常、边界、兼容或组合路径按实际相关性确定，不能用单条快乐路径证明所有行为。

发生失败时保留输入、版本、结果和诊断依据。修改范围内缺陷并重测；发现需求、契约或验收需要改变时记录反馈，不静默放宽测试。无法完成时交付部分产物和阻塞条件，不能把同一失败反复重试当作进度。

中断或交接前记录实际产物/差异、正在执行或可能已产生副作用的命令、相关资源持有者、已知结果、未知部分和下一步条件。恢复时先读记录并核对当前工作区、进程和实际输出；有启动记录但没有完成回执的命令不能凭进程消失或“没看到成功”直接重放。先核查副作用，保存允许重试的理由及证据；无法判断时保持该部分未知。该记录可以是本次实施报告，不另造第二份实时状态。

## 提交与最终工作区

提交依据用户或项目已有授权，选择编排本身不授予提交权限；无明确依据时默认不提交。已有本地提交策略时，按任务边界、依赖与审查便利组织可理解的提交，不要求每个任务一次提交，不 push。用户与项目既有规则优先。提交前检查真实 diff、暂存区和归属，仅纳入本任务变更；不能用 `git add -A` 无差别收拢共享工作区。无法可靠隔离时记录并由调用方处理，不重置他人修改。

提交不等于审查或验收。修复可以形成后续提交；报告说明变化绑定的实际对象。最终记录包括已提交部分与剩余工作区变化，不能只写最后一个提交号。

## 成文自检

- 报告是否明确实际行为而非罗列文件？计划未形成的产物是否可见？
- 是否读过最终 diff 和相关调用位置，检查意外改动、遗漏接线与测试有效性？
- 每个“通过”是否来自实际执行，证据对应的对象是否仍然相同？
- 未执行、受阻与失败是否分别说明？作者自检是否冒充独立结论？
- 重大歧义与决定是否可追溯，用户确认与模型判断是否分开？
- 下游可以做什么、不能跳过什么，是否明确？

这些是语义检查，不能通过标题、字段或文件数量检查替代。项目已有确定性检查可以补充，不要求为了报告添加专用程序。
