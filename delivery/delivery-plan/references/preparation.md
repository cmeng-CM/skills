# 准备、共识承接与输入就绪

本文件负责如何进入规划；七章内容标准只由 `plan-standard.md` 维护。

## 识别输入与权限

先提取用户当前目标、模式、交付位置、指定材料及授权范围。生成、审阅、调整是不同请求；已有写入授权直接承接，不重复征询。仅要求讨论或审阅时交付建议与发现。

| 输入 | 处理 |
| --- | --- |
| 已有技术方案 | 定位当前版本、适用章节、契约、关键决策与验收；核查是否足以规划 |
| 已确认讨论 | 保留结论、理由、前提、限制、未决事项及确认凭据，检查组合后是否仍一致 |
| 明确的小改动需求 | 将必要设计依据内嵌第 1 章或附录；技术机制不明时先澄清 |
| 已有计划 | 先识别当前有效版本、稳定 ID、外部设计与执行记录的权威位置 |
| 实际失败或执行反馈 | 保留原始证据、适用版本、环境与影响范围；不把反馈直接当成新设计批准 |

技术方案是逻辑上的设计依据，不强制独立文件。没有独立方案不构成自动阻塞；有完整文档也不自动代表设计充分或已确认。

## 定向查事实

阅读项目规则与用户指定入口，再按交付范围定位相关实现、消费者、契约、测试和构建说明。注明实际读取的位置、代码版本和有影响的未提交改动。未读取的位置不能写成已核实；计划新增路径要标为拟新增。

代码只能证明当前行为。不能仅从旧实现推断历史设计意图、用户已经确认或某种平台保证成立。命令从项目脚本或说明查得；没有核实的命令标为待核实，说明在何时、由谁或通过什么方式补齐。规划不自动运行项目测试、写入数据、安装软件或修改业务代码。

## 复用共识与处理缺口

先整理“明确事实／已确认决定／模型推断／未决事项”，不要把整段聊天重新转成问卷。来源冲突时列出原文或准确定位、实际差异与受影响对象。

判断缺口是否影响目标、业务行为、模块职责、契约、数据含义、正确性保证、交付恢复或重要风险。涉及这些关键选择时，给出最关键的问题、可查证据、真实选项和推荐，等待必要决定；不在任务步骤中写“实现者自行选择”。

问题只阻塞受影响任务及其必要下游。共享核心契约未定时应扩大到真实影响范围。用户明确要求条件草稿时，可以列备选路径、假设和解除条件，但不得标为可执行定案。

关键决策记录格式遵循规范第 7 章。模型提出、用户确认仍是模型来源；未知来源保持未知。附条件确认必须保留条件。非关键的局部步骤和命名不逐项要求用户批准。

## 决定细化范围

| 情况 | 要求 |
| --- | --- |
| 小改动且路径明确 | 一个阶段或合并表达，一次细化完整 |
| 较大改动或依赖前置实际产物 | 全局成果、范围、主要依赖、验收和收尾完整；先细化当前工作 |
| 后续任务暂不展开 | 记录待细化的部分、细化时点或触发条件、所需材料和影响；不能隐藏范围或设计缺口 |
| 阶段准备启动 | 按实际代码、前置产物与限制补齐任务卡和验证方法，再判断执行所需条件 |

不以任务数量或固定时长机械区分规模。阶段用于细化与检查，不代替依赖和门禁。

## 调整已有计划

先读取有效计划和相关执行证据，识别变更触发、原约束及当前基线。核对哪些事实确实发生变化，区分实现偏差、设计内调整和关键设计变更。

更新有效正文及受影响的任务、条件、覆盖、验证组和恢复约定；稳定 ID 不重排复用，拆并任务保留映射。证据不自动全失效或全复用：记录影响理由，受影响项失效，无法判断的标为待核实。保留历史结论，当前有效状态由执行记录维护。

仅调整计划不能把尚未执行的检查变成成功，也不能重写外部设计或执行记录来制造一致。关联材料确需更改但超出授权时，列出需要联动的文件、内容与原因。
