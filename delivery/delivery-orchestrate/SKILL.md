# Delivery Orchestrate

把五项基础独立能力及按需选用的复杂修复能力组织成一个有明确范围、实际证据和可恢复记录的交付任务。质量由专业判断、独立审查和机械门禁共同保障；脚本不替代语义判断，也不自动调用模型。

## Working Protocol

### 1. 确认入口与承接范围

用户明确选择、项目指定、已有任务续接，或主模型判断开发需要组织依赖、阶段衔接、审查验收与持续交付状态时进入，无需点名。先核对用户限制、已有任务归属和实际影响，再决定是否初始化；可独立完成验证的局部开发优先专业处理。任务难、文件多、使用多个技能或一次额外独立审查，不单独构成编排理由。仅问答、讨论、学习或明确限定的专业结果按其范围处理。已有正式流程继续所属体系，同一目标不能由两个引擎同时控制，不能以本轮改动小绕过原门禁。

路由硬特征：出现下列任一特征时进入编排，或在目标目录 index.md 记录一行「硬特征命中 + 未编排理由 + 时间」作为可审计的路线决定，不静默走轻路径：① 不可逆 DDL 或删除数据/列；② 生产环境部署、发布或配置变更；③ 权限、RLS、密钥或管理员口径变更；④ 需要多批外部授权的操作窗口。特征口径与 delivery-design 的高风险跨边界词表（数据丢失/不可逆迁移、权限越权等）对齐，用于路由判断，不替代其合同包要求。留痕不是审批，不因命中特征重复索要授权。

初始化前允许核对后返回专业处理，不能为判断路线先建立空 runtime。记录简短选择依据即可，不另建评分表或路由报告；无需新增路由技能或逐项目配置。信息可查先查，用户意图或关键决定不明再澄清。单项处理发现新依赖或阶段组织需要时，由主模型在已有授权内升级；保留实际改动、作者、失败、未知副作用和原记录，不重置历史。专业 skill 提供事实与建议，主模型负责安排，不让能力互相递归启动流程。

读取用户目标、项目规则、已有设计/计划/实际记录和授权。已确认决定连同条件复用；只有影响当前工作的新选择才需要处理。用户明确授予质量优先决策权限时记录具体判断与影响，不把模型决定写成逐项用户批准；超出授权、不可逆外部动作或硬约束冲突仍按实际权限处理。

读取[编排协议](references/orchestration.md)及[接入与演进](references/contracts.md)。没有现成设计可从 design 开始，有明确小需求可直接 plan；有有效计划可实施，已有实现可从审查/验证进入。复用前核对范围、版本、真实确认与未决项，不为走流程重建同范围文档。

### 2. 建立工作目录和质量安排

新目标默认 `.delivery/YYYY-MM-DD-主题/`；同目标沿用已有目录，跨日不改名。只建实际需要的文件。`index.md` 仅导航，专业能力写自己的 Markdown，`runtime/` 仅本引擎维护；index.md 的唯一例外是三类单行留痕（路线决定、批准记录、占用登记），每类一行，不属于进度跟踪。执行状态看 `status.md` 生成区与 journal；`status.md` 由命令生成，人工补充区不参与门禁，`index.md` 不复制状态表。

首次 configure 前运行只读 `preflight`，确认依赖/生成目录候选后显式写入 `monitor.exclude`；不在引擎内静默排除。在途工作补 exclude 用 `category=organization` 重新 configure，满足准入输入等价时用 `reuse_gates` 复用 design/plan/mapping gate，change_review 必须新做。任何产品、来源、范围、任务、验收、requirements、resources 或路线变化都不复用。

续接时检查实际目标在 `.delivery/` 或旧版 `docs/delivery/` 的既有目录，沿用已建立的归属；不自动搬迁旧账本或改写历史路径。多个候选时核对目标与来源。

从可用 skill 列表、项目指定路径或实际安装位置定位并读取 `delivery-design`、`delivery-plan`、`delivery-implement`、`delivery-review`、`delivery-verify` 的 SKILL.md。复杂故障按需定位并读取 `delivery-fix`，普通任务不依赖它。按需加载，缺少所需能力时如实报告，不能静默以旧 skill 或模型自述替代。读取技能协议不是一个固定返回值的函数调用。

计划按交付任务实施、按风险和集成边界审查、按验收要求验证。每项任务有审查与验收归属；提前门禁有实际风险依据，整体审查覆盖全交付。联合检查任务、审查、验证依赖无环，组内接入条件不等于最终验收通过。

### 3. 语义接纳与状态初始化

先读真实正文核对要求覆盖、范围、实际基线和授权。新目标使用[契约 2 API](references/runtime-api-v2.md)，明确 `init --contract-version 2`；既有 v1 按 [API 导航与原规则](references/runtime-api.md)继续，不静默升级。编排侧 JSON 绑定来源和准确摘录、映射理由、实际 actor/context、采集的 skill 来源及契约版本；正文仍是专业定义真源。能力独立使用不必输出该 JSON。

大任务初次实施、重大重规划需要真正独立的计划审阅；设计按机制风险触发独立审阅。专业标准分别归 design 和 plan。正文到准入配置的映射始终独立复核，可与专业计划审阅同次开展但分别给结论；实现 review 不替代二者。v2 configure 仅保存候选准入，必要 gate 当前通过后才能推进。规范顺序固定为 configure → gate → implementation：批准前可编辑 plan/design，批准后只读；范围、任务、依赖或验收变化产生新版本并重新 gate，代码位置/局部步骤调整只写实施记录的偏离段，不回写批准版本。

第一次编辑产品文件前运行 `guard`，把结果写进实施记录；未通过不进入实施。review 的 guard 必须带实际 actor/context，并与该审查覆盖任务的全部历史实施作者比对；status/next 同时反映 protected_index。guard 是流程检查与可检测诊断，不阻止模型直接编辑；真正的拒绝仍在 record/run/close。实施与审查按任务切片派发，不把整份 plan/design 粘贴给执行者，需要更多内容时按章节路径读取。

多任务需要按批次一次逻辑审查、独立批次只读并行、最后整体终审时，建议显式启用 review_protocol=2：每个任务恰属一个非 whole 批次，恰有一个 whole final，final 依赖全部批次。协议 2 需要 Git，首次 configure 捕获不可变 base_commit；review record 带 review_commit/base_commit，record 硬校验批次 passed、commit 谱系、HEAD/干净工作树/非空 diff，最终审查者排除实现者和历史批次审查者。它是显式 opt-in，引擎不隐式默认；小型/非 Git 工作保持旧 review。具体契约见 [runtime-api-v2](references/runtime-api-v2.md)。

质量-成本组合的固定顺序：design 冻结 → plan/mapping/change gate → 实施批次 → 独立验收 → final whole review → close。final 读取验收证据；最终审查者排除实现者、历史批次审查者和 verifier。验收后修改代码必须重跑受影响验收并重做 final。batch review 只对含代码且达到最小变更/风险阈值的批次单独进行，小批并入相邻批次；记录 review yield。环境依赖验收在 plan 中前置。试点/统计按 [metrics.md](references/metrics.md) 记录耗时、token 和 first-pass/unknown；没有价格表时只报 token，不报金额。

所有状态操作用本 skill 目录下 `scripts/delivery.py`，不手改 journal 或复制旧运行状态。工作目录只有一个协调者负责准入和流转，子 agent 返回自己的报告；并行执行的文件范围与资源使用必须明确。

初次配置、来源改变后的重新配置都需核对语义。字段齐全不等于计划合理；源文件版本不符时必须重新接纳，不能只换摘要保持旧结论。原始契约版本未知时拒绝接入，按兼容规则处理。

区分授权内局部实现、计划组织调整和重要范围/契约/验收变化，绑定当前具体授权，不对已批准的小调整重复询问。v2 对范围外变化先形成清单，再接纳有依据的影响判断；相关证据定向失效，未知影响保持阻塞，不能全忽略或一律全量重验。

### 4. 质量优先调度与闭环

以预期质量、上下文、工具条件及实际表现选择主 agent 或子 agent，不固定每步一个 agent。委派使用[交接骨架](assets/dispatch-template.md)，带范围、输入、允许修改处、验收归属、报告位置及反馈条件；不因委派扩大权限。部署、批量验收、大型复审等可用 brief 清单化交接的阶段，优先切分到子代理或新会话执行：长会话尾段每次请求重复支付全上下文 cache read，成本随会话长度线性上升；主会话保留协调与判断，阶段产物以报告回流。切分不可行时（强依赖会话内上下文）说明理由。

实施任务默认使用 implement；复杂故障可以显式选择 fix 或从 implement 转交，按 [实施子契约 1](references/runtime-api-v2.md#可选复杂修复接入实施子契约-1) 启用并配置。只读取新包或启用协议不代表准入通过，来源更新和适用 gates 仍须有效。fix 直接返回 bug 目录内具体轮次的报告作为实施产物，不再要求重复实施或另写同内容正文。诊断完成、缓解措施和修复完成分别判断，未完成修复不能登记为实施通过。

实施按实际代码和任务完成产物及自检；所有参与实现的作者和上下文应有真实记录。审查者不得是相关实现者，不能通过更换名称、删除旧作者或换 skill 伪装独立。审查直接读取实际产物，规格与质量分别给结论；缺少独立审查能力时保留待审，不放行依赖它的工作。

接纳报告前核对其内容和实际证据，再用 `record` 留存。运行已声明自动验收用 `run` 捕获真实输出；命令退出码 0 仍需验证者对标准给出判断后记录。人工项须真实项级确认，内容检查须有实际产物证据，缺证据保留 unknown。

发现问题按原因回退：普通实现缺陷回 implement，复杂诊断修复按接纳路线回 fix；拆分和依赖缺口回 plan；机制或契约改变回 design；证据不足回 verify。复审原问题与修复影响，必要时扩大。连续两轮同类失败没有实质新证据时停止原样重试，重新诊断并记录；不是自动放弃、豁免或降低标准。

审查分层：首轮全量，复审只读版本差异、原问题闭合与受影响章节，高风险任务保留一次整体终审；机械变更可用检查表 + 一次针对性审查，但不取消 mapping/change（必要时 plan/design）gate。普通任务最多一次全量设计评审 + 一次全量计划评审，超出预算需在计划说明理由。同一实现范围保持单写者；审查进行中协调者不编辑被审文件；批量同型编辑一次完成，编辑后重新读取再改。

用 `brief/status/next` 的同源视图重建必要上下文，硬约束保留完整来源；摘要不能代替阅读。工作树、Git index、共享测试库与生成物明确资源占用和交接，无冲突只读工作才并行。v2 未完成 run 需要证据化核查和新的真实运行/判断才能解除收尾阻塞，资源 release 或更换 op 都不能独自绕过。若来源已合法变化且旧命令不再适用，按 [API 的恢复子契约 2](references/runtime-api-v2.md#恢复子契约-2旧命令不再适用时转接当前计划) 显式调查并承接责任到新计划；查清副作用只允许重规划，最终验收门槛保持不变。

### 5. 提交、验证和收尾

提交、安装、发布等操作遵循仓库特殊要求；仓库没有特殊要求时，完成一个功能完整、可独立验证的批次后默认本地提交，按功能完整性分批，不把无关改动混入，永不自动 push。仓库禁止提交、要求特定分支/提交格式或用户另有要求时从其规定。提交前核对实际改动和暂存范围，只纳入本批文件，保留用户原有修改；提交、自检、审查通过与验收通过分别记录。

非 Git 工作区仍可实施和留存证据，不伪造提交。存在未提交改动时使用实际范围快照，不以 HEAD 冒充交付版本。提交失败或安装受限不是验收通过；记录实际情况并处理。

运行 `status/check/next` 核对当前绑定、问题及缺口。完整收尾要求当前实施、独立审查和全部必需验收通过。仅已实证失败、允许例外且有具体用户授权的验收可申请 `limited`；未知、过期证据、失败的独立审查不能豁免。验证原不符合项保留，不能称为全部通过。

收尾顺序固定为 `check --preclose` → `close` → 写 `status.md`/`closeout.md`，并同步 `index.md` 的纯导航当前边界。`check --preclose` 只读，`close` 会以同一请求重跑其阻塞判定；阻塞项必须修复，孤儿 admission、旧工作缺 status/index 等警告可带说明继续。`close` 的 `report.path` 必须是 work 下固定的 `closeout.md`；close 后不修改批准版本，视图写失败只警告并允许重试。历史关闭不覆盖；后续修改先显式 `reopen`，不能拿旧收尾证明新版本。恢复时读取 journal、当前产品与原始证据，按真实差异决定复用和复核。

## Exit Criteria

- [ ] 入口、目标、授权和实际来源明确，基础专业能力和可选 fix 仅按需要使用。
- [ ] 计划覆盖任务、独立审查、验收及联合依赖，语义接纳有依据；批准版本未被编辑。
- [ ] 第一次编辑产品文件前 guard 已通过并留证；当前实施和非实现者审查已满足要求；历史失败与处理关系可追溯。
- [ ] 逐项验证有当前有效证据，命令成功、语义通过和人工确认未混淆。
- [ ] 只改本次范围，按适用规则本地提交；未擅自 push。
- [ ] 正常或带限制交付的条件已真实满足，`close` 成功；没有以未完成代替完成。

## Exit Protocol

报告实际完成范围、文档与证据入口、运行状态、本地提交及需要用户查看的重大选择。区分全部通过、带限制交付与尚未完成；机械检查通过不是全局质量证明。

中断时保留真实已完成部分、阻塞和恢复入口，不重建空流程。已接纳配置时，依次用 `python3 -B <本skill目录>/scripts/delivery.py <子命令> --work <工作目录>` 执行 `check`、`status`、`next`；仅初始化时先按真实依据完成 `configure`。详见[中断恢复步骤](references/orchestration.md#中断与恢复)。新会话或新协调者接续实际记录，不依赖旧聊天或子 agent 存活；未留存的步骤不能推断为完成。不写长期记忆或其他项目材料，除非用户另行要求。

维护时使用 [validate_suite.py](scripts/validate_suite.py) 统一执行包检查和确定性回归，或按影响运行原单组命令；真实模型案例见[评测入口](tests/evaluation/README.md)。机械测试、真实行为演练与独立审查分别记录；适用版本、同步范围与活动流程处理见[维护与升级规则](references/maintenance.md)。
