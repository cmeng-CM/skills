# 编排操作与质量协议

## 进入、续接和目录

先识别用户限制、已有任务归属与期望结果，再做必要只读检查。开发需要组织多任务依赖、阶段衔接、审查验收和持续交付状态时，由主模型选择编排；可独立完成验证的局部任务优先专业处理，无需用户点名。任务难、文件多、使用两个技能或额外一次独立审查本身不强制编排。明确只讨论、只设计、只审查等请求不扩大成开发或完整流程，意图不清先澄清。

初始化前允许核对后返回专业能力，不为判断适用性先创建空 runtime；简短选择依据写在已有记录中，不另建路由报告。专业能力负责自己的产物与事实反馈，主模型按需安排后续，不递归调用。独立活动升级时沿用同目标目录，保留改动、作者、失败和未知副作用，再核对版本与真实接纳条件；外部命令回执不能冒充引擎 run。

已有正式工作继续所属体系，局部修补不绕过原门禁；同一目标不能由两个引擎同时控制。存在多个候选工作目录时按真实目标核对，不能按名字相似合并。

默认目录为 `.delivery/创建日期-主题/`，日期不随会话改变。design.md 和 plan.md 维护规范性定义，批准后只读；implementation、review、verification 目录保存带序号的实际活动报告；一般 evidence 保存原始证据；可选复杂修复的报告和证据统一在 `fixes/BUG-标识-简述/NNN/fix.md` 与该轮 `evidence/`，同 bug 的 index 只导航；工作 index 只导航；`status.md` 是脚本生成的派生状态视图，人工补充区不参与门禁；runtime 的状态由脚本独占维护，被拒写命令另记 `runtime/rejected.jsonl`。只生成实际发生的材料。

默认目录变化只作用于新目标。既有目标可继续使用旧版 `docs/delivery/` 或用户指定目录；定位恢复入口时同时核对这些实际记录，不迁移、复制或重写旧 journal 来适应新默认路径。引擎绑定了实际工作目录和项目内来源路径，移动目录需要另行设计迁移，不能仅执行文件夹重命名。

独立活动可以接入同目标编排，先核对依据、版本和权限，保留原文件。更大范围的上游设计精确引用，不复制成当前目标的第二份设计。

## 路线与质量门禁

| 当前输入 | 先做什么 | 进入下一步的条件 |
| --- | --- | --- |
| 只有需求且机制未定 | design | 目标、关键机制、契约和验收足够明确，重要未决范围已处理 |
| 有适用设计或明确小需求 | plan | 当前任务可交接，全局覆盖与审查/验收安排完整 |
| 有可执行计划 | implement；复杂故障可选 fix | 依赖和授权满足，范围及版本可识别 |
| 已有实现 | review / verify | 补足真实要求映射、作者与版本，再按标准检查 |
| 有失败或变化 | 对应能力定向返回 | 问题、影响、处理与新的依据均可追溯 |

已有源文档的确认须保留原文、条件和范围。用户“认可”只对应当时明确提出的事项；模型提出不等于未获批准，也不因来自旧实现就算已确认。一般代码局部组织无需逐项批准，重要方案变化按实际授权处理。

plan 不要求每项任务独立运行同一套测试；审查组与验证组可交叉覆盖。提前审查适用于关键契约被下游消费、错误广泛传播、不可逆影响或现有控制不足。整体审查可与最后一组兼任，但必须覆盖所有交付和跨组关系。

新目标显式使用契约 2；已有契约 1 的目标按原规则继续，升级采用关联的新目标并重新接纳。v2 中 configure 先保存待准入配置：正文到运行快照的 mapping_review 恒为必需；大任务首次实施和重大重规划须 plan_review，design_review 按风险选择。专业审阅方法归 design/plan；编排只管理触发、独立性和版本绑定。同一次独立活动可以给专业计划与映射两种结论，分别登记，不重复审阅同一内容。

首次 configure 前先运行只读 preflight，确认后把依赖/生成目录写进显式 `monitor.exclude`；configure 的未排除高收益目录 warning 不是接纳结果。在途工作补 exclude 只允许 organization + 准入输入等价时用 `reuse_gates` 复用 design/plan/mapping gate，change_review 必须新做。

规范顺序是 configure → gate → 第一次编辑。批准前可编辑 plan/design；批准后只读，范围/任务/依赖/验收变化产生新版本并重新 gate，代码位置/局部步骤调整只写实施记录的偏离段。第一次编辑产品文件前运行 `guard`，把结果写入实施记录；guard 不阻止直接编辑，但 record/run/close 仍拒绝未过门禁或未持资源的工作。status/next 的 `ready_to_implement`/`blocked_reason` 与 guard 同源，被门禁或依赖阻塞的任务不列为可执行。

阶段检查回答本阶段哪项真实能力已成立，实际生产者/消费者是否贯通；不要求所有阶段另建机器状态。原有任务、审查和验收依赖表达必要门禁，组内可接入条件满足即可推进。

引擎 `next` 只反映已接纳的依赖，不证明自然语言的客观接入条件成立。实施者和编排器必须核对实际产物、版本、限制与语义条件，再执行。引擎无法表达的条件不能静默省略，应在准入时声明必要前置或阻塞，并在报告保留理由。

## 委派与身份

根据质量选择主 agent 或子 agent，避免固定“简单主做、复杂子做”。判断上下文掌握、所需工具、专注度、历史结果和可核验性。任务边界明确且文件不冲突时可以并行；共享文件或必要依赖按实际顺序协调。

委派保留原始要求和明确产物路径，子 agent 写自己的报告。编排器直接核对真实变更和证据，再接纳结果；不能仅转述“已完成”。需要沟通新决定时带事实、原约束、方案与影响，已有授权下可继续不受影响工作。

一个任务多个实现者都要如实登记，审查排除全部相关实现者及其上下文。独立者同样需要原始要求和产品上下文；独立不意味着盲审到不知道需求。仅更换名字或角色标签无效。

## 准入记录与检查

编排器先完成语义核对，再准备 JSON。schema、契约和参数按 runtime-api；所有来源路径相对项目根，摘录必须确实存在。来源来自外部会话时，将真实原文与来源说明留在工作目录，不编造当事人确认。

报告和证据的最少存在性检查不能证明结论正确：报告要回答要求、实际行为、证据与限制。检查器发现结构错误时修正真实遗漏，不能降低标准使检查变绿。未知或待验与失败不同，不能混写。

配置变化后默认拒绝旧准入，重新核对受影响对象。需要复用未变结果时显式说明理由与范围，由引擎核对可验证条件；新版本正文不能借旧批准自动放行。仍有效证据可复用，不因换人或换会话机械重跑。`reuse_gates` 只在 organization + 所有准入输入等价 + 仅 `monitor.exclude` 变化时生效；`reused_gates` 在 gate_state 中仍会因 source_hashes、pin、证据或原来源过期而 stale。

configure baseline 与 impact inventory 对象化后，journal 只保留快照引用；旧 inline 仍可读。新工作首次写引用升级日志容器 schema 2，旧引擎显式拒绝；回滚靠 `journal.schema1.bak` 且有损。不要把 schema 2 当作请求契约变化。

v2 的范围外变化先列出新增/删除/修改及对应变化集，专业判断 related/unrelated，再由 impact 固定依据并传播失效。判断证据变化或文件再次编辑须重新判断；不能把声明范围内的产品修改改标 unrelated 复活旧结论。派生记录/缓存排除须具体说明，不整体忽略 `.delivery` 中可能存在的真实来源。

授权内局部实现和任务组织调整保留理由，重要目标、契约、验收或风险变化绑定具体新授权。脚本核对版本与引用，协调者核实真实含义。一次“认可”不能覆盖尚未提出的重要变化，也不对已经授权的实现细节重复询问。

skill_sources 采集实际内容和可恢复对象，恢复时核对实际加载引擎及专业包。纯路径搬迁、兼容更新和不兼容更新按 source-update 分别处理。兼容判断需要实际输入输出/质量/行为检查，摘要相同与语义兼容不是同一事实；五个专业包继续自行记录独立修订，不依赖这些命令。

## 命令证据与人工项

正式自动验收用引擎 `run` 执行计划中声明的 argv，以项目根为工作目录，无隐式 shell。需要 shell 时必须在计划中明确命令与权限。诊断命令是定位证据，不能替换必验命令。

记录实际退出结果、完整输出及前后范围快照。失败/超时保留，重试使用新操作 ID；同一 ID 重试用于恢复同一个操作，不用于强行覆盖失败。若执行改了产品，先处理变化再对正确版本验证。

退出码 0 后，验证者仍需按标准判断并写报告。UI、安装包、跨仓库或外部服务验收需要直接检查实际对象，源代码和本地 diff 不能替代。无法访问对象时记录 unknown，不凭经验写通过。

人工项应列清单、操作、预期结果，由真实用户逐项确认；允许一条答复明确覆盖多项，但未确认项仍未完成。提供具体来源与摘录，脚本只核对引用，编排者对来源真实性负责。

## 问题和修复

| 问题性质 | 返回环节 | 对原证据的处理 |
| --- | --- | --- |
| 实现违反既定要求 | implement；复杂诊断修复可选 fix | 修复后复审及验证受影响范围 |
| 缺任务、错误依赖或验收安排 | plan | 更新映射并核对受影响结果 |
| 机制不成立、契约需改变 | design，再核对 plan | 保留原结论，说明新确认与失效范围 |
| 证据不足或环境不可用 | verify 或环境准备 | unknown不写成实现失败，不制造通过 |

复杂故障按实际需要选择 `delivery-fix`：先合法接纳实际源码，再显式启用实施子契约 1，以正常 configure 登记任务路线和 bug 归属，并通过适用 gate。普通任务不需要 fix。原 implement 转交时保留任务、验收和问题责任，以及全部作者、改动、已排除原因、失败实验和未知副作用；新配置不自动把旧实施通过重用为 fix 通过。

fix 的具体轮次报告直接作为 implementation 产物接纳，记录真实专业 pin 和完整实施作者，不另造重复正文。编排器判断报告是否满足本任务完成要求；诊断完成、暂时缓解、授权修复、自检、独立复审与最终验收分别给结论。修复后仍走既有 review/verify，局部修复不机械重走 design/plan，发现机制或契约变化再反馈相应能力。

同一 bug 跨轮次、日期、会话和复发沿用原目录；新任务引用既有 bug 目录和具体轮次，不复制历史或改旧运行状态。已关闭问题复发按引擎规则登记新问题并关联原身份，不能改写旧关闭事实。恢复先读 bug index 和最新相关报告，再核对真实现场、未处置实验和命令副作用。

记录稳定问题标识、触发条件、影响、严重度、阻断性及实际处置。已解决问题复发时，遵循引擎实际身份规则新增问题并关联原问题，不篡改旧历史。修复结论应有新版本和验证依据，不是作者一句“修好了”。

同类失败连续两轮没有新事实或改善时，停止原样循环，重新诊断、缩小复现或安排更适合的 agent；记录策略变化。可在原授权内持续解决，但不能因为超轮数自动接受风险或宣布完成。

v2 的 attempt 保存失败身份、实际事实与策略；恢复继承原诊断。问题关闭以原要求和实际证据为准，修复建议只是可选路径，不能因为实现者用了另一种正确方案而无限返工。只换策略文字而无实质新判断不能构成质量证据。

## 本地提交与收尾

提交、安装和发布遵循仓库特殊要求；仓库没有特殊要求时，完成一个功能完整、可独立验证的批次后默认本地提交，按功能完整性分批，不把无关改动混入，永不自动 push。仓库禁止提交、要求特定分支/提交格式或用户另有要求时从其规定。提交前查看当前工作区、暂存区及明确路径，保留原有修改；不要用全仓库暂存把不相关文件带入。

提交可以作为阶段快照，不代表最终质量通过。审查、验证绑定实际文件内容，后续提交若只改变提交标识而文件不变，不应人为使证据失效。若提交过程会改文件或生成产物，按实际范围重新检查。

close 前先运行 `check --preclose`，核对来源当前、全任务实施、独立整体审查、所有必验、问题处置、批准后编辑、未知运行、资源与证据缺口；阻塞项修复后再 close。首版 limited 只豁免允许例外且已实证失败的验收；实施和审查仍须通过。未知/过期证据和不可豁免条件不进入例外。close 的报告固定为 work 下 `closeout.md`；收尾顺序为 check --preclose → close → 写 status.md/closeout.md，close 成功后视图写失败只警告并可重试。

`status --write-status` 只替换生成区，保留人工补充；`doctor` 只读检查未匹配 admission、rejected、状态视图、证据和 schema1 回滚点。未被任何事件匹配的 admission 与未处置拒绝是警告，不自动删除用户文件。

关闭后不写入新的活动结果，先 reopen。状态损坏、对象缺失或版本不支持时保留现场，报告恢复需要；不删除 runtime 后重建一个伪装成功的流程。最终报告真实状态、证据、剩余限制和需用户查看的重大选择。

工作树路径、Git index、共享数据库和生成物分别明确读写模式与交接；已持有的写资源不能被另一 actor 强取。只读审查/验收不接管实现者的写锁，close 不重新索取全部写锁。资源是单工作协议，不是阻止未知进程的系统锁；跨工作共享资源仍由协调者排程并检查真实副作用。提交前核对原暂存内容，不能用清空 index 来获得所谓干净环境。

## 中断与恢复

恢复依据是专业文档、已接纳的 journal 事件、原始证据及当前真实产物。聊天历史和子 agent 内存只能补充，不能替代这些依据。引擎不是模型上下文保存器，也不会在新会话里自动继续执行。

1. 定位同目标已有工作目录；先读 index、目标/授权、design/plan 及最近相关活动报告。初始化前中断时可能只有 Markdown，按已有文件续接，不伪造尚未发生的 configure 或执行事件。
2. 检查是否已有初始化账本及 `configure` 接纳事件。仅 `init` 成功、尚未 `configure` 时，`check/status/next` 会返回 `configure required`，这是配置未接纳，不是账本损坏；按真实专业文档和授权完成语义映射，正常 `configure` 后继续，不删除已有 runtime 或伪造历史。已有配置时执行 `check` 核对账本/对象完整性，再执行 `status` 查看当前来源、任务、审查、验收、问题及未完成运行。读取的是当前文件与持久事件，不需要原协调者仍存活。
3. 对照当前 diff/产物核对中断后变化。已记录且仍有效的结果继续使用；来源变化先重新语义接纳，产物或证据变化只复核受影响范围。没有正式记录的部分改动视为待核对，不能猜为已完成，也不能未经查看就全部重做。
4. 执行 `next` 查看机械上可推进的节点，再核对正文中的启动条件。按实际需要重建委派上下文，保留所有实际实施者身份，新协调者不能更名抹掉历史作者以满足独立性。
5. 若存在 `run-started` 而无完成回执，先检查原进程是否仍运行、命令副作用和当前产物。同操作 ID 不会自动再次执行。旧命令仍适用时，v2 用原 resolve-run 留存核查后才允许新 ID 重跑。若 plan/authorization 已合法更新且旧命令不再适用，先按 [恢复子契约 2](runtime-api-v2.md#恢复子契约-2旧命令不再适用时转接当前计划) 留存当前调查；副作用查清后显式承接未完成责任到新计划，经独立准入再执行当前授权命令。无需恢复已经失效的旧授权。两种路径都必须有新的真实 run 和有效验证结论才能收尾；release、safe_to_retry 或 safe_to_replan 都不能代替它们。旧 unknown 保留，解除或替代依据失效后重新阻塞。已有 v1 仍按原规则由协调者留据核对。已完成 run 但未作验证判断时，读取对应原始输出并补充真实验证报告，不把 run 成功当验收通过。
6. 继续写新活动记录及准入事件，不覆盖旧失败或手改 journal。已关闭目标要继续修改时先显式 reopen；全新目标另建目录。

每次有边界的活动完成后及时留存报告并接纳，不能只在最终收尾时一次性补状态。长步骤在可安全暂停的边界留下当前改动、已做/未做检查、阻塞和下一动作；这些进度说明不是通过结论。突然终止时只能恢复到最后实际落盘的信息，未保存的推理与未记录操作不能自动还原。

brief、status 和 next 从同一状态对象解释阻塞来源、缺少证据和下一动作；它们是只读派生视图。任务简报保留必要约束的完整来源，不在摘要中裁掉硬条件；原始文档和持久事件仍是真源。
