# 从需求与共识进入成文

用于新建设计，或更新、审阅时出现需要重新讨论的设计问题。已有共识时直接执行承接与推演，不重新跑一轮完整访谈。

## 事实与共识承接

读取用户指定材料与相关实现。先从代码、文档、日志或工具核实可查事实；资料不可达或互相冲突时说明缺口。用户陈述保留来源，不能写成已独立核验。

从已有对话或材料整理以下信息，保持简短，不要求每轮展示表格：

| 输入 | 必须承接的信息 |
|---|---|
| 目标与范围 | 问题发生的场景、期望结果、包含与排除项、成功条件 |
| 已确认决定 | 所选方案、理由、适用前提、确认依据及范围，保留已否决选项的关键理由 |
| 事实与约束 | 当前实现与基线、材料入口、硬约束、偏好、可复用能力；推断与假设分别标明 |
| 未知与自由度 | 待查事实、待决策、待实测、条件性接受的风险及实施边界，允许实现者自行选择的部分 |

同一会话直接使用可见的讨论，不强制新增交接文件或重复审批。跨会话或上下文缺失时读取用户提供的设计简报、对话记录或已有方案；只补当前缺失且影响设计的信息，不能编造此前共识。需要保存摘要时按授权放项目目录，摘要不是另一份完整方案。

“认可”只确认当时明确提出的事项。继承结论前核对适用前提与版本，来源是人、模型或现有实现，不决定其是否正确或已经确认。设计已确认、代码存在、部署启用、实测通过分别记录。

## 按需使用 delve

| 信息状态 | 动作 |
|---|---|
| 缺少可查事实 | 自己定向查证，说明仍不可达的部分 |
| 有真实设计选择或歧义 | 使用可用的 delve 逐项讨论 |
| 机制已经确定，仅缺效果证据 | 进入下述实证分支 |
| 共识充分、组合约束成立 | 按文档规范直接成文 |

需要沟通时，从当前可用技能列表解析 `delve` 的实际位置并读取其 SKILL.md，在当前任务中遵循它的逐项沟通规则；这是模型读取协议，不是固定返回值的函数调用，不自动创建新任务或子智能体。

把当前问题的事实、既有决定、依赖关系与缺口带入讨论；按依赖先解决会改变后续设计的目标、范围和机制。每次聚焦一个问题，说明影响、真实选项、推荐及代价，等待答复。问题解决后记录决定、理由、前提和依据，回到组合约束检查；不重新询问无关共识。

delve 是可选协作依赖。没有可用 delve 且用户未明确要求它时，按上一段的最低沟通规则继续，不声称已调用。用户明确指定必须使用 delve 而无法找到时，说明缺失并等待处理，不静默代替或自动安装。用户禁止使用 delve 时，遵循用户要求。

未解决的设计疑点不能由模型在写作时自行补全。已明确允许的局部方法拆分、变量命名等不属于未决设计。写作或审阅发现新问题时，只重开受影响的决定，给出变化证据。

## 组合约束推演

在本次设计深度内，沿关键对象的创建、使用、失败／并发和释放走具体场景。对存在状态、生命周期或多机制耦合的场景，记录：

**操作前状态 → 操作 → 操作后状态 → 各项约束是否同时成立及保障机制。**

例如读者仍持有旧版本、发布已切换到新版本、下一次构建又开始时，单写者并不能保证“最多两个活跃版本”。需要生命周期、回收或构建时机的保障机制，不能只把版本上限重写进验收。

成立的关键场景留在正文相关功能处；不成立的给出反例与影响并返回讨论。“全部已经确认”不能替代推演，也不能据此改动用户约束。机制缺失属于设计缺口；机制明确但缺少效果证据才属于待实测。

机制深度由正确性、协作与风险决定。先解释整体如何工作，再解释真实备选及成立条件。对新增机制检查它解决哪个目标或现实失败模式、已有能力能否承担；保留必要的安全、幂等和恢复，不默认加入所有高级机制。

## 实证缺口与成文条件

性能、准确率、容量和可靠性等需要实证的结论，先明确验证方法、代表性环境／数据／负载与通过标准；实际验证须在已有授权内。保存结果、版本和适用范围，不能将目标、估算、代码存在或小样本 POC 写成生产证明。

无法及时取证时，由用户明确选择等待，或接受具体假设、风险、适用条件后形成有条件草稿。条件草稿写明验证方法、门槛、关闭条件及未验证前禁止承诺的内容；它不等于无条件可实施。既有明确接受可以复用，单独标“待验证”不构成接受依据。

进入成文前，核对承接信息能覆盖所需深度、关键机制自洽、剩余实证缺口有明确处理路径。已确认共识不再次审批；若尚有影响设计的选择，继续当前问题的讨论。用户要求先展示讨论片段时可以展示，但明确标为候选，不冒充正式定案。

接着读取 [document-standard.md](document-standard.md)，从六个必选章节和五个可选章节的触发条件确定内容位置。成文后按 [review.md](review.md) 双向核对来源与正文，防止摘要、改写或跨会话承接造成决定遗失。
