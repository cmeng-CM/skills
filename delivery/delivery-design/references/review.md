# 设计检查与更新

供成文自检、已有方案审阅和更新后核验使用。内容要求以 [document-standard.md](document-standard.md) 为准；本文件规定怎样检查与报告，不重新维护章节清单。

## 语义检查

先明确本次检查范围，读取相关需求、已确认讨论和当前有效方案。按范围核实所引用的代码、契约及测试证据，访问不到时记未核实，不用推测判缺陷。

| 检查面 | 检查方法 |
|---|---|
| 共识是否丢失 | 从来源逐项检查目标、边界、决定、理由和限制在正文中的落点；再反向检查正文新增的选择是否有依据。编号出现不等于完整行为已承接 |
| 机制是否成立 | 用真实场景走完输入到结果及相关失败、取消、重试、并发与释放路径；耦合机制按 preparation 的组合约束方法检查，给出反例或保障依据 |
| 契约是否足够 | 检查调用者可以依赖的成功、失败、边界行为，数据权威源和生命周期；区别缺失设计与已明确允许的局部编码自由 |
| 目标如何验证 | 每项重要承诺对应保障机制和可判定证据；环境、负载、门槛及当前结果范围匹配，未把计划或 POC 当生产结论 |
| 范围是否合理 | 每个机制服务目标或现实失败模式；核对能否复用已有能力。必要的鉴权、幂等、恢复不因需求没逐字列出而删除；无依据的额外复杂性同样应指出 |
| 当前正文是否一致 | 正文、接口、数据、决策表、验收与状态使用同一有效口径；继承内容有准确指针及本次适用依据 |
| 人能否读懂 | 开头可理解整体机制和取舍；关键理由与条件有文字，图一图一主题；细节不遮住判断，不用篇幅和图表数量评分 |

六个必选章节及可选章节的实际适用内容均须检查。外部模板按语义映射核对，不因标题不同、可选内容合并或表格较少就报缺陷。已知限制若仍违反目标、契约或阻塞验收，必须报告；已被明确接受且条件仍成立的风险，不重复要求用户接受。

## 发现与处理

| 类型 | 判断依据 | 后续 |
|---|---|---|
| 缺陷 | 有证据违反已确认目标、约束、契约或必要条件 | 说明具体反例、影响和修复方向 |
| 待决策 | 存在真实选择、歧义或尚未确认的假设 | 返回 preparation，只重开相关问题 |
| 待实证 | 机制明确，但结论需要的实验或运行证据不足 | 明确证据缺口、验证条件与允许承诺的边界 |

先给总体结论与检查范围，再列每项的**位置／缺失、依据、影响、是否阻塞、修复方向**。同根因问题可合并，但保留全部受影响位置；不要只检查第一个失效场景。个人偏好不是缺陷，无法判定时如实说明。

只审阅时不修改被审阅文档，正式审阅报告按本 skill 的 delivery-contract 留存。自检可修正表达和已确认内容的遗漏；涉及新机制、范围或接受风险的选择返回讨论。报告可以列出多个发现，向用户索取决定时一次聚焦一个问题。没有发现时说明已核实及未核实范围，不承诺绝对无缺陷。

## 只读机械检查

已保存的默认功能改造文档使用：

```bash
python3 <skill目录>/scripts/check_doc.py <文档路径> --profile feature-change
```

已有组织模板、只检查通用结构时使用 `--profile generic`。`<skill目录>` 取当前加载的 SKILL.md 所在目录，不固定客户端或个人路径。脚本使用 Python 3 标准库，不联网、不修改输入文件、不生成审批或状态记录。

- `feature-change` 从 document-standard 的明确章节声明读取必选标题，检查二级标题是否缺失或重复。标题编号不参与匹配；可选章节省略或合并不报错。
- 两种模式均检查空章节、明确的本地决策编号定义与引用、文内锚点，以及模板占位提示。普通重复引用不算重复定义；“待确认”“待实测”是合法状态。
- 支持 Markdown ATX 标题、可省略外围竖线的管道表格、围栏及缩进代码、常见内联链接及完整／折叠／快捷引用链接、显式 HTML 锚点。遵守链接起始方括号的转义。围栏示例、正文注释和 frontmatter 不参与标题及决策检查；代码中的字面注释保留，代码内容可使所在章节非空。引用块及其嵌套示例提示未检查。
- 决策定义使用表格的“编号”“决策编号”“编号与决定”或 `ID` 列，或以 `D-01` 这类编号开头的标题；正文中的 `D-NN` 默认视为本地引用，包括指向本文锚点的链接标签。只有明确指向其他文档的链接才豁免本地定义；目标无法解析时提示未检查。引用外部决定应带文档链接，示例放代码围栏。不同外部文档的编号不要求在本文件再定义。
- 文内锚点按常见 Markdown 标题规则解析；复杂 HTML、扩展语法或无法判定的链接提示未检查，不猜测。外部链接、本地文件是否已存在、拟新增文件路径均不核验；需要模型按事实与方案的区别处理。
- 脚本不判断共识完整性、机制可行性、来源真实性或批准状态。退出码 `0` 仅表示所覆盖机械项未发现错误（仍可能有警告），`1` 表示发现机械错误，`2` 表示参数、输入或规范无法检查。
- delivery 产物归属、契约版本、skill 修订及交接信息按 delivery-contract 另行核对；该脚本不检查这些信息，不提供编排接纳结论。

机械发现必须结合上下文处理。不能为消除提示删除合法约束、替用户接受风险，或把真实缺口改写成“不涉及”。没有文件或运行环境时说明未运行，按语义检查交付，不伪造成功。

## 更新检查

先读取当前有效决定、相关正文及原验收依据，界定授权修改范围。按 document-standard 的关键决策变更和实施收尾规则更新，再核对：

1. 修改是否有实际确认或事实依据；正文是否仍混有已被替代的行为。
2. 影响是否传播到相关功能、契约、数据、限制与验收；仅追加新决策不能代替同步正文。
3. 实现偏离是否被明确报告和处置；不能直接把文档改成实现的样子掩盖差异。
4. 设计确认、实现完成、部署启用与验收结果是否分别陈述，证据范围是否准确。
5. 当前现状基线是否持续更新；一次性变更记录是否如实收尾后冻结；历史理由与替代关系是否保留。
6. 关联的上游或执行资料是否需要由其维护者同步；只修改已授权文件，已有审批和验证约束由对应流程处理。

更新后重查受影响内容及整体目标覆盖；复用仍适用的既有结论，不机械重做全部讨论。完整成稿交用户评审；自检或脚本结果不能替代该确认。
