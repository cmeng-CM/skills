# 功能改造技术方案章节规范

**状态：现行规范｜版本：1｜最后更新：2026-10-15**

适用于在现有项目上新增、调整或重构功能，服务两个受众：

- **人**：理解设计思路、技术取舍和实现细节，能够评审、开发和验收。
- **AI**：据此拆解实施计划、完成开发与验证，并识别需要反馈的问题。

**一、整体编写规则**

| 项目 | 规范 |
|---|---|
| 设计深度 | 确定关键业务行为、技术机制、模块契约和实现约束；局部方法拆分、变量命名等留给实现者 |
| 组织主线 | 详细设计按功能改造项展开；跨功能共享的接口、数据及约束集中说明 |
| 内容约束 | 各适用章节的最低内容和完成判据必须覆盖；章内小节允许合并、调整，不机械套用固定标题 |
| 表达形式 | 图表按信息结构和复杂度选用；能够完整表达相同信息的表格可以合并，已有精确定义可以引用，不为满足形式重复制作 |
| 必选章节 | 保留章节并回答其核心问题；内容简单时可以简写或引用已有依据 |
| 可选章节 | 不涉及则省略；涉及但内容少则并入相关必选章节；需要集中说明则独立成章 |
| 裁剪依据 | 依据本次改动的实际影响，不单凭“本机应用”“小功能”等标签判断 |
| 未知处理 | “不涉及”可以省略；“尚未查清、尚未决定、尚未验证”必须显式记录 |
| 单一事实来源 | 同一接口、数据结构或决策只维护一份完整定义，其他位置通过编号或链接引用；概览只作摘要，不引入另一套口径 |
| 事实与方案 | 区分现有事实、拟议设计、已确认决定、已存在实现和实测结果 |
| 章节编号 | 删除可选章节后连续编号；下文编号用于标识标准章节。生成方案用 Markdown 二级标题承载标准章节，标题名保留，章内小节按需组织 |

正文前附简短的**文档说明**，包含：

| 信息 | 要求 |
|---|---|
| 文档状态 | 说明设计确认状态与适用版本；实施、验收状态由 `status.md`/`closeout.md` 记录，不逐任务回写批准版本。局部确认时注明范围，不把已确认写成已实现或已验收 |
| 适用基线 | 项目、相关代码版本或日期，确保读者知道方案针对哪个现状 |
| 需求与参考依据 | 相关需求、现有设计、代码入口及必要的讨论记录 |
| 更新信息 | 文档版本或最后更新时间 |
| 交付身份 | 按 delivery-contract 记录目标、范围、skill 名称、契约版本与实际修订；与产品和文档版本区分 |
| 实施边界 | 存在阻塞项时，明确当前哪些部分具备实施条件、哪些需要等待 |

文档说明之后、正文各章之前，附一段简短的**方案概览**。用三至五句话说明：本次改变什么、整体怎样工作、最重要的取舍，以及当前已确定或仍受条件限制的部分。先让读者建立整体理解，再展开各章细节；概览不重复维护完整规则，重要条件和限制不能只藏在后文。

内容的深度由正确性、协作和风险决定；每个重要目标都应对应保障机制与验收证据。硬约束、偏好和假设分别说明，冲突及优先级有确认依据。新增机制说明所服务的目标或现实失败场景，核对能否复用已有能力；既不省略工程必要条件，也不默认加入无依据的复杂机制。

**二、通用图表规范**

能够通过图表更明确表达的结构、过程、规则和比较，应使用图表。

各章所列图表是对应信息的优先表达方式，不以图表数量判断文档质量。适用内容与完成判据不能省略，但可以通过合并后的表格、已有定义的准确引用、精确签名或简短说明表达。关键决策表与验收矩阵保留，以便追溯和承接；其他表格不要求逐张独立制作。涉及关键结构、界面交互或复杂状态流转时，应提供相应图示或状态转换表。

| 内容类型 | 优先表达方式 |
|---|---|
| 系统边界、模块职责、依赖关系 | 上下文图、结构图、依赖图 |
| 执行步骤、条件分支、失败出口 | 流程图 |
| 多参与方调用、异步交互、等待与竞争 | 时序图 |
| 对象状态、转换条件、生命周期 | 状态图或状态转换表 |
| 实体关系、数据流转 | ER 图、逻辑数据模型图、数据流图 |
| 条件组合、业务规则、权限差异 | 决策表、规则表、权限矩阵 |
| 接口字段、配置、约束、风险与验收 | 结构化表格 |
| 界面结构、操作入口、交互变化 | 线框图、交互示意图及交互状态表 |
| 精确算法、嵌套数据契约 | 伪代码、Schema、DDL 或必要示例 |

所有图表遵循以下要求：

1. **一张图说明一个问题**，结构、时序、数据关系分别表达。
2. 图中对象与正文命名一致，箭头明确表示调用、事件、数据流还是依赖。
3. 改造图标明新增、修改、复用或废弃，颜色只作辅助。
4. 详细运行图覆盖相关失败路径；分支复杂时拆图，并通过异常表补齐。
5. 每张图附简短说明，交代结论、适用边界及必要的省略条件。
6. 可以引用已有图表，或合并表达同一组对象的表格；引用时说明本次适用范围及变化，避免重复维护。
7. 流程、时序、状态和关系图优先保留 Mermaid 等可维护图源。
8. 关键理由、精确定义和成立条件须有文字或代码说明，不能要求读者从图形中猜测。
9. 表格用于比较、索引和规则对应；较长的因果解释放在相邻正文，不塞进横向过宽或单元格过长的表格。

**三、章节规范**

**1. 背景、目标与范围——必选**

**最低内容**

- 需求来源，以及具体问题发生的场景。
- 本次改造要达成的结果。
- 包含和不包含的功能或行为。
- 可以判断是否达成目标的成功标准。

**图表约束**

- 优先使用**目标表**关联：问题或需求依据 → 改造目标 → 预期结果 → 验收口径。具体测试场景在验收章展开，此处引用对应验收项。
- 范围通常用**范围表**说明包含项、排除项及必要理由；范围简单时可以使用短列表，也可与目标表合并。
- 涉及业务流程调整时，使用业务流程图呈现变化。

**完成判据**

每项改造都有目标依据，范围边界明确，目标能够转化为验收条件。不能只写“优化体验”“提升性能”等无法判断结果的表述。

**2. 现状分析与影响范围——必选**

**最低内容**

- 与本次改造相关的现有模块、流程、接口和数据。
- 现有实现的约束及可复用能力。
- 新增、修改、复用、废弃的内容。
- 受影响的调用方、行为、数据或配置。
- 支撑现状判断的代码或文档入口。

**图表约束**

- **改造影响必须显式列明**，通常用影响表记录：对象、当前作用、变化类型、改动内容、影响对象、依据。对象少且影响关系简单时，可以用包含同等信息的短列表。
- 涉及关键模块边界或复杂依赖关系时，使用现状结构图；可以与总体方案的改造图合并，标明新旧差异。
- 执行链路需要通过图示才能清楚说明时，使用现状流程图或时序图；已有图示准确适用时直接引用。
- 只展示与本次改造有关的范围。

**完成判据**

能够定位相关现有实现，并说明改动会向哪些地方传播。已核实事实与推断分开，计划新增的文件或模块不能写成已经存在。

**3. 总体方案与技术取舍——必选**

**最低内容**

- 改造后的整体工作机制。
- 模块责任、边界与关键协作关系。
- 重要设计选择、理由及成立条件。
- 有实际选择空间时，说明备选方案和取舍。
- 汇总关键决策，分别记录判断来源和确认状态。

**图表约束**

- 根据变化类型，使用总体结构图、上下文图、端到端流程图或交互示意图展示改造全貌；可以在现状图上标注变化。单点且机制简单、没有关键结构或交互变化时，可用简短机制说明表达，不为填充章节制造结构图。
- 存在真实备选时使用取舍表；只有一种可行选择时说明限制条件，不编造备选。
- 维护**关键决策表**，记录规范见后文。

**完成判据**

读者能够解释方案如何端到端工作、责任如何划分、为什么采用这些机制。详细章节中的关键选择均能追溯到决策记录。

**4. 功能详细设计——必选**

以功能改造项为组织单位，承担主要实现说明。每个功能按下表检查适用内容，不要求机械生成十个小节或十组图表；已有共享定义直接引用，功能内说明其适用方式和必要差异。

| 内容维度 | 必须说明的内容 | 图表与表达要求 |
|---|---|---|
| 场景与结果 | 谁在什么条件下触发；输入、前置条件、输出及完成状态 | 场景表或简短场景说明；复杂使用路径补流程图 |
| 业务规则 | 规则内容、适用条件、优先级、边界行为 | 规则说明或规则表；多条件组合使用决策表 |
| 职责变化 | 哪个模块负责哪一步；新增或变化的责任 | 引用改造影响表或模块图；功能内只补充必要的职责细节 |
| 执行流程 | 从触发到结束的完整路径，包含关键分支和失败出口 | 简单路径可用步骤说明；分支较多时用流程图，多方调用或异步顺序影响正确性时用时序图 |
| 状态与生命周期 | 状态定义、转换条件、禁止转换、结束和释放条件 | 状态转换表或状态图 |
| 界面与交互 | 操作入口、展示结果、加载、空态、错误及可用操作 | 涉及界面变化时提供线框图或交互示意图，并说明交互状态 |
| 关键实现机制 | 关键算法、事务边界、一致性保障及其他影响正确性的机制 | 简短机制说明；涉及复杂流转时用机制流程图，复杂计算或判定补伪代码 |
| 异常与并发 | 适用的超时、重复触发、取消、部分成功、并发冲突及处理结果 | 异常处理表；存在执行交错或竞争时补时序图 |
| 组合约束 | 多个机制共同作用时，是否破坏状态、资源或业务约束 | 使用“操作前状态 → 操作 → 操作后状态 → 约束是否成立”的场景推演表 |
| 关联契约 | 使用的接口、数据定义、关键决策和验收项 | 使用编号或链接关联，完整定义只维护一处 |

**完成判据**

开发者能够直接据此实现，无需重新决定关键业务行为和技术机制。发现机制冲突时，应提出待决策问题，不能只写“实现时保证”或“测试时验证”。

**5. 接口与集成设计——必选**

接口包括对外 API、内部模块契约、事件、回调及相关集成边界。

**最低内容**

- 接口提供方、调用方和用途。
- 输入输出及其准确语义。
- 失败条件、错误语义及调用方处理责任。
- 本次新增或变化的部分。
- 实际涉及的权限、版本兼容、超时、重试和幂等约束。同步调用也可能重复或产生副作用，不能据此跳过幂等分析。

**图表约束**

单一且简单的接口，可以用精确签名、Schema 或示例配合简短说明，完整表达下面的信息，不必分别制作三张表。

- **接口清单**：接口标识、提供方、调用方、用途、变化情况。
- **字段表**：字段、类型、必填性、含义、取值与约束。
- **错误处理表**：触发条件、返回结果、调用方责任。
- 复杂嵌套结构补 Schema 或示例。
- 多方调用顺序复杂时，补充或引用时序图。

**完成判据**

调用双方对成功、失败及边界行为有一致理解。复用接口给出准确引用并说明适用性；没有新增接口时，不虚构接口来填充章节。

**6. 数据设计——可选**

**触发条件**

数据结构、存储方式、读写路径、一致性或生命周期发生变化。

**最低内容**

- 数据含义、来源、归属及权威来源。
- 字段、类型、约束、默认值和空值语义。
- 读写方式，以及涉及的事务、并发冲突处理。
- 按实际需要说明索引、缓存、保留和清理机制。
- 旧数据的解释方式；迁移步骤引用兼容与迁移设计。

**图表约束**

- 数据字典或结构表。
- 有实体关系时使用 ER 图或逻辑数据模型图。
- 复杂数据流转使用数据流图。
- 必要时附 DDL、Schema 或文件格式示例。

**完成判据**

实现者无需自行猜测数据含义和约束；适用的空值、旧数据、重复数据及并发冲突均有处理规则。

**7. 非功能与运行保障设计——可选**

**触发条件**

性能、容量、安全、可靠性、资源使用或排障方式受到影响。

**最低内容**

- 质量要求适用的场景、负载或数据规模。
- 指标口径、目标和验证方法。
- 达到要求的具体机制及适用边界。
- 实际涉及的权限控制、故障处置、日志、指标和告警；说明执行位置、责任与失败处理，复用设施须核实适用性。
- 指标按照场景与负载、度量口径、目标、验证方式、当前证据及范围表达；局部 POC 不能外推生产效果或容量。
- 涉及 AI 输出、检索或规则裁定时，按影响记录模型、提示词、规则及知识版本，代表性评测、门槛、人工接管和版本变更回归。硬约束须有实际执行控制，不能用提示词代替。

**图表约束**

- **质量要求矩阵**：场景、要求或指标、保障机制、验证方式、当前证据。
- 权限差异使用权限矩阵。
- 信任边界或部署关系发生变化时，使用边界图或部署图。
- 观测项使用“信号 → 判断 → 处置”的表格。

**完成判据**

每项要求有机制和验证口径；目标、估算与实测分开。不能以“做好安全”“保证高可用”等原则性表述代替设计，也不能编造指标。

**8. 实施约束与依赖——可选**

**触发条件**

存在影响实施计划的前置条件、执行顺序或实现边界。

**最低内容**

- 外部或内部前置依赖。
- 必须复用的能力、禁止突破的边界。
- 改造项之间必要的先后关系及其原因。
- 实现者可以自行决定与必须反馈的事项。

**图表约束**

- **实施约束表**：约束、影响对象、执行要求。
- 存在跨改造项依赖时画依赖图，注明前置项达到什么条件后，后续项才能开始。

**完成判据**

人和 AI 能据此安排实施顺序，识别独立工作和等待条件。这里只规定影响正确性的实施约束，具体任务拆分与执行计划由后续工作形成。

**9. 兼容、迁移与上线恢复——可选**

**触发条件**

已有行为、接口、数据、配置、在途任务或运行版本需要向新方案过渡。

**最低内容**

- 新旧行为或版本的兼容要求。
- 存量数据、配置和在途任务的处理。
- 必要的发布、迁移、切换顺序。
- 各阶段验证点。
- 失败触发条件、恢复动作与恢复后的状态。
- 不可逆操作对应的备份、前滚或其他真实恢复路径。

**图表约束**

- **变更步骤表**：前置条件、动作、检查点、失败处置。
- 存在新旧组合时使用兼容矩阵。
- 复杂切换、迁移和恢复使用流程图。
- 涉及部署拓扑变化时补部署图。

**完成判据**

旧状态到新状态之间存在完整路径，高风险步骤有明确失败去向。不能承诺实际不存在的回滚能力；有恢复时限要求时，应说明依据和验证方法。

**10. 验证与验收——必选**

**最低内容**

- 改造目标、业务规则和关键设计承诺对应的验收项。
- 正常、异常、边界及必要的并发场景。
- 受影响能力的回归范围。
- 验证所需环境、数据和方法。
- 可观察、可判定的通过标准。
- 已完成验证与尚未验证的部分。

**图表约束**

- **验收矩阵必备**：关联目标或设计项、场景、前置条件或输入、操作、预期结果、验证方法。
- 已有结果另列证据或结果字段，不能把计划中的测试写成已通过。
- 验证流程复杂时补流程图。

**完成判据**

每个目标都有对应的验收条件，关键失败路径可以验证，回归范围与改造影响对应。验证应检查实际行为和设计承诺。

**11. 风险、假设与未决问题——可选**

**触发条件**

存在已知风险、尚未确定的设计、尚未验证的前提或已接受的限制。

**最低内容**

- 事项内容及类型。
- 发生条件或尚缺的证据。
- 对目标、契约和实施的影响。
- 阻塞范围。
- 缓解或处理方式。
- 关闭条件和当前状态。

**图表约束**

使用风险与未决事项表，至少区分：

| 类型 | 需要回答的问题 |
|---|---|
| 待决策 | 谁需要决定什么，决定之前阻塞哪些工作？ |
| 待实测 | 需要什么证据，通过什么标准才能成立？ |
| 已知风险 | 什么条件下发生，影响什么，如何发现和处置？ |
| 已接受限制 | 谁接受、适用范围是什么，是否仍满足已确认目标？ |

关键决策的来源和确认状态引用第 3 章记录，避免重复维护。

**完成判据**

每项事项都有可判断的关闭条件和实施边界。问题被记录，不代表已经解决；已知限制仍违反目标或阻塞验收时，必须明确报告。

**四、关键决策与来源追溯规范**

关键决策属于跨章节要求，由第 3 章统一登记，各相关章节引用，例如 `D-01`。

**关键决策的定义**

> 换一种选择，会改变交付边界、重要行为、模块契约、系统保障，或带来显著的实施与迁移影响，即属于关键决策。

命中以下任意一项，必须记录：

| 判定维度 | 关键决策范围 |
|---|---|
| 目标与范围 | 决定交付什么、不交付什么，或改变验收标准 |
| 业务行为与规则 | 决定重要场景下的系统行为、结果或操作权限 |
| 结构与契约 | 决定模块职责、跨模块交互、外部依赖或共享数据语义 |
| 正确性与保障机制 | 决定状态、事务、并发、一致性、权限等重要约束如何成立 |
| 兼容与实施路径 | 决定新旧兼容、迁移、发布顺序或恢复方式 |
| 重要取舍与风险接受 | 接受会影响目标、验收或实施可行性的成本、限制或未验证前提 |

仅影响局部编码、且不改变既定行为和约束的选择，不强制记录。关键性依据实际影响判断，与代码行数无关。

**关键决策记录字段**

| 字段 | 记录要求 |
|---|---|
| 编号与决定 | 唯一编号、所选方案、适用范围；被替代时标明替代关系与新决定编号 |
| 关键性 | 命中的判定维度及实际影响 |
| 判断来源 | 人提出、模型提出或继承已有设计，附可追溯依据 |
| 理由与证据 | 为什么这样选择，区分事实、推断与假设 |
| 确认状态 | 已确认、待确认或附条件接受 |
| 确认记录 | 确认主体、依据及适用条件 |
| 关联位置 | 对应的功能、接口、数据、验收项或阻塞范围 |

**来源与状态必须分开记录**

| 情形 | 判断来源 | 确认状态 |
|---|---|---|
| 用户明确作出决定 | 人提出，引用相关表述或记录 | 已确认，注明范围 |
| 模型提出，用户明确认可 | 模型提出，保留分析依据 | 用户已确认 |
| 模型提出，尚未获得确认 | 模型提出 | 待确认，标明阻塞范围 |
| 延续已有设计 | 继承设计，引用原文档和版本 | 根据实际记录填写，不能自动推定已确认 |
| 只能从现有代码推测历史意图 | 模型基于代码推断，原始判断来源未知 | 不得冒充已有确认 |

来源不代表正确性，确认不代表已经实测。用户已经明确作出的决定直接复用，不重复确认。

**关键决策变更规则**

1. 需要改变已确认的关键决定时，说明原决定、变化原因、证据及影响范围，取得相应确认后再将新决定作为实施依据。
2. 旧决定保留当时的理由和确认记录，明确标记“已被 D-XX 取代”；新决定关联旧决定。不能复用同一编号表达相反要求，也不能让已被替代的决定继续充当当前要求。
3. 同步修订受影响的功能设计、接口、数据、实施约束和验收项，消除当前有效内容中的冲突；不能仅在决策表追加一行。已有审批或版本约束时，按对应机制修订，不直接覆盖已批准基线或绕过审批。
4. 已形成实施计划时，列明受影响的任务、依赖及验收项，由执行工作流同步。受影响材料尚未同步前，不按相互冲突的指令继续执行；不受影响的部分按既有授权和流程处理。

**五、人和 AI 的实施使用规则**

| 遇到的情况 | 处理要求 |
|---|---|
| 设计已明确，只剩局部编码选择 | 实现者自行安排，不必逐项反馈 |
| 发现方案遗漏、冲突或现有代码不符合方案前提 | 给出具体位置、证据和影响，反馈确认 |
| 需要改变已有关键决策 | 说明原决定、变化原因和受影响范围，确认后再调整 |
| 存在局部未决问题 | 暂停受影响部分；核实不受影响的部分后，可以在既有授权和执行流程允许的范围内形成计划并实施 |
| 未决问题会改变总体结构、核心接口或数据模型 | 阻塞相关整体实施，不能先假定答案继续 |
| 已接受尚未验证的假设 | 仅在明确接受的条件和范围内推进，保留验证要求和关闭条件 |
| 省略了某个可选章节 | 到对应必选章节查找已合并的内容，不能将章节缺失解释为没有约束 |
| 实现结果偏离已确认方案 | 显式说明差异与影响，不能直接修改文档掩盖偏离 |

**批准后的只读与收尾**

设计文档一经批准即只读；执行期和 close 都不修改批准版本的正文与状态字段。实施、验收、未完成项和残余风险写 `status.md` 与 `closeout.md`（或实施报告），通过链接回溯到批准版本；不在设计正文逐任务同步进度。

| 情形 | 处理 |
|---|---|
| 实施偏离批准的局部步骤 | 记录在实施报告/R-2 的偏离段；不改变机制、接口、数据或验收时，不修改批准版本 |
| 机制、接口、数据、兼容或验收变化 | 回到 design 产生新版本并重新评审/接纳；不能只在实现审查中记为偏离，也不能用 R-2 代替设计复审 |
| 实施或验收状态 | 由 status.md/closeout.md 与 journal 记录；journal 冲突时以其为准 |
| 旧设计中的状态字段 | 不阻塞读取；check --preclose 在字段与实际冲突时警告，下一次版本变更时按本规范收敛 |

现状基线随交付持续更新；一次性改造设计在批准版本处冻结，后续改造另立记录并引用。已有决策记录保留当时理由和替代关系，不通过回写历史版本制造“当时已确认”。

正文保留最终有用的设计结论、交付差异和未完成事项。详细运行命令、逐轮修复过程、提交流水与证据明细保留在工作流或项目记录中，通过准确链接追溯，不逐轮追加进方案正文。

方案具备实施条件的范围应当明确：**关键机制和契约足够具体，验收可执行，关键决策可追溯，未决事项及其阻塞边界可识别。**

本规范规定文档内容与实施承接边界，不替代项目已有的审批、任务派发、验证和收尾机制。

## 合同包与风险分级

高风险跨边界改动（数据丢失/不可逆迁移、权限越权、资金错误、跨团队契约、生命周期错误）应在设计/计划阶段形成可执行合同包：API/DTO schema、UI 状态、DB 只读断言、验收命令；合同测试作者不得是实现者，高风险测试必须走真实入口。中风险至少一个合同测试；低风险保留验收命令和合同摘要。合同产物缺失/不可执行才阻断，红测预期失败不阻断。合同包不是第二份设计正文，只把关键契约变成可执行断言。
