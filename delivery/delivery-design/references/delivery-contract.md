# Delivery Design 交付约定

本文件定义 `delivery-design` 的输入输出语义契约，当前版本为 **1**。设计内容以本 skill 的 document-standard 为准；能力不依赖编排引擎，是否组合可用须以实际接纳和验证结果判断。

## 独立使用与工作目录

过渡期由用户点名、项目明确选择 delivery 或新编排委派进入；不自动接替旧入口。单独调用本能力不授权其他能力或完整流程。

用户可以直接调用本 skill。先核对目标、输入材料、授权范围及已有决定；不要求其他 delivery skill、编排脚本或 `.workflow` 存在。缺少影响设计的信息时记录具体缺口，只阻塞受影响部分。

正式生成、调整或审阅默认留存文件，包括条件草稿、审阅发现和未完成原因。用户明确只讨论、只在对话交付或不写文件时遵从，不把对话输出描述为已保存产物。仅审阅允许保存审阅报告，不授权改写被审阅文档；保存失败时报告真实原因和待保存内容。

- 未指定位置的新目标使用项目内 `.delivery/YYYY-MM-DD-主题/`。日期取工作目录创建当天，不因跨日或换会话改名。
- 默认位置只用于新目标。旧版 `docs/delivery/` 或用户明确指定的同目标目录继续沿用；不为适配新默认位置移动历史文件或改写编排账本。
- 同一目标已有明确工作目录时继续使用，独立活动后接入编排也沿用该目录。相近名称不等于同一范围；有多个候选或归属不明时先澄清。
- 已结束目标后新增的独立改动建立新目录并引用原记录。适用范围不同的上游设计只引用，不为凑齐文件复制一份。
- 默认设计文件为 `design.md`；正式设计审阅记录可保存为 `design-reviews/001.md`、`002.md` 等，按一次有边界的审阅留存，不按工具调用分文件。它们不是实现审查记录。
- 首次建目录时保存简短 `index.md`，仅记录目标、边界、依据和实际产物链接；不维护第二份实时进度。只创建本次需要的文件，不预建空计划、实施或验证文件。
- 用户明确指定现有文档或其他保存路径时按授权处理，不擅自迁移；能够引用原文时不复制同范围正文。编排入口要求不同归属时先核对，不自行接管旧 workflow 或写入 `.workflow`。
- 本 skill 不创建或修改 `runtime/`；项目材料不放入 skill 安装目录。

## 最小输入与输出

输入至少能识别目标与范围、需求和当前事实依据、已有决定及其确认情况。没有独立设计文件或正式计划不构成阻塞；材料的实际缺口才构成阻塞。

正式产物在文档说明中保存下列信息；正文已有完整定义时精确引用，不维护另一份可变副本。小文档可以合并表达，不以固定标题作为接纳依据。

| 信息 | 语义要求 |
| --- | --- |
| 产物身份 | 设计或设计审阅、目标、范围、保存位置、文档版本及更新时间 |
| 生成规则 | skill 名称 `delivery-design`、契约版本 `1`、实际使用的 skill 修订标识 |
| 输入依据 | 需求、适用设计或讨论、事实来源、相关产品代码基线及有影响的未提交改动 |
| 内容与覆盖 | 目标、机制、契约、关键决定、验收要求的正文或精确位置；说明未覆盖范围 |
| 结论与确认 | 设计确认、自检、实施及验收状态分别说明；保留真实确认的内容、条件和适用范围 |
| 未解决事项 | 问题或证据缺口、影响范围、阻断性、所需决定与解除条件；无则说明无 |
| 交接与变化 | 当前可承接范围、后续建议、替代关系及受影响材料；不将建议当成调用或执行授权 |

skill 修订可用可恢复的仓库提交标识；相关文件有未提交改动时还需对应差异记录，不能只记 HEAD。无版本库时使用内容指纹及可恢复来源；确实无法取得则明确记录缺口，不能编造版本或宣称可复现。skill 修订、契约版本、文档版本和被设计产品的版本分别记录。

## 组合使用与历史

调用方提供工作目标、授权边界、输入位置和产物目录，本 skill 按相同内容标准完成设计。调用方依据产物判断能否推进；设计生成或自检通过不等于用户批准、实施完成或验收通过。

产物保持可读 Markdown；编排器核对正文后在自身范围内生成机器准入快照，引用原文和实际摘要。该快照是对特定版本的接纳记录，不反向成为设计正文真源，也不要求本 skill 运行编排脚本。来源改变后必须重新核对，不能拿旧摘要放行。

本 skill 不自动调用其他交付能力，不修改调用方的流程状态。独立产物接入编排时需核对范围、版本、真实确认和未决项；不为接入补造历史授权，也不因进入编排重新生成同范围设计。

更新有效设计须保留旧决定、替代关系和确认依据；可通过版本历史和准确引用追溯，不必重复完整正文。审阅发现与后续处理相互关联，不能覆盖原失败或把尚未核实的问题改为已解决。实现反馈只能作为事实输入，不能自动改写设计或验收。

## 本 skill 的更新要求

每次维护先判断是否影响输入、输出、结论含义、必要质量条件或调用权限。内部方法改进可以保持契约版本；兼容扩展须证明旧调用方忽略新增信息仍然能正确判断；必需输入、字段或状态含义变化需升级契约版本并同步受影响的接入规则与检查。

字段未变但降低内容标准、确认要求或阻断条件，也属于需要评估的语义变化。记录影响并验证代表性行为，不以脚本结构检查通过代替质量判断。已有流程不自动切换规则，旧记录不因新版本而重写；是否兼容由实际契约与行为核对决定，不能仅比较版本号。本 skill 独立维护，不自动同步或修改原 `design-tech-doc`。
