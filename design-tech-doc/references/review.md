# 设计审阅与成文自检

按已确认目标、实际约束和证据评估设计；章节数量、篇幅和“看起来完整”不能替代判据。仅审阅时只诊断，未经要求不改写；作者自检不能冒充独立审阅或用户评审。

## 审阅入口

先读取被审文档和用户提供的要求、上游设计、评审约束。文档引用了可查的接口、实现、启用状态或测试结果时，按本次范围核实，记录来源和版本／环境；没有访问能力就写未核实，不拿推测当缺陷证据。

确认或沿用文档类型、评审强度、当前状态与维护方式。它们彼此独立：生产变更不自动要求重点评审，篇幅短不表示轻量，模型自检不意味着已接受。文档类型不清且会影响判据时先问当前最关键的一项；能从文档查到的不要重问。

建立目标 → 机制／契约 → 验证证据的对应关系，并按主协议 M01–M15 检查适用性。组织模板与工作流有精确标题时检查其机械契约；其他情况按语义覆盖，不按固定章节判缺失。继承的内容须有有效指针和本次适用依据。

即使材料声称“全部已确认”，仍在声明的设计深度内沿关键生命周期、失败和并发场景检查组合约束能否同时成立。缺少保障机制是待决策的设计缺口；已有明确候选机制、仅缺效果证据的归入待实证。把冲突条件同时列为“实现必须满足”或“测试需验证”不能关闭缺口，也不能归为局部编码自由；指出反例和影响，再按主协议只确认当前一项，不代改约束。

## 发现类型与输出

先给总体结论和覆盖范围，再列发现；无发现时说清已检查的范围及未核实项，不写“绝对无问题”。同一判据下不同失效场景都要检查，避免只报第一个；相同根因可合并但保留各处证据。

| 类型 | 含义 | 不能混同的情况 |
|---|---|---|
| 缺陷 | 有证据表明违反已确认目标、约束、契约或必要条件 | 个人偏好、未知事实不能直接判缺陷 |
| 待决策 | 存在真实取舍、设计歧义或未经确认的假设 | 模型推荐不是用户决定；承认歧义不等于已选定解释 |
| 待实证 | 结论需要实验或运行证据，现有材料不足 | 意见一致、代码存在、几例 POC 不构成生产验证 |

每条发现包含：**编号／判据、类型、位置或具体缺失、依据、影响、阻塞程度、修复方向**。例如：

```text
[R1 / C09] 缺陷 · 阻塞 | §验收与§已知限制
依据：验收要求失败后不重记账；已知限制说明请求重试可能重记账。
影响：已声明验收无法满足，写成限制不构成豁免。
修复方向：REDESIGN；讨论去重或事务边界，修复后验证重复投递场景。
```

阻塞程度相对于本次目标及评审阶段：阻止定案／验收的问题明确标阻塞；不影响本次结论的改进标非阻塞。资料不足则标“无法判定／待实证”，不能为了给结论而猜。合理分歧属于待决策，不自动归为缺陷。

修复方向沿用三个标记，但不能用分类替代确认：

- **ACKNOWLEDGE：** 仅当限制在已确认范围内可接受、不违反目标且不阻塞验收时，补充适用条件与风险记录；需要新的接受决定就列为待决策，不能替用户承认。
- **SPECIFY：** 补足已确认行为的语义、约束或证据指针，不引入未经确认的新选择。缺失细节若有多种合理设计，先列待决策。
- **REDESIGN：** 需要改变机制、交互、状态或责任边界；说明候选方向和代价，返回主协议逐项讨论，不直接把推荐改进文档。

最后可按根因汇总发现，并说明下一项最有依赖价值的确认或验证。报告可以列出多个发现，但交互中一次只提出一个决策问题，不把问题清单当成批量审批。

## 判据

### 目标、共识与证据

| 编号 | 检查问题 |
|---|---|
| C01 | 问题、目标、范围和不做事项能否追溯到需求、已确认讨论或查证证据？是否把建议或手段变成了既定目标？ |
| C02 | 文档类型、评审强度、状态和维护方式是否独立且有依据？免独立设计的判断是否建立在事实、影响、验证和恢复都明确之上？ |
| C03 | 未解决的设计疑点是否都逐项确认？是否把用户一次“认可”、沉默或催促写作解释为确认全部，或把“全部已确认”当作组合约束自洽的证明？发现新缺口是否只重开受影响决定，而非无故重问其他共识？ |
| C04 | 成文前简报的范围、深度、选节／继承和未知处理是否被确认或由既有确认覆盖？全文自检是否被冒充用户或正式评审？ |
| C05 | 事实、已确认设计、已存在／启用的实现、实测结果及验证范围是否清楚区分？引用的证据是否真的支持该结论？ |
| C06 | 无法实测的关键假设是否有用户明确选择的等待或条件草稿路径？实验方法和门槛是否已确认，假设、风险、适用条件和关闭条件是否完整？ |

### 机制、边界与失败

| 编号 | 检查问题 |
|---|---|
| C07 | 总体机制是否可理解，责任与依赖是否闭合？同一行为、权威源或契约是否在不同段落互相矛盾？沿生命周期、失败或并发场景组合约束能否同时成立，有何保障机制？是否仅重述要求、转交实现或列入测试就假定闭合？真实备选、代价及关键决定间的依赖是否可恢复？ |
| C08 | 一次运行从输入到结果是否说清，涉及的状态、异常、并发、取消、超时、重试和重复副作用是否有语义？有没有用“同步”作为不分析幂等的理由？ |
| C09 | 接口与数据是否足以协调实现：输入输出、错误、权限、版本、权威源、旧数据语义、事务／一致性及生命周期？文档深度是否锁定影响正确性与协作的部分，又保留已允许的局部编码自由？ |
| C10 | 性能、容量与可靠性承诺是否包含场景、负载、度量、目标和验证方式？是否考虑资源预算、瓶颈、故障与过载？改超时是否核对整条调用链预算、重试取消、资源占用、级联风险和副作用？ |
| C11 | 安全威胁与权限／信任边界是否对应实际执行控制及验证？是否把提示词或原则当作硬约束？ |
| C12 | 部署环境、依赖、配置、运行责任与排障入口是否清楚？相关指标、日志、链路、告警是否可用，或有已核实的设施可继承？ |
| C13 | 兼容、存量数据／任务、切流与必要发布顺序是否闭合？恢复是否有触发、动作、耗时及依据，不可逆行为是否有真实恢复路径？ |
| C14 | 目标和不变量是否对应保证方式及可判定验证？是否覆盖受影响的失败与回归场景，区分已做与计划中的验证？ |
| C15 | AI 相关设计是否交代模型／提示词／规则／知识版本、约束执行位置、代表性评测集与指标、人工接管、证据链和回归？是否错误外推 POC 的效果、容量或安全性？ |

### 风险、最小性与载体

| 编号 | 检查问题 |
|---|---|
| C16 | 关键假设不成立或一个现实失败场景出现时，方案是否仍满足目标？风险是否有触发信号、影响、缓解及失效处置，未决是否有关闭条件？ |
| C17 | 已知限制是否仍违反目标、契约或阻塞验收？是则必须报告，不能因“已承认”豁免；不重复报告的前提是已有明确接受且仍适用的处置结论。 |
| C18 | 是否有无助于目标、且不属于工程必要条件的机制？是否重复已有设施？更简单替代在正确性、安全、恢复和成本上是否仍成立？ |
| C19 | 语义覆盖是否与类型、范围和强度匹配？安全、部署、容量是否各有明确责任和内容位置？不适用与继承有理由，强制格式的必填节是否保留？ |
| C20 | 表达是否帮助读者判断：关系是否可追踪、图是否一图一主题并有结论、同类项是否便于比较、细节是否遮住取舍？不把图表比例、表格行数或篇幅当成独立缺陷。 |
| C21 | 基线是否持续更新当前事实，变更记录是否如实回写实际交付、偏离和限制后冻结，ADR 是否保留历史并关联替代？是否用文末优先条款长期掩盖正文矛盾？ |
| C22 | 写入前是否说明同步范围，是否越权改上游材料？批准后偏离是否先确认，而非直接修改设计掩盖？工作流精确标题、D-NN、路径、审批与指纹机制是否被保留？ |

## 最小性检查的方法

从已确认目标与事实推导满足正确性、安全、可靠性和恢复要求所需的最小机制，再与文档比较。独立审阅者可先形成自己的问题与必要条件清单以降低锚定；作者自检也可以做，但不得自称独立。

对额外机制问：解决了哪个目标或现实失败模式？已有设施能否承担？更简单的替代会丢掉什么保证？只在依据不足或代价与目标不符时报告。用户未逐字要求鉴权、幂等或恢复，不等于这些机制多余；同样，不能把本领域的所有高级机制都默认加进范围。

## 发现后的边界

- 只审阅：交付发现、证据范围与下一项建议，不改产物；后续修复需符合用户授权。
- 成文自检：修正表达和已确认事项的遗漏；新增设计疑点退回逐项讨论，实证未知退回实验分支。
- 用户已接受的风险：保留依据与条件；条件不再成立、目标变化或验收仍被阻塞时重新报告。
- 正式结论：仅记录真实评审结果及其覆盖范围；审阅建议不是批准，不承诺“通过即可保证上线”。
