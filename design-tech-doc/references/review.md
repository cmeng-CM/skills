# 审阅模式

对一份已有设计文档做诊断。**只诊断，不改写**——除非用户明确要求改。

判据主体借自一份成熟的开源设计评审清单（`arkbriar/sisyphus-design` 的 `checklist.md`），并按本 skill 的证据要求做了裁剪。

## 输出格式

每条发现一行：

```
[n] <判据号> FAIL | 涉及概念：[X, Y] | <具体问题> | 修复类型：ACKNOWLEDGE / SPECIFY / REDESIGN
```

三种修复类型：

- **ACKNOWLEDGE**：承认它是个限制即可，不动结构，一两句散文
- **SPECIFY**：补一个缺失的行为细节，散文级补充，不引入新部件
- **REDESIGN**：要动部件、交互或状态模型，结构性改动

同一判据下的**所有**失败都要列出来，不要只报第一个。已在「已知限制」里承认过的问题不再报。

最后按根因聚类：

```
ROOT CAUSE [r]: <描述> — 发现：[n1, n2, n3]
```

输出只有这两样：发现清单 + 根因聚类。

## 范围膨胀检测（必须由审阅者做，作者做不到）

作者看不出自己的范围膨胀——他已经把那些机制当成必需的了。所以这一步**只能由独立审阅者做**：

1. 先按输入**独立画一份最简设计**——只有部件名和一句话职责，从输入推导。**不要读被审文档的范围声明**，否则会被它带着走。
2. 把被审文档里出现、而最简设计里没有的每个机制挑出来，逐条要求论证：它对应输入里的哪一条？
3. 论证不出来的，就是范围膨胀。

## 判据

**一致性（输出内部）**

1. 有没有两处承诺互相矛盾？
2. 有没有隐含依赖——删掉某一节会静默打断另一节？
3. 优先级排序有没有自相矛盾？
4. 有没有只在"缺了某样东西"的前提下才成立的术语或区分？
5. 每个命名实体与它交互的每个实体的关系，是否都写明了？
6. 每个操作是否写清了"会发生什么"，而不只是"会发生"？
7. **决策之间有没有标出因果（依赖 / 推论 / 推翻）**，还是只有一组并列的理由？缺了因果关系，读者无法判断"改这条会连带影响什么"。
8. **读者与分界有没有写清**——哪几节给人、哪几节给模型？给模型读的部分是否精确到不用再做设计决策？边界有没有写成 Always / Ask first / Never？

**覆盖（输出 vs 输入）**

9. 有没有输入里要求、文档没回应的？
10. 有没有违反输入里约束的？
11. **文档声称要解决的每个问题，能否引用输入里确立它为问题的原句？引不出 = 自造问题。**
12. 输入有歧义的地方，文档有没有承认歧义并写明选了哪种解释？

**攻击（输出 vs 极端情况）**

13. 有没有一个小而现实的场景会让这个设计失效？
14. 最关键的那个假设，如果反过来，设计还成立吗？
15. 在什么规模上会崩？那个规模现实吗？

**最小性（输出 vs 简单）**

16. 有哪个部件去掉也不影响目标达成？每个粒度层级都查一遍。
17. 每个机制要解决的问题，是不是已经被另一个部件、运行时或环境解决了？
18. 每个机制，说出更简单的替代（**包含"什么都不做"和"交给环境"**）。文档没说为什么不用更简单那个，就报它。

**边界（输出 vs 极限）**

19. 有没有"换一个模型来读也会合理分歧"的判断？这类标 **FLAG 不标 FAIL**——它是固有不确定性，不是缺陷。
20. 有没有本领域常见的失败模式没被处理？只在声明的范围内查；明确写了超出范围的不报。

**范围（输出 vs 输入意图）**

21. 有没有输入没要求、也没直接暗示的功能？逐条问：哪句输入支持它？

**载体（输出 vs 读者）**

22. **档位有没有声明？** 节集与篇幅与档位相符吗——轻量档写满（每节硬凑内容）、重点档缺节（该有的条件节没勾），两头都报。没有档位声明就没有判据，先报这一条。
23. **有没有整段散文本该是图或表？** 判据：并列的同类项（决策、目标、风险、字段、接口、检查项）、结构关系（模块、依赖、流向、状态）写成大段文字，是在把整理工作推给读者。
24. **图的形态合规吗？** 有没有贴图片（png / 截图 —— 评审时 diff 不出来）？是不是一图一主题（架构链路部署挤在一张图上报它）？每张图有没有"从这张图该读出什么"？纯文本图（mermaid）优先。
25. **表有没有超长不拆？** 单表超过 15 行应在拆开、改图、或下沉附录三者中选一个。把什么都塞进一张大表，和大段文字一样难读。
26. **有外部输入 / 权限边界 / 生产影响时，安全与可观测性写了吗？** 安全要有威胁识别表与 MUST 检查清单；可观测性要有指标 / 日志 / 链路 / 告警四类。缺任一报它。
27. **每个不变量都有"怎么测"吗？** 没有测法的不算不变量。只有目标值、没有验证方式的性能指标同样报它。
28. **数据相关改动写了权威源吗？处理链路上动了数据的地方，在数据流转里都能找到对应吗？** 对不上说明方案没闭合——这是处理链路与数据流转两节的核心价值所在。
29. **增量文档专项**：写了"上一版交付了什么"吗？「兼容迁移与回滚」在列吗？回滚写了触发条件、动作、耗时吗（写"可回滚"三个字等于没写）？
30. **文档迭代的痕迹处理了吗？** 有追加节却没有权威优先级声明（"与正文冲突时以本节为准"）、有决策改判却没留痕（`~~原结论~~ **日期 改判：…**`）、正文与追加内容冲突而未标出优先级——三种都报。

## 审阅的纪律

- **只诊断不改写。** 除非用户要求改。
- **不报没有依据的"我觉得"。** 每条发现都要指到具体位置或具体缺失。
- **FLAG ≠ FAIL。** 固有不确定性单独列，不要混进缺陷清单——混了会让作者去"修"一个本来就无法消除的东西。
- **范围有限。** 超出声明范围的东西不报（除非它本身违反了"声明范围必须能追溯到输入"）。
