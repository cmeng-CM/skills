# Design Doc

先定这份文档要承担什么（档位），再决定它有哪些节，每节再决定用什么形式承载。**这里没有固定模板**——模板给的是章节名，本 skill 给的是"这一节在你的项目里该长什么样、颗粒度由什么决定、什么算写坏了"。

判据来自 21 家一手材料：13 份业内模板与流程（Google design docs、arc42、IEEE 1016、Rust/React RFC、Kubernetes KEP、Uber、GitLab、Amazon PR-FAQ、MADR/ADR、GB/T 8567、腾讯云迭代技术方案规范、掘金技术方案模板），加 8 个知名项目的真实文档库（Go、Rust、Kubernetes、CockroachDB、Materialize、dotnet/designs、Swift Evolution、gRPC）逐份解剖与体量实测，另对照了三份中文工程实践的真实方案文档（含一份组织标准）。借用处已在正文标注来源。

**守卫：**

- **这不是 PRD。** PRD 说"用户应该体验到什么"，本文档说"系统如何交付这一体验"。写产品需求请换工具。
- **这不是 ADR。** 单条可逆决策的最小记录用 ADR；本文档是完整方案。一份文档里塞十条互不相关的决策，读者找不到主线。
- **这不是计划。** 任务拆分、依赖图、排期属于计划。设计文档回答"这是什么东西、为什么这么设计"，不回答"谁在第几天做什么"。**但"详细设计"是合法内容**——接口契约、状态机、数据表结构讲的是"这东西长什么样、怎么运作"，不是执行步骤。两者的分界：执行步骤是给执行者的动作序列，详细设计是给实现者的形状约束。
- **在 task-workflow 工作流内时，产物契约以那边为准。** `task-workflow/references/design-doc.md` 规定了十节骨架、`D-NN` 决策校验、回写协议与验证指纹绑定——那些是**机械约束**，本 skill 不覆盖、也不冲突。那十节是地板不是天花板，本文档的地板节与条件节都能作为额外小节加进去（加的小节不校验）。对"该写什么"有分歧时以那边的契约为准。**反向也成立**：本 skill 只写指导，**不规定工作流的时机、指纹与路径约束**——那些一律以那份契约为准。改的时候：**指导改这里，条款改那边，另一处只同步结论。**
- **不做固定模板。** 不要因为某节"模板里有"就写它。每一节的出现都要能说出触发条件，说不出就不加。
- **长度不设上限，但不许凑。** 篇幅由实际需要决定——结构、章节、内容形式固定住了，多长是内容说了算。唯一判据是：**多出来的长度只能来自"真的还有话要说"，不能来自把模板填满**。逐段问一句"删掉它，读者会失去哪个判断依据"，答不出来的那段就是凑的。
- **代码：实现前是规格，实现后是转述。** 方案先于实现时，接口签名、表结构 DDL、关键算法片段是**规格**，该写、写全（实现者照着它干）；实现已完成再来写文档时，贴实现就是**转述**，必然过期，不写，改成指针（指向源码）。判据是"它现在是不是唯一真源"。
- **图与表是主要承载形式，散文只写三样东西**：为什么这么选、边界在哪里、风险是什么。凡"并列 N 个同类项、每项有几个字段"的内容一律用表；凡"结构、关系、流向"一律用图。通篇散文是本 skill 最常见的失败。
- **文档必须对写它的人有即时价值。** 这是设计理由（design rationale）类方法几十年工业应用失败的根本原因，原话很直白：**"没有人会为一个未知的人、在未知的时间、为未知的任务，无私地写高质量的设计理由。必须有即时价值。"** 落到做法上：**让这份文档的第一次真实使用发生在它写完之前**——它本身就是评审呈品，或者执行者要照着它干活。一份"写完就存档"的文档，你不会认真写，写了也没人信。
- **给诚实的省略留出口。** 某节确实不适用时写「无（理由）」，不要凑字，也不要留 `TODO` / `TBD` / 待补。

**反模式（明确不要做的事）：**

- 不要照抄任何一份模板的章节名然后逐节填字——那是"看起来像设计文档"与"是设计文档"的区别
- **不要通篇散文。** 决策、目标、风险、字段、接口、不变量——这些天然是表格；架构、链路、状态、依赖——这些天然是图。写成大段文字是在把整理工作推给读者
- **不要贴图片（png / 截图 / 导出的 svg）。** 评审时 diff 不出来、改不动、过期了看不出来。用 mermaid 这类**纯文本图**：随文本 diff、随版本演进
- **不要用图替代结论。** 每张图下面给一句"从这张图该读出什么"——否则十个读者读出十种理解
- **不要把一图塞满。** 架构、链路、部署不要画在一张图上。图跟着它的节走：总览图在总体方案，链路图在处理链路，状态图在状态机节，不要集中堆成一个"图集"
- 不要在只有一种做法时硬造备选——写「无备选 + 理由」比编两个稻草人方案强
- 不要把"非目标"写成"被否定的目标"
- 不要把执行步骤写进设计文档——文件清单、排期、命令序列属于计划
- 不要写没有依据的断言（"线上一定没问题""性能足够"）——要么标条件句写清须核实，要么不写
- **不要跳过第 0 步直接开写**——档位、读者、可逆性、往下走多远四个判断决定后面几乎每一节的颗粒度
- **不要因为用户催就砍掉风险与未决问题节**——那一节空着，等于告诉后来人"当时没想过"
- **不要只写"为什么选 A"，不写"A 和 B 之间是什么关系"。** 理由是平的，因果是链的。缺了依赖与推论关系，读者无法判断"改了这个决定会连带影响什么"
- **不要把给人读的部分和给模型读的部分混着写。** 人读不懂会来问你，模型读不懂会直接自己编一个

## Working Protocol

### 第 0 步：四个前置判断（不写正文，先定形状）

| 判断 | 怎么看 | 影响什么 |
|---|---|---|
| **档位** | 见下表 | 决定节集，是全篇最大的一个开关 |
| **读者是谁** | 只有同团队工程师 / 要跨团队 / 要过评审门 / 要给非技术方看 | 背景写多厚、要不要参考型章节、要不要成功度量 |
| **变更可逆吗** | 能在一个发布周期内悄悄回退吗 | 可逆 → 写"够用就走"；不可逆（数据格式、公开接口、外部契约）→ 写满、写死、写清判据 |
| **文档往下走多远** | 只服务当次实现？任务结束后还要继续用？还是文档本身就是主源？ | 三级（借自 Martin Fowler 对 spec-driven development 的分层）：**spec-first**——写完即冻结，读者看的是历史；**spec-anchored**——任务结束后仍用于演进与维护，须在元信息头维护最后更新日期并写明本文档会变；**spec-as-source**——文档是主源，人只改文档、不碰代码。级别选错要么白写要么烂掉 |

**档位表**（对应组织流程里的「设计分级」字段）：

| 档 | 判据 | 节集 |
|---|---|---|
| **档 0 · 不写** | 可逆 + 单点 + 不动接口与数据契约 | 不写文档，走 issue / commit message |
| **档 1 · 轻量** | 单模块内、可回退、不动数据与对外契约 | 地板 8 节，条件节 0–1 个 |
| **档 2 · 标准** | 单模块新功能或一次改造，有接口或数据变化 | 地板 + 3–5 个条件节 |
| **档 3 · 重点** | 跨模块 / 不可逆 / 有生产影响 / 动既有契约 | 地板 + 6–9 个条件节 + 评审记录 + 附录 |

**篇幅不在这张表里。** 档位定的是"有哪些节"，不是"写多长"——同档 2 的两份文档可以差三倍，差别来自真有多少话要说。**不要用"字数够不够"当完成判据**，那份判断只能靠"每一节是否都说清了自己该回答的问题"。

**档 0 是最容易被忽略、也最省事的一档。** 如果一份改动小到每一节都只能写「无」，它本来就不该写设计文档——分级的价值一半在于拦住不该写的。

判断结果要落到元信息头与呈现里，不要只在心里过一遍。

### 第 1 步：选节

**地板 8 节**——任何档位都要有，一节不削。轻量档里每节写一两行是合法的，写「无（理由）」也是合法的；但不设这一节，那类信息就永久没有位置。

| # | 节 | 一句话判据 |
|---|---|---|
| 1 | **元信息头** | 状态、**设计分级**、最后更新、讨论入口、关联需求/上游设计、读者与分界 |
| 2 | **背景与现状** | 现在什么样、不改会怎样、为什么是现在；至少一处可核实来源 |
| 3 | **目标与非目标** | 目标写成"做成后谁看到什么不同"+ 可衡量指标；非目标是"本可做但选择不做" |
| 4 | **总体方案** | 一张上下文图 + 三五句话，让读者先建立整体图景 |
| 5 | **处理链路** | 挑一个具体场景，从触发到结果走一遍——这是细节展开的索引 |
| 6 | **关键决策与备选** | 为什么是它而不是别的；决策之间标因果；每条标影响与连带项 |
| 7 | **风险与未决** | 风险的触发信号与缓解；未决要能关闭，并区分待讨论与待实测 |
| 8 | **验收与不变量** | 三列表：不变量 / 保证方式 / 怎么测 |

**条件节 10 节**——每勾一节说清为什么触发；不触发就不加。

| 节 | 触发条件 | 主要承载形式 |
|---|---|---|
| **模块划分与依赖** | 涉及 2 个以上模块/服务，或有"这东西该放哪层"的归属问题 | 职责表（**负责 / 不负责两列**）+ 依赖图 + 循环依赖检查 + 放置判据（几问式） |
| **接口契约** | 对外或跨模块接口有新增、变更 | 接口清单表（含**新增/变更**列）+ 关键接口详情 |
| **状态机与流程** | 有状态、有分支，或有并发 | 状态流转图 + 状态×事件→目标态表 + **并发与幂等** |
| **数据设计** | 表结构/字段变化，或数据归属、一致性、权威归属变化 | 表结构表（字段/类型/允许空/说明）+ 迁移方案 |
| **数据流转** | 数据的读/写路径或权威源发生变化 | 数据流图（谁产生 → 经过什么 → 落到哪）+ 权威源声明 |
| **横切关注点** | 有生产影响、有外部输入，或有合规要求 | 安全（威胁表 + MUST 检查清单）/ 可观测性（指标·日志·链路·告警）/ 性能与容量（指标/目标/验证方式）/ 成本 |
| **兼容迁移与回滚** | **增量改动**；改了既有行为、接口或数据 | 兼容矩阵 + 发布顺序 + 回滚的**触发条件 + 动作 + 耗时** |
| **实施与里程碑** | 需要资源决策或排期，且没有独立计划文档 | 阶段表；有独立计划时只写指针，不重复 |
| **评审记录与 ADR** | 有正式评审门，或组织有 ADR 库 | 评审结论三选一 + 问题记录表；ADR 清单与摘要 |
| **附录** | 需要放查考型内容 | 依赖清单、环境变量、部署片段、**改动索引（实施时逐项核对）** |

**档 2 / 档 3 必须有一节承载「改动点级」的设计。** 这是颗粒度要求，不是节名要求：按对象命名的节（接口契约 / 状态机与流程 / 数据设计）优先；**当这些对象都不存在时**（纯工程改造、配置迁移、流程制度类改动），开一节「**改动点设计**」，逐个改动点写四样东西——**终态、落点、关键实现约束、陷阱**。缺了这一节，方案会停在"要做什么"而没到"怎么做"，实现者只能自己发明；反过来，把详细设计硬塞进某一节（例如全塞进"对外契约"）会让那节变成一个杂货铺。**判据**：实现者读完能不能不再做设计决策；不能，就是缺这一节。

**全新 vs 增量：差异不在节名，在这五节的写法。**

| 节 | 全新功能 | 增量功能 |
|---|---|---|
| 背景与现状 | 现在没有这个能力，痛点是… | **上一版交付了什么**（能力 \| 位置 \| 状态）→ 它暴露了什么 → 为什么需要这一版 |
| 目标与非目标 | 范围以"要不要做"为主 | 范围以"**哪些既有行为一行不改**"为主 |
| 关键决策 | 选型类为主 | 兼容、迁移、替代路径类为主——"旧路径怎么办"必须答 |
| 数据设计 | 建表 | 建表 + 存量数据迁移 + **旧数据的语义**（NULL 是"无归属"还是某个默认账号，不能含糊） |
| 验收与不变量 | 新能力可用 | 新能力可用 + **既有行为不变**（对拍 / 回归） |

另有一条硬差别：**「兼容迁移与回滚」对增量是必上节**，对全新功能只在有生产影响时才勾。

### 第 2 步：起草

**通用顺序**：元信息头 → 背景 → 目标与非目标 → 总体方案 → 处理链路 → 关键决策 → 模块划分 → 接口契约 → 状态机与流程 → 数据设计 → 数据流转 → 横切关注点 → 风险与未决 → 兼容迁移与回滚 → 实施与里程碑 → 验收与不变量 → 评审记录与 ADR → 附录。

规则是**参考型靠末尾**（接口、数据、字段这类给执行者查考的往后放），**人审要判断的往前放**（背景、目标、决策、风险）。节名逐字固定，顺序可按读者路径调。

**每个章节都要有编号**（`第N章 <节名>` 或 `N. <节名>`，按项目惯例；子节用 `N.1`）。跨引用一律写编号（"见第七章"）而不是只写节名——一份十章以上的文档没有编号，读者找不到"§风险与未决"到底指哪一段。编号与节名同时保留，不要只留编号。

**§0 元信息头。** 状态取值必须是终态化的集合（`草稿 / 待评审 / 已接受 / 已实现 / 已被取代 / 已废弃`）——只有"草稿/已接受"两种状态的文档库会烂掉。讨论入口是必填项，不是装饰：八份真实文档里除 dotnet/designs 外全部在头部写死了讨论链接。**读者与分界**要写清哪几节给人读、哪几节是给模型的契约——两者失败模式不同：人读不懂会来问你，模型读不懂会直接自己编一个；给模型的部分要精确到不用再做设计决策，边界写成 **Always / Ask first / Never** 三档（形态来自 GitHub 对 2500+ 份 agent 配置文件的分析）。日期用最后更新而非创建日期。项目已有文档头惯例时沿用惯例。

**§2 背景与现状。** 先写问题现状（现在什么样、不改会怎样），再写为什么是现在——顺序别颠倒。**动机用一个具体场景开头**（Sentry 的 `condense-rfc` 把这条列为硬性要求）；这不只是可读性：Cambridge 那篇设计理由论文发现**逻辑框架显著影响接受度——演绎式推理更容易让人拒绝一个设计，溯因式推理更容易让人接受**。至少捞一处可核实的外部证据（issue 号、监控数据、用户反馈、失败案例、性能数字）。**更锋利的一条**：你声称要解决的每个问题，都要能指出输入里确立它为问题的原句——引不出原句的，是你自己发明的问题。**增量文档在这里写"上一版交付了什么"**（能力 | 位置 | 状态 三列表），这是迭代文档的入口。

**§3 目标与非目标。** 非目标用 Google 的精确定义：不是"被否定的目标"，而是**"本来可以合理地成为目标、但被明确选择不做的事"**。目标写成"做成后谁看到什么不同"，并给**可衡量指标**（形态取自中文工程实践的三列表：目标项 | 描述 | 可衡量指标）。范围边界用 ✅范围内 / ❌范围外 两段式清单。靠评审补条目是正常的，不要为了填满而编。

**§4 总体方案。** 先用一张上下文图（系统边界 + 外部实体 + 数据存储）加三五句话建立整体图景，再进细节。**显式声明颗粒度**：写清本文明确定义了什么、把什么留给实现者——真实文档里这一步常被省掉，结果是执行者要么把留白处当成必须照做，要么在你已定死的地方重新发明。颗粒度由处境决定（Google 管这个谱系叫 **degree of constraint**）：绿地项目留实现空间；受遗留代码/库/协议约束的写到接口契约级；存量系统改造写到"变化点前后各是什么样"。

**§5 处理链路（细节展开的主轴）。** 挑一个具体场景，从触发到结果走一遍：参与方、每步做什么判断、产生什么、失败怎么办。**这一段是后面所有细节的索引**——链路上有几步，后面就有几块展开；静态结构（模块、目录、表）跟在链路之后，因为读者先要理解"跑起来是什么样"才关心"东西放在哪"。用时序图（mermaid `sequenceDiagram`）。**判据**：读完之后，链路上每一段要么已经设计，要么显式标为留白。

**§6 关键决策与备选。** 这是全篇最容易被写空的一节。判据来自掘金那份技术方案模板：**技术方案本质回答两个问题——(1) 为什么该方案可行？(2) 在已有资源限制下，为什么该方案是最优的？普遍毛病是花大力气准备了第一个，忽略了第二个。** 每个有争议的点给 2–3 个方案 + 建议 + 为什么不选；被否决的方案一行带过但**"为什么被否"必须留下来**（Go 把被否决的 `try` 内置函数提案完整公开在 `design/` 目录里，那是后来人唯一的查证依据）。只有一种做法时写「无备选 + 理由」——这不是偷懒，是正确的信息。

每条决策至少标出它与其他决策的三种关系之一，以及它往下带出的必做项（形态取自中文工程实践的"影响 / 连带项"两列）：

- **依赖**——B 成立以 A 为前提（"选了 A 的同步链路，B 才可能不做幂等"）
- **推论**——因为 A，所以 C 才成立（"因为定了单写者，C 的冲突解决才可以省掉"）
- **推翻**——E 让 F 不再成立（"引入 E 之后，F 那条约束自动消失"）
- **连带项**——这条决策定下来之后，必须有谁去做什么（"平台 key = 共享成本 → 接口必须鉴权且可计量"）

第三种关系是现有模板的普遍盲区，有出处：**设计理由（design rationale）领域最著名的框架 IBIS 有一条公认短板——"不处理依赖：一个问题的答案是否依赖于另一个问题的答案"。** 它记的是理由，不是因果。

**§7 风险与未决。** 这两类是不同的问题，分开写。**风险**：已知的坏可能性，每条写清**触发信号 + 缓解措施 + 缓解失效怎么办**；只写"有风险"等于没写。**未决问题**：作者也不知道答案的问题，写成可关闭的形式——

```
**未知**：<是什么> — 待 <什么条件> 确定 — 不影响 <做法 / 接口 / 验收>
```

判据是"它会改变做法、接口或验收吗"——**会，就现在去问，别留成未知**。还要区分**待讨论**与**待实测/待执行**：后者（"脚本已产出，等谁执行"）不是未决问题，挂在这里会让读者以为还没想清。

**§8 验收与不变量。** 写成三列表：**不变量 | 保证方式 | 怎么测**。**没有"怎么测"的不变量不算不变量**。与成功度量分开：验收管"这次交付对不对"，成功度量管"这件事有没有用"。

**条件节的生成指导：**

**模块划分与依赖**——三件东西：职责表（模块 | 负责 | **不负责**，第二列比第一列更能防止边界糊掉）、依赖图、**循环依赖检查**（明确写出"已确认 X 不反向依赖 Y，只通过 Z 关联"）。再加一份**放置判据**：把"这东西该放哪层"写成几问，让后来人能自己判，而不是每次来问（形态取自真实工程实践的五问式）。

**接口契约**——接口清单表（接口名 | 路径或签名 | 方式 | **新增/变更** | 调用方），细节抽到独立文档时写指针（"详见《接口文档》"）。精度判据：**实现者不用再做设计决策**。会破坏既有合法调用的变更要单独标出。

**状态机与流程**——状态流转图 + 状态×事件→目标态表。**并发与幂等必须单独写**：同一动作能否重复触发、并发时以谁为准、重复请求返回什么。这一节最容易漏，也最容易在线上出事。

**数据设计**——表结构表（字段 | 类型 | 允许空 | 默认值 | 说明）、字段变更表、**数据归属**（哪张表归哪个模块）、一致性策略（事务边界、失败重试、补偿）、迁移方案。一条来自中文工程实践的判据值得照做：**查历史数据是否存在与 schema 不符的异常**——他们的例子是"字符串字段实际存的是整数数组结构，历史数据里却有真的字符串数组"，这种要到接口返回时才炸。

**数据流转**——数据流图：谁产生、经过什么变换、落到哪、**谁是权威源**。判据：处理链路上每一步如果动了数据，必须在这里找得到对应；**对不上说明方案没闭合**。旧数据的语义要写死（NULL 是"无归属"还是某个默认账号）。

**横切关注点**——
- **安全**：威胁识别表（威胁场景 | 风险等级 | 应对措施）+ **检查清单**（维度 | 检查项 | 级别 MUST/SHOULD | 结论）。含外部输入、权限边界、密钥处理时必写。
- **可观测性**：指标 / 日志 / 链路 / 告警四类各写什么，形态是四行表。
- **性能与容量**：指标表（指标 | 目标 | **验证方式**）——有目标没验证方式等于没定。
- **成本**：按什么计量、记到谁头上。

**兼容迁移与回滚**——兼容矩阵（维度 | 兼容方案）、发布顺序（写到步骤级）、回滚表（场景 | 回滚步骤 | **触发条件** | **耗时**）。回滚要写到"判据 + 动作"，写"可回滚"三个字等于没写；耗时是承诺，逼你想清楚真的能多快退回来。

**实施与里程碑**——阶段表（阶段 | 产出 | 前置）。**有独立计划文档时只写指针**，不要重复计划的内容。落地前有未验证的关键假设时，写成 **spike 清单**：几条、几天、谁做、**几条全过才算可行**。

**评审记录与 ADR**——最小形态：评审时间 / 评审人 / 意见 / 处置；结论三选一（通过 / 修改后通过 / 重新评审）+ 问题记录表。ADR 部分给清单（编号 | 标题 | 状态 | 链接）与摘要。累积形态值得学（dotnet 的 Q&A）：**"当你在 GitHub 讨论或邮件里不得不解释某件事时，考虑把它更新进文档并链接你的答案，这样你就不用反复解释同一件事。"**

**附录**——依赖清单、环境变量、部署片段、**改动索引**（"实施时按此逐项核对"的表：类别 | 文件）。查考型内容全部下沉到这里，正文只留判断。

**文档迭代时的三条纪律**（增量文档尤其重要）：

- **追加节要声明权威优先级**："本节与正文冲突时以本节为准；冲突段落（列清单）在下一次修订收敛。"没有这句话，读者看到正文与追加内容说法不一致时不知道该信哪个。
- **决策改判就地留痕**：`~~原结论~~ **YYYY-MM-DD 改判：<新结论与依据>**`。不要抹掉旧结论——那是"当时为什么那么想"的唯一记录。这与 §6 的因果关系互补：因果是逻辑序，改判留痕是时间序。
- **事实性修正单独列表**：正文现状 vs 实际，并标"下一版必须改"。这份清单是下一次修订的输入。

### 第 3 步：表征——图、表、散文怎么分工

**按内容形态选形式，不按个人习惯：**

| 内容形态 | 用什么 | 例子 |
|---|---|---|
| 结构、关系、流向、状态 | **图** | 上下文图（flowchart）、处理链路（sequenceDiagram）、状态流转（stateDiagram）、数据流 |
| 并列的同类项，每项有几个字段 | **表** | 决策、目标、风险、字段、接口、不变量、检查清单 |
| 因果、理由、边界、动机 | **散文** | 为什么这么选、留白在哪、失效场景是什么 |
| 层级、目录、树 | **代码块树** | 目录结构 |
| 唯一真源的契约 | **代码块** | DDL、接口签名（仅当它还没实现时） |

**四条纪律：**

1. **一图一主题，图跟着它的节走。** 总览图在总体方案，链路图在处理链路，状态图在状态机节。不要集中堆一个"图集"——读者读到那一节时才需要那张图。
2. **每张图给一句"从这张图该读出什么"。** 图表达关系，结论要写出来；否则十个读者读出十种理解。
3. **用纯文本图**（mermaid）：随文本 diff、可评审、可修改。贴图片等于放弃版本控制——对方眼里只有"图变了"，看不出变了哪里。若导出格式是交付要求（如转 Word/PPT），把 mermaid 当源、导出物当产物，源永远留在文档里。
4. **表也有阅读上限**：单表超过 15 行就考虑拆开、改图，或下沉到附录。把什么都塞进一张大表，和写成大段文字一样难读。

### 第 4 步：读者测试（有条件时做）

写完找**一个没有上下文的读者**过一遍——另一个人，或新开一轮不带本次会话历史的模型。只问三件：

1. 读完能不能复述出这份文档在做什么
2. 哪一节读不懂，或读起来最费劲
3. 有没有哪句话他不知道该不该信

作者自己读不出这个问题——你已经知道全部背景了，所以"我觉得挺清楚的"不构成证据。这一步借自 Anthropic 的 doc-coauthoring（它管这叫 Reader Testing）。没有第二个读者时退而求其次：**隔一段时间再读**，专挑自己写的时候最顺的那几段——写得越顺，越可能是自己知道而没写出来。

### 第 5 步：自查

按 Exit Criteria 逐条过。重点查六处最容易出问题的：背景有没有可核实来源且用具体场景开头；决策节有没有答"为什么最优"、**因果与连带项有没有画出来**；每个条件节是否都能说出触发条件；**给人读的和给模型读的部分有没有混着写**；**有没有为填满而写的段落**（逐段问"删掉它会失去哪个判断依据"）；**有没有整段散文本该是图或表**。

### 第 6 步：审阅已有文档

要对**别人的或已有的**文档做诊断时，走 `references/review.md`：那里有判据清单、发现的输出格式与三种修复类型（ACKNOWLEDGE / SPECIFY / REDESIGN）、按根因聚类，以及一个**只有独立审阅者才做得到**的范围膨胀检测——先按输入独立画一份最简设计，再要求文档里多出来的每个机制逐条论证它对应哪条输入。

## Exit Criteria

- [ ] **档位已明确**，且节集与档位相符（轻量档不多勾、重点档不缺节）
- [ ] 地板 8 节全部存在，每节都能被读者用来做判断（轻量档允许每节一两行或写「无（理由）」，但不缺节）
- [ ] **章节有编号**（`第N章` 或 `N.`，子节 `N.1`），跨引用写的是编号而不是只写节名
- [ ] **档 2/3 有改动点级设计**——按对象的节（接口契约 / 状态机与流程 / 数据设计）或兜底的「改动点设计」节，写到实现者不用再做设计决策
- [ ] 每一个条件节都能对应到一条触发条件；没有"因为模板里有所以写了"的节
- [ ] 增量文档写了"上一版交付了什么"，且「兼容迁移与回滚」在列
- [ ] 元信息头含：状态（终态化取值）、**设计分级**、讨论入口、**读者与分界（哪几节给人、哪几节给模型）**
- [ ] **往下走多远已明确**（spec-first / spec-anchored / spec-as-source）；选 anchored 时元信息头有最后更新日期
- [ ] **文档有即时价值**：能说出它写完之前就会被谁用于什么（评审呈品 / 执行者照它干活），不是"写完存档"
- [ ] 背景用一个具体场景开头，且至少有一处可核实的外部证据
- [ ] 每个声称要解决的问题都能引用输入里的原句；引不出的已删掉或改写成有依据的表述
- [ ] 每个非目标都写了理由，且属于"本可做但选择不做"，不是"被否定的目标"；目标带可衡量指标
- [ ] 总体方案先总览后细节；参考型内容（接口 / 表结构）在末尾或独立成节
- [ ] 总体方案里显式声明了「本文定义到什么程度、把什么留给实现者」
- [ ] **处理链路已画出**，且链路上每一段要么已设计、要么显式标为留白
- [ ] 每个设计点都能指向它的**规格与证据**，或已明确标为"尚未定"
- [ ] 每个有争议的决策点有 2–3 个方案与不选的理由；只有一种做法时写了「无备选 + 理由」
- [ ] **关键决策之间标了因果**（依赖 / 推论 / 推翻 至少一类），且每条标了影响或连带项
- [ ] 每个机制都写了更简单的替代与不用的理由，或明确写「无更简替代」
- [ ] 风险写了触发信号与缓解；未决问题写成可关闭形式，且区分了待讨论与待实测/待执行
- [ ] **每个不变量都有"怎么测"**；没有的不算不变量
- [ ] 有外部输入 / 权限边界 / 生产影响时，**安全与可观测性已写**（威胁表 + MUST 检查清单；指标·日志·链路·告警）
- [ ] 数据相关改动写了权威源；处理链路上动了数据的地方在数据流转里都有对应
- [ ] 增量文档的回滚写了触发条件、动作与耗时
- [ ] 给模型读的部分精确到不用再做设计决策；边界写成 Always / Ask first / Never 三档
- [ ] **内容以图、表承载为主**：并列同类项是表，结构关系是图，没有整段散文本该是图表
- [ ] 图是纯文本（mermaid），一图一主题、图跟节走，每张图有一句"该读出什么"
- [ ] 没有贴图片；没有单表超过 15 行而不拆
- [ ] 实现前写的接口签名 / DDL 是规格（该写）；实现后只留指针（不贴实现）
- [ ] 有追加节时声明了权威优先级；有决策改判时留了痕
- [ ] 没有 `TODO` / `TBD` / 待补 占位符
- [ ] **没有为填满而写的内容**：每一段都能说出它承载了哪个判断依据，说不出的已删
- [ ] 术语在首次出现处就地定义（或遵从项目惯例的独立术语章）
- [ ] 有条件时做过读者测试，并修掉了读不懂的地方

## Exit Protocol

**产出**：一份 markdown 设计文档，落在**项目仓库内**，路径沿用项目既有惯例（如 `docs/designs/`、`doc/developer/design/`、`docs/<模块>方案.md`）。没有惯例时用 `docs/designs/<主题>.md`。

**不要落在**：临时目录、`.workflow/`（自忽略目录，收尾后随工作树消失）、或只留在对话里。

**这份文档之后要走工作流时**（task-workflow）：**把它直接声明为那次工作流的设计文档**——计划头部的 `**设计文档**:` 指向它，工作流只做结构对齐（只动标题）与记锁，**不要再另起一份**。两份并存的代价不是冗余，是**必然漂移**：回写只写一份，而执行者可能读到过时的那份——且它不会知道自己读错了。

**呈现给用户的顺序**：

1. 一句话说清这份文档的**读者与往下走多远**，以及**定的哪一档**（第 0 步四个判断的结果）
2. 列出**本次采用了哪些条件节、各自触发了什么条件**——这条最容易漏，但它让读者能判断"范围对不对"，比逐节讲内容有用得多
3. 再给全文

**只讨论不落盘时**：给出骨架（档位 + 地板节 + 勾选的条件节及触发条件）+ 每节要点与打算用的表征（图 / 表 / 散文），并说明"要落成文档时告诉我你的路径惯例"。
