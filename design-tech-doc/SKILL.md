# Design Tech Doc

帮助研发团队把问题、取舍和实现边界讨论清楚，再形成可评审、可实现、可维护的技术设计。内容覆盖设计问题，章节随文档用途和项目约束组织。

## Working Protocol

### 1. 对齐问题，先查事实

先用一句话复述本次要解决的问题和产物用途。区分新建、更新、仅讨论和仅审阅；仅审阅直接进入第 7 节，不把审阅变成重新设计或代写。

读取用户指定材料、项目已有设计和相关实现。能从文件、代码、日志或工具查到的事实先自己查，不能把“当前接口是什么”这类可查事项直接丢回用户。只读与本次问题相关的内容；资料不可达或互相冲突时说明证据缺口，再问当前最关键的一项。用户给出的状态可以记为用户陈述，不能冒充独立核验。

将信息分开维护，随答复和查证更新，不要求每轮展示整张表：

| 清单 | 记录内容 | 怎么推进 |
|---|---|---|
| 已确认 | 事实及来源；用户已作出的设计决定及适用前提 | 前提未变就复用，不重复问 |
| 待确认 | 尚未决定的范围、机制、取舍、契约与风险处理 | 沿依赖关系逐项讨论 |
| 待实测 | 无法靠意见一致证明的性能、效果、容量或可靠性假设 | 先确认实验方法与通过标准，再取证 |

事实、设计、实现和验证分别陈述。例如“已确认采用去重键”不代表去重已实现；代码已存在不代表生产已启用；POC 成功只证明其环境、数据和负载内的结果。

**范围守卫：** 服务研发内部设计；PRD、客户／售前方案和任务排期不套本协议。单项重要决策可只写 ADR，保留背景、选项、理由、后果和状态；ADR 可记录不可逆决策，也可作为完整设计的伴随记录。设计写机制与契约，任务计划写执行动作和排期；必要的迁移次序属于设计约束。

### 2. 分别判断文档类型、评审强度和状态

| 文档类型 | 回答的核心问题 | 应到的深度 |
|---|---|---|
| 系统总体设计 | 系统边界内有哪些责任，它们怎样协作并满足质量目标？ | 边界、模块、交互、责任、关键质量属性和部署；契约只展开到影响系统判断的程度 |
| 需求／模块技术设计 | 一个需求或模块如何正确交付，怎样接入已有系统？ | 输入输出语义、状态、异常、并发、一致性、兼容和验收 |
| 专项技术设计 | 一个技术问题靠什么机制解决，在什么条件下成立？ | 约束、备选、机制、成立条件、验证及失败路径，例如性能、安全、迁移或算法 |

| 评审强度 | 判据 |
|---|---|
| 轻量 | 影响集中、契约稳定、数据与安全边界清楚，验证和恢复路径已有把握 |
| 标准 | 有需要协调的接口、数据或模块变化，风险可通过明确的验证与恢复措施控制 |
| 重点 | 影响面大、关键契约或安全边界变化、不可逆数据操作、复杂迁移，或关键可行性仍有较大不确定性 |

强度说明评审需要关注多少风险，不决定章节配额。结合影响面、契约、数据、安全、不可逆性、迁移和验证不确定性给出理由；普通生产发布不自动升为重点，行数、工时、篇幅和章节数都不是机械分级依据。

**不写独立文档的出口：** 单点且事实、影响、验证和恢复已经明确，可在 issue／MR 留足记录。先证明这些条件成立，不能凭“只改两个数字”判为免设计。例如“所有超时从 30 秒改为 60 秒”应先核对调用链预算、重试与取消、资源占用、级联放大和重复副作用；这些影响未明时仍是待确认或待实测项。

状态独立使用 `草稿 / 待评审 / 已接受 / 已实现 / 已被取代 / 已废弃`，沿用项目合法的状态映射。模型自检通过不能标为已接受；用户认可一个问题不能标为全文通过；实现已完成也不证明生产验证通过。正式评审结论只引用实际发生的评审及其范围。

### 3. 逐项达成共识，再成文

把待确认问题按依赖排序：先解决会改变后续问题的目标、范围或约束，再讨论依赖它的机制和细节。排序不等于豁免：**所有尚未解决的设计疑点都须用户确认，不能按“影响小”“可逆”自行放行。** 排版表达和用户已明确留给实现者的局部编码自由不属于未决设计。

每轮只提出**一个当前问题**，说明它影响什么，给真实备选、推荐和理由，等待答复。不要把多个独立选择装进一个问号或打包“全部同意”；只有一个可行选择时说明约束，不编造稻草人选项。讨论可用比较表、机制草图或局部片段，显式标为讨论材料，不能把尚未确认的推荐嵌入正式方案。

用户说“认可”只确认当前清楚提出的事项；沉默不是同意，模型推荐不是决定，催促成文也不会补齐缺失的选择。答复有歧义就先澄清同一问题。每轮复用既有共识，前提变化时只重开受影响的决定并说明原因。

**实证未知的分支：**

1. 先与用户逐项确认实验方法、代表性环境／数据／负载及通过标准；能实际验证且已获授权时执行，不能执行则说明原因。
2. 有结果时保留证据、版本与验证范围，再据此讨论决定；失败不能改写为通过。
3. 暂时不能验证时，由用户明确选择“等待证据”，或“接受具体假设、风险和适用条件后先形成有条件草稿”。模型不能代选，也不能只加一个“待验证”标签就继续。
4. 有条件草稿仍须解决其余设计疑点，并写明假设、风险、适用范围、验证方法／门槛、关闭条件以及未验证前禁止作出的承诺。同意假设不等于实测，也不等于无条件可实施。

**成文前检查点：设计简报。** 汇总文档类型、评审强度及理由、读者与范围、设计深度和实现自由、默认提纲的合并／省略／继承及理由、继承文档、关键决策、未知的处理和本次同步文档范围。若前文已明确确认覆盖这些内容，引用既有确认即可继续，不机械追加一轮审批；仍有缺项则按依赖每次只确认一项。

未取得所需共识，不写正式方案。写作中发现新设计疑点，停在该点退回讨论，不能把自己的补全藏在正文中。全文完成后还有一次用户评审检查点，不能用成文前简报或模型自检替代。

### 4. 用默认提纲组织，按语义覆盖裁剪

下列提纲是可用起点，允许合并、继承、条件展开，不要求每类文档都出现同样的章节。元信息说明类型、强度、状态、最后更新、来源、读者及维护方式。选节说明交代重要的合并、省略与继承；不适用内容可省略，有强制格式时保留其章节并写具体不适用理由。

- **系统总体设计：** 定位与依据 → 背景、目标与范围 → 约束与质量目标 → 系统边界及总体取舍 → 模块职责与交互 → 关键运行场景 → 接口与数据概览 → 容量可靠性、安全、部署运维 → 验证、风险与演进。
- **需求／模块技术设计：** 定位与上游依据 → 现状、目标与变化范围 → 机制及取舍 → 职责、流程与状态 → 接口与数据细节 → 异常、并发与一致性 → 性能安全运维影响 → 兼容迁移恢复 → 验收、风险与维护。
- **专项技术设计：** 定位与问题证据 → 目标、约束与边界 → 备选及取舍 → 机制和成立条件 → 所影响的接口、数据与运行环节 → 验证方法和证据 → 失败处置、上线恢复、风险与后续演进。

**强制格式优先。** 先将下述语义模块映射到组织指定标题，保留标题与必填项，不为填满而编造结论。格式有冲突且不能同时满足时先说明冲突并确认处理方式，不能擅自改机构模板。

**与 task-workflow 联用：** 读取该工作流实际使用的 `references/design-doc.md`，保留其路径、审批、指纹和回写机制；本技能提供内容指导，不接管执行流程。以下十个二级标题逐字保留，不加章节编号或换近义名；语义模块放入相应小节，可加三级标题：

```markdown
## 一句话方案
## 背景与目标
## 做法
## 备选与取舍
## 接口与数据形状
## 明确不做
## 实际交付
## 已知限制
## 验收标准
## 决策摘要
```

`决策摘要` 保留全部 `D-NN`、来源与理由；`实际交付` 按工作流阶段如实写。不要另建同范围的重复设计文档或绕过审批指纹。若工作流允许执行者自行裁决，而用户要求逐项共识，仍须先完成用户确认；审批记录不能代替尚未发生的设计共识。

### 5. 内容模块库：写清理念、触发和完成判据

以下十五类是问题覆盖库，不是十五个必建章节。根据已确认范围映射到提纲，必要内容不能只因输入没逐字点名而删掉；未触发者省略或说明继承依据。

#### M01 定位与依据

- **理念：** 让读者知道文档解决什么、根据什么、当前能信到哪一步。
- **触发：** 每份独立设计；更新时核对既有元信息和上游承接关系。
- **完成：** 类型、强度及理由、状态、读者、日期、来源、维护方式明确；标明继承什么、本次改变什么，以及设计已确认／实现存在或启用／实测验证各自的证据。没有讨论链接不编造链接。

#### M02 问题、目标与范围

- **理念：** 用可核查的问题和结果约束方案，防止把手段写成目标。
- **触发：** 每份设计；增量需要交代已有能力与本次变化。
- **完成：** 具体场景、问题依据、目标及可判定结果、范围内外及理由清楚；问题可来自需求或查证证据，不要求只能逐字引用输入。假设和建议不能伪装成既定目标。

#### M03 约束与质量驱动

- **理念：** 约束决定可选空间，质量目标解释为何取舍。
- **触发：** 技术栈、环境、资源、组织或质量要求会改变方案时。
- **完成：** 硬约束、偏好和假设区分，来源可追溯；冲突和优先级经确认。质量目标有适用场景及验证口径，无法证明的列入待实测。

#### M04 总体机制与取舍

- **理念：** 先解释整体如何工作，再解释为什么选它。
- **触发：** 每份设计；简单设计可用几句话，复杂关系用上下文图。
- **完成：** 边界、关键机制、真实备选与不选理由可理解；标出存在的决策依赖、推论、失效前提和连带事项，不为每条决定硬造因果关系。已确认选择与讨论候选区分。

#### M05 模块职责

- **理念：** 通过责任和依赖边界减少协作歧义。
- **触发：** 多模块协作、责任调整，或存在功能归属问题。
- **完成：** 各模块负责／不负责、依赖方向、数据或契约责任清楚，循环依赖有处理依据；新增职责的归属能从规则判断，不靠类名或目录清单代替设计。

#### M06 运行时流程

- **理念：** 用一次真实场景贯穿静态结构，暴露分支和失败窗口。
- **触发：** 请求、任务、事件、状态或并发行为发生变化。
- **完成：** 从触发到结果，含关键状态、事件、异常、超时、取消、重试、并发和重复触发的语义；按实际情况说明幂等与补偿。同步调用同样可能重复、有副作用，不能据此豁免幂等分析。

#### M07 接口与集成

- **理念：** 契约说明调用者能依赖什么，不只是列 URL 或函数名。
- **触发：** 新增／变更对外或跨模块调用、事件与外部依赖。
- **完成：** 调用方、输入输出及语义、错误、版本兼容、权限、超时／重试责任清楚；受影响调用和破坏性变化显式列出。已有契约给准确指针，新契约写到双方无需猜测的程度。

#### M08 数据

- **理念：** 数据语义、权威源和一致性比表名更重要。
- **触发：** 结构、读写路径、生命周期、归属或一致性变化。
- **完成：** 谁产生／变换／存储／负责数据可追踪；关键字段、空值与旧数据语义、约束、事务边界、并发冲突、保留清理明确。必要时给 DDL；历史异常、迁移与不可逆影响有处置路径。

#### M09 性能、容量与可靠性

- **理念：** 质量承诺必须在特定负载和故障条件下成立。
- **触发：** 延迟、吞吐、容量、成本、资源占用、可用性或恢复目标受影响。
- **完成：** 指标包含场景、数据规模／负载、度量口径、目标、验证方式；说明瓶颈、资源预算、过载和故障处置，所需恢复目标可检验。区分估算、目标和实测，不能由局部 POC 推到生产。

#### M10 安全

- **理念：** 在实际执行边界阻止威胁，不能用原则或提示词替代控制。
- **触发：** 外部输入、权限／信任边界、敏感数据、密钥或安全要求变化。
- **完成：** 相关威胁、身份与授权、输入处理、数据保护和审计责任对应到具体执行位置及验证；说明失败时如何拒绝、隔离或接管。控制仍未确定时回到讨论，不编造“已保证”。

#### M11 部署、运维与可观测性

- **理念：** 可运行不仅是进程能启动，还须能发现、定位和处置失败。
- **触发：** 服务拓扑、环境、依赖、配置、发布运行或排障方式受影响。
- **完成：** 部署边界、依赖和配置、运行责任、健康判断、相关指标／日志／链路／告警及处置入口清楚；复用既有设施写依据。不要机械要求无分布式调用的工具另建链路系统。

#### M12 兼容、迁移与恢复

- **理念：** 从旧状态到新状态及失败后的去向都是方案的一部分。
- **触发：** 改变已有行为、契约或数据，或新系统需要切流与恢复。
- **完成：** 新旧兼容、存量数据／任务、必要的发布顺序、回退触发与动作、预计耗时及其依据明确；不可逆操作写备份、前滚或其他恢复方式，不承诺不存在的回滚。增量必须检查这些影响，可继承已验证机制并说明适用性。

#### M13 验证与验收

- **理念：** 把设计承诺变成可观察证据，分清正确性和收益。
- **触发：** 每份设计；具体方法按目标和风险裁剪。
- **完成：** 目标、不变量与保证方式、测试方法、环境／数据、通过门槛可对应；覆盖受影响的失败和回归场景，说明未验证项。结果写实际证据，计划写未来验证，二者不混用。

#### M14 风险与未决

- **理念：** 限制和不确定性必须能被决策或验证关闭。
- **触发：** 每份设计检查一次；确无相关风险时简述依据。
- **完成：** 风险有条件、影响、信号、缓解与失效处置；待确认与待实测分开，关闭条件可判断。有条件草稿记下用户接受的假设、风险和适用范围；已知限制仍违反目标或阻塞验收就必须报告。

#### M15 演进与维护

- **理念：** 当前事实应自洽，历史决定应可追溯。
- **触发：** 每份文档确定维护方式；变更涉及其他基线、接口或 ADR 时列同步范围。
- **完成：** 明确基线持续维护或变更记录收尾冻结；相关文档更新范围在写入前说明，状态与替代关系可追溯。实际交付、偏离和限制归位，不用文末优先条款长期容忍正文自相矛盾。

### 6. 控制深度、证据和表达

**深度由协作、正确性和风险决定。** 锁定接口语义、状态边界、数据约束和高风险算法；局部类名、文件拆分、无外部影响的代码组织可明确留给实现者。必要时写伪码、DDL、迁移细节，不把“实现者不能再做任何选择”作为完成标准。已有实现通常引用真源，仍需在文档说明关键语义与约束。

指标统一按“场景与负载 → 度量口径 → 目标 → 验证方式 → 当前证据及范围”表达。缺口先查或讨论，不制造精确数字。设计决定、代码存在、部署启用、实测结果分别标识，并给支持该层结论的来源。

**AI 场景条件扩展：** 涉及模型输出、检索或规则裁定时，按影响记录模型、提示词、规则和知识版本；写清硬约束实际由何处执行及绕过／失败时的处理，评测集代表性、指标门槛、人工接管、输入到结果的证据链和版本变更回归。不能承诺提示词等于硬约束，或几例 POC 等于生产准确率与容量证明；未知按第 3 节处理。

表达按阅读任务选择：结构与流转优先用可维护的文本图，并给出图要传达的结论；同类项比较用表；因果和边界用简短散文。图一张一个主题，避免大表和重复叙述。沿用组织交付格式和项目编号惯例；不要让形式要求盖过语义完整性，也不要改写机器要求的精确标题。

### 7. 审阅、自检和用户评审

审阅已有文档或成文后自检时读取 [references/review.md](references/review.md)，按已确认范围、必要条件和证据定位问题。只审阅时不擅自改写；自检可以修正表达和已定事项的遗漏，新设计问题仍返回逐项讨论。

区分确定缺陷、待决策和待实证项。承认限制不等于解决它；不能因写进“已知限制”就豁免目标或验收阻塞。最小性按目标与工程必要条件判断，不能只因用户没有逐字要求重试、鉴权或恢复就删除这些机制。

全文自检后交用户评审，说明当前状态、关键取舍、尚存限制和证据边界。若有正式评审流程，等待实际评审结果再记录；不冒充用户或组织批准。不强制额外模型审阅；需要独立审阅时遵循当前授权与工作流。

### 8. 更新与生命周期

写入前说明本次新增／同步哪些设计、基线、契约或 ADR；只修改授权范围。用户指定路径和组织惯例优先，未指定时独立设计默认放项目内 `docs/designs/<主题>.md`；仅讨论或仅审阅不强制落盘。工作流产物遵循它的路径约束。

- **系统／模块现状基线：** 随交付更新正文当前事实、版本／日期、来源和相关引用，保留可追溯变更记录，避免两套互相冲突的现状。
- **一次性变更设计：** 收尾更新实际交付、相对批准设计的偏离及原因、已知限制和状态，然后冻结；后续改造另立记录并引用。
- **ADR：** 保留旧决定及当时理由，变更时标为被取代并关联新决定，不抹除历史。

批准后发现实现偏离设计，先显式说明差异与影响，取得用户确认后改实现或修订设计；不能直接改文档掩盖偏离。关联范围更大的上游文档是否同步，取决于其维护契约和本次授权，不因被引用就自动重写。工作流有审批或验证指纹时，按其机制处理受影响审批，并在回写后重新验证。

## Exit Criteria

- [ ] 问题、范围、类型、评审强度、状态及维护方式有依据，未把它们混为一档。
- [ ] 可查事实已查或明确说明不可达；设计、实现、启用和实测结论均有相应来源与范围。
- [ ] 所有设计疑点已逐项确认；已有共识复用，排版与被明确保留的实现自由没有被误当作设计门槛。
- [ ] 实证缺口已验证，或用户明确接受了具体假设、风险和条件草稿路径；等待证据时未擅自成文。
- [ ] 成文前简报已覆盖类型、强度、范围、深度、提纲裁剪、继承、决策、未知和同步范围；既有确认可复用。
- [ ] 三类默认提纲按实际问题裁剪，十五类语义模块已检查适用性；必要机制、安全、容量与部署责任没有被空泛表述替代。
- [ ] 强制模板和工作流机械契约完整保留；没有以章节数量或篇幅判合格。
- [ ] 关键契约、失败路径、受影响兼容和恢复、验收证据足够明确；局部实现自由有边界。
- [ ] 自检按审阅规则完成，阻塞目标的已知限制仍显式报告；未伪造实测或正式评审。
- [ ] 全文已呈交用户评审；只在用户或正式流程真实确认后标相应状态。
- [ ] 更新时正文当前事实自洽，实际交付、偏离和限制如实回写，历史决定及替代关系可追溯。

## Exit Protocol

未形成共识时，只给当前一项讨论及真实选项，说明阻塞点；不以“待确认”文档代替用户决定。免独立文档时给出理由和够用的 issue／MR 记录；仅审阅时交发现与证据，不改文档。

成文时交付用户要求的文档或路径，简述类型、评审强度、当前状态、关键裁剪／继承和待评审事项。有条件草稿显著列出假设、风险、适用范围与未通过的验证门槛，不能呈现为可直接实施的定案。用户评审后按真实结论更新状态，执行与发布仍遵循其自身授权。
