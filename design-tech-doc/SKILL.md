# Design Doc

按「默认 + 追加」两层决定一份技术设计文档该有哪些内容，并给出每一节的生成指导。**这里没有固定模板**——模板给的是章节名，本 skill 给的是"这一节在你的项目里该长什么样、颗粒度由什么决定、什么算写坏了"。

判据来自 21 家一手材料：13 份业内模板与流程（Google design docs、arc42、IEEE 1016、Rust/React RFC、Kubernetes KEP、Uber、GitLab、Amazon PR-FAQ、MADR/ADR、GB/T 8567、腾讯云迭代技术方案规范、掘金技术方案模板），加 8 个知名项目的真实文档库（Go、Rust、Kubernetes、CockroachDB、Materialize、dotnet/designs、Swift Evolution、gRPC）逐份解剖与体量实测。另对照了 GitHub 上 10 余份同类 skill（Anthropic 的 doc-coauthoring、sisyphus-design、design-doc-mermaid、spec-writer 等），借用处已在正文标注来源。

**守卫：**

- **这不是 PRD。** PRD 说"用户应该体验到什么"，本文档说"系统如何交付这一体验"。写产品需求请换工具。
- **这不是 ADR。** 单条可逆决策的最小记录用 ADR；本文档是完整方案。一份文档里塞十条互不相关的决策，读者找不到主线。
- **这不是计划。** 任务拆分、依赖图、排期属于计划。设计文档回答"这是什么东西、为什么这么设计"，不回答"谁在第几天做什么"。
- **在 task-workflow 工作流内时，产物契约以那边为准。** `task-workflow/references/design-doc.md` 规定了十节骨架、`D-NN` 决策校验、回写协议与验证指纹绑定——那些是**机械约束**，本 skill 不覆盖、也不冲突。两者叠加使用：那边的十节骨架可看作本 skill 默认节在项目内的固定化，本 skill 管的是"每一节怎么写扎实"。对"该写什么"有分歧时以那边的契约为准（它有机械校验和审批绑定，优先级更高）。
- **不做固定模板。** 不要因为某节"模板里有"就写它。每一节的出现都要能说出触发条件，说不出就不加。
- **长度有纪律。** 实测四个公开文档库（Rust / Go / Materialize / CockroachDB，共 1090 份）的中位数是 3–6 页。更可执行的锚来自 Sentry 在自家 RFC 仓库里那套规格：**正文约 1500 词（中文约 2500–3000 字），目标 5–10 分钟读完**，代码块与表格不计入。超出部分要有说得出的理由，长度只能来自"真的还有话要说"，不能来自把模板填满。
- **文档必须对写它的人有即时价值。** 这是设计理由（design rationale）类方法几十年工业应用失败的根本原因，原话很直白：**"没有人会为一个未知的人、在未知的时间、为未知的任务，无私地写高质量的设计理由。必须有即时价值。"** 落到做法上：**让这份文档的第一次真实使用发生在它写完之前**——它本身就是评审呈品，或者执行者要照着它干活。一份"写完就存档"的文档，你不会认真写，写了也没人信。
- **给诚实的省略留出口。** 某节确实不适用时写「无（理由）」，不要凑字，也不要留 `TODO` / `TBD` / 待补。

**反模式（明确不要做的事）：**

- 不要照抄任何一份模板的章节名然后逐节填字——那是"看起来像设计文档"与"是设计文档"的区别
- 不要在只有一种做法时硬造备选——写「无备选 + 理由」比编两个稻草人方案强
- 不要把"非目标"写成"被否定的目标"（见 §2）
- 不要把执行步骤写进设计文档——文件清单、符号名清单、命令序列属于计划
- 不要写会被代码取代的内容（完整实现、逐行算法）——必然过期，而且读者会以为它可信
- 不要在没有依据时写断言（"线上一定没问题""性能足够"）——要么标条件句写清须核实，要么不写
- **不要跳过第 0 步直接开写**——读者、可逆性、往下走多远三个判断决定后面几乎每一节的颗粒度，跳过它就只能套模板
- **不要因为用户催就砍掉风险与未决问题节**——那一节空着，等于告诉后来人"当时没想过"
- **不要只写"为什么选 A"，不写"A 和 B 之间是什么关系"。** 理由是平的，因果是链的。缺了依赖与推论关系，读者无法判断"改了这个决定会连带影响什么"（见 §4）
- **不要把给人读的部分和给模型读的部分混着写。** 两者的失败模式不同：人读不懂会来问你，模型读不懂会直接自己编一个（见 §0）

## Working Protocol

### 第 0 步：三个前置判断（不写正文，先定形状）

| 判断 | 怎么看 | 影响什么 |
|---|---|---|
| **读者是谁** | 只有同团队工程师 / 要跨团队 / 要过评审门 / 要给非技术方看 | 背景写多厚、要不要参考型章节、要不要成功度量 |
| **变更可逆吗** | 能在一个发布周期内悄悄回退吗 | 可逆 → 写"够用就走"；不可逆（数据格式、公开接口、外部契约）→ 写满、写死、写清判据 |
| **文档往下走多远** | 只服务当次实现？任务结束后还要继续用？还是文档本身就是主源？ | 三级（借自 Martin Fowler 对 spec-driven development 的分层）：**spec-first**——写完即冻结，读者看的是历史（RFC/KEP 形态）；**spec-anchored**——任务结束后仍用于演进与维护，须在元信息头维护最后更新日期并写明本文档会变（Chromium 形态）；**spec-as-source**——文档是主源，人只改文档、不碰代码。**级别选错要么白写要么烂掉**：按 anchored 的预期写完却从不更新，文档会悄悄变成谎言；按 first 的力度写却被长期依赖，读者会发现它处处不够用 |

判断结果要落到元信息头与呈现里，不要只在心里过一遍。

### 第 1 步：选节

从默认七项起底，再按触发条件勾追加节。**每勾一节说清为什么触发**；不触发就不加。

**默认七项**（六节 + 一条纪律）：

| # | 节 | 能否省 |
|---|---|---|
| 0 | 元信息头 | 不可省 |
| 1 | 背景与问题 | 不可省 |
| 2 | 目标与非目标 | 不可省 |
| 3 | 方案总览 | 不可省 |
| 4 | 关键决策与备选方案 | 不可省 |
| 5 | 风险与未决问题 | 不可省（空着 = 没想过） |
| 6 | 术语就地定义 | 纪律，不设独立章节 |

**追加节与触发条件**：

| 追加节 | 触发条件 |
|---|---|
| 兼容性与存量数据 | 改变既有行为 / 接口 / 数据格式，或系统已有存量数据 |
| 成功度量 | 目标是行为改变或业务指标，而不是"功能上线" |
| 上线、灰度与回滚 | 有生产影响 |
| 依赖与阻塞权方 | 跨团队 / 跨系统 |
| 原型或可行性验证 | 方案含未验证的关键假设 |
| 验收标准 | 需要判断"做完了没有"，且不是一句话能说清 |
| 评审记录 | 有正式评审门 |
| 工作量与排期 | 需要资源决策 |

### 第 2 步：起草默认七项

#### 0. 元信息头

**要回答**：谁写的、什么时候、什么状态、去哪讨论、**这份文档的哪部分给谁看**。

**怎么生成**：

- **状态取值必须是终态化的集合**，例如 `草稿 / 待评审 / 已接受 / 已实现 / 已被取代 / 已废弃`。只有"草稿 / 已接受"两种状态的文档库会烂掉——CockroachDB 的真实 RFC 头部写的是 `Status: completed`，NATS 用 `Proposed / Approved / Partially Implemented / Implemented / Deprecated`。**没有终态，读者无从判断一份文档还该不该信。**
- **讨论入口是必填项，不是装饰。** 八份真实文档里除 dotnet/designs 外全部在头部写死了讨论链接（`Discussion at` / `RFC PR` / `Review`）。设计文档的价值一半在正文、一半在它指向的那个讨论线程。单人起草、还没有讨论入口时，写"讨论入口：<将要发到哪>"。
- **读者与分界（新）**：写清**哪几节给人读、哪几节是给模型/执行者的契约**。这不是分类癖——两者的失败模式完全不同：**人读不懂会来问你，模型读不懂会直接自己编一个**。所以"给人读"的部分要能 5–10 分钟读完并讲清因果，"给模型读"的部分要精确到不用再做设计决策（接口签名、数据结构、状态流转），边界写成 **Always / Ask first / Never** 三档——这条形态来自 GitHub 对 2500+ 份 agent 配置文件的分析，"Never 提交密钥"是其中出现频率最高的有效约束。
- 日期用**最后更新**而非创建日期。
- 项目已有文档头惯例时**沿用惯例**，不要另起一套。

**失败模式**：状态永远停在"草稿"；没有讨论入口，读者想问不知道去哪问；没画分界线，结果人读到一半撞进接口签名表，模型读到一半开始自己发明数据结构。

#### 1. 背景与问题

**要回答**：读者凭什么判断这个方案好不好。

**决定内容的因素**：读者的先验知识离这个问题有多远。离得越远背景写得越厚——但只写**判断所必需**的，不是作者知道的全部。

**怎么生成**：

- 先写**问题现状**（现在是什么样、不改会怎样），再写**为什么是现在**。顺序别颠倒——先给现状，读者才有位置安放后面的方案。
- **动机用一个具体场景开头**（Sentry 的 `condense-rfc` 把这条列为硬性要求）。这不只是可读性问题，有实证支撑：Cambridge 那篇设计理由论文发现**逻辑框架显著影响接受度——演绎式推理更容易让人拒绝一个设计，溯因式推理更容易让人接受**。所以从"发生了什么"讲起，而不是从"按照某原则，我们应当……"讲起。
- **至少捞一处可核实的外部证据**：issue 号、监控数据、用户反馈、失败案例、性能数字。判据很直白——如果背景全是叙述而没有任何可核实的来源，那它是印象不是事实。
- **更锋利的一条（评审会直接问到）**：你声称要解决的**每个**问题，都要能指出输入里确立它为问题的原句——需求原文、issue 描述、数据。引不出原句的，是你自己发明的问题。这条借自 `references/review.md` 那份评审清单，它把"引不出原句"直接判为自造问题。
- 承接已有设计时写**承接关系**：源路径 + 继承它哪些结论 + 本次增量或修正。不重述它已经说过的东西，但也别省掉关键结论——本文档仍要自包含到能独立读懂。
- 这条判据可直接用（腾讯云迭代技术方案规范）：**"对需求的理解，不是复述，而是总结和抽象"**。背景段读起来像把需求文档换了个说法，就是没写。

**失败模式**：写成需求复述；没有一处可核实来源；读者读完不知道为什么要有这份文档。

#### 2. 目标与非目标

**要回答**：本次范围到哪里为止。

**怎么生成**：

- **非目标用 Google 的精确定义**：不是"被否定的目标"，而是**"本来可以合理地成为目标、但被明确选择不做的事"**（他们举的例子是"不追求 ACID 合规"——那不是坏事，是范围选择）。写成"不做 XX"而不给理由，等于没写。
- 非目标有两个自然来源：**评审中被提出但决定排除的**（dotnet 模板明说"你会在早期评审后往这里加条目"），以及**一看就相关但在范围外的相邻问题**。起草时通常只写得出后者——**靠评审补前者是正常的，不要为了填满而编。**
- 目标写成"做成后谁看到什么不同"，不要写成"完成 X 功能"——后者是同义反复。

**失败模式**：非目标写成了被否定的坏目标；目标与方案节重复；非目标空着（几乎总是意味着范围没想过）。

#### 3. 方案总览

**要回答**：用一屏让读者建立整体图景，然后才进细节。

**决定颗粒度的因素**——全篇最需要判断的一处：

| 项目处境 | 写到什么程度 |
|---|---|
| 绿地项目（无既有约束） | 留出实现空间即可，细节由实现者定 |
| 受遗留代码 / 库 / 协议约束 | 写到接口契约级——约束会吃掉实现者的选择空间，不写清就会设计出无法落地的方案 |
| 存量系统改造 | 写到"变化点前后各是什么样"，只画改动涉及的部分 |

Google 管这个谱系叫 **degree of constraint**（从"绿地软件项目"到"被遗留系统和库锁死"）。**同一份模板在谱系两端写出的东西完全不同**——这正是不能有固定模板的原因。

**怎么生成**：

- **两段式**：先总览（一张系统上下文图，或三五句话讲清主干），再细节。读者读不下去通常就是因为一上来全是细节。
- **显式声明颗粒度**：写清本文明确定义了什么、把什么留给实现者。真实文档里这一步常被省掉，结果是执行者要么把留白处当成必须照做，要么在你已经定死的地方重新发明一遍。一句话就够：「本文定到接口契约级；内部数据结构的选型留给实现者」。
- **参考型内容排到末尾或独立成节**：接口签名、表结构、字段定义这类是给执行者查考的，不是给人读的散文，夹在中间会把人挡在门口。真实文档里 CockroachDB 把实现细节单列一节、Swift 把它升级成元信息头字段，是同一个动作的两种做法。
- **不贴会被代码取代的内容**。Google 的判据实用：API 只画相关部分不复制完整定义、数据存储谈大致形态不贴完整 schema、代码和伪代码很少出现（除非是新颖算法）。统一判据是"它会不会过期"。
- **每个设计点要能指向它的规格与证据**（FSE 三元结构：Feature → Specification → Evidence）。这是 Cambridge 那篇设计理由论文的核心主张——**只描述"做了个什么功能"不够，要把功能与定义它的规格、支撑它的证据连起来**。落成一句话：说清"这个功能做什么、它的规格是什么、你怎么知道它成立"。反过来，一个指不出规格也指不出证据的功能点，通常是还没想清楚的东西。
- 留了自由度的地方要写明"这里实现者可自定"——否则执行者会以为必须照做。

**失败模式**：一上来就是细节；贴了大段会过期的代码或 schema；绿地项目写死了不该写死的东西。

#### 4. 关键决策与备选方案

**要回答**：为什么是这个方案，而不是别的；**以及这些选择之间是什么关系**。

**怎么生成**：

- 这是全篇最容易被写空的一节。判据来自掘金那份技术方案模板：**技术方案本质回答两个问题——(1) 为什么该方案可行？(2) 在已有资源限制下，为什么该方案是最优的？普遍毛病是花大力气准备了第一个，忽略了第二个。**
- **每个有争议的点给 2–3 个方案 + 建议 + 为什么不选；没有争议的点不必造备选。** 逐个对比时 CockroachDB 的真实 RFC 用 `Complexity` 与 `Applicability` 两个维度——可以借用，它同时覆盖"做起来多难"和"适用面多大"。
- **被否决的方案一行带过**（名字 + 否决理由），不要复活成一整节重新论证。但**"为什么被否"必须留下来**——Go 把被否决的 `try` 内置函数提案完整公开在 `design/` 目录里，那是后来人唯一的查证依据。
- 只有一种做法时写「无备选 + 理由」，例如"这是框架既定的扩展点，没有选择空间"。**这不是偷懒，是正确的信息。**
- **每个机制都要能说出更简单的替代**，包括"什么都不做"和"交给运行时 / 框架 / 环境"。说不出为什么不用更简单那个，评审就有理由质疑它是不是过度设计。这是那份评审清单里最容易被问倒的一问，也是中文技术评审里"避免过度设计 vs 留扩展余地"那场老争论唯一的可操作落点。
- 需要被计划或任务引用的决策，在这里给编号。
- **决策之间要画出因果关系，不只是并排罗列。** 每条关键决策至少标出它与其他决策的三种关系之一：
  - **依赖**——B 成立以 A 为前提（"选了 A 的同步链路，B 才可能不做幂等"）
  - **推论**——因为 A，所以 C 才成立（"因为定了单写者，C 的冲突解决才可以省掉"）
  - **推翻**——E 让 F 不再成立（"引入 E 之后，F 那条约束自动消失"）

  这是现有模板的普遍盲区，有出处：**设计理由（design rationale）领域最著名的框架 IBIS 有一条公认短板——"不处理依赖：一个问题的答案是否依赖于另一个问题的答案"。** 它记的是理由，不是因果。缺了这层，读者读到"改 A"时无法判断"会不会连带弄坏 B"，而这恰恰是"根据这份文档往下走"时最需要的信息。

**失败模式**：只答了"可行"没答"为什么最优"；备选是稻草人（拿明显更差的方案陪跑）；被否方案直接删掉不留痕，未来有人重新提出同一个方案时无从查起；**决策只有并列没有因果**，读者看得到每条的理由，却看不出它们怎么互相撑住。

#### 5. 风险与未决问题

**要回答**：什么可能出事，以及我还没想清楚什么。

**怎么生成**——这两类是**不同的问题**，分开写：

- **风险**：已知的坏可能性。每条写清**触发信号 + 缓解措施 + 缓解失效怎么办**。只写"有风险"等于没写。
- **未决问题**：作者也不知道答案的问题。GB/T 8567 叫它"尚未解决的问题"，定义是"设计者认为在系统完成之前必须解决"——这个界定很准，它把"可以带着走的未知"和"必须现在解决的未知"分开了。
- 未决问题要**写成可关闭的形式**，否则会永远挂着：

  ```
  **未知**：<是什么> — 待 <什么条件> 确定 — 不影响 <做法 / 接口 / 验收>
  ```

  判据是"它会改变做法、接口或验收吗"——**会，就现在去问，别留成未知**。写「无」与写未知是两回事：写「无」表示想过了，写未知表示还没想。

  另一种做法（`dannwaneri/spec-writer` 的策略）是**先生成、把没指定的判断内联标成 `[假设: ...]` 让用户来纠正**，理由是比一问一答快。它有效，但只适合低风险文档：假设一旦滑进正文而没被纠正，后来的读者会把它当成已确认的结论。高风险或会被当作契约执行的文档，用上面那条"现在问"。
- 争议如果集中在正文某一段，可就地标记而不堆到末尾——Kubernetes KEP 用 `<<[UNRESOLVED]>><<[/UNRESOLVED]>>` 把有争议的段落圈出来。

**失败模式**：风险只有名字没有信号与缓解；未决问题写成开放式问句（"如何处理 X？"）而非可关闭条目；这一节整节空着。

#### 6. 术语就地定义（纪律，不是章节）

**怎么生成**：**不设独立术语章**。真实文档里几乎没有独立 Glossary——Go、Rust、Kubernetes、Materialize、gRPC 都是就地定义，只有 CockroachDB 保留了一个 `Vocabulary` 小节。做法是缩写或专有名词**首次出现时就地给一句话定义**，之后直接用。

例外：项目惯例要求独立术语章时遵从惯例（中文政企 / 招投标场景常见，因为文档要独立交付）。

### 第 3 步：追加节（只写触发了的）

| 追加节 | 生成动作 |
|---|---|
| **兼容性与存量数据**<br><small>触发：改变既有行为 / 接口 / 数据格式，或系统已有存量数据</small> | 写三件事：哪些既有使用方式会受影响；**存量数据怎么办**（迁移 / 双写 / 回填 / 不处理及理由）；能否灰度。<br>一条具体判据值得照做（腾讯云规范）：**查历史数据是否存在与 schema 不符的异常**——他们的例子是"字符串字段实际存的是整数数组结构，历史数据里却有真的字符串数组"，这种要到接口返回时才炸。<br>Swift Evolution 的做法可借鉴：只有会破坏既有合法代码时才需专门处理，**这种情况升级为元信息头的一个字段**（`Upcoming Feature Flag`），而不是让读者自己从正文里找 |
| **成功度量**<br><small>触发：目标是行为改变或业务指标</small> | **先写度量再写方案。** Materialize 模板的顺序值得照搬：Success Criteria 的作用是"帮助验证某个方案能解决问题，但**不要指名具体方案**，聚焦你希望的结果"——再写方案。顺序反了会写成"本方案的目标就是实现本方案"。<br>定量定性都行，但要写明**什么时候看、看什么** |
| **上线、灰度与回滚**<br><small>触发：有生产影响</small> | Kubernetes KEP 的形态最全，按需取用：发布签核清单、上线顺序、灰度策略、回滚**步骤与判据**、监控指标与告警阈值、升级降级策略、版本倾斜策略。<br>腾讯云规范里一条务实的：写清**上线顺序**（web 机、脚本机、SQL、外部服务的先后）以及是否需刷历史数据。<br>**回滚要写到"判据 + 动作"**，写"可回滚"三个字等于没写 |
| **依赖与阻塞权方**<br><small>触发：跨团队 / 跨系统</small> | dotnet 把 `Stakeholders and Reviewers` 单列成节，理由写在模板里：**"即使有规格说明，也常常因为没在早期评审中主动拉进关键利益相关方而让他们措手不及。"**<br>GitLab 更进一步：区分**"被咨询"与"有阻塞权"**，并在文档里写清谁属于哪类（他们的例子是 App Sec 对安全相关变更持有阻塞权）。只写"需要知会 XX"不够 |
| **原型或可行性验证**<br><small>触发：方案含未验证的关键假设</small> | Materialize 把 Minimal Viable Prototype 列为必填、默认要求先做原型，同时留了出口：**"如果你认为有正当理由跳过或推迟，请在这一节明确说明并给出理由。"**<br>原型形态由假设决定：体验假设 → 线框图；接口假设 → 不接后端的假数据；性能假设 → 一次性压测脚本；可行性假设 → 跑在笔记本上的粗糙演示。目标是**证伪**，不是演示 |
| **验收标准**<br><small>触发：需要判断"做完了没有"</small> | 逐条写成**可判定**（能落实成"跑什么、看什么结果"）。<br>与成功度量分开：验收标准管"这次交付对不对"，成功度量管"这件事有没有用"。两者都要时分成两节，别混 |
| **评审记录**<br><small>触发：有正式评审门</small> | 最小形态：评审时间 / 评审人 / 意见 / 处置。<br>累积形态（dotnet 的 Q&A）值得学：**"当你在 GitHub 讨论或邮件里不得不解释某件事时，考虑把它更新进文档并链接你的答案，这样你就不用反复解释同一件事。"** 这是把评审对话沉淀成资产的机制 |
| **工作量与排期**<br><small>触发：需要资源决策</small> | 腾讯云规范的颗粒度可直接用：开发、自测、联调、CR、showcase、测试、上线，并考虑并发与紧急插入需求带来的风险。<br>注意这是**资源决策的依据**，不是任务拆分——任务拆分属于计划 |

### 第 4 步：读者测试（有条件时做）

写完找**一个没有上下文的读者**过一遍——另一个人，或新开一轮不带本次会话历史的模型。只问三件：

1. 读完能不能复述出这份文档在做什么
2. 哪一节读不懂
3. 有没有哪句话他不知道该不该信

作者自己读不出这个问题——你已经知道全部背景了，所以"我觉得挺清楚的"不构成证据。这一步借自 Anthropic 的 doc-coauthoring（它管这叫 Reader Testing），原话的理由是：在别人读之前，先用一个没有上下文的读者接住盲点。

没有第二个读者时退而求其次：**隔一段时间再读**，专挑自己写的时候最顺的那几段——写得越顺，越可能是自己知道而没写出来。

### 第 5 步：自查

按 Exit Criteria 逐条过。重点查五处最容易出问题的：背景有没有可核实来源且用具体场景开头；决策节有没有答"为什么最优"，**以及决策之间的因果有没有画出来**；每个追加节是否都能说出触发条件；**给人读的和给模型读的部分有没有混着写**；**篇幅有没有超**——超 1500 词的部分是真有话要说，还是在填模板。

### 第 6 步：审阅已有文档

要对**别人的或已有的**文档做诊断时，走 `references/review.md`：那里有 21 条判据的评审清单、发现的输出格式与三种修复类型（ACKNOWLEDGE / SPECIFY / REDESIGN）、按根因聚类，以及一个**只有独立审阅者才做得到**的范围膨胀检测——先按输入独立画一份最简设计，再要求文档里多出来的每个机制逐条论证它对应哪条输入。

## Exit Criteria

- [ ] 默认七项全部存在，且每一项都能被读者用来做判断（没有空洞的节）
- [ ] 每一个追加节都能对应到一条触发条件；没有"因为模板里有所以写了"的节
- [ ] 元信息头含：状态（取值是终态化集合）、讨论入口、**读者与分界（哪几节给人、哪几节给模型）**
- [ ] **往下走多远已明确**（spec-first / spec-anchored / spec-as-source）；选 anchored 时元信息头有最后更新日期
- [ ] **文档有即时价值**：能说出它写完之前就会被谁用于什么（评审呈品 / 执行者照它干活），不是"写完存档"
- [ ] 背景用一个具体场景开头，且至少有一处可核实的外部证据（issue 号 / 数据 / 用户反馈 / 失败案例）
- [ ] 每个声称要解决的问题都能引用输入里的原句；引不出的已删掉或改写成确实有依据的表述
- [ ] 每个非目标都写了理由，且属于"本可做但选择不做"，不是"被否定的目标"
- [ ] 方案总览先总览后细节；参考型内容（接口 / 表结构）在末尾或独立成节
- [ ] 方案总览里显式声明了「本文定义到什么程度、把什么留给实现者」
- [ ] 每个设计点都能指向它的**规格与证据**，或已明确标为"尚未定"
- [ ] 每个有争议的决策点有 2–3 个方案与不选的理由；只有一种做法时写了「无备选 + 理由」
- [ ] **关键决策之间标了因果**（依赖 / 推论 / 推翻 至少标出一类），不只是一组并列的理由
- [ ] 每个机制都写了更简单的替代与不用的理由，或明确写「无更简替代」
- [ ] 风险写了触发信号与缓解；未决问题写成可关闭形式，或明确写「无」
- [ ] 给模型读的部分精确到不用再做设计决策；边界写成 Always / Ask first / Never 三档
- [ ] 没有 `TODO` / `TBD` / 待补 占位符
- [ ] **正文约 1500 词（中文约 2500–3000 字），5–10 分钟能读完**；超出时有说得出的理由
- [ ] 术语在首次出现处就地定义（或遵从项目惯例的独立术语章）
- [ ] 有条件时做过读者测试，并修掉了读不懂的地方

## Exit Protocol

**产出**：一份 markdown 设计文档，落在**项目仓库内**，路径沿用项目既有惯例（如 `docs/designs/`、`doc/developer/design/`、`docs/<模块>方案.md`）。没有惯例时用 `docs/designs/<主题>.md`。

**不要落在**：临时目录、`.workflow/`（自忽略目录，收尾后随工作树消失）、或只留在对话里。

**呈现给用户的顺序**：

1. 一句话说清这份文档的**读者与往下走多远**（第 0 步三个判断的结果）
2. 列出**本次采用了哪些追加节、各自触发了什么条件**——这条最容易漏，但它让读者能判断"范围对不对"，比逐节讲内容有用得多
3. 再给全文

**只讨论不落盘时**：给出骨架（默认节 + 追加节及触发条件）+ 每节要点，并说明"要落成文档时告诉我你的路径惯例"。
