# 对抗性审查

派干净上下文的子代理证伪已成型产物，作者裁决后整合修订版。

## Working Protocol

1. **落盘产物**：被审对象写成自包含文件（含必要的背景节）；无法落盘的先补全再审。落盘路径按用户现行目录规则。
2. **派子代理**（Agent 工具，general-purpose）：只给产物文件路径和背景事实包（决策者身份、约束、环境、时间预算），不给创作过程与调研记录。prompt 按此模板，替换【】槽位：

```
你是对抗性审查专家。工作假设：这份【方案/计划/结论】不合理。你的任务是证伪它，不是评价它。
先用 Read 读取：【产物文件路径】

决策者/使用者背景（判断适配性用）：【背景事实包】

逐维度攻击（每个维度至少尝试一次）：
1. 反例：外部证据有没有与核心主张矛盾的？（业界反例、已知失效模式、研究反证）
2. 边界：什么场景下失效或得不偿失？（项目形态、时间尺度、极端情况）
3. 适配：上述背景事实会不会让某些步骤落不了地或成本倒挂？
4. 机制漏洞：方案自身怎么被绕过、架空或自指失败？

输出契约：
- 按 P0（方案失效/造成损害）/ P1（显著降低效果/成本倒挂）/ P2（局部改进）分级
- 每条 = 问题描述 + 具体场景或推理链（可核验）+ 修正方向
- 上限 15 条，宁缺毋滥；禁止空泛的"可能""建议关注"
- 禁止客套、禁止复述方案优点、禁止"总体不错"类缓和结论
- 允许用 WebSearch 核实反例，引用必须真实

结尾给一段结构性判断：这份东西最可能的失败路径是什么。
```

3. **裁决**：主会话以作者立场逐条裁决（采纳/部分采纳/驳回），驳回必须写明理由；不安排审查者反驳轮。
4. **整合**：产出修订版，附裁决记录表（条目/裁决/落点），保留原版对照。

预算约束：一次子代理调用为上限；被审对象过大时先拆分再审，不追加审查者。

## Exit Criteria

- [ ] 子代理报告符合 P0/P1/P2 契约，每条含具体场景与修正方向
- [ ] 每条反例均有裁决与理由，无静默丢弃
- [ ] 修订版与原版并存，裁决记录附于修订版

## Exit Protocol

对话中交付裁决摘要（采纳/部分/驳回计数）与修订版文件路径。未完成时说明阻塞点（产物无法落盘、子代理失败等）与已覆盖部分，不按完成交付。
