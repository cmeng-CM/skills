# 实现审查工作规则

## 准备与独立性

确认用户要审查的目标、实际产物、依据、范围、实现者和审查者。此前亲自实施相关范围的 agent 即使换名字或换 skill，也不能成为该范围的独立审查者。主/子 agent 不是质量等级；选择应依据上下文、专注度、所需工具和独立性。

不能满足独立性时准确说明，并由调用方安排独立上下文或人工审查。若用户只授权本次自检，可以交付自检发现，但不伪称实现审查通过，也不自动启动完整编排。

先从需求建立应有行为，再读取实际变化和相关上下文。作者的报告是有待核实的输入；不能让它决定全部审查范围。读取需求、差异、必要调用方和配置，防止“新增函数正确但根本没有接入”的遗漏。

## 调查与判断

- 按最可能造成真实影响的路径检查规格与质量，复杂状态或集成关系可画简图推演。
- 可运行有授权的测试、构造隔离数据或复现脚本；写自己的报告不违反只读边界。不得为复现方便修复产品、改正式测试或改验收标准。
- 运行检查前了解它是否会修改被审查对象；需要隔离副本时用可识别的同版副本，并记录与原对象的关系。涉及额外外部副作用时不能从审查授权推导许可。
- 缺陷用具体触发条件、实际链路和影响证明。无法复现并不自动否定静态证据，但必须说明证据性质和不确定性。
- 判断严重度、是否阻断和处置状态分别给依据；风格建议不伪装正确性缺陷。

## 复审

读取原报告、稳定问题 ID、作者修复声明和真实修复差异。检查原问题是否解决及相关副作用；范围扩大、契约变化或影响不明时扩大检查，说明理由。原发现记录保留，复审新建关联报告。

作者修改了代码不等于问题解决；明确接受遗留不等于技术修复；安排以后处理不等于风险已接受。复审可同时确认旧问题解决并提出新的问题，使用不同 ID。

整体审查关注全体交付与共享约束，只有报告实际覆盖这些内容才能满足整体要求。任务组内的局部审查不能仅靠“通过”被自动提升为整体通过。

## 报告自检

检查每个结论能否对应依据与真实对象；两类判断是否独立；未覆盖区域是否显式；发现是否足够让实施者采取行动；报告是否越权重新定义需求。无发现时也要报告检查方法与范围，不能给无限制的安全或正确性保证。

审查活动结束后，将发现与建议交给调用方。存在阻断缺陷仍可完成报告，但不能把活动完成标成产物符合。对需要设计/规划决定的问题说明反馈原因，不自主组织修复循环。
