# delivery 技能修复与表达方式整改方案

日期：2026-10-29　状态：**批 1 已实施**（2026-10-29，机械检查通过、两个行为探针符合预期）；批 2、批 3 待实施
范围：`delivery/delivery-*` 各 Skill 的正文与契约；路由与正文表达方式。
依据：两批真实执行的现场材料 + 官方文档与公开研究；均标注来源与未验证部分。

## 0. 结论摘要

1. 两批停顿的根因不在引擎门禁，而在 SKILL.md 缺三条规则：**无事继续、收尾前分流、汇报口径**；无引擎的批次还缺一个等价的自律物。
2. "文字描述"本身不是问题，官方模式就是文字 + 渐进披露。问题在**平铺的长条款**：句长、条条带限定、无法检索、无法机械校验。
3. 路由部分可以保留文字，但应改成**判定表 + 指针**；能机械判定的交给脚本，文字只解释"为什么"和"何时"。

## 2. 根因

**规则层（主因）**

- 缺"无事继续"：技能写满了何时必须停（授权、不可逆外部动作、推送、真实人工确认），没写"不在这些情况里就继续下一批"。
- 缺"收尾前分流"：没有要求在停之前把计划剩余项分成用户侧 / 模型侧，模型侧不得遗留。
- 缺"汇报口径"：`Exit Protocol` 只要求"报告真实状态"，没有禁止性词表，导致"全绿""通过"可以和"待配""需 admin"并排出现。

**结构层**

- 无引擎批次没有规定等价的自律物。计划里写了 `status.md` 是权威记录，但没有触发机制保证它被创建和更新。
- R-3 / 最终审查的触发点和独占责任写得像"可选步骤"，不是"收尾前置条件"。

**表达层**

- 条款平铺：`delivery-orchestrate/SKILL.md` 95 行、6,966 字符，平均每行 73 字符，多为带 2–3 个限定条件的长句。
- 可机械判定的规则（批次归属、依赖有环、gate 顺序）和纯判断规则（什么算重大歧义）混在一起，读者（模型）无法区分哪些是硬约束。
- `research-topic-selection/SKILL.md` 340 行、5,264 字符：行多字少，属于典型"密集短条款"，同样难检索。

## 3. 修复方案

分批实施，每批独立可验证。批 1 只动规则，不改结构。

### 批 1：规则（P0）

**1.1 续航条款**（加到 `delivery-orchestrate/SKILL.md` 第 4 节末尾，`delivery-implement` 同步一句）

> 只有三种情况可以停：需要用户提供信息或授权；需要不可逆外部动作（推送、发布、删除、付费）；存在真实歧义且已给出候选。其余情况按计划继续下一批，不停在批次出口。引擎拒绝时先判断是输入错误还是流程缺口，能自行修复就修复后重试，不把拒绝转述成"需要用户确认"。

**1.2 收尾前分流**（加到 `Exit Protocol` 之前）

> 停下前先把剩余工作的清单列成两组：
> - **用户侧**：必须由用户提供或决定的事项，逐条写出来源（密码、流水线、授权点、业务决定）。
> - **模型侧**：不依赖用户的事项（审查、材料回写、部署对齐、状态更新），不得遗留；确实不做的，写明原因和影响。
> 用户侧清单为空时不得停下。

**1.3 汇报口径**

> 汇报完成状态只用三种词：**已实现**（代码/产物在）、**已审查**（有独立审查记录）、**已验收**（有验收证据）。三者缺一不可用"完成""全绿""通过"。存在 unknown 或未验证项时，先列这些项，再列已完成项。

**1.4 待用户标记不是停止理由**

> `status.md` 里出现"待用户"不等于停下：只有它阻塞当前批次出口时才停，否则继续推进其他任务，并在汇报里单列。

**验证**：用两批现场材料做回放——给定同样的状态，看模型是否继续推进、是否把模型侧待办做完、汇报里是否还出现"全绿"。

### 批 2：结构（P1）

- **无引擎批次**：`status.md` 变为强制产物，每批出口必须更新（写失败也保留原文并报告）。
- **R-3 / 终审**：从"可执行步骤"改为"收尾前置条件"，并写明由谁触发、谁不能担任。
- **机器可读待办**：`delivery.py next` 的输出增加 `remaining`，分 `user_side` / `model_side` 两组。这样"还剩什么、归谁"不再靠模型自己数。
- **可判定规则下沉**：依赖有环、gate 顺序、批次归属这类检查，`next`/`check` 直接给出结论，正文只解释后果。

### 批 2 新增：审查循环（设计与计划阶段）

**触发条件（硬）**：涉及机制或契约变化、跨任务依赖、不可逆操作（删列/迁移/部署）、规模 large，满足任一即必须独立审阅；不满足的写一行未审理由。

**缺审不算完成**：设计、计划的出口条件各加一条，与"已实现/已审查/已验收"三态口径对齐。

**干净上下文的定义**：新会话或新 agent，不得 `fork` 当前对话；审查产出由审查者自己落盘，不得由作者或实现者转写、修改、补全。审查结论绑定被审版本，版本一变旧结论失效。

**循环形状**

```
独立审 → blocker 清零? 是 → 出口
          否 → 作者修 → 代码类重跑受影响验收 → 独立增量复审 → 循环
                        增量复审读：版本差异 + 上轮问题闭合 + 受影响章节
```

**引擎落什么（只记账与出口判定）**

- review record 增加三个字段：`round`、`blocker_ids[]`、`closed_from[]`。
- 出口硬判定：推进下一 gate 或 `close` 时，最近一条 review 的 `blocker_ids` 必须为空，且 `closed_from` 是上一轮问题 id 的子集，否则拒绝。
- 引擎不判断 blocker 是否真被修好，只对照审查者的声明。这条信任边界要写进文档，不假装引擎能验证语义。

**刹车（按版本算，不按任务算）**

| 状态 | 判定 | 动作 |
|---|---|---|
| 收敛 | `blocker_ids` 为空 | 通过 |
| 停滞 | 同一版本第二轮，blocker 集合未缩小也未更换 | 停，转升级 |
| 超限 | 同一版本第 3 轮仍有 blocker | 停，转升级 |

设计演进产生新版本不占额度（个人项目C 的 v1→v3.6 八轮属于这种）。另设一条：连续两轮针对同一问题没有新证据时停止原样重试，重新诊断。

**升级清单（转 `user_side`）**

停下后产出待用户决定清单：每条 blocker 的原文与证据、两到三个候选处理（改设计 / 缩范围 / 接受风险 / 换方案）、各自影响与代价、一句推荐。选完后继续同一版本（算新一轮）或改版本重来。清单进 `next` 的 `user_side`。

**不落引擎的部分**：审得够不够狠。引擎只能保证有审查、有记录、blocker 清零，保证不了审查质量。换模型、换客户端审属于建议项，写成"建议"，不写"必须"。

### 批 3：表达（P2）

- **正文模板**：`何时用 → 判定表 → 步骤 → 指针`。细则进 `references/`，正文只留"判断"和"去哪儿看"。
- **一行一条判据**：合并嵌套限定条件；一条只放一个可判定的条件。
- **路由部分**：入口交给 frontmatter 的 description（只写触发与排除），正文给"用/不用"判定表和跳到各专业能力的指针，不重复专业能力自身的内容。
- **示例胜过描述**：容易出错的地方给 1 个正例 + 1 个反例，代替一段解释。
- **校验脚本**：加一个结构检查（行数上限、长句比例、必须含判定表），进 `validate_suite.py`。

## 4. 调研：别人怎么做的

### 4.1 官方

- **三层渐进披露**：启动只加载 name + description；命中才读 SKILL.md 正文；需要时才读 `references/`。这是官方设计的核心，目的就是让常驻上下文保持很小。
- **正文 < 500 行**，接近上限就拆分到独立文件；SKILL.md 当作"目录/导航"，不是手册。
- **description 是唯一的路由信息**：写清"做什么 + 何时用 + 何时不用"，模糊描述（"Helps with documents"）等于不可发现。
- **能写成脚本的不要写成文字**：代码是确定性的，排序这类操作交给脚本比让模型逐 token 生成更可靠、更省。
- **先做评测再写文档**：先在无 skill 的情况下跑代表性任务，记录实际失败点，再针对性写规则；避免写"想象出来的问题"。
- **按脆弱度决定规定程度**：多种做法都行的地方给原则，容易出错的地方给严格步骤。

### 4.2 实证研究

- **Context Rot（Chroma，2025-07）**：评测 18 个模型，输入变长时性能下降，且**不均衡**；干扰项和语义模糊会放大衰减。结论是"长窗口不等于均匀使用"，与我们的观察一致：几百字的核心规则埋在十几 KB 的条款里，命中率会掉。
- **技能列表本身占上下文**：一个 53 个 skill 的平台的系统前缀里，技能名和描述占 26.2%（24.9KB / 92.5KB），其中 45% 的技能从未被触发。这说明**入口描述的体积**和**正文体积**要分开管。

### 4.3 社区做法

| 做法 | 代表 | 适用 | 代价 |
|---|---|---|---|
| 单技能瘦身 + references 拆分 | 官方、mgechev/skills-best-practices | 大多数技能 | 需要维护更多文件，链接要可达 |
| 路由技能（只做分发） | mgechev 的 skill composition；红迪上的 skill-router | 技能数量多、边界清晰 | 多一跳加载；路由本身要准 |
| 运行时检索（skill router 工具） | 红迪 Skill Router（local-first 检索） | 几十到几百个技能 | 需要额外工具与索引 |
| 确定性脚本 + 少量文字 | 官方"code over tokens"建议 | 有固定判定/固定顺序的流程 | 规则要能写成代码，改规则要改代码 |
| 结构分层（pinned + 按需发现） | dev.to 平台实践 | 大型技能库 | 要改框架；多数人做不了 |

共同点：**没有人靠"写得更全"解决上下文问题，都在减少常驻体积、把判定交给结构或代码。**

## 5. 对"纯文字还有用吗"的回答

有用，但分工要清楚：

- **文字擅长**：解释为什么、给取舍原则、说明何时不该用、描述不可机械判定的判断。
- **文字不擅长**：保证执行顺序、计数、边界阻断。这类靠文字写多少遍都不稳，因为它是建议不是约束——个人项目C 那批里，引擎拒绝是唯一真正拦住它的东西。
- **上下文越长越失效**：官方研究显示长度本身就会降低可靠性；条款彼此冲突时模型会挑一条执行。
- **应对**：能判定的下沉为脚本；不能判定的写成判定表；两者都做不到的，才用文字，并且只写一条。

## 6. 实施顺序与验证

| 批次 | 内容 | 验证 |
|---|---|---|
| 1 | 四条规则（续航、分流、口径、待用户） | 两批场景回放 + `validate_suite.py` |
| 2 | status.md 强制、R-3 前置、审查循环（触发/干净上下文/引擎记账/刹车/升级清单）、`next` 输出 `remaining` | 引擎单测 + 一次真实小批次 |
| 3 | 正文模板、路由重构、结构检查脚本 | 结构检查 + 触发案例（该用/不该用） |

每批完成后本地提交，不改历史记录；技能替换期间保留旧版本可回退。

## 7. 未验证与风险

- 回放是构造场景，不等于真实续跑；项目A 场景没有引擎，无法复现门禁行为。
- 批 1 会增加文字；如果不同时做批 3 的瘦身，可能加剧"条款膨胀"。
- 不同客户端加载技能正文的时机不同，规则效果需在 Claude Code 与 Codex 分别验证。
- 审查循环的刹车按版本计数，前提是审查者如实标注 blocker；若审查者不列 blocker，引擎的出口判定会直接放行。
- 每轮审查都要写 record，小改动也可能增加操作成本；实施时需确认哪些规模的改动可以只做自检并留理由。
- 本文引用的官方文档与研究均为公开材料，未在本地复现其评测。
