# 实现审查记录内容规范

状态：现行规范；输入输出语义契约版本：1。

本记录让人理解“为什么这里可能或已经有问题”，让模型能定位、修复并复查；不以问题数量证明审查质量，不以代码风格偏好制造阻断。

## 总体规则

五块语义必备，允许合并标题。先简要给出规格符合性和实现质量的结论、阻断问题及审查限制，再展开证据。事实用精确引用，推断说明前提；列表和表格组织索引，复杂因果写成段落。报告不能只有 JSON、状态枚举或散落的代码行评论。

正文前记录报告 ID、目标、时间、审查者、相关实现者、独立性、skill 名称与实际修订、契约版本、报告版本、产品基线、输入依据版本。无可靠来源时明确未知。完整留存规则见 [delivery-contract.md](delivery-contract.md)。

## 1. 审查依据与范围

**核心问题：这次审查凭什么判断，实际检查了什么？**

最低内容：

- 需求、设计或已确认讨论的具体依据及版本；已有计划说明任务覆盖，不替代需求。
- 实际被审查对象：提交范围、工作区差异、未跟踪文件、构建产物或其他实际交付物。
- 审查覆盖的功能、任务或集成边界，以及必须读到的调用者、数据或共享上下文。
- 审查者与相关实现者的关系；同一作者切换 skill 不是独立审查。
- 方法：阅读、搜索、复现或诊断检查；哪些未执行、哪些环境无法获得及其影响。

可合并为范围表，但不能把“读取实施报告”写成“检查了实际代码”。当前环境不支持独立审查时，保留明确的独立性缺口，已有自检仍可交付但不能称作独立通过。

**完成判据：** 读者能还原审查对象、方法和限制，理解本结论覆盖与不覆盖什么。

## 2. 规格符合性

**核心问题：交付物是否实现了要求，而非只看起来工作正常？**

检查相关目标、业务行为、边界条件、接口和数据语义、兼容性、禁止改变的行为及验收要求。按“要求 → 期望行为 → 实际产物 → 判断”检查。要求多时提供覆盖矩阵；少量要求可以简明列举。

| 要求与来源 | 期望行为 | 实际对应位置/缺失证据 | 判断及关联问题 |
| --- | --- | --- | --- |
| 可追溯需求 | 可观察行为或约束 | 调用路径、实现、配置等 | 符合/不符合/尚不能判断 |

不能用任务 ID 已出现、文件已新增或测试变绿证明要求已落实。发现设计本身冲突时区分“实现偏离设计”和“按设计实现但设计有问题”，均说明实际影响及建议反馈方向。不要在报告中自行改变要求后宣布满足。

**完成判据：** 关键要求有实际对应，遗漏和未判断范围明确；规格结论不会被质量结论替代。

## 3. 实现质量

**核心问题：实现机制在相关条件下是否可靠，并能合理维护？**

按实际风险选择检查维度：

| 维度 | 何时重点检查 | 判断关注点 |
| --- | --- | --- |
| 正确性与异常 | 分支、边界、错误恢复变化 | 错误是否被吞掉，部分成功是否可识别 |
| 状态与并发 | 状态机、异步、重入或资源共享 | 时序、取消、重复事件、一致性与释放 |
| 集成与兼容 | 接口、配置、数据格式或调用路径变化 | 上下游契约、默认值、迁移、真实接线 |
| 数据与权限 | 数据写入、读取范围或权限变化 | 数据损失、错误暴露、越界访问与既有约束 |
| 测试有效性 | 行为改变或测试自身变更 | 是否能发现回归，是否只镜像实现、被跳过或改低标准 |
| 可维护性与性能 | 复杂机制或规模相关路径 | 实际复杂度与成本，明确影响而非个人偏好 |

维度不适用时不制造检查任务；相关高风险路径缺证据不能以“没发现问题”代替。运行测试可以辅助判断，但审查不是将整个验收再跑一次。

**完成判据：** 质量判断与实际机制、失败场景或约束相连，读者能区分确认缺陷、待核实风险和非阻断建议。

## 4. 问题与证据

每条可行动发现须有稳定 ID，例如 `R-001`；同目标不得重用旧 ID 表示不同问题。复审继续使用原 ID，新增发现分配新 ID。

必要信息：

- 简明标题：发生条件和错误结果。
- 触发条件、前置状态、输入或操作顺序。
- 预期与实际，依据、文件/符号/行或复现证据。
- 影响范围与严重程度；说明实际后果，不只填数字。
- 是否阻断当前范围及理由；与严重程度分开。
- 证据确定性：已确认缺陷、尚需核实的风险或改进建议。
- 当前处置：未解决、作者声明已修复待复审、复审确认解决、明确接受的遗留等。
- 建议修复方向、应反馈的能力或待补证据；不替实施者写完整补丁。

遗漏问题的证据可以是“要求有 X → 预期入口 Y → 检查到该链路没有 X”，不强迫附上一行错误代码。怀疑存在缺陷但尚不能证实时说明核实方法，不把推测升级为确认阻断缺陷；是否因缺乏必要保证暂不能放行，需要单独说明。

严重度、阻断性、处置状态是三个独立属性。例如低严重度的明确验收遗漏也可能阻断；重大但范围外的风险需要报告影响，不能直接扩张本次修复范围。

“用户说继续”“安排后续处理”“代码已改”均不自动表示问题已解决。接受遗留必须有明确对象、范围、后果与真实授权依据；仍保留原缺陷事实，不能标成技术修复完成。

**完成判据：** 实施者无需猜测即可理解问题，复审者有客观核实条件，调用方能识别阻断和风险。

## 5. 审查结论与后续

分别给出规格符合性和实现质量的结论及范围，可用“满足本次审查要求 / 存在阻断问题 / 证据不足”表述；不能把未审查写成通过。另列未解决 ID、缺口、限制、反馈方向和后续条件。

复审还必须记录：原报告与问题 ID、修复版本、实际修复检查、相关副作用检查、复审结论和仍未覆盖范围。原问题解决和新问题发现可以同时成立。

默认复审原问题及修复影响；以下情况扩大范围并说明原因：

- 修复超出原定边界或影响多个调用方；
- 关键接口、数据或生命周期契约改变；
- 变更不完整，无法可靠确定影响范围。

局部复审不自动替代编排要求的整体审查。整体审查可与最后一批审查合并，但报告须明确覆盖全体交付、共享约束和集成关系，不能只改标题。

**完成判据：** 后续行动、阻断和独立性限制可识别；报告保留发现与修复链，结论不冒充验收或发布批准。
