## 背景与目标

承接原 `design-tech-doc/SKILL.md` 的工程设计覆盖、`delve/SKILL.md` 的逐项共识机制，以及本会话对以下材料的分析：

- 物料主数据技术方案：`/Users/cm/workspace/10-物料主数据/04-方案设计/物料主数据AI智能化应用技术方案-20261012.md`。
- 研发体系：`/Users/cm/workspace/obsidian/obsidian-repository/20-Projects/02-rd-system` 中的架构设计规范、需求技术方案模板与示例、产品详细设计模板。

样例存在 POC 已验证路径与目标能力并置、性能目标缺测试口径、规则硬约束缺实际执行位置等审阅问题；没有核实生成时的技能调用记录，不能把这些问题直接归因于原 Skill。

原 Skill 的固定八节、按条件节数量分级、仅凭生产影响升为重点，以及“实现者不再做任何设计决策”混淆了文档类型、风险与深度。本次保留有价值的设计问题，移除格式堆叠和未经核实的权威背书。

目标是让模型在信息不足时只推进当前最有依赖价值的一项讨论，在信息充分且已确认时顺畅成文；不重新询问已确认的设计，不把未知伪装成事实。范围仅为研发内部系统、模块和专项设计。

## 做法

### 分型、评审和状态分别判断

三类文档为系统总体设计、需求／模块技术设计、专项技术设计。评审强度为轻量、标准、重点，按影响面、契约、数据、安全、不可逆性、迁移和验证不确定性判断。普通生产发布不自动升为重点，行数、工时、篇幅和章节数不参与机械分级。

保留“不写独立设计文档”出口：单点且事实、影响、验证和恢复已经明确的变更在 issue／MR 留记录。ADR 是重要单项决策的伴随记录，不是第四档，也不限于可逆决策。

文档状态独立记录草稿、待评审、已接受、已实现、已被取代／废弃。模型自检、用户认可某个问题和正式评审通过不能混为一谈。

### 共识协议自包含

先用一句话对齐问题；可从文件、代码和工具查到的事实先自己查。维护已确认、待确认、待实测清单，按依赖先后讨论；每次只提出一个问题，给真实备选、推荐和理由，等待用户答复。所有未解决的设计疑点都须确认，不能自行按“影响小”放行；排版表达及已明确保留给实现者的局部编码自由不属于待确认设计。

静默不是同意，推荐不是决定；“认可”只确认当前清晰提出的事项。前提未变，不重问已确定事项。未经共识不写正式方案，讨论中的草图和比较材料须标为讨论材料。写作中出现新设计疑点，退回讨论。

两处主要检查点是成文前设计简报和全文自检后的用户评审。简报说明类型、强度、范围、深度、默认提纲裁剪及理由、继承文档、关键决策与未知处理。前文已确认覆盖简报内容时复用已有确认，不机械多设一轮审批。

### 实证不确定性

不能靠讨论证明的事项，先确认实验方法与通过标准，取得证据后决策。暂时无法验证时，由用户明确选择等待，或接受具体假设、风险和适用条件后形成有条件草稿。模型不能代选；同意假设不是实证验证，也不等于无条件可实施。

### 按问题覆盖组织内容

为三种文档提供各自默认提纲，同时允许合并、继承、条件展开；固定语义覆盖，不固定八节或选节数量。不适用的内容省略并在选节说明交代；强制模板必须保留的节写不适用理由。组织强制格式和工作流机械契约优先于默认提纲。

内容库覆盖十五类问题，每类给设计理念、触发条件和完成判据：定位与依据；问题目标范围；约束与质量驱动；总体机制和取舍；模块职责；运行时流程；接口集成；数据；性能容量可靠性；安全；部署运维可观测性；兼容迁移恢复；验证验收；风险未决；演进维护。安全、部署、容量各有明确位置，不能隐在一句“横切关注点”。

系统总体设计写边界、模块、交互、责任、质量与部署；模块设计写输入输出语义、状态、异常、并发、一致性和验收；专项设计写约束、机制、成立条件、验证及失败。决定协作、正确性和风险的地方写实，局部类名、文件名等保留实现自由。算法或不可逆数据等有必要时写伪码、DDL、迁移细节。

### 证据、审阅与维护

区分设计已确认、实现已存在／已启用、实测已验证及其范围。指标必须有场景、负载、度量、目标和验证方式。AI 场景补充模型／提示词／规则／知识版本、实际执行约束的位置、评测集及指标、人工接管、证据链、回归，不承诺提示词等于硬约束或 POC 等于生产验证。

审阅按已确认范围和证据定位缺陷、待决策项、待实证项，报告影响和修复方向；已知限制仍违反目标或阻塞验收时必须报告。仅审阅不擅自改写。最小性按目标与工程必要条件判断，不能只因输入没逐字要求就删必要机制。

系统／模块现状基线持续维护；一次性变更文档收尾更新实际交付、偏离与限制后冻结；ADR 保留旧决定并关联替代。写入前说明本次同步的相关文档范围；不以末尾追加优先条款长期保留自相矛盾的现状。批准后发生设计偏离须显式确认，不能改文档掩盖。

## 备选与取舍

| 备选 | 取舍 |
|---|---|
| 分为多个生成 Skill | 采用一个 Skill 内按类型分流，共享事实和共识协议，避免规则漂移。 |
| 运行时必须调用 delve | 内嵌其核心，避免依赖另一个技能安装位置；不复制无关流程。 |
| 固定章节或任意自由写作 | 默认提纲加语义覆盖，兼顾上手与裁剪，强制模板做映射。 |
| 模型直接填补未知 | 用户决定；事实自行查证，实验未知按已确认验证路径处理。 |
| 所有实现细节写死 | 只锁定影响协作、正确性和风险的选择，避免把系统方案写成代码清单。 |

设计参考及适用范围：[arc42 的架构内容视图](https://arc42.org/overview/)、[C4 的按价值选视图](https://c4model.com/diagrams)、[SEI Views and Beyond](https://www.sei.cmu.edu/library/views-and-beyond-collection/)、[Rust RFC 的取舍与未决](https://github.com/rust-lang/rfcs/blob/master/0000-template.md)、[Kubernetes KEP 的验证和生产准备](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/README.md)、[GitLab 架构演进流程](https://handbook.gitlab.com/handbook/engineering/architecture/workflow/)、[Nygard ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。三类文档和三档评审是本次结合研发用途的选择，不宣称为这些来源的统一标准。

## 接口与数据形状

- `design-tech-doc/SKILL.md` 保持原名称；按仓库 frontmatter、Working Protocol、Exit Criteria、Exit Protocol 组织。description 不超过 249 字符，全部规则不依赖特定客户端或本机路径。
- `design-tech-doc/references/review.md` 与主协议一致，供审阅和成文自检读取。
- `design-tech-doc/test-prompts.json` 保持数组 `[{"id": 数字, "prompt": 字符串, "expected": 字符串}]`；补入多轮确认上下文和充分输入，避免所有用例只验证第一问。
- `task-workflow` 联用时保留该工作流的十个原样二级标题、D-NN、路径、审批和指纹机制。将语义模块映射为其小节；不修改工作流技能。用户明确要求的逐项共识规则始终生效。

## 明确不做

不改写物料主数据样例、研发体系、delve、task-workflow 或安装配置；不生成客户／售前方案或 PRD；不拆多个 Skill；不引入新的执行引擎。不修改现有 research-router 与 folo 工作区改动，不推送远端。

## 已知限制

提示词不能从机制上保证所有模型都遵守。测试集定义了 23 个提示，本轮未逐条全量运行；实际执行并独立复核的是九个代表场景，不能外推为多模型、全部客户端或长期对话稳定性证明。

未完成 Darwin 正式新旧／无技能对照评分，不声称达到仓库“合格可发布”评分门槛。现有研发体系是参考输入，不直接安装为所有项目的强制标准；物料主数据样例未核实生成时的 Skill 调用链，也未验证项目代码或生产环境。模型审阅及结构验证不替代用户全文评审或项目上线验收。

## 验收标准

1. Skill frontmatter、资源链接、测试 JSON 和 diff 格式检查通过。
2. 独立审阅核对全部 D-NN，无未解决的阻塞问题；三份技能文件没有残留旧硬规则。
3. 独立行为测试至少覆盖：事实先查和一问一答、所有超时调整的风险、完整共识后的成文、有条件草稿、已知限制仍阻塞目标、强制工作流标题兼容。保存原始回答并由独立审阅者按预期评判，不能以关键词扫描替代。
4. 本次确认只证明被执行案例的行为；未执行用例如实标明，不伪造正式评审或线上验证结论。
