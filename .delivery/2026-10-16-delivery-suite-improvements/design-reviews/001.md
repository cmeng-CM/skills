## DR-001：未知运行未定义可验证的解除条件，换新操作 ID 仍可能重复副作用

- 位置：design.md 第 6.2、7 章，尤其第 137—139、153、157、161 行。
- 要求与依据：AC-08 要求未知运行不盲重跑。设计要求 `run-started` 后不得自动重放，同 op 重试返回未完成；新 op 前核查副作用。
- 反例：进程在真实命令完成副作用后、写入 `run` 前崩溃；恢复者以原 actor 释放资源，再换新 op 执行同一验收命令。当前 `resource.release` 只有 reason，没有绑定旧 run 操作的核查报告或证据；共用准入条件没有明确列出未解决 run-started，亦无持久化的“已核查、允许重试”解除语义。原 v1 的 `run()` 在新 op 下也不会阻止这种重放。
- 影响：资源占用可阻断并发，但资源释放不能证明旧命令未产生副作用。只保留规则文字，会在跨会话恢复时丢失“为何允许新运行”的客观依据；反过来若永不解除，会永久阻塞合法恢复。
- 阻断性：阻断 T-08 对 AC-08 的设计接纳。不是要求导入旧命令成功回执，也不是要求把未知自动改为完成。
- 修复方向：定义未完成运行的状态计算、它阻塞的具体活动，以及显式解除所需的旧 run op、实际核查报告/证据、判断人和结果。可复用既有事件类别；只要在新 op 执行前能验证解除依据且保留旧未知事实即可。必须覆盖“仅释放资源仍拒绝”“有证据解除后允许新 op”“解除依据变更后重新阻塞”三种场景。

## DR-002：采集配置目录不能单独证明实际运行的引擎属于所记录 pin

- 位置：design.md 第 5.1—5.2、7 章，第 107—109、115、120、153 行。
- 要求与依据：AC-07 要求记录实际 skill 来源、识别修订变化且不静默换规则。设计已声明“引擎自身文件及模块也必须属于 orchestrate pin”，但采集入口仍是请求提供的 `skill_sources.root`。
- 反例：配置把旧稳定包 A 填为 orchestrate 根；实际 CLI 来自候选包 B。A 目录与 pin 始终相同，普通目录漂移检查没有变化，运行仍可能按 B 的门禁接纳，却记录为 A 的规则。相同问题也存在于新 CLI 驱动旧工作续接时。
- 影响：实际执行规则与保存的可恢复规则可能不同，pin 将退化为另一种调用者声明，不能支持“恢复原规则继续”的保证。
- 阻断性：阻断 T-07 的来源信任边界接纳；这不是身份认证问题，脚本可获得自己的实际文件位置。
- 修复方向：明确在执行类准入和来源更新时，如何由当前进程实际加载的 `delivery.py` 与 v2 模块定位/核对执行包，并与所用 orchestrate pin 比较；声明 root 或仅存在相同文件名不够。明确恢复旧副本与纯路径迁移的合法路径。增加 A/B 包字节不同但请求声明 A 的反例，以及原样恢复/迁移可继续的正例。

## 非阻断检查与实施注意

1. **monitor 排除需有正例。** 当前 work 排除可避免本目标报告/日志自激；没有默认排除整个 `.delivery`，有助于保护跨目标需求来源。其他目标或评测记录若位于监测根内，会形成变化，应通过明确且不与产品/来源重叠的生成物排除处理；不要为降低噪声一概排除 `.delivery`。实施测试应覆盖当前 work 写报告不自激和其他目标真实来源变化仍被发现。
2. **资源占用与关闭分别解释。** 必须说明实现、只读审查、验收和 close 各需哪些 read/write 资源；不要把“资源属于 actor”机械解释为独立 reviewer 或 coordinator 必须永久持有实现者的写锁。正常 claim/release 后的完整组合需要可达。
3. **v1 保持原规则是合理边界。** 容器 1、工作契约 1/2 分发，旧活动原规则续接、新工作显式使用 2、关联新工作不冒充原地迁移，未发现原则性冲突。实际兼容仍须原回归和真实旧样本验证。
4. **语义判断仍需专业活动。** mapping 清单可能自洽而漏正文、风险规模与授权分类、impact 相关性及 source-update 的兼容性均不能由摘要证明。设计已承认这些边界，独立真实评测须分别验证，不能只做字段断言。
