## 3. 实现质量

当前实现确实具有原子 journal 写入、对象摘要校验、操作幂等、历史作者保留、明确的范围外变化判断及来源更新链；不是只有规则文字。专业报告也清楚区分机械检查、作者自检、独立审查、实测和完整收尾。本次没有以脚本检查数量作为这些判断的依据。

两个缺陷都位于机制组合处：FR-001 是同类活动的版本有效性规则不一致；FR-002 是安全阻断条件组合后缺少仍然可用的恢复路线。它们不说明五项专业 skill 不能独立使用，但影响完整编排对升级和长任务恢复的承诺。

## 4. 确认缺陷

### FR-001：来源兼容证据失效后，该新版本产生的准入 gate 仍可放行

- **严重度：P1／高。阻断：是，阻断“当前编排的来源失效链完整可靠”这一范围通过。** 处置状态：未解决。证据性质：静态调用链确认。
- **触发条件：** 配置绑定专业包 P0；通过 `source-update compatible` 接纳 P1；用 P1 完成必需的 `plan_review`（设计审阅或编排准入审阅存在同类情况）；随后兼容更新的报告/证据发生变化，P1 不再位于有效 pin 链。gate 自身报告、专业正文等文件保持原样。即使把实际专业包恢复为 P0、消除所有来源漂移，以下问题仍成立。
- **预期：** P1 产生的 gate 应保持历史事实，但当前不能继续提供准入保证，除非补齐 P0→P1 的有效兼容证据，或按有效来源重新审阅；不应因恢复旧包而让 P1 的审阅自动成为 P0 的审阅。
- **实际调用链：**
  1. `delivery/delivery-orchestrate/scripts/delivery_sources.py:82-101` 的 `pin_lineage` 只把证据当前且旧 pin 可达的更新加入有效链，因此此时 P1 正确地失效。
  2. `delivery/delivery-orchestrate/scripts/delivery_v2.py:308-310` 的 `gate` 保存了当时的 `skill_pins`，具备识别 P1 的信息。
  3. 同文件 `272-285` 的 `gate_state` 却只检查 gate 的 `references` 和配置 `sources`，没有检查保存的 pin 是否仍在有效链中，结果继续是 `passed`。
  4. 同文件 `402-419` 的 `assert_ready` 读取这个 `passed`；implementation 只检查 orchestrate/implement 的实际漂移，恢复 P0 后更无漂移可拦截。它不会重新验证该 plan gate 的来源。相对地，普通 record 在 `334-345` 明确检查了自己的 pin 有效链，说明 gate 没有得到同等保护。
- **规格证据：** `references/runtime-api-v2.md:169` 要求兼容判断证据过期使新来源及其对应新记录待确认；当前设计 `design.md:109` 要求 record/gate 保存实际使用 pin，`design.md:127` 要求更新证据持续有效。不能以 gate 的正文未变代替其生成规则仍有效。
- **用户后果：** 一个已经失去来源接纳依据的计划/映射审阅可以继续授权后续实施、审查、验证，最终可能收尾；升级恢复看起来没有漂移，但实际准入结论来自未获当前认可的规则。
- **最小修正方向：** 将 gate 的相关专业 pin 与 orchestrate pin 纳入有效性判定，并区分历史记录保留与当前准入可用；不必把无关专业包变更一律传播给全部 gate。
- **客观关闭条件：** 上述 P0→P1→兼容证据失效的状态链中，相关 gate 被判 stale/不可用，`next` 与 `record/run/close` 一致阻断；恢复 P0 不自动恢复 P1 gate；有效重新接纳或按有效包重新审阅后可继续，旧事件不改写。可用等价证据关闭，不要求某一种补丁或全量重测。

### FR-002：来源变更与未知运行同时出现时，恢复依赖重新准入，重新准入又依赖旧运行恢复

- **严重度：P2／中。阻断：是，限于“已确认需求更新后仍可可信续接未知运行”这一恢复能力；不阻断五专业独立调用。** 处置状态：未解决。证据性质：静态调用链确认；同时涉及恢复设计的缺口。
- **触发条件：** v2 已持久化 `run-started`，但因进程中断没有 `run` 回执；随后 plan 或 authorization 的实际文件按新的已确认决定更新，原 configure 的来源摘要变为 stale。尤其是新决定已替换或撤销旧验收命令，此时不应为了恢复流程继续执行旧命令。
- **预期：** 可以留存对旧进程及副作用的真实调查，并在保留原 unknown 事实、原 owner 和关联关系的前提下，按当前授权完成必要的重新准入与替代验证；不能用新配置洗掉未知副作用，也不能要求假装旧要求仍有效。
- **实际调用链：**
  1. `delivery/delivery-orchestrate/scripts/delivery_recovery.py:99-120` 的 `resolve_run` 在保存调查前于 `109` 调用 `current_config()`。
  2. `delivery/delivery-orchestrate/scripts/delivery.py:322-329` 默认要求旧配置来源当前；plan/authorization 已变更就拒绝，并提示先 `configure/readmission`。
  3. 但 `delivery/delivery-orchestrate/scripts/delivery_v2.py:115-135` 在重新配置时调用旧配置的 `unknown_runs`，`130-132` 要求先恢复未 settled 的运行，否则拒绝。`delivery_recovery.py:74-96` 对没有有效调查与替代链的旧 run 返回未 settled。
  4. `delivery_recovery.py:51-72` 的 settled 条件又要求原绑定配置有退出成功的替代真实 run 和 passed verdict；在不能按旧来源继续时，没有受支持 API 路径先接纳当前计划，再使用当前授权的替代命令完成这条链。
- **已有回退路径及其限度：** 这不是不可恢复的数据损坏。旧来源字节留在 runtime 对象中；若旧授权和命令仍然有效，可以另存新正文、把被绑定来源临时恢复旧字节，按旧配置调查并完成替代运行，再重新接纳新正文。这个办法并不普遍成立：当用户已撤销旧命令或新要求使其不再适用，恢复旧文件字节不会恢复旧授权；要求旧命令取得成功 verdict 会迫使调用方停住，或在文件中暂时呈现已经失效的依据。现行恢复说明也没有提供此类复合变化的合法分支。
- **规格证据：** `references/orchestration.md:94-101` 的恢复流程要求根据当前真实差异处理来源变化与未知运行；`references/runtime-api-v2.md:92-94` 支持有真实授权的重大重配置，同时禁止用重配置抹掉未知运行。这里两个保护条件共同形成了恢复缺口，不能靠删除账本或伪造旧回执解除。
- **用户后果：** 大任务中断后，一次合法的计划/授权更新可能使“调查旧副作用”和“接纳当前要求”都无法登记；若旧命令已经不再允许执行，只能在正式流程外保留阻塞或另行人工处置，不能按现行恢复说明继续原目标。
- **最小修正方向：** 先由设计明确来源 stale 时的调查与重规划衔接：调查仍绑定原运行及不可变旧配置，但观察当前副作用；允许有依据地转接到当前授权的替代方案，保留未解决阻塞。不能简单取消未知运行门禁或把历史 unknown 改为成功。
- **客观关闭条件：** 对“未回执运行＋已确认来源更新＋旧命令已撤销”给出可实际执行的支持路径：能保存调查、保留旧 unknown/owner/证据、按新授权重新准入并取得当前验证；无需重写 journal、伪造成功、重放已撤销命令或恢复已经失效的授权。旧命令仍适用的普通恢复路径也应保留。
