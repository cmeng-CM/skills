# Delivery Orchestrate

把五项独立能力组织成一个有明确范围、实际证据和可恢复记录的交付任务。质量由专业判断、独立审查和机械门禁共同保障；脚本不替代语义判断，也不自动调用模型。

## Working Protocol

### 1. 确认入口与承接范围

过渡期仅用户明确选择、项目明确指定或已经属于本体系的任务续接时进入。已有旧 workflow 按原入口处理，同一目标不能由两个引擎同时控制。用户只点名单个能力时执行该能力，不扩大为完整流程。

读取用户目标、项目规则、已有设计/计划/实际记录和授权。已确认决定连同条件复用；只有影响当前工作的新选择才需要处理。用户明确授予质量优先决策权限时记录具体判断与影响，不把模型决定写成逐项用户批准；超出授权、不可逆外部动作或硬约束冲突仍按实际权限处理。

读取[编排协议](references/orchestration.md)及[接入与演进](references/contracts.md)。没有现成设计可从 design 开始，有明确小需求可直接 plan；有有效计划可实施，已有实现可从审查/验证进入。复用前核对范围、版本、真实确认与未决项，不为走流程重建同范围文档。

### 2. 建立工作目录和质量安排

新目标默认 `.delivery/YYYY-MM-DD-主题/`；同目标沿用已有目录，跨日不改名。只建实际需要的文件。`index.md` 仅导航，五能力写自己的 Markdown，`runtime/` 仅本引擎维护。

续接时检查实际目标在 `.delivery/` 或旧版 `docs/delivery/` 的既有目录，沿用已建立的归属；不自动搬迁旧账本或改写历史路径。多个候选时核对目标与来源。

从可用 skill 列表、项目指定路径或实际安装位置定位并读取 `delivery-design`、`delivery-plan`、`delivery-implement`、`delivery-review`、`delivery-verify` 的 SKILL.md。按需加载，缺少所需能力时如实报告，不能静默以旧 skill 或模型自述替代。读取技能协议不是一个固定返回值的函数调用。

计划按交付任务实施、按风险和集成边界审查、按验收要求验证。每项任务有审查与验收归属；提前门禁有实际风险依据，整体审查覆盖全交付。联合检查任务、审查、验证依赖无环，组内接入条件不等于最终验收通过。

### 3. 语义接纳与状态初始化

先读真实正文核对要求覆盖、范围、实际基线和授权。新目标使用[契约 2 API](references/runtime-api-v2.md)，明确 `init --contract-version 2`；既有 v1 按 [API 导航与原规则](references/runtime-api.md)继续，不静默升级。编排侧 JSON 绑定来源和准确摘录、映射理由、实际 actor/context、采集的 skill 来源及契约版本；正文仍是专业定义真源。能力独立使用不必输出该 JSON。

大任务初次实施、重大重规划需要真正独立的计划审阅；设计按机制风险触发独立审阅。专业标准分别归 design 和 plan。正文到准入配置的映射始终独立复核，可与专业计划审阅同次开展但分别给结论；实现 review 不替代二者。v2 configure 仅保存候选准入，必要 gate 当前通过后才能推进。

所有状态操作用本 skill 目录下 `scripts/delivery.py`，不手改 journal 或复制旧运行状态。工作目录只有一个协调者负责准入和流转，子 agent 返回自己的报告；并行执行的文件范围与资源使用必须明确。

初次配置、来源改变后的重新配置都需核对语义。字段齐全不等于计划合理；源文件版本不符时必须重新接纳，不能只换摘要保持旧结论。原始契约版本未知时拒绝接入，按兼容规则处理。

区分授权内局部实现、计划组织调整和重要范围/契约/验收变化，绑定当前具体授权，不对已批准的小调整重复询问。v2 对范围外变化先形成清单，再接纳有依据的影响判断；相关证据定向失效，未知影响保持阻塞，不能全忽略或一律全量重验。

### 4. 质量优先调度与闭环

以预期质量、上下文、工具条件及实际表现选择主 agent 或子 agent，不固定每步一个 agent。委派使用[交接骨架](assets/dispatch-template.md)，带范围、输入、允许修改处、验收归属、报告位置及反馈条件；不因委派扩大权限。

实施按实际代码和任务完成产物及自检；所有参与实现的作者和上下文应有真实记录。审查者不得是相关实现者，不能通过更换名称、删除旧作者或换 skill 伪装独立。审查直接读取实际产物，规格与质量分别给结论；缺少独立审查能力时保留待审，不放行依赖它的工作。

接纳报告前核对其内容和实际证据，再用 `record` 留存。运行已声明自动验收用 `run` 捕获真实输出；命令退出码 0 仍需验证者对标准给出判断后记录。人工项须真实项级确认，内容检查须有实际产物证据，缺证据保留 unknown。

发现问题按原因回退：实现缺陷回 implement；拆分和依赖缺口回 plan；机制或契约改变回 design；证据不足回 verify。复审原问题与修复影响，必要时扩大。连续两轮同类失败没有实质新证据时停止原样重试，重新诊断并记录；不是自动放弃、豁免或降低标准。

用 `brief/status/next` 的同源视图重建必要上下文，硬约束保留完整来源；摘要不能代替阅读。工作树、Git index、共享测试库与生成物明确资源占用和交接，无冲突只读工作才并行。v2 未完成 run 需要证据化核查和新的真实运行/判断才能解除收尾阻塞，资源 release 或更换 op 都不能独自绕过。

### 5. 提交、验证和收尾

独立能力默认不提交。完整编排可以按任务拆分、依赖与交付边界安排本地提交，不要求一任务一提交，不 push；用户或项目明确规则优先。提交前核对实际改动和暂存范围，只纳入本次授权文件，保留用户原有修改。提交、自检、审查通过与验收通过分别记录。

非 Git 工作区仍可实施和留存证据，不伪造提交。存在未提交改动时使用实际范围快照，不以 HEAD 冒充交付版本。提交失败或安装受限不是验收通过；记录实际情况并处理。

运行 `status/check/next` 核对当前绑定、问题及缺口。完整收尾要求当前实施、独立审查和全部必需验收通过。仅已实证失败、允许例外且有具体用户授权的验收可申请 `limited`；未知、过期证据、失败的独立审查不能豁免。验证原不符合项保留，不能称为全部通过。

将实际交付、证据、例外和仍需用户查看的事项写入收尾报告，再调用 `close`。历史关闭不覆盖；后续修改先显式 `reopen`，不能拿旧收尾证明新版本。恢复时读取 journal、当前产品与原始证据，按真实差异决定复用和复核。

## Exit Criteria

- [ ] 入口、目标、授权和实际来源明确，五能力仅按需要使用。
- [ ] 计划覆盖任务、独立审查、验收及联合依赖，语义接纳有依据。
- [ ] 当前实施和非实现者审查已满足要求；历史失败与处理关系可追溯。
- [ ] 逐项验证有当前有效证据，命令成功、语义通过和人工确认未混淆。
- [ ] 只改本次范围，按适用规则本地提交；未擅自 push。
- [ ] 正常或带限制交付的条件已真实满足，`close` 成功；没有以未完成代替完成。

## Exit Protocol

报告实际完成范围、文档与证据入口、运行状态、本地提交及需要用户查看的重大选择。区分全部通过、带限制交付与尚未完成；机械检查通过不是全局质量证明。

中断时保留真实已完成部分、阻塞和恢复入口，不重建空流程。已接纳配置时，依次用 `python3 -B <本skill目录>/scripts/delivery.py <子命令> --work <工作目录>` 执行 `check`、`status`、`next`；仅初始化时先按真实依据完成 `configure`。详见[中断恢复步骤](references/orchestration.md#中断与恢复)。新会话或新协调者接续实际记录，不依赖旧聊天或子 agent 存活；未留存的步骤不能推断为完成。不写长期记忆或其他项目材料，除非用户另行要求。

维护时使用 [validate_suite.py](scripts/validate_suite.py) 统一执行包检查和确定性回归，或按影响运行原单组命令；真实模型案例见[评测入口](tests/evaluation/README.md)。机械测试、真实行为演练与独立审查分别记录；适用版本、同步范围与活动流程处理见[维护与升级规则](references/maintenance.md)。
