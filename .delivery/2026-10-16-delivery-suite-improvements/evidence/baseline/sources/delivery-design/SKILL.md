# Delivery Design

把功能改造的事实、共识和技术机制组织成人能评审、模型能据此实施的设计文档。首版覆盖现有项目功能改造；系统总体设计、独立专项与 RFC 不强套本规范，超出范围时先明确需要的产物。

## Working Protocol

### 1. 选择路径与加载材料

过渡期仅在用户明确点名、本项目明确选择 delivery 体系或 delivery 编排明确委派时使用；普通设计意图不自动替代原有入口。用户选择单独设计不等于授权完整编排。

先读取用户指定的需求、讨论、设计与相关实现，识别新建、更新或仅审阅。明确本次范围和产物；已说清的内容直接承接，不为走流程再确认一次。

读取本 skill 自带的[交付约定](references/delivery-contract.md)，确定工作目录、输入输出与版本记录。独立使用不要求先有计划、编排器或 `.workflow`；组合使用时承接调用方给定的范围和目录。

| 当前任务 | 需要读取的资源 | 下一步 |
|---|---|---|
| 从需求开始设计 | [preparation.md](references/preparation.md)；[document-standard.md](references/document-standard.md) 的整体规则和章节适用条件 | 先查事实，按需讨论，再成文 |
| 已经通过 delve 或其他讨论形成共识 | preparation 的共识承接、组合约束和成文条件；document-standard | 核对后直接成文，仅重开具体缺口 |
| 更新已有方案 | document-standard 的受影响章节与变更规则；[review.md](references/review.md) 的更新检查 | 找到当前有效决定与影响范围，再按授权更新 |
| 仅审阅 | document-standard；review 的语义检查与发现输出 | 交付问题和证据，不代写或重新访谈 |
| 成文后自检 | review；必要时执行 [check_doc.py](scripts/check_doc.py) | 修正已定事项的遗漏；新设计问题返回讨论 |

只读取当前阶段需要的内容，不默认展开全部参考文件。六个必选章节均须覆盖，五个可选章节均须判断适用性；实际触发的内容读完整。更新或审阅发现新设计疑点时，再读取 preparation 的对应规则。

### 2. 保持关键边界

- 可查事实先查；区分用户陈述、推断、设计决定、已有实现、部署启用和实测结果。
- 已确认决定连同理由、前提与范围一起复用；未确认的设计选择不得写成定案。局部编码自由按已有授权保留。
- 有状态、生命周期或机制耦合时检查组合约束。缺少保障机制不能写成“实现时保证”或“测试时验证”后交给实现者。
- 沟通只解决当前未决事项。如何使用 delve、何时结束讨论，按 preparation 执行；不要复制它的协议或写死安装路径。
- 脚本只做机械检查，不判断设计可行性、不批准方案、不证明验收通过。
- 只修改用户授权的产物。仅审阅不改写被审阅文档，正式审阅报告按交付约定留存；写方案不自动授权实现、发布或更改执行状态。
- 这里的审阅对象是设计文档，不替代实现审查；输出设计结论与待处理事项，不自行串联规划、实施、审查或验证。

### 3. 成文与承接

按 document-standard 写文档说明、方案概览和适用章节，将已确认需求、决定与限制落到具体机制、契约和验收。整份规范是唯一内容依据，不另维护一份完整模板。

已有组织模板或执行流程时，将适用内容映射进去，承接其明确的范围、路径和已有确认；无法同时满足内容要求和交付约定时说明具体冲突，先确认处理方式。由调用方判断结果能否进入后续流程；本 skill 不调用执行引擎、不维护运行状态、不复制同范围方案、不硬编码其他 skill 的章节。

成文后按 review 做语义自检和适用的机械检查。正式活动按交付约定留存产物与阻塞；用户明确只讨论、只在对话交付或不写文件时遵从其范围，并说明尚未形成落盘产物。文档已保存且 Python 3 可用时执行校验；不可运行则说明未检查范围，不能声称通过。

组合使用时仍交付可读 Markdown，由编排器读正文并形成绑定版本的准入快照；本 skill 不要求独立使用者生成编排 JSON，也不能把机械接纳当作设计批准。

## Exit Criteria

- [ ] 已确认范围、决定、理由与重要限制在正文中有对应位置；新增选择有确认依据。
- [ ] 关键机制、接口与数据语义足够明确；相关组合约束经过推演，未把缺失机制留给实现者。
- [ ] 必选内容完整，可选内容按实际影响覆盖、合并或省略；图表帮助解释，未为凑格式重复定义。
- [ ] 目标、机制与验收可对应；待决策、待实测及阻塞范围可识别，条件草稿有明确接受依据。
- [ ] 语义检查已完成；机械检查的结果与未覆盖范围如实说明，未冒充用户或独立评审。
- [ ] 更新后的有效正文一致，旧决定与替代关系可追溯；没有越权改动关联材料。
- [ ] 正式产物、依据、适用版本与未解决事项已按交付约定留存；对话交付或保存受阻时如实说明，没有伪造可供编排接纳的记录。

## Exit Protocol

未具备成文条件时，给出当前最关键的问题、证据、真实选项与推荐；已确认事项不重问。仅审阅时按 review 交付发现与核实范围。

成文时给出正文或文件路径，说明设计状态、关键取舍、剩余限制和待用户评审事项。沿用已发生的确认，不把本次自检写成批准。新建正式方案默认保存到项目内 `.delivery/YYYY-MM-DD-主题/design.md`；同一目标继续沿用原工作目录，具体归属、审阅记录及更新规则见交付约定。项目产物不写入 skill 目录。

维护本 skill 时使用 [behavior-cases.json](tests/behavior-cases.json) 检查实际行为，运行 `python3 -B -m unittest discover -s <skill目录>/tests -p 'test_*.py' -v` 验证脚本。日常设计不加载测试文件；用例存在不等于行为已经验证。
