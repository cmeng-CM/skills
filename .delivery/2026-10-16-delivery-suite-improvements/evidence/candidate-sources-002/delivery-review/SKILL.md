# Delivery Review

由未参与相关实现的审查者，对照需求和实际产物分别判断规格符合性与实现质量。把可行动的问题、判断证据和未覆盖范围写清楚；没有发现问题不等于完成交付验证。

## Working Protocol

### 1. 建立独立性与审查范围

仅在用户明确选择本 skill、新 delivery 体系、项目明确指定或收到相应编排委派时使用，不自动接管旧工作流。独立调用不要求设计、计划文件齐全，不依赖其他 skill、编排脚本或 `.workflow`。

读[交付约定](references/delivery-contract.md)和[审查工作规则](references/work-rules.md)。确定目标、需求依据、实际变更基线、审查范围、关联实现者和审查者。审查者未参与相关实现才具备独立性；切换 skill 名称不改变身份。不能满足时可在授权下交付明确标注的自检或有限检查，不能宣称独立审查通过；由调用方安排独立审查，不把缺口藏在结论里。

### 2. 对照实际产物进行审查

先从需求确定应该存在的行为，再检查真实代码、配置、文档、集成和必要上下文。实施报告、测试和既有审查是证据输入，不能代替实际检查。

- 分别判断规格符合性与实现质量；实现质量良好不能弥补漏掉要求。
- 按风险检查相关异常、边界、状态和集成路径；只提出有证据、有影响的问题，不堆砌通用清单或风格偏好。
- 允许调查、复现、写自己的报告和隔离探针；不修改被审查业务代码、正式测试、设计依据或验收条件。
- 对遗漏可引用需求、预期接入点与实际缺失，不强求必须存在一行错误代码。
- 发现设计本身冲突，说明证据及影响；按设计实现不免除报告冲突，但不能在审查中替用户重新决定设计。

### 3. 记录发现或复审

读[审查记录规范](references/review-standard.md)，使用[记录骨架](assets/review-template.md)。需要判断具体措辞和复审深度时读[完整示例](references/example-review.md)。每条发现保留稳定 ID，分别记录严重度、是否阻断和处置状态，不将“用户让继续”解释为接受风险。

复审默认检查原问题及修复相关影响；范围扩大、关键契约变化或影响不明时扩大审查并说明理由。检查实际修复版本与副作用，不能只看实施者回复；保留原发现、修复和复审链。尚未复查的“已修复”只能是作者声明。编排要求的整体审查仍需覆盖全体交付及集成，局部复审不能代替它。

原问题以客观要求和关闭证据为准，允许满足同一性质的替代修复；建议补丁或风格偏好不是唯一答案。审查真实消费者与测试有效性，避免 skip、空跑或全 mock 让遗漏行为仍然变绿。

## Exit Criteria

- [ ] 依据、实际版本、范围、未覆盖项和审查独立性明确。
- [ ] 规格符合性与实现质量分别判断，重要结论能追溯到真实产物和依据。
- [ ] 发现有稳定 ID、触发条件、证据、影响、严重度、阻断性与处置状态；不把猜测写成确认缺陷。
- [ ] 修复声明经过实际复查才标为已解决，复审范围与扩大理由可解释。
- [ ] 没有修改被审查产物、替换验收要求、覆盖历史问题或自行接受交付风险。
- [ ] 报告与证据已按约定保存；保存受阻或用户要求仅对话时如实说明。

## Exit Protocol

先给两类结论，再给阻断发现、其他发现、审查限制及报告路径。无发现时说明检查范围与方法，不声称“没有任何缺陷”。建议反馈的能力和处理范围，由调用方决定是否回退与推进；本 skill 不主动修复或启动下一能力。

默认报告为 `.delivery/YYYY-MM-DD-主题/review/001.md`。同一目标复用目录，复审生成关联记录，失败和未完成也留存。维护本 skill 时执行[行为案例](tests/behavior-cases.json)的实际前向验证；文档存在或结构检查通过不等于独立审查行为已经验证。
