# Delivery Fix

从故障现象建立可检查的因果依据，完成授权修复并留下人和后续模型能够理解、复核与续接的记录。诊断、缓解、根因修复、自检和独立验收分别陈述。

## Working Protocol

### 1. 确认故障、授权与归属

仅在用户明确选择本 skill、新 delivery 体系、项目明确指定或相应编排委派时使用，不自动接管旧流程。独立调用不要求其他 skill、完整设计计划、Git、`.workflow` 或编排状态。

先读[交付约定](references/delivery-contract.md)和[诊断修复规则](references/work-rules.md)。核对预期行为依据、实际现象、影响、授权范围、当前产品和已有修改。只有诊断授权时不修改产品；明确授权的范围不重复索要确认，重大行为或机制歧义反馈具体事实和影响，不能自行改写要求。

找到同一 bug 的既有目录和关联任务，承接已排除原因、失败尝试、实际改动及全部实施作者。归属不明先核对，不能仅凭名称相似合并问题。开始正式排查即建立本轮记录，失败或受阻也保留。

### 2. 用证据推进诊断与修复

依工作规则循环“当前假设 → 有区分力的检查 → 实际证据 → 判断更新”。无法稳定复现不等于不能继续，但必须说明采用何种证据、排除了什么、仍有哪些不确定性。

- 实验性修改注明诊断目的、预期观察及最后处置；不能以不断猜测修改、测试偶然通过代替根因依据。
- 选择足以解决原因且影响可控的修复，不以改动行数最少作为唯一标准。临时缓解与根因修复分别判断。
- 检查原故障条件和直接受影响行为，完成项目规定的必要检查。没有新变化、失败或未解决风险时停止重复测试。
- 需求、接口契约、验收要求或授权范围必须改变时交回调用方决定，不主动串联其他 skill、不降低验收标准。
- 中断恢复先核对实际现场、未回执动作和副作用，再决定下一步；交接不能重置失败历史或遗漏作者。
- 独立使用默认不提交。组合中按明确任务安排本地提交、不 push，用户或项目明确规则优先；保全无关修改和已有暂存内容。

### 3. 持续留存并交接

读取[修复报告规范](references/fix-standard.md)，用[报告骨架](assets/fix-template.md)覆盖七块内容；目录入口用[问题索引骨架](assets/bug-index-template.md)。需要理解多轮记录粒度时读[完整示例](references/example-fix.md)。

同一 bug 的报告与证据始终放在同一目录，默认 `.delivery/YYYY-MM-DD-主题/fixes/BUG-001-问题简述/`，每轮使用 `001/fix.md` 和 `001/evidence/`。不按工具调用或会话切轮。正式交接、提交审查或被编排接纳后保留该轮版本，后续新建关联轮次。索引只导航，不维护第二份通过状态。

报告记明真实 skill 修订、实际产品版本、全部相关实施作者及遗留。调用方可直接接纳指定轮次报告作为实施类产物，不另抄实施正文；本 skill 不生成或修改编排账本、审查或验证结论。

## Exit Criteria

- [ ] 预期、现象、授权、实际版本和问题归属可定位，重要歧义及未决项未被隐藏。
- [ ] 关键诊断判断有依据，已复现、证据支持和仍属推测可以区分；失败与被推翻判断保留。
- [ ] 正式修复、实验改动处置和实际影响明确；仅完成诊断或缓解时没有宣称根因已解决。
- [ ] 原故障和必要回归有实际自检结果或明确未完成原因，未通过修改验收要求制造通过。
- [ ] 本轮报告包含七块必要语义和身份信息，交接现场可恢复；全部相关实施作者及前次记录未丢失。
- [ ] 授权范围内成果已形成，或已准确说明部分成果与阻塞；自检不冒充独立审查或整体验收。

## Exit Protocol

报告 bug 目录与具体轮次、根因判断及证据程度、实际修复、自检结果、剩余限制和后续条件。用“根因有证据支持，修复已实施，相关自检符合，待独立审查”等有范围的结论；只完成调查时明确未完成修复。

用户明确只对话或不留文件时遵从并说明没有可读取记录；保存失败时交付可用内容和原因，不宣称已留存。维护本 skill 时使用[行为案例](tests/behavior-cases.json)做针对性的实际验证，案例定义和结构检查均不等于行为通过。
