# 复杂故障诊断与修复规则

目标是把异常现象收敛成有证据的判断和足够的修复。下面是判断路径，允许根据证据返回前一步，不要求先猜出根因再开始工作。

## 1. 固定问题和现场

核对预期行为的真实依据、实际差异、用户影响、发生版本、环境、输入、时序和影响范围。测试失败、用户报告、监控异常都是线索，不自动等同产品根因。需求与现实现象冲突但正确行为未定时，先提出具体冲突；不能用修改测试期望代替确认需求。

检查相关已有改动、启动的进程、数据和共享资源。会破坏现场的重启、清空、重新生成或覆盖之前，保存必要证据并确认操作在授权内。保全与本次无关的工作，不以重置工作区获得“干净状态”。测试系统的副作用也要纳入范围。

优先建立能区分预期与实际的失败条件。可稳定复现时保存最小足够的触发条件；缩小问题不能去掉决定性的并发、配置、数据或调用路径。无法稳定复现时记录实际发生证据及缺口，使用日志、代码路径、状态变化或受控实验继续调查，不虚构可重现性。

## 2. 建立并检验诊断

围绕事实建立少量能解释现象的候选原因。每项主要检查说明：在区分哪些原因、预期观察是什么、实际结果如何改变判断。优先检查真实调用链、相关变更和因果边界，再扩大搜索；不要只检查最容易修改的函数。

将“已观察事实”“由事实支持的解释”“尚未验证的假设”分开。相关性、一次未复发、测试变绿都不足以单独证明根因。排除原因需说明排除了哪种条件，不把有限实验写成普遍不可能。

同类失败连续两次且没有新增事实或改善时，停止原样重试。根据现有授权改进观察、缩小复现或换假设；需要额外环境、权限或不同执行者时说明必要性与当前缺口，交由调用方安排。重试次数不是自动放弃或放宽要求的依据。

## 3. 管理实验与修复

为验证假设可以在授权范围内增加日志、控制时序、替换隔离依赖或制作探针。每项可能影响产品的实验注明目的、位置、预期、实际观察和处置；临时改动不得混入正式修复而不说明。对外部服务、真实数据和共享环境的动作遵守实际权限，不因“诊断需要”自行扩大。

有证据支持原因后，说明“修改作用于哪一段因果链、为何足够、哪些行为受影响”。修复可包含生产代码、正式测试、配置与必要文档；改动范围由正确性决定，不能以行数少为目标遗漏关联路径。

无法确认根因但有必要实施缓解时，明确缓解目标、依据、剩余风险和验证办法，且必须在授权范围内。用户只授权诊断时不进行正式修复。需求、接口契约、数据语义或验收要求需要变化时，报告具体矛盾与选择，等待调用方决定受影响部分；不主动重做设计或规划。

实施前后检查真实消费者、错误分支和状态恢复，不能以增加检查或接口文件代替接线。记录全部相关实施作者及既有成果来源，不能把继承工作列为自己新写的内容。

## 4. 自检与收敛

围绕原故障条件取得修复前后可比较的证据，尽量使用同一触发方式和判据。无法直接重现原故障时，说明替代检查覆盖的因果环节及未覆盖条件，不能把诊断探针当作规定验收已经完成。

按实际影响选择必要回归：直接调用者、相关边界、失败恢复与项目规定检查。测试应识别外部行为或不变量，避免只复述实现。偶发故障的重复执行应有明确诊断目的、条件与停止标准；“多跑几次没错”不能独立证明消除。

检查通过后，只有新变化、真实失败或未解决风险才增加测试。已有有效证据可以引用，适用版本、环境和要求必须匹配。保留重要失败和修复关联，不只保存最后绿色输出。

修复结论回答三个独立问题：根因判断有多强的依据、实际改动完成到哪里、自检覆盖到哪里。诊断未收敛、只做缓解、未执行必要检查时准确说明，不将提交或报告存在等同修复完成。独立审查和正式验收由相应调用方处理。

## 5. 中断、交接与复发

重要发现、实验和修改后更新本轮报告。交接前写明实际产品版本、实验改动处置、资源持有、已启动未回执动作、可能副作用、尚未排除的原因及下一项有信息价值的检查。

恢复先阅读最新轮次及相关历史，再核对实际文件、环境、进程与副作用。进程消失、缺日志或记录写“准备重试”都不是重放依据；能确认安全才继续，无法确认则保留未知并反馈条件。已接纳结论依赖的材料改变时，明确影响并由调用方重新核对。

复发沿用 bug 目录，新轮次说明与旧触发条件是否相同、旧证据现在是否适用、哪些假设需要重新打开。保留旧关闭事实和问题 ID 关联，不把复发简单记作旧修复从未发生。
