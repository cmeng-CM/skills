# task-workflow 设计说明

把一句话需求做成可执行计划、逐任务派 subagent 执行、用外部证据验证到通过。

这个 README 讲**为什么这么设计**。具体怎么用看 [`SKILL.md`](SKILL.md)，字段格式看 [`references/plan-format.md`](references/plan-format.md)，执行轮协议看 [`references/dispatch-protocol.md`](references/dispatch-protocol.md)。

---

## 一、要解决什么问题

三个具体症状：

1. **随口说个需求，出的计划乱。** 没有结构，任务边界模糊，做到一半发现漏了东西。
2. **内容不全。** 讨论时说好的几件事，写进计划时悄悄少了几条，没人发现。
3. **跑不长。** 上下文一压缩就漂移；断了之后接不上；跑完声称"完成了"但其实没验证过。

这三个症状对应三个机制缺口：**计划质量无校验**、**需求与计划之间无可追溯的映射**、**状态活在上下文里而不在磁盘上**，外加一个**完成声明无外部证据**。

所以本 skill 的每条机制都能追到上面某一条症状。**没有具体症状对应的机制就不做**——这是控制复杂度的唯一纪律，否则它会膨胀成又一个笨重框架。

### 设计参考与教训来源

| 来源 | 借用的是什么 | 为什么借 |
|---|---|---|
| obra/superpowers | 任务切片派发、独立审查、账本、防自我欺骗的措辞纪律 | 它对"同一个模型既写又审"这个根本缺陷处理得最彻底 |
| open-gsd/gsd-core | 决策编号与命中检查、`<fails_when>` 强制、整体终审、fix 循环熔断 | 它在"每个完成声明都要外生证据"上最工程化 |

## 二、四条设计理念

### 1. 状态外置：磁盘是真相，上下文不是

上下文窗口是易失的。压缩、清空、崩溃都会让它失效，而**长任务必然经历这些**。

所以：**任何重要的东西都写进文件**。计划、进度、裁决、验证证据、审批全部落 `<project>/.workflow/<slug>/`。恢复时的规则是硬的——**不相信对对话的回忆，只相信账本与 `git log`**。

这条不是理论。规划参考的 superpowers 记录过一个真实事故：控制器丢失进度后重派了**整个已完成的任务序列**，是它观测到的最贵的失败。

### 2. 外生证据：完成不是声明，是可验证的事实

模型说"做完了"不是证据。所以每个完成声明都必须有**外生**支撑：

- 验证命令的**退出码**（不是"我跑了，通过了"）
- 工作树**内容指纹**（证明验证的就是当前这份代码）
- 每个任务的**提交范围**（证明改动真实存在）
- 整体终审的 **Ready to merge 判定**

关键设计是**指纹绑定内容而非提交**：验证之后又改了代码，指纹变化，那次验证自动失效。反过来，改回原样指纹会复原，同内容不被误判。

### 3. 阶段边界必须停，阶段内部不停

这是最容易做反的一处，两边都有真实失败：

- **边界不停** → 没人拦，计划乱、内容不全（本 skill 要解决的原始问题）
- **内部频繁停** → 用户得守着屏幕。superpowers 记录过有会话在一个本可自己拍板的问题上**卡了 9 小时**

所以规则分开写：

| | 规则 |
|---|---|
| **阶段边界**（方案 → 计划 → 执行 → 验证） | **必须停**，等用户明确答复 |
| **没有答复** | 停住并报告，**不当作默许** |
| **阶段内部**（执行轮里） | **不停**，能自己拍板就拍板并记进账本 |

### 4. 能机械化就别靠自觉

同样一条规则，写成散文和写成程序，可靠性差一个数量级。所以本 skill 里所有**可判定**的约束都做进了引擎，散文只用来承载**不可判定**的判断。

判断标准很直接：**这条规则违规时，机器能不能查出来？** 能，就做成机制；不能，才写成纪律。第二节的"强制力分级"如实列出哪些做到了、哪些没做到。

## 三、架构分层

```
L1 协议层   SKILL.md + references/*.md      纯 markdown，任何 skills-compatible runtime 都能跑
L2 状态层   <project>/.workflow/<slug>/      计划 + 账本 + 报告，落在被操作的项目里
L3 引擎层   scripts/workflow.py              python3 标准库，零依赖，确定性操作
L4 路由层   SKILL.md 内的轮次路由表           自动触发 / 状态路由 / 手动唤醒
   ┈┈┈┈┈┈┈┈┈┈ 以下为可选，默认不装 ┈┈┈┈┈┈┈┈┈┈
L5 门禁层   hooks（SessionStart 注入 + Stop 打回）
```

**分层的意义是降级可用**：L5 缺失时 L1–L4 仍然完整工作，只是少了"上下文清空后自动带回状态"这一层便利。L3 缺失时（没有 python3）协议仍在，但所有机械门退化为纪律。

**为什么状态落在被操作项目而不是 skill 目录**：同一个 skill 会作用于多个项目，状态必须跟着项目走。这也和仓库里既有的 `.handoffs/`、`.context/project-learning/` 惯例一致。

## 四、状态文件

```
<project>/.workflow/
├── .gitignore                    # 内容为 *，目录自己忽略自己（不靠用户记得加）
└── <slug>/
    ├── plan.md                   # 方案 + 决策 + 任务（机器可解析）
    ├── ledger.md                 # 账本：审批/完成/裁决/错误/验证/收尾
    └── reports/<任务>.md          # 派发产出的报告正文（主会话不读回）
```

### `plan.md` 结构

```markdown
# <标题>
**Goal** / **Slug** / **Created**

## 验证命令          ← "完成"定义的唯一来源
## 全局约束          ← 每条隐含适用于所有任务
## 方案              ← 第一道门的对象：做法 / 备选与取舍 / 明确不做
## 决策              ← | ID | 决策 | 来源 | 理由 |，来源=用户/agent
## 阶段
  ### Phase N        ← 带 Checkpoint
    #### T<n>        ← 八个字段：文件/依赖/并行/接口/验收/失败信号/决策/状态
```

### `ledger.md` 的六个区

| 区 | 记什么 | 作用 |
|---|---|---|
| **审批** | 谁在什么时候批了方案/计划，绑定的内容指纹 | 门的证据；指纹失配即审批失效 |
| **完成记录** | 每个任务 + 提交范围 + 审查结论 | 压缩后判断"做到哪了" |
| **裁决** | 控制器自己拍板的事 + 理由 + 错的代价 | **收尾时必须汇总给用户**——随工作区消失的裁决等于秘密决定 |
| **错误** | 错误 + 尝试次数 + 处理 | 防止重复失败 |
| **验证记录** | 时间/标签/提交/命令/退出码/指纹/结果 | 收尾门的依据 |
| **收尾** | 完成度 + 指纹 + 交接去向 + 下一步 | 证明收尾真的发生过 |

## 五、主流程逻辑

### 轮次路由（门）

判据是**状态文件**，不是对话记忆：

| 观察到的状态 / 用户的话 | 轮次 |
|---|---|
| 没有对应工作流 | **P1**（写方案） |
| 方案写好待看 | 停在**方案门** |
| 计划写好待看 | 停在**计划门** |
| 有活跃工作流且有未完成任务 | **E**（执行） |
| 全部任务 complete | **V**（验证） |
| "验证一下" / "执行 T3" / "看看进度" / "计划改一下" | 对应轮次或只读 |

### P 轮：需求 → 方案 → 计划（两道审阅门）

```
需求 → [delve 澄清] → 写 ## 方案 → 🚧 方案门 → 写任务与决策 → check → 🚧 计划门 → E 轮
                                     approve 方案                      approve 计划
```

**方案门**：把 `## 方案` 呈现给用户，**停下等明确答复**。用户说要改就改完再呈现。

**计划门**：`check` 零 ERROR 后才能申请审批。把计划呈现给用户，**停下等明确答复**。

**两道门都是机器强制的**：

- `slice`（派发任务）和 `record`（记录完成）都调 `require_plan_approval`
- 审批绑定**内容指纹**：方案绑 `## 方案` 段落，计划绑整份计划（**剥离状态字段**——状态每次执行都变，纳入哈希会让正常执行作废自己刚拿到的审批）
- 批准后偷改内容 → 审批自动失效 → 必须重新审批
- 不带 `--by`（审批依据）一律拒绝：**没有依据的审批等于自己给自己盖章**

### E 轮：逐任务执行

```bash
$W next                   # 依赖图算出的可执行任务（不是线性从头做）；提示哪些可合并
$W slice <slug> T3        # 抽单任务派发片段（不给整份计划）
$W slice <slug> T3 T4 T5  # 合并成一批（同型机械改动才这么做）
# 派实现者 → 派独立审查者 → 通过则：
$W record <slug> T3 --commits <base7>..<head7> --verdict clean
```

要点：

- **上下文经济**：派发只给"任务 + 依赖接口 + 全局约束 + 报告路径"四样；子 agent 回话 ≤15 行，正文写 `reports/`；diff 不进主会话
- **独立审查**：每任务一次，审查者不得是实现者；禁在审查 prompt 里写"不要报 X"（那是预判）
- **fix 循环熔断**：1–3 轮 resume 原实现者 → 4–5 轮换 fresh + 升级模型 → 之后控制器裁决。**控制器绝不自己修代码**
- **裁决不停机**：能拍板的自己拍板并记账；只有四类事必须停（不可逆操作、安全敏感、工作区外的副作用、计划坏到每条路都是猜）
- **依赖图状态**：`BLOCKED` / `READY` / `RUNNING` / `DONE` 由依赖算出，不靠人工标

### 粒度：同型机械改动要合并

**每个任务在执行轮至少是两次 subagent 派发**（实现者 + 独立审查者），所以粒度切错会直接反映成成本：

| 切错 | 切对 |
|---|---|
| T1 改 a.py 常量 / T2 改 b.py 常量 / T3 改 c.py 常量（**6 次派发**） | **T1 统一三处常量**（**2 次派发**） |

判据是**"这次改动需要自己的判断、自己的测试、自己的审查面吗"**——不需要就合并成一个任务（一个任务可覆盖多个文件）。

**这不是"按体量开快路径"**：合并只改**执行粒度**，审批门、`check`、独立审查、验证覆盖审计、`close` 一样都不少。省掉的是纯重复的流程，不是质量底线。

计划已经切细了、执行时才发现几个任务同型，还有逃生通道：`slice` 给多个任务合并成一批。引擎先挡掉三类不该合并的（批次内含依赖 / 任务已完成或被阻塞 / 超过 4 个）；文件重叠只报警告——同批是**一个** subagent 顺序做的，重叠不是并发冲突，但通常说明它们不同型。

### 只读并行 vs 写操作并行

| | 规则 | 原因 |
|---|---|---|
| **只读**（调研、多路审查、排查多个独立失败） | **随时可并行，且应该用** | 不写文件、零冲突；等待时间直接除以 N |
| **写操作**（实现者） | **一律串行** | 写面没隔离，同树并发会抢 `index.lock` 且 diff 互相污染 |

写操作并行的三个前提只满足一个：任务独立 ✅、写面隔离 ❌（用户明确不做 worktree）、提交串行化 ❌。注意**"文件不重叠"并不足以支持同树并发写**——即使不重叠，并发提交也会互相污染。

**并行的正确单位是独立的工作流，不是"同一工作流的多个任务"**：gstack 的 10-15 并行 sprint 每个有自己的 workspace 和完整流程；gsd 的波次并行必须配 worktree + base-check。没人把"一个任务"切开并行做。

### E 轮收束：整体终审

所有任务过了逐任务审查后、进 V 之前，做**一次覆盖整段改动范围的终审**。

逐任务审查看"这个任务做对了吗"；终审看"这些任务合起来是自洽的整体吗"。后者才能发现：两个任务用不同方式解决同一问题、后一个任务削弱了前一个的保证、跨任务接口理解偏差、**范围缩减**（说好要做的被拆散后没人真正做）。

规则：审从第一个提交到 HEAD 的完整 diff；用**当前最强模型**（唯一一处刻意升档）；审查者必须没参与过任何实现和任务级审查；产出明确的 `Ready to merge: Yes/No` + 分级问题。有 Critical/Important 时派**一个**修复 subagent 带完整清单修（不是每问题一个 fixer），**只有一波**。

### V 轮：验证到通过

1. **先分类再判断**——`DIFF-VERIFIABLE` / `CROSS-REPO` / `EXTERNAL-STATE` / `CONTENT-SHAPE`。**`git diff` 对后三类是结构性不可见的**，不分类就会把没做的判成做完了
2. **路径具体化规则**——写了具体路径的条目必须用 `[ -f <path> ]` 判，"不想检查"不算"无法验证"
3. **诚实规则**——"处理交付物的代码"不等于交付物本身
4. `$W verify` 跑验证并留证（命令/退出码/提交/指纹）
5. **审计验证覆盖**（见下节）——核对声称的验证产物是否真实存在
6. 未通过 → 缺口写成新任务追加回计划，回 E 轮，**重复到收敛**
7. 标`人工`的条目**逐项**向用户确认，**不给"一次性确认全部"的选项**

### 验证覆盖：回答"验证范围够不够"

前面几步只能判断"我要求的都做到了吗"，**判断不了"验证范围本身够不够"**。这是两个不同的问题，而后者才是漏检的来源。

所以 `plan.md` 有一节 `## 验证覆盖`，把验证范围变成**可审查**的东西：

```markdown
| 对象 | 验证手段 | 类型 |
|------|---------|------|
| D-01 | `tests/test_logging.py::test_level_mapping` | 自动化 |
| D-02 | `tests/test_cli.py::test_verbose_count` | 自动化 |
| 边界：空文件 | 人工：跑 `mytool --verbose empty.txt`，期望无 DEBUG 输出 | 人工 |

### 不验证的部分

- 并发下的日志顺序不验证：本次改动未引入并发路径
```

两件事让它不只是"写给人看"：

**一、双向覆盖是 ERROR 级的。** 每条决策都必须出现在覆盖表里（决策 ↔ 验证互查），且必须显式写「不验证的部分」——真的没有也要写"无"。不写就只有"验证了什么"、没有"没验证什么"，而**没验证的才是风险所在**。

**二、V 轮会去核对声称的产物是否真实存在。** 标`自动化`的条目，引擎真的去查文件在不在、文件里有没有那个测试：

| 写法 | V 轮怎么核 |
|---|---|
| `` `tests/test_cli.py::test_verbose_count` `` | 文件存在吗？里面有 `test_verbose_count` 吗？ |
| `` `tests/test_cli.py` `` | 文件存在吗？ |

对不上就是**覆盖缺口**：`verify` 报出来，**`close` 拒绝收尾**。这条堵的是"声称有测试但测试根本不存在"——那等于什么都没验证。

**诚实地说"这个没验证"是被允许的；声称验证了却拿不出东西不是。** 前者进「不验证的部分」并列明风险，后者过不了门。

### bug 路径

bug 的"需求"是一个**症状**而不是规格，没有可审的方案（要做的事已被症状决定大半）。所以 bug 工作流**免两道审批门**：

```bash
$W init <slug> --bug --goal "<症状>"
```

补偿控制是**三项强制**：

| 强制项 | 为什么 |
|---|---|
| `## 复现`——可复现的最小步骤 | 没有可复现的失败，就无法证明修好了。**修之前先确认它确实失败** |
| `## 根因`——说清为什么错 | 说不清根因就只是在让症状消失，换个输入就复现 |
| **回归测试**——覆盖表里必须有一行明确标为回归测试 | 修复不带回归测试，**同一个 bug 会回来，而且回来时没人记得修过** |

三项都是 `check` 的 ERROR 级拦截，回归测试还会在 V 轮被核对真实存在。

**验证比常规更严**：复现用例必须从失败变为通过 **+ 全量测试不回归**（修复最容易打破别处，特别要检查是否改动了共享函数或默认值）。

**不夹带无关改动**——顺手重构是 bug 修复最常见的坏味道。要重构就单独开一个工作流。

**期望行为要确认一次**："bug 报告"本身可能有歧义——用户觉得是 bug，其实是有意行为。开工前用一句轻确认："当前行为是 X，期望行为是 Y，是吗？" 这不是审批门，是确认对问题的理解。

**升级条件**（任一命中就改走完整路径，此时它实际是"探索 + 改造"）：复现不出来 / 根因不明 / 需要改 3 处以上或跨模块 / 涉及数据正确性、安全、并发 / 发现要改的是一段设计。

### 收尾

```bash
$W close <slug> --next-step "<建议>"
```

`close` 同时是门，四种情况拒绝执行：**还有未完成任务**、**账本无验证记录**、**最近一次验证的指纹与当前工作树不符**、**存在验证覆盖缺口**。无法自动化验证的走 `--manual-confirmed "<谁确认了什么>"`——同样落账本，**不存在静默通过的口子**。

收尾两件事：汇总全部裁决给用户 / 报告验证证据。

**然后本 skill 的职责就结束了。** 不改代码、不写长期记忆、不更新项目契约。**收尾之后做什么由用户自己判断**——包括是否把产出写回别处；工作流不代判、不探测、不代办。

## 六、机制的强制力分级（诚实版）

这是最重要的一节。**不要以为写了就一定会执行。**

| 机制 | 强制力 | 说明 |
|---|---|---|
| 审批门（方案/计划） | 🟢 机器 | `slice`/`record` 拒绝未审批的派发 |
| 审批失效（内容改动） | 🟢 机器 | 内容指纹比对 |
| 计划质量检查 | 🟢 机器 | `check` 十余类规则 |
| **验证覆盖双向覆盖** | 🟢 机器 | 每条决策必须出现在覆盖表里；缺「不验证的部分」也报错 |
| **覆盖产物核对** | 🟢 机器 | V 轮真的去查声称的测试文件/函数是否存在；有缺口 `close` 拒绝 |
| **bug 三项强制** | 🟢 机器 | 复现/根因空节报错；缺回归测试行报错；验证命令不允许未声明 |
| 依赖图状态 | 🟢 机器 | 拓扑排序，非人工标 |
| **批次合并的三条守卫** | 🟢 机器 | 批次内含依赖 / 已完成或被阻塞 / 超 4 个任务 → 拒绝；文件重叠仅警告 |
| 完成前验证 | 🟢 机器 | `close` 四条件 |
| 验证失效判定 | 🟢 机器 | 内容指纹 |
| 账本防串 | 🟢 机器 | 首行必须命名本计划 |
| 自忽略 | 🟢 机器 | `.workflow/.gitignore` |
| 计划质量 | 🟡 半机器 | 机器查结构，语义靠 `check` 的 WARNING + 人看 |
| 逐任务派发 | 🟡 半机器 | `slice` 生成片段，但"是否真的派了 subagent"机器不知道 |
| **复现与根因的内容质量** | 🟡 半机器 | 机器只查空节，写得对不对要人看 |
| **"是否同型机械改动"** | 🟡 半机器 | 合并的三条硬条件机器挡，但"同型"要人判 |
| 独立审查 | 🔴 纪律 | 靠模型遵守；模型可以跳过而不被发现 |
| 整体终审 | 🔴 纪律 | 同上 |
| 裁决记账 | 🔴 纪律 | 靠模型主动 `record --note` |
| 回话 ≤15 行 | 🔴 纪律 | 无强制 |
| 不预判审查 findings | 🔴 纪律 | 无强制 |
| **「不验证的部分」是否诚实** | 🔴 纪律 | 机器只能查它存在，查不出它是否避重就轻 |

**如实说**：绿色的部分是可靠的，红色部分在有压力的长任务里**可能会被跳过**。想把这些也变硬，需要 L5 的 hook 层或 harness 级的支持——那是刻意没做的部分（见第九节）。

## 七、触发设计（三层，零配置）

| 层 | 机制 | 作用 |
|---|---|---|
| **自动触发** | SKILL.md 的 description 覆盖多种措辞 | 用户说"实现 X"/"继续"/"验证一下"，模型自行判断是否加载 |

**为什么零配置**：仓库里既有的 7 个 skill 一个 hook 都没有，靠"状态文件存在性路由"照样工作。这说明状态路由足够，不需要为了触发去改三个客户端的全局配置。

## 八、与现有 skill 的衔接

```
需求 → [delve 澄清*] → ┌─ P/E/V 本 skill ─┐ → 结束
                       └──────────────────┘
    * = 条件调用，探测到才调，缺失则降级
```

**拿项目约定与验证命令不依赖任何外部 skill**：直接读项目根的 `AGENTS.md` / `CLAUDE.md` / `README.md`；读不到就问用户一次。**绝不猜默认值**（拿不到宁可在计划里标 `未声明`）。

| skill | 时机 | 探测不到时的降级 |
|---|---|---|
| `delve` | 需求有歧义时 | 自己一次问一个，答案写进决策表 |
| `session-handoff` | **换人/换 agent 接手**时（用户提出才用） | 账本本身已能跨会话恢复，不需要 handoff |

**不衔接的**：`project-learning`（理解项目 ≠ 完成任务）、收尾写回类（**本 skill 收尾后即结束，是否写回由用户判断**，见上文「收尾」）、memory 三件套、工具型 skill（无结构关系）。

**收尾之后为什么不由本 skill 决定**：工作流解答的是"把这个需求做完并验证通过"，而"把产出写回哪里"是另一件事，取决于用户当时想留下什么。所以这里既不探测下游、也不给建议——**由用户自己判断**。

## 九、刻意没做的

| 没做 | 理由 | 何时重新考虑 |
|---|---|---|
| **hook 门禁层**（SessionStart 注入 + Stop 打回） | 你自己 7 个 skill 零 hook 也跑得通；hook 要改三个客户端全局配置，Codex 还多一步信任审批，写坏了会挡住会话 | 真的观察到"上下文清空后接不上"或"没验证就说完成"再加 |
| **worktree 隔离** | 改动面小时是纯开销 | 按你的决定，**不动** |
| **estimate 自校准闭环** | 最工程化但最重（gsd 那套要 frontmatter + 校准样本 + factor 回喂）；"每任务 2–5 分钟 + ≤5 文件"的硬约束已能防计划爆炸 | 觉得计划规模总是估错时 |
| **并行波次派发** | superpowers 明确禁止并行实现者（工作树冲突） | 有真正的隔离方案时。`并行` 字段已保留作排序参考 |
| **信任存储** | 防的是"声明的命令被篡改后执行"，单人机器风险低 | 多机/团队场景 |
| **依赖模型自动写计划**（Script Workflow / 内部 workflow 引擎） | 会把计划格式绑死在某个 harness 上，破坏跨客户端可移植性 | 不再需要跨客户端时 |

## 十、已定的两个设计决定

### 决定一：不做按体量的轻量路径

**曾考虑**：给"单文件 / 少量代码"的小改动开一条免两道门的快路径。

**结论：不做。** 理由：

- **阈值模糊**。`≤2 文件 / ≤2 任务` 是规模指标，但规模不等于风险——3 行的 CLI 参数改名很"小"，却绝对需要用户确认；80 行的内部重构可能完全不用问。**规模决定要不要写文档，但决定不了要不要问用户**
- **易被滥用**。任何"这里可以简化"的判据都会被当作省事的借口，而省掉的恰是拦错误的那道门
- **可逆性更好**。现在没开这个口子，将来真觉得小活太啰嗦，加一条快路径是加法；反过来先放宽再收紧会让"什么算小活"变成长期争论

真正的规律是：**任务小不小时用户往往一眼就看得出来**。所以与其让 agent 用判据替用户决定要不要审，不如让用户直接说"这个直接做，不用给我看"——那会用 `--by` 把用户的话记成审批依据，**是用户绕过门，不是 agent 自己绕过**。

### 决定二：bug 修复走免门路径，但三项强制

**结论：已实现。** bug 的"需求"是一个症状而不是规格，没有可审的方案，所以免两道门；补偿控制是三项 `check` 级别强制的：

1. **`## 复现`** —— 可复现的最小步骤，且**修之前先确认它确实失败**
2. **`## 根因`** —— 说清为什么错，不靠试错
3. **回归测试** —— 覆盖表里必须有一行明确标为回归测试，V 轮核对它真实存在

第 3 条是硬要求（**你确认过**）。理由：修复不带回归测试，同一个 bug 会回来，而且回来时没人记得修过。项目确实没有测试框架时，把它记成一条决策说明理由并写进「不验证的部分」——但那是退让，不是默认。

**升级条件**（任一命中改走完整路径）：复现不出来 / 根因不明 / 需改 3 处以上或跨模块 / 涉及数据正确性、安全、并发 / 发现要改的是一段设计。

## 十一、验证覆盖：补上的一个实质缺口

**原设计的问题**：V 轮只验"需求被满足了吗"，**没有任何东西声明"验证覆盖了哪些范围"**。也就是说验证范围是隐式的——只有"跑了个命令，过了"，没人能审查漏了什么。

**补上的机制**：`plan.md` 增加 `## 验证覆盖` 一节，两件事让它不只是文档：

| 机制 | 强制力 | 堵的是什么 |
|---|---|---|
| 每条决策必须出现在覆盖表里（双向） | 🟢 `check` ERROR | "某个决策其实没人验证" |
| 必须显式写 `### 不验证的部分`（没有就写"无"） | 🟢 `check` ERROR | "范围是隐式的" ——**没验证的才是风险所在** |
| V 轮真的去查声称的测试文件/函数是否存在 | 🟢 运行时 | "声称有测试但测试不存在" |
| 有覆盖缺口时 `close` 拒绝收尾 | 🟢 门 | 带着假覆盖收工 |
| 「不验证的部分」是否避重就轻 | 🔴 人看 | 只能靠人，机器查不出诚实度 |

**设计取向**：**诚实地说"这个没验证"是被允许的**（进「不验证的部分」并列明风险）；**声称验证了却拿不出东西不被允许**（报缺口、拒绝收尾）。给"诚实的省略"留出口，是为了不逼出"编一个假测试来填空"。

## 十二、完整路由

```
需求
 ├─ 是 bug（能复现） ──→ bug 路径：复现 → 根因 → 修 → 回归测试 → 验证（含覆盖审计）
 │                        init --bug；免两道门，三项强制
 └─ 其余 ─────────────→ 完整路径：方案门 → 计划门 → 执行 → 终审 → 验证 → 收尾
                          init；两道门都停
    任一 bug 路径执行中命中升级条件 → 改走完整路径（单向）
```

两条路径**共用**的东西：`.workflow/` 状态目录、`check`、`next`/`slice`/`record` 派发协议、独立审查、整体终审、验证覆盖审计、`verify` 留证、`close` 四道门。**路径差别只在"要不要写方案"和"要不要两道审批门"**。
