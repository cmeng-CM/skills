# 派发协议

执行轮的每一步都按本协议走。核心原则一句话：**主会话只做路由，产出物一律落文件。**

## 上下文经济（为什么这么苛刻）

主会话里粘贴的任何内容，都会在本会话剩下的每一轮被重新读取。实测过的教训：一次派发 prompt 膨胀到 42k 字符，其中 99% 是粘贴的历史——而一个 fresh subagent 真正需要的只有"它的任务 + 它要碰的接口 + 全局约束"。所以：

| 规则 | 做法 |
|---|---|
| 派发不给整份计划 | 用 `workflow.py slice` 抽单任务片段 |
| 子 agent 回话 ≤15 行 | 正文写进 `reports/<任务>.md` |
| diff 不进主会话 | 审查子 agent 自己读 diff，只回判决 |
| 报告文件不重读 | 需要时用 `tail`/`grep`，不整份读回 |

## 派发流程

```bash
# 1. 看当前能做什么（依赖图算出来的；会提示哪些任务可合并）
python3 scripts/workflow.py next

# 2. 抽出这个任务的派发片段（多个任务即为合并成一批）
python3 scripts/workflow.py slice <slug> T3
python3 scripts/workflow.py slice <slug> T3 T4 T5

# 3. 把片段作为 prompt 派给 subagent（片段已含目标/约束/提交契约/任务/依赖接口/报告契约）
# 4. 子 agent 回来后，派第二个 subagent 审查
# 5. 记账（提交范围由 record 校验：sha 必须真实存在、非空范围）
python3 scripts/workflow.py record <slug> T3 --commits <base7>..<head7> --verdict clean
python3 scripts/workflow.py record <slug> T3 T4 T5 --commits <base7>..<head7> --verdict clean

# 格式 ≥4：记「已实现」（无 --verdict），证据随任务记账；操作 ID 首次执行前生成、重试复用
python3 scripts/workflow.py record <slug> T3 --commits <base7>..<head7> --evidence "<验收与结果>" --operation-id <id>
```

**一次只派一个实现者。** 不要并行派发多个实现任务——它们会同时改同一个工作树，产生冲突。`并行` 字段标的是"可以并行的候选"，当前实现是串行派发（原因见下面「只读并行 vs 写操作并行」）。

## 提交契约（谁提交、什么时候、能不能推）

**提交由实现者做**，控制器只校验。理由是它有上下文（知道改了哪些文件、为什么），而且中断时工作不会丢在未提交状态。

| 规则 | 内容 |
|---|---|
| **自动** | 任务完成即提交，**不逐次问用户**——问一次就多一次打断，而提交是可逆的本地动作 |
| **分阶段** | 单任务至少一次提交；批次一次提交即可，但批次内部按顺序做完再提交。**不要把几个任务攒成一次**——审查范围（`BASE..HEAD`）和中断恢复都靠它 |
| **只 stage 自己的文件** | 逐个写明路径，**不要 `git add -A` / `git add .`**——工作树里可能有别人的改动（或控制器刚写的设计文档回写），一勺烩会把它们卷进这次提交 |
| **提交信息** | `T<N>: <任务名>`（批次写 `T3+T4: <批次名>`），正文一两句说清改了什么 |
| **不推送** | `push` / `merge` / `rebase` / 改历史 / 发布都是**工作区之外的副作用**，必须在用户明确要求后单独做 |

修复循环里每次修复也照常提交——`record` 的范围是 `原 BASE..最终 HEAD`，自然覆盖多次提交。

**确实无需改动的任务**（核实后不用动）：没有提交就写不出非空范围，把理由写进 `--note`，`record` 会放行并在账本里留痕。

## 合并派发（同型机械改动）

**先看计划层的规则**（`plan-format.md`「同型机械改动要合并」）：同一种小改动在多个地方重复时，本就该是**一个任务**。这一节讲的是没来得及改计划的逃生通道。

计划已经切细了、但执行时发现几个任务是同型机械改动，**不要逐个派**：

```bash
python3 scripts/workflow.py slice <slug> T3 T4 T5      # 一份 brief，一个 subagent
# 做完后
python3 scripts/workflow.py record <slug> T3 T4 T5 --commits <base7>..<head7> --verdict clean
```

**判据是任务形态，不是任务数量**（学自 superpowers 的 "Batch small same-shape work"）：

| 值得单独派 | 应该合并成一批 |
|---|---|
| 需要自己写测试 | 同一个一行修复重复在多个文件 |
| 需要自己的判断（设计、取舍） | 改常量、改字段名、加日志 |
| 有自己的审查面（不同关注点） | 机械重复的同型改动 |

**引擎会先挡掉三类不该合并的情况**（不用你判）：

| 守卫 | 为什么 |
|---|---|
| 批次内含相互依赖 → 拒绝 | 有依赖就是顺序工作，后一个的审查要看前一个的结果 |
| 有任务已完成或被阻塞 → 拒绝 | 批次只对当前能做的任务有意义 |
| 超过 4 个任务 → 拒绝 | 一个 subagent 一次能高质量做完的量有限；超了拆两批或逐个派 |

**格式 ≥4 另加一条：批次成员须同属一个审查节点**（跨节点批次 → 拒绝并逐条列出 `T1→N1、T3→N2`）。节点是验收单位——一批跨节点就没法在批末一次性送审，合并的意义消失。同节点批次同时受"互不依赖、文件不重叠、可合并"的既有提示约束（`next` 按同节点分组给出候选）。

**文件重叠只报警告，不拒绝**——因为同批是**一个** subagent 顺序完成的，重叠不是并发冲突。但它通常意味着"这几个任务不是同型改动"，值得确认一下。

合并批次的记账：账本每个任务一行，`审查` 列标明所属批次（`clean（批次 T3 + T4 + T5）`），恢复时能看出这次审查覆盖了哪几个任务。

**省下的是纯重复的流程**：3 个机械改动从 6 次派发降到 2 次。审查、验证、覆盖审计一样不少——**合并只改执行粒度，不跳过任何门**。

## 只读并行 vs 写操作并行

这两件事的规则完全不同，不要用一条规则概括。

### 只读并行：随时可用，而且应该用

**只读 subagent 不写任何文件，没有冲突问题**，可以放心并行。收益是等待时间直接除以 N。该用的场景：

| 场景 | 并行的方式 |
|---|---|
| P 轮的代码调研（摸清模块、找现有模式、查依赖） | 按模块分几路并行查，各自汇报发现 |
| P 轮的计划语义审查（`plan-review.md`） | 只读，可与其它只读调研并行；但必须在计划门之前完成 |
| 整体终审 | 按关注点并行（安全 / 性能 / 契约一致性），再汇总成一份判定 |
| 多方案调研 | 各查一路，回来对比 |
| 排查多个独立失败 | 一个 agent 查一个失败原因（superpowers 的并行 skill 就是这个场景） |

派只读 agent 时**同样要给它自包含的指令**——它没有你的上下文，也不知道别的 agent 在查什么。

### 写操作并行：需要三个前提，当前不满足

| 前提 | 说明 | 我们满足吗 |
|---|---|---|
| **任务真独立** | DAG 无依赖 + 文件集不重叠 | ✅ `next` 能算 |
| **写面隔离** | 每个 agent 有自己的工作树 / 检出 | ❌ **本项目明确不做 worktree** |
| **提交串行化** | 不能并发 `git add`/`commit` | ❌ 未设计 |

②③ 缺一不可：即使文件不重叠，两个 agent 在同一工作树里同时提交也会抢 `index.lock`，而且各自的 diff 会混入对方的改动——**"文件不重叠"并不足以支持同树并发写**。

因为 ② 被明确排除（`worktree 隔离不做`），**本项目里写操作一律串行**。

**一个容易搞错的地方**：并行的正确单位是**独立的工作流**，不是"同一工作流的多个任务"。gstack 能跑 10-15 个并行 sprint，是因为每个 sprint 有自己的独立 workspace 和自己的完整流程；gsd 做波次并行必须配 worktree，且波次之间还要做 base-check 防止 fork base 过期。没人把"一个任务"切开并行做——那既拿不到隔离，也说不清谁负责验收。

## 实现者 prompt

`slice` 已经生成了大部分内容。派发时只需要在片段之外补一条**控制器对歧义的裁决**（如果有）：

```
<slice 生成的片段>

## 控制器裁决

<若本任务有需要拍板的模糊点，在这里给出决定与理由；没有就省略本节>
```

不要往 prompt 里加：项目背景介绍、历史对话摘要、其他任务的细节、"参考之前那个实现"。执行者读不到那些，加了只会挤占它的上下文。

**实现者不得自己派 subagent。** 它自己找的审查者是在给自己打分，且会和控制器派的那次重复。这条要写进 prompt。

## 报告契约

子 agent 回话必须包含（**≤15 行**）：

```
状态：DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
提交：<base7>..<head7>（无改动时写"无改动"并说清为什么）
改动：<文件列表>
命令：<跑了什么，结果如何>
遗留：<未解决的问题，没有写"无">
```

详细内容（完整 diff 说明、调试过程、TDD 证据）写进 `.workflow/<slug>/reports/<任务>.md`。

### 报告只装证据，不装判断

**报告是"我做了什么、凭什么说做完了"的记录，不是设计记录。** 历史案例曾出现账本裁决区堆了几十条判断、收尾后随 `.workflow/` 丢失，而设计文档只有结论的风险。现行协议保留工作流记录；它们仍不进版本库，长期设计判断必须另行归位。

| 内容 | 去哪 | 为什么 |
|---|---|---|
| 命令 + 退出码、产物路径、实测结果 | **报告** | 这是证据，只有实现者/审查者见过 |
| 与计划的偏离、阻塞、待人工验收的部分 | **报告** | 同上 |
| **技术选择、边界裁定、设计判断** | **设计文档的「决策摘要」**（运行期新增的接着 `D-NN` 编号） | 判断必须活到工作流之后 |
| 谁在什么时候拍的板、错的代价 | 账本「裁决」区 | 运行时记账；**内容结论仍要进设计文档** |
| 改变了任务范围/验收标准 | **回填计划的决策表**，重新走计划门 | 用户批准过的东西被改了 |

**实现者和审查者不做最终裁定**，但要**把判断显式交出来**：报告的「遗留」一栏里，凡属"我做了某个技术选择"或"我认为该这样做"的，都必须写成可裁决的候选决策（`候选决策：<选择> — <理由> — <代价>`），不要混在叙述里。控制器负责把它归位——进设计文档、回填计划，或明确裁定不采纳并记理由。

**判断只留在报告里没有被上浮，就没有进入长期设计视图**：状态记录虽保留，版本库和设计读者仍缺这条依据。

### 报告保留，不删

`.workflow/<slug>/reports/` **收尾后保留**，不清理。

理由很实际：任务中断、上下文清空、隔几天重启时，**报告保存任务执行细节，是恢复的重要依据**。只有一行"complete + 提交范围"不足以接着干；还要对齐计划、结构化事件与原输出。

注意报告**不进版本库**（`.workflow/` 自忽略），所以它不是长期记录——长期记录是设计文档。两者的分工就是上面那张表。

### 四态的分诊

| 状态 | 含义 | 控制器动作 |
|---|---|---|
| `DONE` | 完成且自认无问题 | 进入独立审查 |
| `DONE_WITH_CONCERNS` | 完成但有保留意见 | 把保留意见写进审查 prompt，让审查者重点看 |
| `NEEDS_CONTEXT` | 缺信息做不下去 | 补齐上下文（接口、约束、示例）后重新派发 |
| `BLOCKED` | 遇到做不了的障碍 | 按下面分诊 |

`BLOCKED` 的四种分诊：

- **上下文缺失** → 补上下文重派
- **推理能力不够** → 换更强的模型重派
- **任务太大** → 拆成两个任务（改 plan.md 后重跑 `check`）
- **计划本身错了** → 控制器裁定该怎么改，记账，带着裁决重派

## 独立审查

**每个任务完成后必须审查一次，且审查者不得是实现者。** 实现者的自评不能替代这一步。

审查者一次读 diff，出**两个判决**：规格符合（是否满足任务的验收标准）+ 代码质量。

### 格式 ≥4：审查单位是节点（两态验收）

格式 ≥4 下派发仍逐任务（或同节点批次），**审查与放行按计划声明的「审查节点」组织**：

- 归属任务全部 `record`（已实现）构成送审条件；节点送审前控制器核对必要验证完成、未解决事项列明（这两件事引擎不判）。
- 审查者读取实际改动与必要上下文，对规格符合性、实现质量及**组内集成关系**作出判断；实现者报告只作线索。产出＝**逐任务一行结论**（`--lines "T1: 结论＋依据；T2: …"`，逐行覆盖归属任务、每行须关联验收依据或具体问题）＋**节点整体结论**（防"每项单独成立、组合后不成立"）。
- 记账：`$W review <slug> <节点> --verdict pass|fail --commits <base7>..<head7> --lines "<…>" --evidence "<引用>" [--premises "<类型: 路径; …>"] --operation-id <id>`。
  - `pass` 后成员任务才映射 `complete`（＝已验收）；`fail` 保持 `implemented`、**不释放跨节点依赖**、也不把已实现退回待实现；未通过时即使部分任务没问题，也不提前释放该节点的跨边界依赖。
  - **`fail` 的退出码是 0**（结论成功落盘）——调度器必须读结果里的 `verdict`/`mapped_status` 字段，**不要只看退出码**。
- 跨节点依赖只在上游节点整体已验收后解除——**「上游」取沿等待图可达的传递闭包**（多跳，不只一跳：链式图 N1←N2←N3 上 N1 未验收时 N3 同样被拒；终审节点本就等待全体）；组内任务可继续消费彼此的"已实现"成果（同节点内按"已实现"放行，不等待审查）。**状态判断各入口一致（同一套三态派生），放行门各有其位**：派发门在 `slice`（对未验收的跨节点上游拒绝派发）、就绪检查在 `close`/`verify`（对未验收节点拒绝放行）、`record` 记录既成事实不做派发门（上游未验收时仍可记实现，只是跨节点下游不放行）、`impact` 与 record/review/slice 同一道计划门（审批失效即拒绝）。**`verify` 记账入口按就绪校验拒绝，不给诊断豁免**——底层验证命令仍可直接运行作诊断；"验证命令可以用于诊断"指的正是这一点，不是给 `verify` 开后门。
- **`--lines` 书写纪律**：结论正文里不要出现 `T<n>:` 形态（`；T2:` 之类会被解析成下一个行边界，任务集合对不上即 fail-closed 拒绝）；行数只证明覆盖记录齐全，不证明检查充分。

### 格式 ≥4：结论绑定、失效与去重

每次审查记录：节点版本（节点块＋归属任务声明字段的规范化摘要，剔除 `状态` 等运行字段；**取字段原文，分隔符、注解等取值排版差异也会换版本（字段顺序不影响——按键排序摘要）；保守，可接受**）、审查阶段、已审提交范围（另存解析后的完整 sha **锚**——读路径**优先用锚**，只有旧记录缺锚时才回退重新解析 `--commits`；`HEAD` 是会移动的引用，读取时重新解析会让「已审范围上的新提交」整体失效）、逐任务行、证据引用、结论、未关闭问题（`open_issues`，**首版恒空占位——审查记录没有提交未关闭问题的入口**）、依赖前提清单、**`全局约束摘要`**（计划的 `## 全局约束` 一节的文本摘要——该节改写即使无提交、无节点/任务声明变化，也转「待重新确认」，由 `--recheck` 重记摘要恢复）。**前提**由调用方逐条声明（**非自动采集**）：不只记上游契约锚点（产出任务的文件集、接口签名摘要、基线提交），还须纳入影响结论成立的共享实现与配置（共享函数、默认值等，逐条声明，不以接口签名为限）。

**结论有效性＝已审范围＋依赖前提**，失效三条——**前两条命中即转「待重新确认」并记 `node_invalidated` 事件**（记录即拦阻，不因现场改动被回退而自动恢复）；**第三条先暂停放行，由 `impact` 结论分流**（判「无关」解除暂停，判「相关」/判不出则转「待重新确认」）：

1. **已审范围出现新提交或工作树变化**（未提交/未跟踪内容）——工作树变化与提交一视同仁；
2. **已声明前提被触及**（提交或工作树变化，含共享实现与配置）——另含计划的 `## 全局约束` 一节变化（走 `全局约束摘要`，不依赖提交）；
3. **无法判定影响的变化**——范围外变化先全局枚举（逐项 path＋内容摘要）、**在判断作出前暂停该节点放行**，再走影响判断；不以"尚未提交"豁免（判断对内容生效，同一改动提交前后摘要一致即可继续复用）。

判定口径统一：以【当前节点版本 × 当前审查阶段】下的**最近一条有效审查结论**为准，必须为 `pass`；其后出现 `fail`、`node_invalidated` 或触及前提的新提交任一即**阻止放行，不得回看更早的 `pass` 抵消**，直到其后再出现有效的复核 `pass` 才恢复。**任务验收要求变化（无代码提交、节点块不变）同样使旧结论失放行资格**（节点版本含归属任务声明字段）；**计划的 `## 全局约束` 一节改写同理**（全局约束摘要随记录保存）。**失效历史挂在谱系根上**：已记录的 `node_invalidated` 按**谱系根**过滤（改名/拆分后的新节点仍承接旧观察——只比节点 ID 会让改名节点看不见已记录的失效）。

**去重身份**：重复记账按**稳定操作 ID** 识别同一次操作的重试（同一操作重试不计轮次）；**不得仅凭（谱系根，已审范围，结论）相同去重**——同一范围在**新契约或新阶段**下的复核通过是与旧记录不同的新证据，必须保存（不同操作 ID 的复核各存一条）。

### 格式 ≥4：影响判断（`impact`）

范围外变化（提交与工作树差异一视同仁）由主控经 **`impact` 命令**提交判断，随事件 `impact_assessed` 持久化：

```bash
# 预期值取自 status 的 pending_changes（被评估结论操作 ID + 变化集摘要，逐项 path＋内容摘要）
python3 scripts/workflow.py impact <slug> <节点> --verdict irrelevant|related|undecidable \
  --basis "<依据>" --expect-review <审查记录操作ID> --expect-changes <变化集摘要> --operation-id <id>
```

- **提交前核对**：引擎先核对预期审查记录仍为该节点当前有效结论、当前待判断变化集摘要与 `--expect-changes` 一致——**一致才写入**；不一致 → **拒绝本次提交、保持阻塞并返回新快照**（不得把判断绑定到主控未评估的内容）。**同操作 ID 重试返回原结果、不重新绑定**。
- **入口协议与 record/review/slice 同款**：`impact` 也过计划门（`require_plan_approval`）——审批失效时同样拒绝，不因"只写事件、不改投影"而例外。
- 结论「无关」→ 绑定并保存依据、机械暂停解除；「相关」或判不出（`undecidable`）→ 转「待重新确认」并定向复核，不默认保留。
- **绑定有效期内重启直接复用**（重放事件即可识别，不重复提问）；**判断对内容生效、不按路径沿用**——同路径内容再次变化即绑定过期、重新暂停；审查记录更替（新结论、新阶段、节点版本变化）同样使绑定过期。
- 没有待判断变化集时 `impact` 拒绝（它不是常规推进步骤）；缺判断或绑定过期 → 暂停放行（展示在 `status` 的 `pending_changes`，含 `impact` 所需的全部预期值）。

### 格式 ≥4：定向复核（`--recheck`）

上游契约变更使已声明依赖它的结论转「待重新确认」时，恢复条件＝针对新契约做**定向复核**：确认结论在新契约下仍成立（影响无法判断则升级为节点审查）。

```bash
# 普通 review 参数照给（verdict/commits/lines/evidence），另附：
# --recheck 的值是**所关联原审查记录的操作 ID**；本次复核自身的重试身份用 --operation-id（两者不同）
python3 scripts/workflow.py review <slug> <节点> --verdict pass|fail --commits <base7>..<head7> \
  --lines "<T1: 结论＋依据；…>" --evidence "<引用>" \
  --recheck <原审查记录的操作ID> [--recheck-mode 主控核对|定向复核] --operation-id <id>
```

- `--recheck-mode` 只认 `主控核对` / `定向复核`（默认 `定向复核`——未显式声明时按独立复核记，不按主控核对记）；只在带 `--recheck` 时有效，普通 review 带它会被拒。
- 关联校验：原操作必须存在且是节点审查记录，且与该节点当前谱系（含继承）一致。
- 复核记为新操作、**不去重**；`pass` 后新结论为准、恢复「已验收」，原结论保留为历史。

### 格式 ≥4：操作 ID 协议（记账操作的稳定身份）

`record` / `review`（含 `--recheck`、`--new-phase`）/ `impact` **必须**携带 `--operation-id`——**未提供即拒绝**；首版**不提供**引擎自动生成分支（自动生成会在"事件已写、未及返回"时丢失 ID，重试必然新开一条）。调用方在**首次执行前生成并保存**该 ID，**重试必须复用**：

- **相同 ID＋相同请求 → 幂等重放**：返回原结果（receipt 随事件持久化，中断后重建再重试仍据此返回）、恢复投影、**不新增事件/轮次/阶段**；重放不重复跑审批门等当前校验（原操作已通过那次校验），也不重复追加账本行（缺则补、有则跳过）。
- **相同 ID＋不同请求 → 拒绝**（"已用于另一次操作"）。
- **真正的新复核用新操作 ID**、经 `--recheck` 另行关联原审查记录——两者是两个不同的 ID。
- 请求身份按各操作的判据计算（`record`：任务集合＋提交范围＋证据；`review`：节点＋结论＋已审范围＋逐任务行（任务序不敏感）＋证据＋复核关联；`impact`：节点＋判定＋依据＋预期值）。`--note` 等运行参数不进请求身份。

### 审查 prompt 的纪律

审查者 prompt 里**禁止**出现这些：

- "不要报 X"、"X 不算缺陷"、"最多算 Minor"、"计划就是这么定的"
- 任何形式的"这个我们已经知道了"

出现以上任何一条，就是在**预判 findings**——通常是为了给自己省一轮修复。预判会让审查形同虚设。

正确的做法是把已知情况作为**事实**陈述，让审查者自己判断严重度：

```
## 已知情况（事实，不是让你忽略）
本任务只做 T3 范围内的改动，T4 会处理 X 的边界。
```

### 审查者的两条要求

1. **把实现者的报告当作未经证实的声明**。报告里的"这里按 YAGNI 保持简单"、"故意这样写的"同样是声明——**实现者在给自己的作品打分**。按代码本身判断，陈述的理由不降低问题的严重度。
2. **报问题必须引用触发它的具体代码行**（`文件:行号` + 该行原文）。引不出来就说明没验证过，强制把置信度降到低位、不进入主报告。**不要为了绕过这条而虚报高置信度**——那就是这条规则存在的意义。

审查者不要去爬整个代码库。只为了评估一个**能具体命名**的风险，才看 diff 之外的代码，且每个风险只做一次聚焦检查。

## 修复循环

审查发现 Critical / Important 问题时：

| 轮次 | 做法 | 理由 |
|---|---|---|
| 1-3 | **resume 原实现者** | 它的上下文还 intact：知道任务、知道代码、知道自己的选择 |
| 4-5 | **换 fresh 实现者 + 升一档模型** | 连过三轮的循环说明它看不见自己的问题，需要新眼睛加能力提升 |
| 5 轮后 | **控制器裁决**（park 或裁定） | 封顶 |

每轮 = 一次修复派发 + 一次**限定范围**的重审（只看修复涉及的部分，不重跑全量审查）。

**不要提前裁决来终止循环。** 提前裁决只是"预判"换了个名字。

**控制器绝不自己修代码。** 控制器改代码会让"写"和"审"重新耦合，而且它没有实现者手里的上下文。

### 格式 ≥4：修复分流与两轮上限

格式 ≥4 的修复派发方式不变（resume / 换人 / 控制器裁决照旧），但**轮次预算与重审频率按节点控制**（节点是验收单位）：

**主控验收五项（须同时满足，缺一走独立复核）**：① 原问题与正确结果明确；② 修复不涉及复杂行为或关键契约变化；③ 影响范围清楚且没有扩大；④ 有充分的验证证据；⑤ 主控**实际核对修复 diff、原问题与结果**。"文件未超出节点范围""测试由失败变通过"只是**辅助条件**——复杂状态机、权限、并发等修复即使只改一个文件，也可能需要独立定向复核；**拿不准时走独立复核**。两条路径都**不自动重启全面审查**。

**轮次与封顶**：每个节点最多**两轮**集中修复（主控验收计入，新增问题**不重置轮次**）。超限后停止相关推进，重新分析根因、设计或验证方法。是否换实现者、是否升档由失败原因决定（**不设**"第二轮固定换人升档"的硬规则）；终审原有的独立性与模型要求保留。轮次语义：该【谱系 × 阶段】内的审查记录条数 − 1（首审不计轮，幂等重放不双计）。

**超限（已用 2 轮）后普通 `review` 与 `--recheck` 都被拒绝**，恢复路径不是再修一次，而是：

```bash
# 封顶后的合法恢复＝开启新审查阶段（不是第三轮）
python3 scripts/workflow.py review <slug> <节点> --new-phase --basis "<实质变化>" \
  --confirmation <记录引用> --confirmed-commit <A..B> --operation-id <id>
```

- **实质变化由审查者判断，不由文本检查承担**：根因、设计或验证方法至少一项有证据支撑的改变（**仅补一段说明不构成**）；`--basis` 非空必填，引擎只校验非空。确认引用是**独立审查的确认记录**：本工作流一条 `node_review`/`impact_assessed` 记录的操作 ID（**其事件序须晚于该谱系当前阶段的最后一条 `node_review`**——本阶段自己的审查记录不构成「独立确认」），或 `.workflow/<slug>/reports/` 下（三种写法皆可：仓内相对路径 / `reports/x.md` / 名字 `x.md`，归一化到同一身份）一份真实存在的报告——**报告形态的路径归一化后不在该目录内一律拒绝**（`..` 逃逸、绝对路径、兄弟目录、仓外路径都不接受）。
- **影响面重评**：触及任务范围、验收或设计判断时回填计划并**重过受影响的审批门**——方案正文变化时方案门同样失效（引擎按内容指纹拒绝放行）、只改计划则重过计划门；**原问题清单连续追踪、编号接续**。
- **引擎按六项机械校验**：① 确认引用存在且属于该谱系（记录形态须属白名单且所载阶段==当前阶段；报告形态校验存在性与路径＋摘要，是否属该谱系由审查者判断）；② **一次性**——未被此前任何 `review_phase` 引用过（不得换个操作 ID 重复重置预算；报告按路径＋摘要，同路径内容变了＝新凭据）；③ 所确认版本 `<A>..<B>` 存在、A 为 B 祖先、B 在 HEAD 历史里，**且该谱系至少有一条非空已审范围**（全部 `HEAD..HEAD` 时第三项会空转——显式拒绝），其后该谱系范围（已审文件集）无未纳入确认的新变更；④ **阶段衔接**——新阶段号＝该谱系当前阶段＋1（引擎推导并写入事件）、既往 `review_phase` 序列连续（1..k）；⑤ **已封顶门槛**——该谱系×当前阶段的轮次必须已用尽（`≥ 2`），未到封顶时继续常规修复轮次（防借分段开阶段无限重置预算）；⑥ **确认时序**——记录形态的确认（含最后一条本阶段审查记录）必须晚于该谱系当前阶段的最后一条 `node_review`，等于或早于即拒绝。
- **新阶段＝未验收**：成员任务写回「已实现」（不退回待实现），重新送审通过后才映射 `complete`；跨节点依赖在新阶段通过前不释放。**轮次在新阶段重新计两轮，总账保留**（"阶段 1：两轮用尽 → 新阶段：…"）。
- `--new-phase` 与普通 review 参数**互斥**（`--verdict`/`--commits`/`--lines`/`--evidence`/`--premises`/`--recheck` 任一同时出现即拒绝）；新阶段内的审查另起一次普通 review（或 `--recheck`）。

## 裁决不停机

遇到需要拍板的事，**控制器自己定，然后记账**：

```
python3 scripts/workflow.py record <slug> <任务> --note "<决定> — <理由> — <错的代价>"
```

不要停下来问"要不要继续"。只有四类事必须停：

1. 不可逆或破坏性操作（删数据、force push、改历史）
2. 安全敏感动作（涉及密钥、权限、外部系统的凭据）
3. 工作区之外的副作用（merge / push / 发布 / 改别人的仓库）
4. 计划坏到"每条路都是猜"的程度

收尾时把所有裁决行汇总给用户并保留历史。**裁决不能只存在于不入库的状态记录；涉及设计的结论须另行归位。**

## 收敛判据

审查 → 修复 → 重审，**重复到某一整轮零修复为止**，才算这个任务通过。上限 3 轮整体循环；第 3 轮还在产生修复就停下，报告哪些问题反复出现。

```bash
# 单个任务的收敛：verdict 为 clean 才算过
python3 scripts/workflow.py record <slug> T3 --commits a..b --verdict clean
```

## 整体终审

所有任务都通过逐任务审查之后、进入 V 轮之前，做**一次覆盖整段改动范围的终审**。

**格式 ≥4：终审并入最后一个节点。** 不另开一轮——由计划里**兼任终审**的那个节点承担（恰一个，且不得为其它节点上游）。启动条件：**其它节点已验收**、全部实现完成、交付文档已就绪。最后节点的审查者保持独立，读取**从工作流基线到当前版本的完整改动**（含首次修改）。同一次审查承担两部分职责：

- **验收最后节点**（逐任务行＋节点整体结论，与其它节点同款）；
- **整体检查**：整个交付是否满足目标、决策与全局约束，跨节点契约是否一致，后续修改是否削弱前面的保证，文档是否与实现一致。

已审内容可以复用已有结论，深入检查集中到新改动、集成影响与具体疑点；但**整体需求覆盖仍须逐项核对**（范围缩减检测不可豁免）。两部分都通过，最后节点才验收；随后执行最终验证与收尾。

**它和逐任务审查解决的不是同一类问题。** 逐任务审查看的是"这个任务做对了吗"；终审看的是"这些任务合起来是一个正确、自洽的整体吗"。只有终审能发现：

- 两个任务用不同方式解决了同一个问题（各自都"对"，但合起来不一致）
- 后一个任务悄悄削弱了前一个任务建立的保证
- 跨任务接口的理解有偏差（各自按自己的理解实现了"同一个"契约）
- 整体与最初的设计/决策表不符——尤其**范围缩减**：说好要做的，被拆散到各任务后没人真正做

### 派发规则

| 项 | 要求 |
|---|---|
| 范围 | 从工作流第一个提交到当前 HEAD 的**完整 diff**，不是单任务 |
| 模型 | **当前可用的最强模型**——这是唯一一处刻意升档的地方 |
| 审查者 | 必须**没有参与过任何实现、也没做过任务级审查**的独立 subagent |
| 产出 | 明确的 `Ready to merge: Yes / No` + Critical / Important / Minor 分级问题列表 |
| 输入 | diff + 计划的决策表 + 全局约束 + **设计文档**。前两样必须给它——终审要对照"说好要做的"逐条核，这是范围缩减检测的唯一机会 |
| 额外产出 | **文档与实现不符的清单**（见下），与代码问题同一份报告 |

**终审同时是"文档与实现对齐"这一波。** 把它挂在这里而不是单开一轮，是因为终审本来就拿着完整 diff 和设计文档——对照是顺手的事，成本最低：

1. 让终审者逐节核对设计文档：**文档里写了但代码没做到**的（失实陈述）、**代码做了但文档没写**的（漏记）
2. 失实陈述按严重度报：影响读者判断的算 Important，措辞级的小瑕算 Minor
3. **`实际交付` 必须在这一波补成真的**：交付物清单（文件/接口/表/脚本/文档）+ 与计划的偏离及原因 + 遗留项。起草时写的「无（尚未实现…）」留到收尾会让 `close` 直接拒绝
4. **实现偏离了文档里的决策**（不是文档写错，是实现改了口径）→ 单独一栏报出来，逐条裁定：改实现 / 改文档并在「决策摘要」说明口径为什么变 / 记进「已知限制」。**不要默认改文档迁就实现**——那等于抹掉这次偏离
5. 修复波次一并处理文档问题——**通常只需重写文档，不需要动代码**
6. 改完文档后重跑 `verify`（指纹要重新绑）

历史上这一波抓出的全是真问题：一次真实回写里，终审后的两轮修订改掉了 **4 处与代码不符的陈述**（接口签名、幂等语义、归属描述、id 写错）和 2 处超出可验证范围的断言。**这些 `grep` 级验收一个都抓不到**——所以必须靠人/模型逐节比对，不要以为"验收命令通过"就够了。

### 决策上浮（与对齐同一波）

做对齐时顺手做一件事：**把这一路产生的判断从报告和账本里捞出来，写进设计文档的「决策摘要」。**

按上文「报告只装证据，不装判断」那张表归位：执行期新增的技术选择与边界裁定 → 设计文档（编号接着 `D-NN`）；改变了范围/验收的 → 回填计划决策表并重新走计划门；纯运行时操作取舍 → 留账本裁决区。

**这一步不做，判断就只留在不入库的状态记录，长期设计视图缺失依据。** 判据很简单：**如果这个工作流明天被删掉，哪些结论是你希望六个月后还能读到的？** 那些就是必须上浮的。

### 终审 prompt 要点

```
<全分支 diff 或告诉它怎么取>

## 你要判断的三件事
1. 这段改动作为整体是否自洽、是否满足计划的目标与全局约束
2. 是否满足决策表里的每一条（逐条核对，漏掉的按 Critical 报）
3. 逐节核对设计文档：文档里写了但代码没做到的（失实陈述）、代码做了但文档没写的（漏记）、**实现偏离了文档决策的**（单列一栏，不要默认改文档迁就实现）
4. 把「实际交付」这一节补成真的：交付物清单 + 与计划的偏离及原因 + 遗留项

## 报告
- Ready to merge: Yes | No
- 问题按 Critical / Important / Minor 分级，每条必须有 文件:行号 + 该行原文
- 文档问题单独一栏，逐条给「文档第几节 → 与代码如何不符 → 该改成什么」
- 如果发现两个任务之间理解不一致，明确指出是哪两个、各自怎么理解的

## 禁止
不要因为"逐任务审查已经通过了"就降低标准；不要在两个任务做法不一致时假设是故意的；
不要因为文档的验收命令通过了就认定文档没问题——那是 grep，不是核对。
```

### 修复波次

有 Critical 或 Important 时：

- 派**一个**修复 subagent，带**完整的问题清单**去修——不是每个问题一个 fixer（那会产生互相冲突的改法）
- 修完重跑验证，再重跑一次终审确认
- **只有一波修复。** 再来一轮说明问题不在实现，而在计划或设计——停下来回 P 轮重新审视，把裁决记账

### Minor 不进修复循环

逐条裁定并写明"修 / 留作后续 / 不修"，记进账本裁决区。**裁定必须留痕**——"我们决定不修它"和"我们没注意到它"是两件完全不同的事，只有记账能区分。

## 隔离

**派发前记录 base commit**，这样审查者能精确看到"这个任务改了什么"：

```bash
git rev-parse --short HEAD   # 记下来，作为本任务的 BASE
```

任务完成后提交范围就是 `<BASE>..<HEAD>`，写进 `record --commits`。

**审查包用记录下来的 BASE，不要用 `HEAD~1`**——多提交的任务会被 `HEAD~1` 切掉一部分。

工作树隔离（git worktree）是可选增强：改动面大、或需要在执行期间保持主工作树干净时启用。启用时先跑一遍基线测试，**脏基线会让之后每一次失败都变得歧义**。

**格式 ≥4 的失效检测依赖 git**：已审范围与"自 HEAD 起的变化"由 `git diff`/`ls-files` 取数——**非 git 环境整体不生效**（不暂停、不写失效，判定按"无变化可检测"），属容忍边界。检测排除 `.workflow/` 自身状态，与整树指纹同口径。

## 反模式清单

- 让 subagent 读整份 plan.md
- 派发 prompt 里粘贴对话历史
- 子 agent 把完整报告贴回主会话
- 实现者自审，或自己派审查者
- 审查 prompt 里出现"不要报 X"
- 控制器亲自改代码
- **实现者不提交、攒着让控制器最后一起提交**（中断就丢，审查范围也没了）
- **`git add -A` / `git add .` 式提交**（会把工作树里别人的改动卷进来）
- **自动 push / merge / 发布**（工作区之外的副作用，必须用户确认）
- 用 `HEAD~1` 而不是记录下来的 BASE 做审查包
- 并行派发多个实现者
- 停下来问"要不要继续"
- **格式 ≥4 下把"已实现"喊成"完成"**（`complete` 只能由节点 `review` `pass` 映射；`record` 的判词由节点审查承担）
- **只看 `review` 的退出码判断结论**（`fail` 退出码为 0——读 `verdict`/`mapped_status` 字段）
- **在审查 prompt 里替审查者接受"逐任务行数足够"**（每行必须关联验收依据或具体问题）
- **把 `impact` 的判断绑到没核对过的快照上**（必须回传 `--expect-review`/`--expect-changes`，引擎核对一致才写入）
- **封顶后换操作 ID 重开 `--new-phase` 或绕过 `--recheck` 恢复**（确认是一次性凭据；轮次沿谱系累计、不因换节点 ID/拆分/重启清空）
- **把技术判断、裁定、设计选择留在报告或账本里不上浮**（状态记录虽保留，但不进入版本库）
- **终审时只核代码不核设计文档**（`grep` 级验收抓不出失实陈述，必须逐节比对）
- 收尾时清理 `reports/`（中断后重启就没了依据）
