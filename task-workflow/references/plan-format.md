# 计划文件格式

计划落在 `<project>/.workflow/<slug>/plan.md`。这个格式是**机器可解析**的：`scripts/workflow.py` 靠它算依赖图、做计划检查、切派发片段。写歪了引擎会报错而不是静默出错。

## 整体骨架

````markdown
# <任务标题>

**Goal**: <一句话目标>
**Slug**: <slug>
**Created**: YYYY-MM-DD
**格式**: 2
**设计文档**: <项目仓库内的路径，或 `无 — <理由>`>

## 验证命令

```
<可执行命令>
```

## 验证覆盖

| 对象 | 验证手段 | 类型 |
|------|---------|------|
| D-01 | `` `tests/test_x.py::test_y` `` | 自动化 |

### 不验证的部分

- <明确不验证什么、为什么；没有就写"无">

## 全局约束

- <每条一行>

## 方案

### 背景与目标

<为什么做 + 做成什么样：问题现状、预期结果、关键约束；已有设计来源时写明承接关系>

### 做法

<怎么实现，2-3 句到一节，随任务规模伸缩；不写文件清单>

### 备选与取舍

<考虑过的其他做法，以及为什么没选；只有一种做法时写"无备选"并给理由>

### 明确不做

<这次范围以外的事。范围边界是四类敏感决策之一，用户要在这里看到它>

## 决策

| ID | 决策 | 来源 | 理由 |
|----|------|------|------|
| D-01 | <决定了什么> | <用户 / agent> | <为什么> |

## 阶段

### Phase 1: <阶段名>

**Checkpoint**: <本阶段全部完成后可判定的检查点>

#### T1 <任务名>

- **文件**：`create <路径>` / `modify <路径>:<行范围>`
- **依赖**：无
- **并行**：否
- **做法**：<这一步具体做什么：动作 + 关键取值 + 边界/禁止项>
- **接口**：consumes <签名> / produces <签名>
- **预期**：<做完后应观察到什么——可观察的行为或产物>
- **验收**：<用什么证明：命令/检查，可判定>
- **失败信号**：<什么现象表示它没做对>
- **决策**：D-01
- **状态**：pending
````

## 字段规范

### 头部五个 meta

`**Goal**` 一句话说清终态。`**Slug**` 必须与目录名一致。写错 slug 不影响运行，但会让账本防串检查失灵。`**Created**` 建库日期。

`**格式**` 是计划格式版本，`init` 自动写当前版本（`2`）。**本次升级新增的强制项只在格式 2 的计划上生效**（任务的 `做法`/`预期`、方案的 `背景与目标`）——没写这行的计划按格式 1 处理，新要求降为 WARNING，这样升级不会打断正在进行中的工作流。老计划想升级：补上这行并补齐缺的字段，`check` 就会开始强制。

`**设计文档**` 是本工作流的设计记录落在哪，**必填**（写一份路径，或写 `无 — <理由>`）：

```
**设计文档**: docs/agent-runtime/编排内核方案.md
**设计文档**: 无 — 单文件文案改动，没有设计取舍值得单独成文
```

| 写什么 | `check` 怎么处理 |
|---|---|
| 项目仓库内的路径 | 文件必须存在、含十节骨架、非空节、无占位符、`决策摘要` 覆盖全部 `D-NN`——缺任一条报 ERROR |
| `无 — <理由>` | 理由不短于 10 字，否则 ERROR；合格时出一条 WARNING（在计划门上被看见） |
| 什么都不写 | ERROR——设计记录必须有归属，无意识遗漏和第 1 类一样有害 |
| `.workflow/` 下的路径 | ERROR——自忽略目录，收尾后随工作树消失 |

**这四条判据命中任一条就必须写设计文档，不能声明"无"**（判断靠人，机器只查"声明了没有"）：

- 跨模块改动，或引入了新的架构模式
- 新增外部依赖，或数据模型有实质变化
- 涉及安全、性能、迁移复杂度
- 需要先定技术决策才能开工（不定就会各写各的）

骨架、篇幅原则、回写时机、决策摘要的归属规则见 [`design-doc.md`](design-doc.md)。

### `## 验证覆盖`（验证范围必须写出来）

**这一节回答的是"验证覆盖了哪些范围、哪些没覆盖"。** 没有它，覆盖范围是隐式的——只有"跑了个命令，过了"，没人能审查漏了什么。

```markdown
## 验证覆盖

| 对象 | 验证手段 | 类型 |
|------|---------|------|
| D-01 | `tests/test_logging.py::test_level_mapping` | 自动化 |
| D-02 | `tests/test_cli.py::test_verbose_count` | 自动化 |
| 边界：空文件 | 人工：跑 `mytool --verbose empty.txt`，期望无 DEBUG 输出 | 人工 |

### 不验证的部分

- 并发下的日志顺序不验证：本次改动未引入并发路径
- 既有日志调用的位置不变：靠 diff review 覆盖，无自动化测试
```

规则：

| 规则 | 级别 |
|---|---|
| 有决策表就必须有这一节 | ERROR |
| **每条决策都要出现在覆盖表里**（决策 ↔ 验证 双向覆盖） | ERROR |
| `类型` 只能是 `自动化` 或 `人工` | ERROR |
| 标 `人工` 的必须写清具体命令或步骤 | WARNING |
| 必须有 `### 不验证的部分`（真的没有就写"无"） | ERROR |
| 同一对象不要重复出现（重复行会虚增覆盖数） | WARNING |

**为什么必须显式写"不验证的部分"**：不写就只有"验证了什么"，没有"没验证什么"。而**没验证的东西才是风险的所在**。写"无"也是一次主动确认——比留空强。

#### 自动化条目会在 V 轮被核对

标 `自动化` 的条目，V 轮会**真的去检查它声称的产物是否存在**：

| 写法 | V 轮怎么核 |
|---|---|
| `` `tests/test_cli.py::test_verbose_count` `` | 文件存在吗？文件里有 `test_verbose_count` 吗？ |
| `` `tests/test_cli.py` `` | 文件存在吗？ |

**对不上就是覆盖缺口，`verify` 会报出来，`close` 会拒绝收尾。** 这条堵的是"声称有测试但测试根本不存在"——那等于什么都没验证。

真有东西测不了，就把它放进「不验证的部分」并说明理由。**诚实地说"这个没验证"是被允许的；声称验证了但拿不出东西不是。**

### `## 验证命令`

V 轮执行的命令，写在一个代码块里。**这是整个工作流"完成"定义的唯一来源。**

- 好：`python3 -m unittest discover -q`、`npm test`、`cargo test`
- 坏：`跑一下测试`（不是命令）、`手动检查`（无法执行）
- 真的没有可自动化验证的（纯文档、纯探索任务）：写 `未声明`，V 轮会要求人工逐项确认，**不会**默认判通过

### `## 方案`（第一道审阅门的对象）

**四段**，**在写任务之前**完成，单独呈现给用户审阅：

| 段 | 写什么 | 反例 |
|---|---|---|
| **背景与目标** | 为什么做 + 做成什么样：问题现状（现在是什么样、不改会怎样）、预期结果（做完后谁看到什么不同）、关键约束。**已有设计来源时在这里写明承接关系**：源路径 + 继承它的哪些结论 + 本次增量/修正了什么 | 只写"要加个 --dry-run"不说为什么；或已有方案还从零重写一份薄的（该做的是承接 + 补缺口） |
| **做法** | 怎么实现。2-3 句到一节，随任务规模伸缩 | 写成一堆文件清单（那是任务的事）；重复"背景与目标"里的动机（动机只在背景节写） |
| **备选与取舍** | 考虑过的其他做法 + 为什么没选 | 只写"无备选"不给理由（真的没得选时，说明为什么没得选） |
| **明确不做** | 这次范围以外的事 | 留空——范围边界是四类敏感决策之一，用户必须在这里看到它 |

**背景与目标这一节是"为什么"的唯一归属**：做法节只写"怎么做"，设计文档的「做法」也不重复动机。三处（方案节 / 设计文档 / 代码注释）各写各的，重复的部分改成指针（"见 `docs/x.md` §1"）。

方案与计划的**篇幅都随任务规模伸缩**（小改动 2-3 句话就够），但**两道审阅门本身不因任务小而省略**。省的是字数，不是门。

方案的审批绑定 `## 方案` 这一段的内容指纹：方案被改写后，方案审批会失效，必须重新呈现。计划的审批绑定整份计划（**状态字段除外**——状态每次执行都会变，纳入哈希会让正常执行把自己刚拿到的审批作废）。

#### 已有设计来源要先承接，不要从零重写

本次改动如果已有设计依据（用户给的文档、项目 `docs/` 下的既有方案、前一个工作流留下的设计文档），**先读再写**：

1. **列清单**：把相关的既有文档列出来（用户指定的优先）。判断依据是"它讲的是不是同一个模块/同一件事"，不是文件名像不像
2. **过滤读**：先只看目录、决策摘要、小节标题——别一上来把整份文档拉进上下文，那会挤掉真正要做的事
3. **决策前完整读**：决定"哪些已经定了、哪些要改"之前，把相关小节**完整读一遍**。只读摘要会漏掉约束、边界和已否决的方案，于是把定过的事重新讨论一遍
4. **归位**：已有文档已经回答的（做法/取舍/边界）**不重写**；本次方案只写增量与修正。**术语、字段名、表名、接口名逐字沿用**已有文档的写法，不要另起近义名——近义名会让两份文档看起来在说两件事

**反模式**：明明有一份多轮沟通定下的方案，却从零写一份薄方案——此后没人知道哪份是准的。这一节写进「背景与目标」：承接哪份、继承什么、本次增量是什么。

### `## 全局约束`

每条一行，**逐字写清确切取值**。派发时整段会附在每个任务的片段里，所以每一条都隐含适用于所有任务。

```markdown
- Python 3.8+，只用标准库
- 不引入新的第三方依赖
- 错误信息一律用中文
```

反例：`- 代码要写得好`（无法判定，等于没写）。

**提交契约不必在这里重复**：任务完成即自动提交、不推送，是协议层的默认规则（见 `dispatch-protocol.md`）。项目确有不同约定时，它属于「兼容性影响」这类敏感决策——在 P 轮问过用户，作为一条决策写清。

### `## 决策`（防"说好的事丢了"）

讨论阶段敲定的每个决策给一个编号 `D-01`、`D-02`…，一行一条，并标注**来源**。

**这张表是需求的锚点**：计划检查会验证每个决策至少被一个任务引用；没被任何任务承载的决策会报 ERROR（范围缩减检测）——它会抓住"讨论里说好要做，写计划时悄悄没了"这种失败。

#### 来源列决定"要不要问用户"

| 来源 | 含义 |
|---|---|
| `用户` | 用户明确说过、或你问过并得到答复 |
| `agent` | 你自己决定的 |

**下面四类决策必须标 `用户`**——也就是必须停下来问一次，不能自行决定后只记进表里：

1. **输入容错** —— 遇到非法输入是报错、跳过、还是用默认值？退出码是多少？
2. **输出格式取值** —— 字段名、精度、单位、排序、编码
3. **范围边界** —— 做什么、明确不做什么
4. **兼容性影响** —— 是否改变既有行为、是否破坏已有用法

判据是"**这个选择会直接影响用户看到的行为吗**"——会，就问。

这四类之外的技术细节（怎么分层、用什么数据结构）自行决定并标 `agent` 是正常的，不必事事问。

计划检查会列出所有来源非 `用户` 的决策，让你在门槛处再确认一遍它们确实不属于上面四类。

#### 决策要写到"任务能引用它"的粒度

- 好：`| D-02 | 缺少 --name 时退出码为 2 | 用户 | 与 argparse 默认行为一致 |`
- 坏：`| D-02 | 做好错误处理 |  |`（太泛，任务没法引用）

### `## 阶段` 与 `**Checkpoint**`

阶段把任务分组，每个阶段声明一个 Checkpoint——**本阶段全部任务完成后可判定的检查点**。

```markdown
### Phase 1: 数据层

**Checkpoint**: `python3 -m unittest tests.test_models -q` 退出码 0
```

阶段之间的顺序约束由依赖图表达（后面的任务 `依赖` 前面的任务），Checkpoint 只是给人看的阶段验收。

### 任务块 `#### T<n> <名称>`

ID 必须是 `T` + 数字，不能有别的形式。**每个任务十个字段，缺一个就报错。**

| 字段 | 必填 | 说明 |
|---|---|---|
| 文件 | 建议 | 精确路径。写了路径的条目在 V 轮**必须**用存在性判定，不许标"无法验证" |
| 依赖 | 是 | `无` 或 `T1` / `T1, T2`。引擎据此算 BLOCKED/READY |
| 并行 | 是 | `是` / `否`。标记是否可以与其他任务同时进行（当前实现串行派发，标记只作排序参考） |
| **做法** | **是** | 这一步具体做什么：动作 + 关键取值 + 边界/禁止项。判据见下 |
| 接口 | 是 | `consumes <上游给的签名> / produces <本任务产出的签名>` |
| **预期** | **是** | 做完后应观察到什么——**可观察的行为或产物** |
| 验收 | **是** | 用什么证明：命令/检查，可判定 |
| 失败信号 | **是** | 什么现象表示它没做对 |
| 决策 | 是 | 引用的 `D-NN`，或 `无` |
| 状态 | 是 | `pending` / `in_progress` / `complete` / `blocked` |

#### 为什么 `失败信号` 是必填

**没有失败信号的验收标准等于没写**——"跑通"这种标准在失败时看不出失败。每个验收标准必须配一个可观察的反面：

- 验收：`python3 app.py --name x` 退出码 0 且 stdout 含 x
  失败信号：传 --name 仍报错，**或不传时退出码不是 2**
- 验收：函数返回长度正确的列表
  失败信号：返回空列表，或对空输入抛异常

#### 接口字段的作用

执行者只看得到自己那一个任务的片段，看不到完整的计划。`接口` 字段是它了解邻居任务用什么的唯一渠道。

- 好：`consumes greet(name: str) -> str / produces main() -> int`
- 坏：`consumes 上面的函数 / produces 结果`（执行者不知道名字和类型）

写完之后检查一遍：**后面任务 `consumes` 的名字，必须和前面任务 `produces` 的逐字一致**。

#### `做法` 与 `预期` 的作用

这两个字段补的是同一个洞：**执行者只看得到自己那一个任务，接口字段只给签名，给不了"做什么"和"期望看到什么"**。缺了它们，执行者要么自己发明设计决策，要么把"命令跑过了"当成"做对了"。

| 字段 | 写什么 | 判据 / 反例 |
|---|---|---|
| `做法` | 动作序列 + 关键取值 + 边界与禁止项 | **判据：换一个执行者拿到它，不问问题就能做完吗？**不能就写细。反例："实现 dry-run 支持"（等于没写）；正例："把现有各处写盘调用改为收集后由 `apply_actions(actions, dry_run)` 统一执行；dry_run=True 时只打印 `动作 路径`，不调用任何写盘 API" |
| `预期` | 做完后**可观察**的结果：行为、产物、输出 | 必须是外部可观察的，不是实现细节。反例："函数写好了"、"用了 jose 库"；正例："`--dry-run` 的 stdout 里每个将写入路径出现一次，且 `git status --porcelain` 为空" |

「预期」和「验收」是两件事，不要混：**预期=应该看到什么，验收=用什么命令或检查去证明**。只写验收（"跑 npm test"）会出现"命令过了但结果不是想要的那个"。

## 任务粒度的三条硬线

1. **任务是交付单元，不是计时单位**。一个任务 = **一次派发能做完、有自己的验收、值得一次独立审查**的最小交付单元（一次能跑完它的测试）。**"2-5 分钟"约束的是步骤，不是任务**：任务的 `做法` 里写清步骤（2-8 步，每步一个动作、2-5 分钟）。**"完成"包含提交**——任务做完即提交（提交契约见 SKILL.md 的 E 轮与 `dispatch-protocol.md`），`record` 的提交范围就来自它。
2. **垂直切片，不水平分阶段**。切错的样子：先"DB 阶段"再"API 阶段"再"前端阶段"——端到端反馈被推迟到最后。切对的样子：每个任务同时穿过它需要的层。
3. **单任务不超过 5 个文件修改，计划不超过 8 个任务**。超了 `check` 会警告，应该拆成多个工作流。

**为什么把计时降到步骤**：挂在任务上会两头出错——要么把任务切成半小时一步的碎片（审查面碎掉、派发次数翻倍），要么任务实际远超 5 分钟却不敢写步骤。任务边界该由"独立验收 + 独立审查面"决定，时间只用来判断步骤是不是切得太粗。

## 同型机械改动要合并，不要一文件一任务

**这是最容易被切错的粒度。** 如果要做的是同一种小改动在多个地方重复——改常量、改字段名、同样的调用替换、加同一行日志——**它们是一个任务，不是一个文件一个任务**。

| 切错 | 切对 |
|---|---|
| T1 改 a.py 的常量<br>T2 改 b.py 的常量<br>T3 改 c.py 的常量 | **T1 统一三处常量**<br>（文件：`modify a.py` / `modify b.py` / `modify c.py`） |

判据是**"这次改动需要自己的判断、自己的测试、自己的审查面吗"**：

| 值得单独成一个任务 | 该合并进一个任务 |
|---|---|
| 需要自己写测试 | 同一个一行修复重复在多个文件 |
| 需要自己的判断（设计、取舍） | 改常量、改字段名、加日志 |
| 有自己的审查面（不同关注点） | 机械重复的同型改动 |

**为什么**：每个任务在执行轮是至少两次 subagent 派发（实现者 + 独立审查者）。把三次机械改动拆成三个任务 = 六次派发，而合成一个任务只要两次。**这不是省流程，是省掉纯粹重复的流程**——审查、验证、覆盖审计一样都不少。

注意这**不是**"按体量开快路径"（那条明确不做）：合并只改**执行粒度**，不跳过任何门。审批门、`check`、独立审查、验证覆盖审计、`close` 全部照旧。

计划写完时如果发现已经切细了、不好回头改，执行轮还有一条逃生通道：**同型任务可以合成一批派发**（见 `dispatch-protocol.md` 的"合并派发"）。

## 别忘了文档任务

如果这次改动改变了**用户可见**的东西——命令、选项、输出格式、行为——计划里要有一个更新 README / 用法文档的任务。

漏掉文档**不会让任何测试变红**，所以它只能靠计划兜住。决定不更新时，把它作为一条决策写清理由——"用法未变，无需更新"是完全合理的决策；不写理由才是问题。

## 完整正例

````markdown
# 给 CLI 加 --verbose 输出

**Goal**: 让 `mytool` 支持 `--verbose` 打印每个处理步骤
**Slug**: verbose-flag
**Created**: 2026-09-10
**格式**: 2

## 验证命令

```
python3 -m pytest -q
```

## 验证覆盖

| 对象 | 验证手段 | 类型 |
|------|---------|------|
| D-01 | `tests/test_logging.py::test_level_mapping` | 自动化 |
| D-02 | `tests/test_cli.py::test_verbose_count` | 自动化 |

### 不验证的部分

- 并发下的日志顺序不验证：本次改动未引入并发路径
- 既有日志调用位置不变：靠 diff review 覆盖，无自动化测试

## 全局约束

- Python 3.9+，只用标准库
- 日志一律走 logging，不 print

## 方案

### 背景与目标

**问题现状**：`mytool` 出错时只有一行报错，用户想知道"卡在哪一步"只能改代码加 print，再改回去。

**预期结果**：`mytool -v run` 在 stderr 打印每个处理步骤（读配置、解析、写库），不加 `-v` 时输出与现在完全一致；最多 `-vvv` 三级。

**关键约束**：不引入配置项开关（用一个参数就够了），不改现有日志调用的位置。

### 做法

在 logging 层加一个 `setup_logging(verbosity)` 入口，把 verbosity 映射到 logging 级别；CLI 侧用 argparse 的 `action="count"` 收集 `-v` 次数后传给这个入口。

### 备选与取舍

- 备选一：直接调 `logging.basicConfig(level=...)`。没选，因为它无法在多次调用间安全地改级别，重复调用会叠加 handler 导致日志重复打印。
- 备选二：自己维护一个全局级别变量。没选，重复造轮子，且与既有日志体系割裂。

### 明确不做

- 不做日志文件输出（需求只要求控制台分级）
- 不改动现有日志调用的位置和内容
- 不引入任何配置文件的读取

## 决策

| ID | 决策 | 来源 | 理由 |
|----|------|------|------|
| D-01 | 用 logging 的 DEBUG 级别承载 verbose | 用户 | 与现有日志体系一致，不用新增开关 |
| D-02 | --verbose 可重复出现累加级别，最多三级 | 用户 | 与 kubectl -v 习惯一致，用户不用记新参数 |

## 阶段

### Phase 1: 日志层

**Checkpoint**: `python3 -m pytest tests/test_logging.py -q` 退出码 0

#### T1 建立 logging 配置入口

- **文件**：`create mytool/logging_setup.py` / `create tests/test_logging.py`
- **依赖**：无
- **并行**：否
- **做法**：新增 `setup_logging(verbosity: int) -> None`：先把 verbosity 夹到 0-3，再映射到 logging 级别（0=WARNING、1=INFO、2=DEBUG、3=DEBUG 且带 `%(module)s` 前缀）；用 `logging.getLogger().handlers` 判断是否已配置，已配置时只改 level，**不重复 addHandler**。
- **接口**：consumes 无 / produces `setup_logging(verbosity: int) -> None`
- **预期**：`setup_logging(0)` 后根 logger 级别为 WARNING，`setup_logging(2)` 后为 DEBUG；连续调用两次后 `len(root.handlers)` 不变
- **验收**：`python3 -m pytest tests/test_logging.py -q` 退出码 0
- **失败信号**：verbosity=0 时输出 DEBUG 行，或重复调用会叠加 handler 导致日志重复打印
- **决策**：D-01
- **状态**：pending

#### T2 接入 CLI

- **文件**：`modify mytool/cli.py:12-40`
- **依赖**：T1
- **并行**：否
- **做法**：给 argparse 加 `-v` 参数并设 `action="count", default=0`；在 `main()` 里拿到参数后**第一件事**就是调 `setup_logging(args.verbose)`，再进原有逻辑；不要在各命令函数里重复调它。
- **接口**：consumes `setup_logging(verbosity: int) -> None` / produces 无
- **预期**：`mytool --verbose -v run` 时 stderr 出现 DEBUG 行；`mytool run` 时没有 DEBUG 行
- **验收**：`mytool --verbose -v run` 的 stderr 含 DEBUG，不加参数时不含
- **失败信号**：`-v` 被重复计数时抛错，或不加参数仍打印 DEBUG
- **决策**：D-01, D-02
- **状态**：pending
````

## 反例对照

| 写法 | 问题 | 引擎反应 |
|---|---|---|
| `### T1 任务` | 任务头必须是 `####` | 该任务不被识别，等于没有 |
| `- **验收**：TODO` | 占位符 | ERROR |
| 缺 `失败信号` 字段 | 无法判定失败 | ERROR |
| 缺 `做法` / `预期` 字段（格式 2） | 执行者不知道做什么、也不知道做完该看到什么 | ERROR（格式 1 的老计划降为 WARNING） |
| 方案缺 `### 背景与目标`（格式 2） | 读者不知道这个改动为什么做 | ERROR（格式 1 的老计划降为 WARNING） |
| `- **依赖**：T1、T2` | 全角顿号能识别，但混写 `T1, 2` 不行 | `2` 不是任务 ID，被忽略 |
| 决策 D-03 没有任务引用 | 范围缩减 | ERROR |
| `- **状态**：完成` | 状态值必须是英文枚举 | ERROR |
| 9 个任务 | 超出单工作流上限 | WARNING |
| 决策表缺 `来源` 列 | 无法区分"用户定的"和"agent 自己定的" | WARNING 列出所有来源非 `用户` 的决策 |
| 改了用户可见行为但没文档任务 | 测试不会红，只能靠计划兜 | 无自动检测——靠 P 轮自检 |

## 真正可推迟的未知：合法写法

留占位符（`TODO` / 待补 / 待定）是**禁止**的：它把"没想清楚"混进了一份"已批准"的文档里，`check` 会直接拦。

但**确实存在可以推迟的未知**，它们有合法写法：

```markdown
**未知**：上游 429 时的退避上限取多少 — 待压测出基线后再定 — 不影响接口形状与任务拆分
```

判据一句话（学自 OpenSpec）：**它会改变做法、接口、验收标准或任务拆分吗？**

- **会** → 必须现在解决。**去问用户**，不要猜着写、也不要留成未知——那会在执行轮变成返工
- **不会** → 按上面格式写清"是什么 / 待什么条件确定 / 不影响什么"，三样缺一不可。没有第三样（不影响什么），它多半是"我还没想"，不是"可以推迟"

这条和「不验证的部分」是同一个思路：**给诚实的省略留出口，同时把省略显式化**。

## 改计划的原则

- **改的是同一个意图**（发现边界情况、方案微调、范围收窄）→ 直接改现有 plan.md，改完重跑 `check`，**并且重新审批**（内容变了，旧审批已自动失效）
- **意图变了**（"加个开关"变成"重做配置系统"）→ 收尾当前工作流，新开一个 slug
- 改完计划后**必须重跑 `workflow.py check`**，否则可能把新引入的洞带进执行轮
- 改完计划后**必须重新走审阅门**：`slice` 会因为审批失效而拒绝派发，这是有意设计的——改了用户批准过的东西，就该让用户再看一眼

## 两道审阅门的位置

```
需求 → [承接研究 + 澄清：一次一个问题] → 写 ## 方案 → 🚧 方案门 ──→ 起草设计文档 → 写任务与决策 → check
                                          approve 方案                                              ↓
                                    🚧 计划门 ← 独立语义审查（目标倒推：覆盖/正确/一致）←──────────┘
                                    approve 计划
                                          ↓
                    E 轮执行 → 终审（回写设计文档 + 决策上浮）→ V 轮 verify → close
```

**为什么计划和设计文档之间多一道语义审查**：`check` 是机械的——它只能证明"每个决策编号都被某个任务引用了""字段都填了"。它能证明的东西不等于计划是对的：一条决策被引用，不等于它承诺的行为都有任务承载（`D-08 分析结果确认后落库` 可以被 T5 引用，而 T5 的工具清单里根本没有"保存分析结果"这个动作）。这类缺口只有**从目标倒推读一遍**才能发现，所以放在计划和设计文档都齐了、还没呈给用户之前。审查清单与 prompt 见 [`plan-review.md`](plan-review.md)。

设计文档在**方案门之后**起草（此时才有可依据的、已批准的方案），在**计划门之前**必须存在——它和任务、决策表同属"计划门要审的东西"。回写则必须在 **`verify` 之前**完成，否则工作树指纹失配、`close` 会拒绝收尾。

两道门都用 `approve` 子命令记账，依据是**用户的原话**：

```bash
workflow.py approve <slug> 方案 --by "用户说：这个做法可以，往下写"
workflow.py approve <slug> 计划 --by "用户说：计划没问题，开始吧"
```

拒绝规则：方案为空或含 TODO 时不能批方案；计划有 ERROR 时不能批计划；不带 `--by` 一律拒绝——**没有依据的审批等于自己给自己盖章**。

# bug 修复的格式差异

bug 工作流用 `workflow.py init <slug> --bug` 创建，头部多一行 `**类型**: bug`，并多两节、一条硬规则。

## 为什么 bug 免门

bug 的"需求"是一个**症状**而不是规格——没有可审的"方案"，因为要做的事已经被症状决定了大半。所以 bug 工作流免两道审批门。

补偿控制是三项强制，它们替代门起的作用。

**`### 背景与目标` 对 bug 不是必填**：它的"为什么做"已经由 `## 复现` + `## 根因` 两节回答了（症状是什么、为什么会这样）。`check` 对 bug 路径不查这一节，`init` 也不会生成它。任务的 `做法`/`预期`/`验收`/`失败信号` 照旧必填——修复同样要知道"做什么、做完看到什么、怎么证明、失败长什么样"。

## `## 复现`

```markdown
## 复现

`python3 -c "import m; m.parse('')"` → 抛 ValueError: invalid literal for int()
```

**必须是可复现的最小步骤或命令。** 修之前先确认它确实失败——没有可复现的失败，就无法证明修好了（`check` 会拒空节）。

## `## 根因`

```markdown
## 根因

`int('')` 抛 ValueError，`parse` 未处理空输入。上游调用方会把空串传进来。
```

**说清为什么错。** 说不清就只是在让症状消失，不是在修复——那种"修法"换个输入就复现。`check` 拒绝空节。

## 回归测试（硬要求）

验证覆盖表里**必须有一行明确标为回归测试**：

```markdown
| 对象 | 验证手段 | 类型 |
|------|---------|------|
| 回归测试（捕获本 bug） | `tests/test_parse.py::test_empty_returns_none` | 自动化 |
| D-01 | `tests/test_parse.py::test_empty_returns_none` | 自动化 |
```

`check` 会找 `对象` 或 `手段` 里含"回归"的行，没有就报 ERROR。

**为什么是硬要求**：修复不带回归测试，同一个 bug 会回来——而且回来时没人记得修过。这条是从 gstack 的 `/qa` 学的（它规定每个修复必须生成回归测试）。

项目确实没有测试框架时，把它记成一条决策说明理由，并写进「不验证的部分」——但那是退让，不是默认。

## bug 工作流的验证特别要求

| 要求 | 理由 |
|---|---|
| 复现用例必须从**失败**变为通过 | 这是"修好了"的定义 |
| **全量测试不回归** | 修复最容易打破别处，这一步不能省 |
| 特别检查是否改动了**共享函数或默认值** | bug 修复最常伤到的地方 |
| **不夹带无关改动** | 顺手重构是 bug 修复最常见的坏味道；要重构就单独开工作流 |

## bug 路径的升级条件

任一命中就该改走完整工作流（此时它实际是"探索 + 改造"，不是"修复"）：

- 复现不出来，或根因不明
- 修复需要改 3 处以上，或跨模块
- 涉及数据正确性、安全、并发
- 修着修着发现要改的是一段设计

## bug 工作流的计划骨架

````markdown
# <症状描述>

**Goal**: <一句话：让 X 不再 Y>
**Slug**: <slug>
**类型**: bug

## 复现
## 根因
## 方案（照常写——bug 也值得说清怎么修）
## 决策
## 验证覆盖（必须含回归测试那一行）
## 阶段
````
