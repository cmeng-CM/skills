# 计划文件格式

计划落在 `<project>/.workflow/<slug>/plan.md`。这个格式是**机器可解析**的：`scripts/workflow.py` 靠它算依赖图、做计划检查、切派发片段。写歪了引擎会报错而不是静默出错。

## 整体骨架

````markdown
# <任务标题>

**Goal**: <一句话目标>
**Slug**: <slug>
**Created**: YYYY-MM-DD
**格式**: 3
**审批模式**: gated | execution
**审批模式依据**: <为什么这次有/没有新的用户判断>
**设计文档**: <项目仓库内的路径，或 `无 — <理由>`>

## 验证命令

```
<可执行命令>
```

## 验证覆盖

| 对象 | 验证手段 | 类型 |
|------|---------|------|
| D-01 | `` `tests/test_x.py::test_y` `` | 自动化 |

### 不验证的部分

- <明确不验证什么、为什么；没有就写"无">

## 全局约束

- <每条一行>

## 方案

### 背景与目标

<为什么做 + 做成什么样：问题现状、预期结果、关键约束；已有设计来源时写明承接关系>

### 做法

<有设计文档：一行指针 + 本次特有的实现机制。无设计文档：怎么实现，2-3 句到一节>

### 备选与取舍

<有设计文档：一行指针。无设计文档：考虑过的其他做法与为什么没选；只有一种时写"无备选"并给理由>

### 明确不做

<有设计文档：一行指针。无设计文档：这次范围以外的事>

## 决策

| ID | 决策 | 来源 | 理由 |
|----|------|------|------|
| D-01 | <决定了什么> | <用户 / agent> | <为什么> |

## 阶段

### Phase 1: <阶段名>

**Checkpoint**: <本阶段全部完成后可判定的检查点>

#### T1 <任务名>

- **文件**：`create <路径>` / `modify <路径>:<行范围>`
- **依赖**：无
- **并行**：否
- **做法**：<这一步具体做什么：动作 + 关键取值 + 边界/禁止项>
- **接口**：consumes <签名> / produces <签名>
- **预期**：<做完后应观察到什么——可观察的行为或产物>
- **验收**：<用什么证明：命令/检查，可判定>
- **失败信号**：<什么现象表示它没做对>
- **决策**：D-01
- **状态**：pending
````

## 字段规范

### 头部 meta

`**Goal**` 一句话说清终态。`**Slug**` 必须与目录名一致。写错 slug 不影响运行，但会让账本防串检查失灵。`**Created**` 建库日期。新目标通过 `init --from <原 slug>` 创建时还会记录 `**来源工作流**`，只用于关联，不继承原周期验收。

`**审批模式**` 只有两个取值：`gated`（默认，方案门与计划门都要按规则执行）或 `execution`（已明确规格、范围和验收，不在这两处停，但仍走全部计划、审查、验证和收尾控制）。老计划没有这一行时按 `gated` 处理，不能因为升级 skill 就把进行中的工作流变成无门路径。

`**审批模式依据**` 是选择 `execution` 时的可回溯理由：要写清这次工作的规格/范围/验收来自哪里，以及为什么没有新增用户判断。`gated` 也保留这行，写「进入 gated 路径，待方案与计划审阅」即可。它不是用户审批记录，不能写成 agent 自己批准。

`**格式**` 是计划格式版本，`init` 自动写当前版本（`3`）。逐档只加不删，计划结构按旧档规则继续；证据门禁和历史 close 兼容见 [verification.md](verification.md)：

| 档 | 新增的强制项 |
|---|---|
| 1（默认，不写这行即按此处理） | 基础字段。升级前建的计划不该被新校验打断，所以**没写这行的按 1 处理，新要求降为 WARNING** |
| 2 | 任务的 `做法`/`预期` 两个字段；方案的 `背景与目标` 一节 |
| 3 | **方案只写一遍**：声明了设计文档时，`## 方案` 退化为承接 + 增量 + 指针，方案审批的指纹绑设计文档的「一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做」五节；声明「无」时方案四段照旧写在计划里 |
| 4 | **审查节点制**（首版非默认，见下）：`## 审查节点` 段与节点校验、任务状态收窄为 `pending`/`implemented`/`complete`、两态记账（`record` 记「已实现」，节点 `review` 通过后成员任务才映射 `complete`）与事件权威源（`events.jsonl`） |

**格式 4 首版非默认**：`init` 仍写格式 3，默认路径维持既有行为（逐任务审查）；格式 4 仅限**显式选择**（开发测试与受控试用），效果评估通过并获明确确认后才切换默认为格式 4。旧格式（≤3）不因引擎升级改变行为——格式 4 的新解析与新校验一律挂在 `is_v4` 分支上。

老计划想升级：把 `**格式**` 的数字改大，并补齐对应档要求的字段，`check` 就会开始强制。**改格式号本身会让已审批的指纹失效**（方案与计划都要重新审批），所以别在审批之后随手改。

`**设计文档**` 是本工作流的设计记录落在哪，**必填**（写一份路径，或写 `无 — <理由>`）：

```
**设计文档**: docs/<模块>方案.md
**设计文档**: 无 — 单文件文案改动，没有设计取舍值得单独成文
```

| 写什么 | `check` 怎么处理 |
|---|---|
| 项目仓库内的路径 | 文件必须存在、含十节骨架、非空节、无占位符、`决策摘要` 覆盖全部 `D-NN`——缺任一条报 ERROR |
| `无 — <理由>` | 理由不短于 10 字，否则 ERROR；合格时出一条 WARNING（在计划门上被看见） |
| 什么都不写 | ERROR——设计记录必须有归属，无意识遗漏和第 1 类一样有害 |
| `.workflow/` 下的路径 | ERROR——自忽略的过程记录不能替代进版本库的设计产物 |

**这四条判据命中任一条就必须写设计文档，不能声明"无"**（判断靠人，机器只查"声明了没有"）：

- 跨模块改动，或引入了新的架构模式
- 新增外部依赖，或数据模型有实质变化
- 涉及安全、性能、迁移复杂度
- 需要先定技术决策才能开工（不定就会各写各的）

骨架、篇幅原则、回写时机、决策摘要的归属规则见 [`design-doc.md`](design-doc.md)。

**声明了路径时（格式 3 起），`## 方案` 与设计文档是一份内容的两处安排**：正文（一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做）归设计文档，计划里只留承接关系、本次增量、以及指向文档的指针。**方案门审的就是设计文档那五节**，审批指纹也绑在它们上面——所以起草要排在方案门之前（见 `design-doc.md`「什么时候写」）。

反过来，声明「无」时没有可承接的文档，方案四段就写在计划的 `## 方案` 一节，指纹也绑在计划上。两条路都不会出现"同一份方案写两遍"。

### execution 模式：不走审批门，但走完整工作流

`execution` 不是按文件数、任务数或“看起来简单”开的快路径。只有以下条件都满足时才能选它：

- 用户已经明确了目标、范围、实现规则和验收结果；
- 本次没有新增方案、取舍、兼容性、数据、安全、性能或用户可见契约判断；
- 执行者按既定规格落地，不需要替用户在多个合理方案中选一个；
- 计划仍然经过 `check` 和独立语义审查，所有任务仍有做法/预期/验收/失败信号。

`execution` 只跳过方案/计划的人工等待和 `approve` 指纹门，不跳过：计划质量检查、验证覆盖、逐任务独立审查、阶段 Checkpoint、整体终审、`verify`、`close`。如果判断不了是否满足条件，使用 `gated`。

**升级为 gated**：执行中发现要改变方案、范围、任务验收、公开接口/默认行为、数据或安全边界，或发现原规格存在多个合理解释，立即停止相关派发，运行：

```bash
$W gate <slug> --reason "<新增判断及其影响>"
```

`gate` 会把计划和账本的审批模式改为 `gated`，把升级原因写入账本；之后 `slice`/`record` 会重新要求方案门和计划门。只呈现这次变化的 diff，不重念已经锁定的内容。不能手改字段冒充升级，也不能继续用 execution 模式掩盖新判断。

### `## 验证覆盖`（验证范围必须写出来）

这一节声明验收对象、验证手段与必需性；每条决策仍要对应验收，不能只说“跑了命令”。原三列表兼容且默认必需，新增列按需使用：

```markdown
## 验证覆盖

| ID | 对象 | 验证手段 | 类型 | 必需性 | 证据 |
|----|------|---------|------|--------|------|
| A1 | D-01 | 执行日志级别测试，预期映射与边界断言通过 | 自动化 | 必需 | `tests/test_logging.py::test_level_mapping` |
| A2 | D-02 | 打开设置页，切换选项后重启，预期保存且正确回显 | 人工 | 必需 | |
| A3 | 边界：空文件 | 运行 `mytool --verbose empty.txt`，预期无 DEBUG 输出 | 人工 | 可选 | |

### 不验证的部分

- 跨进程日志顺序：本次未引入该路径，范围已明确
```

| 字段/规则 | 契约 |
|---|---|
| 对象 | 每条决策都要出现于覆盖对象；`check` 检查决策引用 |
| ID | 可选；不写时以唯一对象名寻址。confirm/waive/evidence 的 `--item` 使用此身份；重复身份拒绝 |
| 验证手段 | 完整步骤与预期，属于验收要求；改此文字会使旧证据失效，不能把改要求称作修引用 |
| 类型 | `自动化` 或 `人工`；人工要写清步骤和可判定预期 |
| 必需性 | 可选列（也接受列名 `必需`）；不写默认必需。建议只写 `必需/可选`；`可选/optional/否/false/no` 视为可选，其它值保守视为必需 |
| 证据 | 可选的独立引用列；为空或不写时从手段中取引用。只修该列不使原验收指纹失效，但新引用需 evidence 关联并记录摘要才能收尾 |
| 不验证的部分 | 必须显式写，没有则写“无”。已确认为必验的要求不能擅自移入此处 |

同一对象有不同验收可以使用不同稳定 ID；重复对象仍可能有 `check` 警告，应核实没有虚增覆盖。可选只适用于事先明确的非阻塞反馈，不能验不过再自行改可选。用户明确取消具体要求时记录逐项豁免及其理由、原答复与来源；人工确认和豁免都不能覆盖命令失败。

覆盖表支持的列名只有 `对象`、`验证手段`、`类型`、`ID`、`必需性`（或 `必需`）、`证据`，顺序可变；前三列必须存在，列名不得重复，`必需性` 与 `必需` 不得并存。每行必须有完整的外侧 `|`，数据行和完整分隔行的列数须与表头相同。未知列保留原文诊断为“不支持/无法解释”，不能自行当成备注忽略。只有每个单元格都由横线及可选对齐冒号组成才算分隔行；`--` 开头的对象照常验收。无表头旧格式只支持三列（对象/手段/类型，默认必需）或四列（末列为必需性）。多列、缺列或表头不明属于结构错误，`check` 与活跃验收入口拒绝；不能猜该项是否可选或已豁免。旧 closed 的状态查询与幂等 close 仍可读取历史，附结构诊断，不改写记录。

“不验证”小节只排除其标题范围：更深的 `#### 排除依据` 仍在排除范围，同级 `### 补充验证`、`### 必验分组` 或后续 `## 验证覆盖…` 恢复覆盖解析。排除说明表不计为验收行，但全部内容参与验收绑定；不能把条件列误当成独立证据列。验收指纹复用实际覆盖行/列身份，已接受的行首空白表也允许纯证据修正而不失效。

自动化引用支持可读取文件和可选符号，如 `tests/test_cli.py::ClassName::test_verbose`。引擎做文件/符号存在性检查并记录内容摘要；符号检查不等于证明测试实际覆盖行为，仍需要独立审查。目录不能当成一个已摘要的文件。必验缺失或 unknown 都阻止 close，先核实已有输出与引用，能补证则不重跑。

独立 `证据` 列非空时，整格只能是**一个完整裸路径**（允许路径中有空格），或一个/多个完整反引号引用，如 `` `source.py::test_example` `结果 文件.txt` ``；引用之间可用空白、英文/中文逗号、顿号、英文/中文分号或加号。全部引用都要核对，不能只采纳成功的一部分。混入未包围的残余文本、空反引号、未闭合标记、空路径/符号均为 invalid/unknown，不能用 evidence 掩盖；路径中的反引号、管道分隔符、换行没有转义语法支持。单元格为空时回退到手段。

旧手段允许说明文字围绕反引号引用，但每个显式引用都须完整有效；没有反引号时，整段非空且无空白的 token 按旧裸路径处理（包括纯中文文件名），有空白的说明文字保持 none/unknown，可补真实证据。不会用语言或扩展名猜测含义：无空白的中文说明也会被当成文件路径核对，可改写为明确步骤并用独立证据列消歧；带空格文件名须用反引号或独立列。人工步骤完全不按自动化引用解析。结构有效的可选 unknown/missing 只反馈；必验 unknown/missing 阻塞，具体有效的逐项豁免照旧生效。

具体命令、批量答复逐项登记、完整引用链和旧数据兼容见 [verification.md](verification.md)。

### `## 验证命令`

自动验证契约写在该节的三反引号代码围栏中；围栏外只写说明，不会作为命令执行。管道、多行和 here-doc 空行可以保留，原命令写入结构化验证事件，不依赖 Markdown 表格往返。

- 好：`python3 -m unittest discover -q`、项目已有构建/测试命令。
- 坏：`跑一下测试`、`手动检查`；这类说明不是可执行命令。
- 多步骤命令必须正确传播失败；需要 Bash 管道失败语义时显式用项目支持的 shell/选项，不能靠最后一条成功证明全段通过。
- `verify --command` 可作诊断，但与计划命令不同的结果不能用于收尾；改变验证契约先按计划变更处理。
- 无自动化命令时可写 `未声明/无` 或留空围栏。只有没有尚未豁免的必验自动化项、有明确非空清单且必验人工结论完整时才可能收尾；已存在的失败验证不能靠删命令抹去。bug 工作流仍必须声明命令。

命令成功只是验收的一部分；还须结合必需性、逐项人工结论、双指纹和原输出/引用链完整性。验收指纹保守包含整份计划规范化正文，覆盖 Checkpoint、围栏约束和额外验收说明，仅排除任务状态和独立证据列。

### `## 方案`（第一道审阅门的对象）

**四段**，**在写任务之前**完成，单独呈现给用户审阅：

| 段 | 写什么 | 反例 |
|---|---|---|
| **背景与目标** | 为什么做 + 做成什么样：问题现状（现在是什么样、不改会怎样）、预期结果（做完后谁看到什么不同）、关键约束。**已有设计来源时在这里写明承接关系**：源路径 + 继承它的哪些结论 + 本次增量/修正了什么 | 只写"要加个 --dry-run"不说为什么；或已有方案还从零重写一份薄的（该做的是承接 + 补缺口） |
| **做法** | 怎么实现。2-3 句到一节，随任务规模伸缩 | 写成一堆文件清单（那是任务的事）；重复"背景与目标"里的动机（动机只在背景节写） |
| **备选与取舍** | 考虑过的其他做法 + 为什么没选 | 只写"无备选"不给理由（真的没得选时，说明为什么没得选） |
| **明确不做** | 这次范围以外的事 | 留空——范围边界是四类敏感决策之一，用户必须在这里看到它 |

**四段的正文写在哪，取决于设计文档声明**——同一份方案只写一遍：

| 设计文档声明 | 方案正文位置 | 方案审批的指纹绑在 |
|---|---|---|
| 项目仓库内的路径（格式 3） | **设计文档的对应五节**；计划这一节只写承接关系、本次增量、指针 | 设计文档那五节 |
| `无 — <理由>` | 计划的 `## 方案`（本节四段） | 计划的 `## 方案` |

声明了设计文档时，**起草它要排在方案门之前**——否则方案门没有可审的东西（见 [`design-doc.md`](design-doc.md)「什么时候写」）。

**gated 门呈现的是散文，不是执行细节**：方案门给人看的是"为什么做、做成什么样、取舍、不做什么"；任务的 `做法`/`预期`/`接口`/`验收`/`失败信号` 是写给执行者的逐字指令，既不进方案门的呈现，也不进计划门的呈现（见 `SKILL.md`）。execution 不呈现、不等待这两道人工门，但仍必须完成这些任务字段和独立语义审查。

**背景与目标这一节是"为什么"的唯一归属**：做法节只写"怎么做"，设计文档的「做法」也不重复动机。三处（方案节 / 设计文档 / 代码注释）各写各的，重复的部分改成指针（"见 `docs/x.md` §1"）。

方案与计划的**篇幅都随任务规模伸缩**（小改动 2-3 句话就够）。gated 的审阅门不因任务小而省略；execution 是否无门也不看任务大小，而看规格、范围、规则和验收是否已明确且没有新增用户判断。

**方案的审批绑定方案正文的内容指纹**（位置见上表）：方案被改写后，方案审批会失效，必须重新呈现。计划的审批绑定整份计划，只有解析器通过 `Task.field_lines["状态"]` 确认的真实任务状态行替换为固定占位；合法的单/双空格等任务记账不会使后续任务误需重批。全局约束、额外验收及围栏内的同名状态文字仍按正文绑定；重新 verify 不能代替已失效的计划审批。两者分开：批准方案之后再写任务、补设计文档的其余小节，都不会把方案审批弄失效。

计划指纹仍为 16 位，保留默认读取换行行为和标准旧状态占位结果（英文/中文冒号均兼容），不删除状态整行或改其它正文。标准旧审批继续可用，历史 closed 不重算。有旧全局替换歧义的布局内部另作区分，避免非任务要求后来写成旧占位文字 `- **状态**：<忽略>` 时碰巧沿用旧授权；不使用危险旧算法兜底，不自动补写审批。特殊旧审批先核对原获批文本，能证明相同则沿用原答复通过已有 approve 登记并保留旧行，不能证明才重新呈现。

#### 已有设计来源要先承接，不要从零重写

本次改动如果已有设计依据（用户给的文档、项目 `docs/` 下的既有方案、前一个工作流留下的设计文档），**先读再写**：

1. **列清单**：把相关的既有文档列出来（用户指定的优先）。判断依据是"它讲的是不是同一个模块/同一件事"，不是文件名像不像
2. **过滤读**：先只看目录、决策摘要、小节标题——别一上来把整份文档拉进上下文，那会挤掉真正要做的事
3. **决策前完整读**：决定"哪些已经定了、哪些要改"之前，把相关小节**完整读一遍**。只读摘要会漏掉约束、边界和已否决的方案，于是把定过的事重新讨论一遍
4. **归位**：已有文档已经回答的（做法/取舍/边界）**不重写**；本次方案只写增量与修正。**术语、字段名、表名、接口名逐字沿用**已有文档的写法，不要另起近义名——近义名会让两份文档看起来在说两件事

**反模式**：明明有一份多轮沟通定下的方案，却从零写一份薄方案——此后没人知道哪份是准的。这一节写进「背景与目标」：承接哪份、继承什么、本次增量是什么。

### `## 全局约束`

每条一行，**逐字写清确切取值**。派发时整段会附在每个任务的片段里，所以每一条都隐含适用于所有任务。

```markdown
- Python 3.8+，只用标准库
- 不引入新的第三方依赖
- 错误信息一律用中文
```

反例：`- 代码要写得好`（无法判定，等于没写）。

**提交契约不必在这里重复**：任务完成即自动提交、不推送，是协议层的默认规则（见 `dispatch-protocol.md`）。项目确有不同约定时，它属于「兼容性影响」这类敏感决策——在 P 轮问过用户，作为一条决策写清。

### `## 决策`（防"说好的事丢了"）

讨论阶段敲定的每个决策给一个编号 `D-01`、`D-02`…，一行一条，并标注**来源**。

**这张表是需求的锚点**：计划检查会验证每个决策至少被一个任务引用；没被任何任务承载的决策会报 ERROR（范围缩减检测）——它会抓住"讨论里说好要做，写计划时悄悄没了"这种失败。

#### 来源列决定"要不要问用户"

| 来源 | 含义 |
|---|---|
| `用户` | 用户明确说过、或你问过并得到答复 |
| `agent` | 你自己决定的 |

**下面四类决策必须标 `用户`**——也就是必须停下来问一次，不能自行决定后只记进表里：

1. **输入容错** —— 遇到非法输入是报错、跳过、还是用默认值？退出码是多少？
2. **输出格式取值** —— 字段名、精度、单位、排序、编码
3. **范围边界** —— 做什么、明确不做什么
4. **兼容性影响** —— 是否改变既有行为、是否破坏已有用法

判据是"**这个选择会直接影响用户看到的行为吗**"——会，就问。

这四类之外的技术细节（怎么分层、用什么数据结构）自行决定并标 `agent` 是正常的，不必事事问。

计划检查会列出所有来源非 `用户` 的决策，让你在门槛处再确认一遍它们确实不属于上面四类。

#### 决策要写到"任务能引用它"的粒度

- 好：`| D-02 | 缺少 --name 时退出码为 2 | 用户 | 与 argparse 默认行为一致 |`
- 坏：`| D-02 | 做好错误处理 |  |`（太泛，任务没法引用）

### `## 阶段` 与 `**Checkpoint**`

阶段把任务分组，每个阶段声明一个 Checkpoint——**本阶段全部任务完成后可判定的检查点**。

```markdown
### Phase 1: 数据层

**Checkpoint**: `python3 -m unittest tests.test_models -q` 退出码 0
```

阶段之间的顺序约束由依赖图表达（后面的任务 `依赖` 前面的任务），Checkpoint 只是给人看的阶段验收。

**谁在什么时候核对**：本阶段最后一个任务 `record` 成功后，`record` 的输出里会带一条 ▸ 提醒，把该阶段的 Checkpoint 摆出来；**推进下一阶段之前，控制器必须逐条核对它是否成立，核对结论记进账本「裁决」区**。

**它是规程，不是机械门**：引擎只提醒、不做校验——"检查点成立没成立"要人判，引擎能查的只有"字段填了没"。给它一个假的强制力（让人以为"引擎会验 Checkpoint"）比不验更坏：下一代人看到那条校验，会以为它验的是检查点成立。

### 任务块 `#### T<n> <名称>`

ID 必须是 `T` + 数字，不能有别的形式。**每个任务十个字段，缺一个就报错。**

| 字段 | 必填 | 说明 |
|---|---|---|
| 文件 | 建议 | 精确路径。写了路径的条目在 V 轮**必须**用存在性判定，不许标"无法验证" |
| 依赖 | 是 | `无` 或 `T1` / `T1, T2`。引擎据此算 BLOCKED/READY |
| 并行 | 是 | `是` / `否`。标记是否可以与其他任务同时进行（当前实现串行派发，标记只作排序参考） |
| **做法** | **是** | 这一步具体做什么：动作 + 关键取值 + 边界/禁止项。判据见下 |
| 接口 | 是 | `consumes <上游给的签名> / produces <本任务产出的签名>` |
| **预期** | **是** | 做完后应观察到什么——**可观察的行为或产物** |
| 验收 | **是** | 用什么证明：命令/检查，可判定 |
| 失败信号 | **是** | 什么现象表示它没做对 |
| 决策 | 是 | 引用的 `D-NN`，或 `无` |
| 状态 | 是 | `pending` / `in_progress` / `complete` / `blocked`（**格式 ≥4 只认 `pending` / `implemented` / `complete`**） |

#### 为什么 `失败信号` 是必填

**没有失败信号的验收标准等于没写**——"跑通"这种标准在失败时看不出失败。每个验收标准必须配一个可观察的反面：

- 验收：`python3 app.py --name x` 退出码 0 且 stdout 含 x
  失败信号：传 --name 仍报错，**或不传时退出码不是 2**
- 验收：函数返回长度正确的列表
  失败信号：返回空列表，或对空输入抛异常

#### 接口字段的作用

执行者只看得到自己那一个任务的片段，看不到完整的计划。`接口` 字段是它了解邻居任务用什么的唯一渠道。

- 好：`consumes greet(name: str) -> str / produces main() -> int`
- 坏：`consumes 上面的函数 / produces 结果`（执行者不知道名字和类型）

写完之后检查一遍：**后面任务 `consumes` 的名字，必须和前面任务 `produces` 的逐字一致**。

#### `做法` 与 `预期` 的作用

这两个字段补的是同一个洞：**执行者只看得到自己那一个任务，接口字段只给签名，给不了"做什么"和"期望看到什么"**。缺了它们，执行者要么自己发明设计决策，要么把"命令跑过了"当成"做对了"。

| 字段 | 写什么 | 判据 / 反例 |
|---|---|---|
| `做法` | 动作序列 + 关键取值 + 边界与禁止项 | **判据：换一个执行者拿到它，不问问题就能做完吗？**不能就写细。反例："实现 dry-run 支持"（等于没写）；正例："把现有各处写盘调用改为收集后由 `apply_actions(actions, dry_run)` 统一执行；dry_run=True 时只打印 `动作 路径`，不调用任何写盘 API" |
| `预期` | 做完后**可观察**的结果：行为、产物、输出 | 必须是外部可观察的，不是实现细节。反例："函数写好了"、"用了 jose 库"；正例："`--dry-run` 的 stdout 里每个将写入路径出现一次，且 `git status --porcelain` 为空" |

「预期」和「验收」是两件事，不要混：**预期=应该看到什么，验收=用什么命令或检查去证明**。只写验收（"跑 npm test"）会出现"命令过了但结果不是想要的那个"。

## `## 审查节点`（格式 ≥4：节点是验收单位）

格式 ≥4 把执行阶段的**验收单位**从任务改为计划中预先声明的「审查节点」：任务是执行单位（派发、证据、恢复仍挂在任务上），节点是验收单位。放行采用「待执行 → 实现中 → 已实现、待审查 → 已验收」的统一状态——`record` 记「已实现」，节点 `review` 通过后成员任务才映射 `complete`（既有的"完成＝已验收"语义不被改软）。节点划分在计划期**显式声明**，不做"按体量自动降频"（不由 agent 按规模自行推断）。

段标题是二级标题 `## 审查节点`（与 `## 阶段` 同级；**段名精确匹配**——写成「审查节点与边界」按缺段报错）。节点块标题是三级标题 `### N1 <名称>`，**块标题即节点 ID**（`N<n>`）。每个节点块＝**节点 ID ＋ 六项必填字段 ＋ 一个可选字段**：

```markdown
## 审查节点

### N1 解析与校验

- **归属任务**：T1, T2
- **分组理由**：同一解析契约的连续改动合并验收；错误会沿 T3 的派发契约扩散（消费者：T3；后果：下游按错误字段派发）
- **审查职责**：验收对象＝解析契约完整性；逐任务一行结论＋节点整体结论
- **依赖节点**：无
- **送审条件**：T1、T2 全部已实现，必要验证完成，未解决事项列明
- **兼任终审**：否

### N2 收束与整体验收

- **归属任务**：T3
- **分组理由**：最后节点兼任终审，读取从工作流基线到当前版本的完整改动
- **审查职责**：验收 T3＋整体需求覆盖逐项核对（范围缩减检测不可豁免）
- **依赖节点**：N1
- **送审条件**：T3 已实现；其它节点已验收
- **兼任终审**：是
- **前身**：无
```

| 字段 | 必填 | 写什么 |
|---|---|---|
| **归属任务** | 是 | `T1, T2`（逗号分隔的真实任务 ID；**每个任务恰属一个节点**） |
| **分组理由** | 是 | 功能或契约完整性依据，含下游依赖与判断错误的返工影响；**提前审查节点**须含「审查对象—消费者或操作—后果」三元组 |
| **审查职责** | 是 | 验收对象与整体结论要求（逐任务一行＋节点整体结论，防"每项单独成立、组合后不成立"） |
| **依赖节点** | 是 | `无` 或节点 ID 列表（**多值**：逗号分隔，如 `N1, N2`）——**声明即约束**，与任务依赖导出的边一并纳入等待图 |
| **送审条件** | 是 | 归属任务全部已实现＋必要验证完成＋未解决事项列明 |
| **兼任终审** | 是 | `是` / `否`（**恰一个**为 `是`；该节点不得为其它节点上游） |
| **前身**（可选） | 否 | `无` 或**最多一个**节点/谱系 ID——仅在由已有节点拆分、改名或调整而来时声明 |

**节点是验收单位、任务是执行单位。** 节点围绕一个可以完整判断的功能、契约或风险边界组织，可含多个连续任务，也可只含一个任务；**整个工作流只有一个节点同样合法**——前提是不存在需要提前检查的边界，且审查者能够完整覆盖。组内任务可以消费彼此的"已实现"成果；**跨节点依赖（含显式声明的节点依赖）只在上游节点整体已验收后解除**——节点是放行的原子单位。

**提前审查只针对明确的风险边界**——命中任一条才设置提前节点：① 关键契约存在新增或实质变化、下游将据此实现；② 错误会向多个模块扩散或造成明显返工；③ 后续步骤将产生难以撤回的外部影响；④ 当前验证不足以控制相关风险。提前节点必须在 `分组理由` 里写明「**审查对象 —— 后续消费者或操作 —— 判断错误的后果**」。普通内部数据结构或辅助函数，不因为被下一项任务调用就自动需要提前独立审查；**也不按任务名称含关键词恢复逐任务审查**。被认定为关键边界的依赖，通过**拆分节点**使其在消费之前完成验收。

**节点调整纪律**：只在出现新的依赖、契约变化或修改范围扩大等具体依据时调整，并记录原因；调整产生的新节点在 `前身` 声明来源并继承审查谱系与问题清单。

### 值解析（严格）

`归属任务` / `依赖节点` / `前身` 三个列表字段共用同一条解析路径：先剥离**一个**尾部括号注解（全角 `（）` 或半角 `()`），再严格解析「`无` 或逗号分隔的 ID 列表」；残余不可解析、注解剥空、空列表项任一即 **ERROR**（不静默降级为空集）。`none` / `n/a` / `-` / `待确认` 之类**不是** `无`。注解只剥一个：`N0（a）（b）` 因残余文本报值非法。

### 结构校验（`check`，仅格式 ≥4）

- **节点 ID 唯一**：两个块共用一个 ID → ERROR（归属、终审与等待图都会塌缩到同一节点上）；
- `兼任终审` 只能是 `是`/`否`（块名与字段都读不出时按缺项报）；六项必填字段任一缺失/为空 → ERROR（带节点 ID）；
- **每个任务恰属一个节点**：任务不属于任何节点、或同时归属多个节点（`归属任务：T1, T2` 在两块里都列 T1）→ ERROR；
- 归属任务 / 依赖节点引用不存在的任务或节点 → ERROR；
- **恰有一个 `兼任终审：是`**；终审节点**不得为其它节点的上游**（"最后一个节点"由此成为可检查的调度规则——防终审等待死锁）；
- **等待图无环**：等待图＝任务依赖导出的跨节点等待边 ∪ **`依赖节点` 显式声明的边** ∪ ｛终审节点 → 每个其它节点（仅恰一个终审时加入）｝；方向统一「**等待者 → 被等待者**」（B 依赖 A → 等待边 `B → A`）；**两条来源合并为同一张图后判环**——跨来源组合成环（任务依赖 A→B ＋ 声明 B→A，各自无环、合并成环）或单来源成环均即 ERROR，消息含成环路径。判环、`slice` 派发与就绪检查（`close`/`verify`）共用同一张图；
- **前身**（可选字段）：多于一个引用即视为**合并已送审节点**——首版不支持，ERROR；不得指向本计划中仍在使用的节点 ID（调整应替换/移除原节点）；**从历史记录解析**（当前计划文本 ∪ 本工作流历史记录——审查记录与事件中已生成的谱系 ID、已声明的前身链），不得因被替换节点已不在计划文本中而判「引用不存在」；**本节点自己声明的 `前身` 值不进入它自己的解析集合**（否则任意拼错的引用都自证成立，"解析不到"永远报不出来）；完全解析不到、或解析结果歧义（同一引用映到多个谱系根）→ ERROR；多个子节点可分别以同一前身作为唯一前身（拆分场景），各自继承同一谱系根。**谱系根**形如 `N1-<8 位摘要>`：首审生成一次并随事件持久化，重放/重试不重新生成——拆分、改名或调整不换根，修复预算沿根累计（不重置、不相加）。

> 终审节点被依赖时**两条 ERROR 同时出现**（等待图成环＋"不得为上游"）——根因是同一处，双报便于定位，不是两条独立问题。

**状态集合收窄（格式 ≥4）**：任务状态只认 `pending` / `implemented` / `complete`；`in_progress` / `blocked` **没有写入口**（写它们 → ERROR）。

### 两态记账与事件权威源（格式 ≥4）

- **三种判断分别计算，不得混同**：① 任务实现是否完成（`implemented` 事件，`record` 记）；② 节点结论是否有效（前提与失效规则，`review`/`impact` 记）；③ 是否因依赖而阻塞（上游未验收）。上游失效或结论转「待重新确认」只改变 ②③——**不把已完成的实现退回「待实现」**。
- **`events.jsonl` 是权威记录，计划里的 `状态` 是可重放的展示投影**；写入顺序**先事件、后状态**；中断于两者之间时按事件重放修复投影——**有实现证据的偏差按事件双向修复**（投影落后修复上；投影 `complete` 但无 `pass` 支撑修复下为 `implemented`）；**没有任何实现证据却声称进度的领先**拒绝。投影与事件推导不一致 → 先恢复；无法恢复 → 拒绝放行（`slice` / `record` / `review` / `close` / `verify` 同一入口阻断）。

### 格式 ≥4 的记账命令

```bash
# 记「已实现」+ 证据（格式 ≥4 不再使用 --verdict）
$W record <slug> T3 --commits <base7>..<head7> --evidence "<验收怎么跑/结果/失败信号自查>" --operation-id <id>

# 节点审查：pass 后成员任务映射 complete；fail 保持已实现、不释放跨节点依赖
$W review <slug> N1 --verdict pass|fail --commits <base7>..<head7> \
   --lines "T1: 结论＋依据；T2: 结论＋依据" --evidence "<引用>" \
   [--premises "契约锚点: <路径>; 共享实现: <路径[,路径…]>; 配置: <路径>"] --operation-id <id>

# 定向复核：在普通 review 参数之外附 `--recheck`（值是**原审查记录的操作 ID**，原记录关联）；
# 本次复核的重试身份用 `--operation-id`——两者不同；不显式给 `--recheck-mode` 时按「定向复核」记
$W review <slug> N1 --verdict pass|fail --commits <base7>..<head7> \
   --lines "<T1: 结论＋依据；…>" --evidence "<引用>" \
   --recheck <原审查记录的操作ID> [--recheck-mode 主控核对|定向复核] --operation-id <id>

# 封顶恢复：开启新审查阶段（普通 review 与 --new-phase 两种模式互斥）
$W review <slug> N1 --new-phase --basis "<实质变化>" --confirmation <记录引用> --confirmed-commit <A..B> --operation-id <id>

# 影响判断：判定范围外变化对结论的影响（六参数）
$W impact <slug> N1 --verdict irrelevant|related|undecidable --basis "<依据>" \
   --expect-review <审查记录操作ID> --expect-changes <变化集摘要> --operation-id <id>
```

**`--lines` 的书写要求**：行以 `<任务ID>:` 开头——从行首、换行后、或 `；`/`;` 之后识别（全/半角冒号都认）。**结论正文里不要出现 `T<n>:` 形态**——它会被当作下一个行边界切开，任务集合对不上即 fail-closed 拒绝。逐行覆盖归属任务，缺行/多行/重复行/空结论任一即拒绝（信息列明差异）。行数只证明覆盖记录齐全，**不证明检查充分**——每行必须关联验收依据或具体问题。

**`--premises` 的写法**：`"<类型>: <路径[,路径…]>; …"`，类型 ∈ `契约锚点` / `共享实现` / `配置`；引用路径必须存在（不存在即拒绝，不静默降级）；目录递归展开成文件列表；空串＝空清单。条目随结论保存 `{类型, 引用[], 摘要, 基线提交}`，摘要取 sha256 前 16 位。

**操作 ID 协议**：`record` / `review`（含 `--recheck`、`--new-phase`）/ `impact` **必须**携带 `--operation-id`——未提供即拒绝；首版**不提供**引擎自动生成分支。调用方在**首次执行前生成并保存**，**重试必须复用**。相同 ID＋相同请求 → **幂等重放**（返回原结果、恢复投影、不新增事件/轮次/阶段）；相同 ID＋不同请求 → 拒绝；真正的新复核使用新操作 ID、经 `--recheck` 另行关联原记录。**结果 receipt 随事件持久化**——中断后重建再重试仍据此返回原结果。

**批次派发（合并 `slice`）成员须同属一个节点**——跨节点批次被拒（`T1→N1、T3→N2` 逐条列出）。同型机械改动的既有合并判据不变，只新增"同批须属同一节点"这一条约束。

**格式 ≤3 计划不解析此段、不新增任何校验**——没有 `## 审查节点` 段、没有两态记账（`record` 仍用 `--verdict`、无 `--evidence`/`--operation-id`）；在格式 ≤3 计划上携带格式 ≥4 专有参数会被明确拒绝（不静默忽略）。

## 任务粒度的三条硬线

1. **任务是交付单元，不是计时单位**。一个任务 = **一次派发能做完、有自己的验收、值得一次独立审查**的最小交付单元（一次能跑完它的测试）。**"2-5 分钟"约束的是步骤，不是任务**：任务的 `做法` 里写清步骤（2-8 步，每步一个动作、2-5 分钟）。**"完成"包含提交**——任务做完即提交（提交契约见 SKILL.md 的 E 轮与 `dispatch-protocol.md`），`record` 的提交范围就来自它。
2. **垂直切片，不水平分阶段**。切错的样子：先"DB 阶段"再"API 阶段"再"前端阶段"——端到端反馈被推迟到最后。切对的样子：每个任务同时穿过它需要的层。
3. **单任务不超过 5 个文件修改，计划不超过 8 个任务**。超了 `check` 会警告。

   规模不是审美问题，它直接决定两道门的成败：任务越多、计划越长，人在门上的注意力越不够用，审批就越容易退化成走过场——而走过场的审批比没有审批更糟，它留下一个"已批准"的假象。所以超限时**首选拆成多个工作流**；确实不拆时，在决策表里记一条「接受超限，因为 <理由>——代价是两道门的审阅有效性下降」。拆与不拆是用户的决定，但代价必须说清。

**为什么把计时降到步骤**：挂在任务上会两头出错——要么把任务切成半小时一步的碎片（审查面碎掉、派发次数翻倍），要么任务实际远超 5 分钟却不敢写步骤。任务边界该由"独立验收 + 独立审查面"决定，时间只用来判断步骤是不是切得太粗。

## 同型机械改动要合并，不要一文件一任务

**这是最容易被切错的粒度。** 如果要做的是同一种小改动在多个地方重复——改常量、改字段名、同样的调用替换、加同一行日志——**它们是一个任务，不是一个文件一个任务**。

| 切错 | 切对 |
|---|---|
| T1 改 a.py 的常量<br>T2 改 b.py 的常量<br>T3 改 c.py 的常量 | **T1 统一三处常量**<br>（文件：`modify a.py` / `modify b.py` / `modify c.py`） |

判据是**"这次改动需要自己的判断、自己的测试、自己的审查面吗"**：

| 值得单独成一个任务 | 该合并进一个任务 |
|---|---|
| 需要自己写测试 | 同一个一行修复重复在多个文件 |
| 需要自己的判断（设计、取舍） | 改常量、改字段名、加日志 |
| 有自己的审查面（不同关注点） | 机械重复的同型改动 |

**为什么**：每个任务在执行轮是至少两次 subagent 派发（实现者 + 独立审查者）。把三次机械改动拆成三个任务 = 六次派发，而合成一个任务只要两次。**这不是省流程，是省掉纯粹重复的流程**——审查、验证、覆盖审计一样都不少。

注意这**不是**"按体量开快路径"：合并只改**执行粒度**。gated 仍走审批门；execution 仍走 `check`、独立审查、验证覆盖审计、`close`，不能用合并任务暗中减少质量控制。

计划写完时如果发现已经切细了、不好回头改，执行轮还有一条逃生通道：**同型任务可以合成一批派发**（见 `dispatch-protocol.md` 的"合并派发"）。

## 别忘了文档任务

如果这次改动改变了**用户可见**的东西——命令、选项、输出格式、行为——计划里要有一个更新 README / 用法文档的任务。

漏掉文档**不会让任何测试变红**，所以它只能靠计划兜住。决定不更新时，把它作为一条决策写清理由——"用法未变，无需更新"是完全合理的决策；不写理由才是问题。

## 完整正例

````markdown
# 给 CLI 加 --verbose 输出

**Goal**: 让 `mytool` 支持 `--verbose` 打印每个处理步骤
**Slug**: verbose-flag
**Created**: 2026-09-10
**格式**: 2

## 验证命令

```
python3 -m pytest -q
```

## 验证覆盖

| 对象 | 验证手段 | 类型 |
|------|---------|------|
| D-01 | `tests/test_logging.py::test_level_mapping` | 自动化 |
| D-02 | `tests/test_cli.py::test_verbose_count` | 自动化 |

### 不验证的部分

- 并发下的日志顺序不验证：本次改动未引入并发路径
- 既有日志调用位置不变：靠 diff review 覆盖，无自动化测试

## 全局约束

- Python 3.9+，只用标准库
- 日志一律走 logging，不 print

## 方案

### 背景与目标

**问题现状**：`mytool` 出错时只有一行报错，用户想知道"卡在哪一步"只能改代码加 print，再改回去。

**预期结果**：`mytool -v run` 在 stderr 打印每个处理步骤（读配置、解析、写库），不加 `-v` 时输出与现在完全一致；最多 `-vvv` 三级。

**关键约束**：不引入配置项开关（用一个参数就够了），不改现有日志调用的位置。

### 做法

在 logging 层加一个 `setup_logging(verbosity)` 入口，把 verbosity 映射到 logging 级别；CLI 侧用 argparse 的 `action="count"` 收集 `-v` 次数后传给这个入口。

### 备选与取舍

- 备选一：直接调 `logging.basicConfig(level=...)`。没选，因为它无法在多次调用间安全地改级别，重复调用会叠加 handler 导致日志重复打印。
- 备选二：自己维护一个全局级别变量。没选，重复造轮子，且与既有日志体系割裂。

### 明确不做

- 不做日志文件输出（需求只要求控制台分级）
- 不改动现有日志调用的位置和内容
- 不引入任何配置文件的读取

## 决策

| ID | 决策 | 来源 | 理由 |
|----|------|------|------|
| D-01 | 用 logging 的 DEBUG 级别承载 verbose | 用户 | 与现有日志体系一致，不用新增开关 |
| D-02 | --verbose 可重复出现累加级别，最多三级 | 用户 | 与 kubectl -v 习惯一致，用户不用记新参数 |

## 阶段

### Phase 1: 日志层

**Checkpoint**: `python3 -m pytest tests/test_logging.py -q` 退出码 0

#### T1 建立 logging 配置入口

- **文件**：`create mytool/logging_setup.py` / `create tests/test_logging.py`
- **依赖**：无
- **并行**：否
- **做法**：新增 `setup_logging(verbosity: int) -> None`：先把 verbosity 夹到 0-3，再映射到 logging 级别（0=WARNING、1=INFO、2=DEBUG、3=DEBUG 且带 `%(module)s` 前缀）；用 `logging.getLogger().handlers` 判断是否已配置，已配置时只改 level，**不重复 addHandler**。
- **接口**：consumes 无 / produces `setup_logging(verbosity: int) -> None`
- **预期**：`setup_logging(0)` 后根 logger 级别为 WARNING，`setup_logging(2)` 后为 DEBUG；连续调用两次后 `len(root.handlers)` 不变
- **验收**：`python3 -m pytest tests/test_logging.py -q` 退出码 0
- **失败信号**：verbosity=0 时输出 DEBUG 行，或重复调用会叠加 handler 导致日志重复打印
- **决策**：D-01
- **状态**：pending

#### T2 接入 CLI

- **文件**：`modify mytool/cli.py:12-40`
- **依赖**：T1
- **并行**：否
- **做法**：给 argparse 加 `-v` 参数并设 `action="count", default=0`；在 `main()` 里拿到参数后**第一件事**就是调 `setup_logging(args.verbose)`，再进原有逻辑；不要在各命令函数里重复调它。
- **接口**：consumes `setup_logging(verbosity: int) -> None` / produces 无
- **预期**：`mytool --verbose -v run` 时 stderr 出现 DEBUG 行；`mytool run` 时没有 DEBUG 行
- **验收**：`mytool --verbose -v run` 的 stderr 含 DEBUG，不加参数时不含
- **失败信号**：`-v` 被重复计数时抛错，或不加参数仍打印 DEBUG
- **决策**：D-01, D-02
- **状态**：pending
````

## 真正可推迟的未知：合法写法

留占位符（`TODO` / 待补 / 待定）是**禁止**的：它把"没想清楚"混进了一份"已批准"的文档里，`check` 会直接拦。

但**确实存在可以推迟的未知**，它们有合法写法：

```markdown
**未知**：上游 429 时的退避上限取多少 — 待压测出基线后再定 — 不影响接口形状与任务拆分
```

判据一句话（学自 OpenSpec）：**它会改变做法、接口、验收标准或任务拆分吗？**

- **会** → 必须现在解决。**去问用户**，不要猜着写、也不要留成未知——那会在执行轮变成返工
- **不会** → 按上面格式写清"是什么 / 待什么条件确定 / 不影响什么"，三样缺一不可。没有第三样（不影响什么），它多半是"我还没想"，不是"可以推迟"

这条和「不验证的部分」是同一个思路：**给诚实的省略留出口，同时把省略显式化**。

## 改计划的原则

- 已 closed 的原目标修补先 `reopen --reason --by --work`：保存原 close、建立新周期并追加 pending 任务模板，补齐后按下列模式走；用户已有明确修补请求即足够，不重复求重开许可。
- **gated 改的是同一个意图**（发现边界情况、方案微调、范围收窄）→ 直接改现有 plan.md，改完重跑 `check` 和语义审查，**重新审批**（内容变了，旧审批已自动失效）
- **execution 改的是同一个已定意图**且没有新增用户判断 → 直接改现有 plan.md，改完重跑 `check` 和语义审查，不伪造审批；若改动引入新的范围、方案、取舍、契约或验收判断，先运行 `$W gate <slug> --reason ...`
- **意图变了**（"加个开关"变成"重做配置系统"）→ `init <新 slug> --from <原 slug>` 新建并关联，按是否有新判断选审批模式。旧流程仍待验或未完成时保留其真实状态，不能为了换目标强行 close
- 改完计划后**必须重跑 `workflow.py check`**，否则可能把新引入的洞带进执行轮
- gated 计划改动后 `slice` 会因审批失效而拒绝派发；execution 计划改动后仍由 `check`/语义审查拦质量问题，出现新判断则由 `gate` 转入 gated

## 审批门的位置（按模式分流）

```
需求 → [承接研究 + 澄清：一次一个问题]
     → 起草设计文档的方案五节（声明「无」时，方案四段就写在计划的 `## 方案`）
     ├─ gated：方案门 → 补齐文档/写任务与决策 → check → 独立语义审查 → 计划门
     └─ execution：补齐文档/写任务与决策 → check → 独立语义审查（不暂停）
     → E 轮执行 → 终审（回写设计文档 + 决策上浮）→ V 轮 verify → close
```

execution 只省两个人工等待点和对应 `approve` 指纹门；计划、账本、审查、验证和收尾仍然存在。执行中产生新判断时，用 `$W gate <slug> --reason ...` 切回 gated，再只呈现变化 diff。

**为什么计划和设计文档之间多一道语义审查**：`check` 是机械的——它只能证明"每个决策编号都被某个任务引用了""字段都填了"。它能证明的东西不等于计划是对的：一条决策被引用，不等于它承诺的行为都有任务承载（`D-08 分析结果确认后落库` 可以被 T5 引用，而 T5 的工具清单里根本没有"保存分析结果"这个动作）。这类缺口只有**从目标倒推读一遍**才能发现，所以放在计划和设计文档都齐了、还没呈给用户之前。审查清单与 prompt 见 [`plan-review.md`](plan-review.md)。

设计文档在 gated 的**方案门之后**、execution 的计划检查和语义审查之前必须写全——它和任务、决策表同属工作流的设计记录；execution 不因不走人工门而省略它。回写则必须在 **`verify` 之前**完成，否则工作树指纹失配、`close` 会拒绝收尾。

gated 的两道门用 `approve` 子命令记账，依据是**用户的原话**；execution 不调用 `approve`，而在计划头部和账本记录无门依据：

```bash
workflow.py approve <slug> 方案 --by "用户说：这个做法可以，往下写"
workflow.py approve <slug> 计划 --by "用户说：计划没问题，开始吧"
```

拒绝规则：方案为空或含 TODO 时不能批方案；计划有 ERROR 时不能批计划；不带 `--by` 一律拒绝——**没有依据的审批等于自己给自己盖章**。

# bug 修复的格式差异

bug 工作流用 `workflow.py init <slug> --bug` 创建，头部多一行 `**类型**: bug`，并多两节、一条硬规则。

## 为什么 bug 免门

bug 的"需求"是一个**症状**而不是规格——没有可审的"方案"，因为要做的事已经被症状决定了大半。所以 bug 工作流免两道审批门。

补偿控制是三项强制，它们替代门起的作用。

**`### 背景与目标` 对 bug 不是必填**：它的"为什么做"已经由 `## 复现` + `## 根因` 两节回答了（症状是什么、为什么会这样）。`check` 对 bug 路径不查这一节，`init` 也不会生成它。任务的 `做法`/`预期`/`验收`/`失败信号` 照旧必填——修复同样要知道"做什么、做完看到什么、怎么证明、失败长什么样"。

## `## 复现`

```markdown
## 复现

`python3 -c "import m; m.parse('')"` → 抛 ValueError: invalid literal for int()
```

**必须是可复现的最小步骤或命令。** 修之前先确认它确实失败——没有可复现的失败，就无法证明修好了（`check` 会拒空节）。

## `## 根因`

```markdown
## 根因

`int('')` 抛 ValueError，`parse` 未处理空输入。上游调用方会把空串传进来。
```

**说清为什么错。** 说不清就只是在让症状消失，不是在修复——那种"修法"换个输入就复现。`check` 拒绝空节。

## 回归测试（硬要求）

验证覆盖表里**必须有一行明确标为回归测试**：

```markdown
| 对象 | 验证手段 | 类型 |
|------|---------|------|
| 回归测试（捕获本 bug） | `tests/test_parse.py::test_empty_returns_none` | 自动化 |
| D-01 | `tests/test_parse.py::test_empty_returns_none` | 自动化 |
```

`check` 会找 `对象` 或 `手段` 里含"回归"的行，没有就报 ERROR。

**为什么是硬要求**：修复不带回归测试，同一个 bug 会回来——而且回来时没人记得修过。这条是从 gstack 的 `/qa` 学的（它规定每个修复必须生成回归测试）。

项目确实没有测试框架时，先呈现影响并取得用户对省略回归测试的明确决定，再记录理由和「不验证的部分」；不能自行取消必验要求。

## bug 工作流的验证特别要求

| 要求 | 理由 |
|---|---|
| 复现用例必须从**失败**变为通过 | 这是"修好了"的定义 |
| **全量测试不回归** | 修复最容易打破别处，这一步不能省 |
| 特别检查是否改动了**共享函数或默认值** | bug 修复最常伤到的地方 |
| **不夹带无关改动** | 顺手重构是 bug 修复最常见的坏味道；要重构就单独开工作流 |

## bug 路径的升级条件

任一命中就该改走完整工作流（此时它实际是"探索 + 改造"，不是"修复"）：

- 复现不出来，或根因不明
- 修复需要改 3 处以上，或跨模块
- 涉及数据正确性、安全、并发
- 修着修着发现要改的是一段设计

## bug 工作流的计划骨架

````markdown
# <症状描述>

**Goal**: <一句话：让 X 不再 Y>
**Slug**: <slug>
**类型**: bug

## 复现
## 根因
## 方案（照常写——bug 也值得说清怎么修）
## 决策
## 验证覆盖（必须含回归测试那一行）
## 阶段
````
