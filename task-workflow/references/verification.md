# 验证、补证、收尾与恢复

进入 V 轮、处理证据问题、恢复旧工作流或重开时读取。本文件是这些操作的详细协议；任务拆分和独立审查仍按 SKILL.md 与派发协议执行。

## 状态与真源

先运行 `status <slug>`。计划和任务留在 `plan.md`；旧审批、完成记录和裁决仍读 `ledger.md`。新验证、人工结论、豁免、补证、close/reopen 以 `events.jsonl` 为准，完整输出在 `evidence/<验证事件 ID>.json`。账本的“结构化事件”区由引擎呈现，不能反向手改它来改结论。恢复还要对齐关联报告与 `git log`。

| 观察 | 后续动作 |
|---|---|
| 任务 complete，尚无有效验收 | 进入 V 轮；complete 只表示实现任务完成 |
| 必验人工 pending/rejected | 报告“实现完成，等待人工验收”，呈现具体清单，不先 close |
| 必验 unknown/missing | 优先核实原结果、路径、符号和绑定；不能直接判实现坏了或盲目重跑 |
| 计划命令实际失败 | 保留失败；查原因，确认实现缺口才追加任务回 E 轮 |
| 当前周期验收全部通过 | close 保存结论快照 |
| closed，只查询状态 | 报告历史收尾；无关提交不改变该历史结论 |
| closed，用户明确要求原目标修补 | 显式 reopen，新增任务并重新验收；修补请求本身已是重开依据 |
| 新目标 | init 新 slug 并关联来源；旧工作流未满足验收时不得强行 close |

不指定 slug 时只选活跃工作流；多个活跃对象仍需用户选择。历史 closed 用显式 slug 查看。`status` 只读。结构化记录损坏时报告“无法确认”，不跳过坏行、不退回旧 Markdown PASS；先恢复完整原记录，不能伪造新的成功。

## 先确定实际验什么

按四类选择证据，不能只看本仓库 diff：

| 类别 | 手段 |
|---|---|
| DIFF-VERIFIABLE | diff 与测试 |
| CROSS-REPO | 检查另一个仓库的实际状态 |
| EXTERNAL-STATE | 检查部署、线上配置或外部后台的实际状态 |
| CONTENT-SHAPE | 检查交付物的存在、内容和结构 |

明确路径必须实际检查；读取受阻就记录待核实，不能把“未检查”写成完成。“生成交付物的代码存在”也不能代替“交付物确实存在”。引擎的文件/符号核对仅提供确定性检查，语义覆盖仍由独立审查判断。

覆盖表默认必需。明确可选项只提供反馈、不阻塞收尾；不得因验不过才自行改成可选。人工项要写步骤和预期，自动化项要给实际文件引用；具体列格式见 [plan-format.md](plan-format.md)。

## 执行验证并区分结果

以下示例将 `W` 设为脚本路径，在项目根调用；将 `demo` 换成实际 slug。

```bash
W="$HOME/.agents/skills/task-workflow/scripts/workflow.py"
python3 "$W" verify demo --json
```

读取实际命令的 `exit_code`，以及整体验收 `passed`、`command_passed`、`pending`、`unknown`、`gaps`、`blockers`。命令退出 0 但人工待验或必验证据未知时，整体仍未通过；CLI 退出 2，不叫实现失败。整体通过退出 0，输入/证据损坏等操作错误退出 1。

运行前后都取工作树与验收指纹；漂移的结果不能 close。原命令、退出码与完整 stdout/stderr 保存在 receipt，摘要进入事件。`--command` 保留诊断用途，但不同于当前计划命令的成功结果不能替代必验命令；改变命令先按计划变更处理，不能偷换为 `true`。

无命令时 `verify` 只汇总验收、不执行 shell。只有没有尚未豁免的必验自动化项、必验人工结论完整且具有明确来源时才可能通过；空清单不通过。若当前周期已经执行过验证，最近结果仍参与门禁，删除命令不能抹掉失败。bug 计划仍必须声明命令。

## 明确清单后一次答复、逐项登记

```bash
python3 "$W" acceptance demo --json
```

将返回的 ID、手段/步骤、预期和必需性呈现给用户。用户可明确回复“A1、A2 都通过”，也可只确认 A1；“继续执行”“可以往下做”不能自行解释成验收通过。控制器保存原答复与可追溯来源，取返回的 `checklist` 绑定值登记，用户无需理解或输入哈希。

```bash
python3 "$W" confirm demo --item A1 --item A2 \
  --checklist '<acceptance 返回的 checklist>' \
  --by '<用户对这两项的实际答复>' --source '<实际会话/消息来源>'
```

每个 `--item` 单独生成事件，未选项不变。`--status rejected` 可记录未通过；后续明确的新结论再用相同入口登记。清单绑定失效后必须核对新版本，不能把旧答复套上去。已有有效旧授权可如实引用原来源，不为登记再问一遍。`confirm` 仅处理人工项，不替代自动化结果。

用户明确豁免具体要求时：

```bash
python3 "$W" waive demo --item A2 \
  --checklist '<当前 checklist>' --by '<用户的具体豁免答复>' \
  --source '<实际答复来源>' --reason '<取消该项要求的理由>'
```

豁免逐项保存，不能覆盖失败的验证命令。若用户要改变计划验收契约，按原审批模式更新计划并记录用户决定；不能把必验项悄悄移进“不验证的部分”。

## 优先补证，不重跑已有结果

证据缺口先区分“引用/解析不对”和“实际上没验证”。仅引用问题可用：

```bash
python3 "$W" evidence demo --verify '<最近一次 verify 的 event ID>' \
  --item A1 --ref 'tests/test_feature.py' --source '<该文件与原验证的真实关联依据>'
```

该入口不执行命令、不改原始结果，只追加引用与内容摘要。要求同周期、同工作树、同验收指纹、最近一次验证命令成功且运行稳定，完整 receipt 未损坏；不得绕过后来的失败回选旧成功。不支持旧 Markdown PASS 或外部结果导入；它们缺运行当时的绑定时保持待核实，不事后用当前计划补造指纹。

完整手段文字属于验收要求，不能改了文字还声称只是改引用。独立 `证据` 列的路径可以修正而不使原验证绑定失效，但新引用仍须用 evidence 关联取得摘要，不能只因文件存在就 close。`evidence --ref` 只接受项目内可读取文件；覆盖表本身可引用项目外文件，并在 verify 时记录摘要。目录不能充当一个已摘要的文件。

验证时采纳的全部引用，以及该项之后每次 evidence 采纳的引用，组成同一证据链。新增补证和 status/close 都重新检查整条链：任一原产物改变、损坏或缺失，就保持待核实，不能反复登记或换个文件路径清洗失效。原链完整时可以补正确关联并继续保留原链；“内容与验收目标真实相关”仍需要控制器依据和独立审查，摘要只证明内容未变。

确认是缺实现/缺验证后再形成修补任务；要重跑有外部副作用的命令，先检查现有授权和执行环境。没有足够绑定就如实待核实，不为获得绿色结果自动重跑或降级要求。

## 保守失效范围

- 工作树指纹包含 HEAD、未提交内容、未跟踪完整文件内容（包括大文件），排除 `.workflow` 记账；读取失败不能跳过。有 `.git` 却不能读取 Git 状态时不降级。
- 验收指纹绑定整份计划的规范化正文，只排除任务状态行与覆盖表明确的独立 `证据` 列。包含 Checkpoint、完整验证手段/人工步骤、围栏内约束及额外验收说明；其它计划文字变化也可能保守失效。
- 仅追加账本/事件、记录用户答复或修独立引用，不使已有验证的工作树/验收绑定变化。被采纳的 `.workflow` 证据文件另外受内容摘要约束，不能借记账目录排除而修改它。
- 活跃流程的文档改动、提交或要求变化都可能需要当前版本证据。引擎没有按文件影响范围复用或缓存；不要凭“应该没影响”沿用旧结果。
- closed 保存当时结论，不随无关提交重算。历史结果不等于验证了后来改动。

## close、reopen 与历史记录

```bash
python3 "$W" close demo --next-step '<下一步建议>'
python3 "$W" reopen demo --reason '<原目标的遗漏/回归>' \
  --by '<用户已明确要求修补的原话>' --work '<新增修补工作>'
python3 "$W" init next-goal --goal '<不同的新目标>' --from demo
python3 "$W" sync demo
```

这些是不同场景的入口，不是每次收尾都执行的一组步骤。close 要求任务完成、设计记录就绪以及当前周期全部必验通过/明确豁免；失败命令、无绑定/漂移结果、未知证据、损坏输出或引用链、必验人工待验均拒绝。`--manual-confirmed` 仅保留参数解析，活跃工作流会收到迁移提示；改用逐项 confirm，不存在泛确认旁路。

重复 close 返回已有结论且不重复记账。closed 上的执行、证据与确认写入先 reopen。reopen 保留旧 close，建立新周期，追加下一个 T 编号的 pending 任务模板；补充字段、check/审查及相应审批后执行，新周期不继承旧验收。用户明确要求原目标修补已足够，不重复问“能否重开”。新目标用 init --from 记录来源，不改旧工作流。

保留 `.workflow/<slug>/` 的计划、旧账本、事件、receipt 与报告。sync 仅从事件重建账本呈现，旧区保留；不是修复坏事件的工具。用户另行决定清理时，应先确认历史与恢复记录如何保存，不能把“收尾成功”当作删除记录的授权。

旧格式 1/2/3 和审批规则继续适用，不批量重写历史。旧账本中可识别的 close，只有任务数仍对应、任务完成且无其后完成/审批/验证记录时才认作历史 closed；complete 无 close 不补造。时间按表的固定时间列读，命令或“下一步”里的日期不作事件时间；普通裁决备注不触发重开。分钟级旧记录无法可靠判同分钟先后，也不推断裁决散文中的执行意图。旧 active 的单独 PASS 无历史验收绑定，不能作为新的收尾依据。

## 常见失败处理

本表保留 P/E 相关异常的原处理原则；验证问题优先按上面的状态和证据边界分流。

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| `$W status` 报没有工作流 | 用户想新做一件事 → 走 P 轮；用户以为有 → 检查是否在错误的目录下（引擎按 `.git` 定位项目根） | 确认路径后仍无 → 按新任务走 P 轮，不试图从对话里重建旧计划 |
| gated `slice`/`record` 报"方案/计划尚未审批" | 把该阶段呈现给用户并**等答复**，拿到答复后用 `approve` 记账 | 用户暂时不在 → **停住并报告"正在等用户对 X 的答复"**，不要当作默许继续 |
| execution `slice`/`record` 报计划检查未通过 | 修正计划结构、字段、验证覆盖或设计文档，重跑 `check` 和语义审查 | 发现修正需要新的范围/方案/取舍判断 → `$W gate <slug> --reason ...`，转 gated 后再审 |
| execution 中发现新的范围/方案/契约判断 | 立即停止相关派发，运行 `$W gate <slug> --reason ...`，只呈现受影响 diff | 不能继续用 execution，也不能把判断只留在报告里 |
| `slice` 报"审批已失效"（内容被改过） | 说明改了什么、为什么改，重新呈现给用户并重新审批 | 用户认为不该改 → 先确认保留哪个版本，不覆盖用户改动；按确认版本重新审批 |
| 方案被用户打回要求换做法 | 改 `## 方案` 后重新呈现，**重新走方案门**（方案审批会自动失效） | 改了几轮仍谈不拢 → 说明需求本身没定清楚，回到第 1 步重新澄清（一次一个问题） |
| `check` 报"决策没有出现在验证覆盖里" | 为该决策补可执行/可确认的验收手段 | 确实需要取消要求 → 呈现影响并取得用户明确决定；不得自行移出必验清单或编假证据 |
| `check` 持续报同一个 ERROR | 读该条 ERROR 的具体指向，改计划对应位置 | 仍不通过 → 说明计划结构本身有问题，考虑拆成多个工作流 |
| `verify` 报必验 unknown/missing | 核实旧输出、引用及绑定，能补证则用 evidence，不直接判实现失败 | 确认是实现/验证缺口再追加任务回 E；不能证明则保持待核实，取消要求须用户明确决定 |
| 想合并的几个任务被守卫拒绝（含依赖/已完成/超 4 个） | 按提示逐个派发，或拆成两批 | 含依赖说明它们是顺序工作 → 逐个派，别硬合 |
| 批次派发后审查发现只有其中一个任务有问题 | 修复只针对那个任务，重审限定在它的改动范围 | 若批次里多数任务都有问题 → 说明这批不是同型改动，改回逐个派发 |
| 有多个活跃工作流，用户没指明 | `$W status` 列出全部，让用户选 | 用户不确定 → 逐个展示 goal 和进度帮他判断，不要猜 |
| 验证命令未声明 | 查项目约定与既有验收，缺信息才问用户 | 无命令须无尚未豁免的必验自动化项、有明确逐项人工依据且清单非空；bug 不允许未声明 |
| bug 修着发现要改设计 | 停下改走 gated 完整路径（新开工作流，把已查清的复现与根因带过去） | 说不清是 bug 还是改造 → 按 gated 完整路径走——多走一道门的代价远小于漏审 |
| 子 agent 连续 5 轮修不好 | 控制器裁决并记账 | 计划本身错了 → 改 plan.md 后重跑 `check`，**并因内容变更重新审批**，再带裁决重派 |
| 验证未通过但任务 complete | 区分命令失败、绑定失效、证据待核实与人工 pending | 只有真实修补才回 E；标准不可判定时提出修改并取得用户决定，不擅自换标准 |
| 执行中发现工作流外的新问题 | 记进计划的决策区或新任务，**不在计划外开工** | 与当前目标无关 → 记进账本交给收尾，不扩大本次范围 |
| `check` 报"缺少 `**设计文档**` 声明" | 在计划头部声明路径，或写 `无 — <理由>`（命中四条判据时不许写「无」） | 判断不了该不该写 → 按判据走：任一条命中就写 |
| `check` 报设计文档缺小节/有空节/漏 `D-NN` | 补那一节，或写「无（<理由>）」；决策摘要补上缺的 `D-NN` | 缺的节确实不适用 → 写「无（理由）」，不要留空 |
| `approve 方案` 报"设计文档不存在" | 格式 3 且声明了设计文档时，方案正文归它——先起草那五节（一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做），再呈现方案门 | 确实不需要这份文档 → 把声明改成 `无 — <理由>`（命中四条判据的不许改），方案四段改写进计划的 `## 方案` |
| 回写设计文档后 `slice`/`record` 报"『方案』审批已失效" | 说明改到了方案那五节——回写只该动 `接口与数据形状` / `已知限制` / `实际交付` / `决策摘要` | 那五节确实要改 → 那是方案变更，呈现给用户重新审批；不要为了绕过门把内容塞进别的节 |
| 计划语义审查报 BLOCKER（决策行为没承载 / 缩水 / 与设计冲突） | 改计划或设计文档 → 重跑 `check` → 重跑审查（只核改动涉及的部分） | 同类问题反复出现 → 需求本身没定清，回第 1 步重新澄清（一次一个问题） |
| `close` 报「实际交付」还是未回写状态 | 补成真的：交付物清单 + 与计划的偏离及原因 + 遗留项 | 这次确实没有产出（纯调研等）→ 写「无（<理由>）」，理由要站得住 |
| 设计文档回写后 `close` 报指纹不符 | 说明回写发生在验证之后——重跑 `$W verify` 绑定当前内容 | 反复发生 → 把回写固定排在终审那一波，不要拖到验证之后 |
| 设计文档与代码不符（终审报出） | 改文档对齐实现；文档描述了没做的事就从文档删掉 | 发现是计划本身错了 → gated 工作流改 plan.md、重跑 `check`、**重新审批**；execution 工作流若形成新判断，先 `gate` 再审 |
