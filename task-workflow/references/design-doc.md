# 设计文档

计划之外**唯一会留在版本库里的设计记录**。计划、账本、任务报告都活在 `.workflow/`（自忽略、收尾后随工作树消失），所以"这次改动做了什么、为什么这么做、边界在哪、留了哪些坑"必须有另一个归属产物。

## 为什么必须和状态控制分开

| | 状态控制（计划 / 账本 / 报告） | 设计文档 |
|---|---|---|
| 位置 | `<项目>/.workflow/<slug>/` | **项目仓库内**，计划里声明 |
| 进版本库 | **不进**（`.workflow/.gitignore` 内容是 `*`） | **进** |
| 生命周期 | 一次工作流 | 长期——半年后还有人读 |
| 读者 | 控制器自己（路由、恢复、记账） | 人：未来的你、接手的同事、下一个 agent |
| 内容 | 状态、任务、证据、运行时记账 | 设计：机制、取舍、接口、边界、限制、决策 |

**一句话**：状态控制回答"做到哪了"，设计文档回答"这是个什么东西"。

**实测依据**：一个真实工作流跑完后，`.workflow/` 里 1837 行产出（220 行计划 + 80 行账本 + 9 份任务报告）**全部不入库**，唯一活下来的是写进 `docs/` 的那份 276 行方案文档——而它当时存在，只是因为恰好排了一个"回写文档"的任务。**没有机制保证它，就会没有它。**

## 放哪、叫什么

- **项目仓库内**，路径在计划头部 `**设计文档**:` 声明。放在 `.workflow/` 下会被 `check` 直接拦下（等于没有设计记录）。
- 沿用项目既有惯例命名，不要另起一套。例：`docs/<模块>方案.md`、`docs/designs/<主题>.md`。
- 一个工作流一份。多个工作流各写各的，不要共用一个文件（否则回写会互相打架）。

## 什么时候写

```
P 轮：起草方案的五个小节 ──→ 🚧 方案门（人审的就是这五节）
                              ↓
      补齐其余小节 ──→ 写计划与决策 ──→ 🚧 计划门
                              ↓
E 轮：实现 ──→ 末尾【回写 + 决策上浮】，并入整体终审那一波
                              ↓
V 轮：verify（指纹从此覆盖设计文档）──→ close
```

**为什么起草排在方案门之前**：计划声明了设计文档时（计划格式 3），**方案的正文以本文档为准**——计划里的 `## 方案` 只写承接、增量与指针，**方案审批的指纹绑的是本文档的「一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做」五节**。理由有两条：同一份内容写两遍，改一处忘一处，读者不知道信哪个；人审的对象应当是会长期留存的那一份，而不是一份会消失的副本。

声明「无」设计文档时，方案四段照旧写在计划的 `## 方案` 一节（格式 ≤2 的计划也一样）——没有文档可承接，就没有重复可言。

- **P 轮起草，不是执行完再补**。执行者要能读到它——`接口与数据形状` 一节是它做判断的依据，缺了它执行者只能自己发明。
- **回写必须在 V 轮之前**。`verify` 记录的是**整个工作树的指纹**，验证之后改设计文档会让指纹失配，`close` 会拒绝收尾并提示"回写要在 V 轮之前做完"。这条不需要自觉，是机械的。
- **回写不碰方案那五节**。回写只动 `接口与数据形状` / `已知限制` / `实际交付` / `决策摘要`——方案五节是用户批准过的东西，改它会让方案审批失效（那是正确行为，但别在收尾阶段才发现）。
- **起草不等于写完**。P 轮只能写到"基于方案能确定的那部分"，剩下的（实际接口长什么样、踩到哪些限制、最终交付了什么）要靠回写补——那是这份文档最值钱的部分。

### 回写补什么（E 轮末尾，并入整体终审那一波）

| 小节 | 回写时的动作 |
|---|---|
| **实际交付** | 补成真的：交付物清单（文件/接口/表/脚本/文档）、**与计划的偏离及原因**、遗留项。起草时的「无（尚未实现…）」到这里必须换掉——`close` 会拦 |
| **接口与数据形状** | 按**实际实现**校正（起草时写的是预期签名） |
| **已知限制** | 补上实现期真正踩到的边界与失效场景 |
| **决策摘要** | 把执行期新增的判断从报告/账本里捞出来，编号接着 `D-NN` |

判据：**如果这个工作流明天被删掉，哪些结论是你希望六个月后还能读到的？** 那些就是要回写的。

## 十节骨架（二级标题，缺一节 `check` 报 ERROR）

```markdown
# <标题>

## 一句话方案
## 背景与目标
## 做法
## 备选与取舍
## 接口与数据形状
## 明确不做
## 实际交付
## 已知限制
## 验收标准
## 决策摘要
```

**这十节是地板不是天花板**：按需要加小节（能力清单、数据模型、部署前置、相关文档……）。加的小节不校验，十节必须都在。

**标题逐字一致，顺序可调**（`check` 核对的是"小节在不在、空不空"，不核对先后）。顺序**按读者的阅读路径排**，不要照抄模板默认顺序：

| 谁在读 | 何时读 | 先给他什么 |
|---|---|---|
| 审方案的人 | 方案门 | 一句话方案 → 背景与目标 → 明确不做 → 备选与取舍 |
| 执行者与机器 | 每次派发（由 `slice` 指引） | 背景与目标 + 接口与数据形状 |
| 半年后的接手人 | 维护、改造、追溯 | 已知限制 → 实际交付 → 决策摘要 |

**开头加一段导读**（两三行，放引用块里），说清哪几节是人审要看的、哪几节是参考型可跳过、哪一节是执行者的契约。人审不该靠猜哪节重要：

```markdown
> **怎么读**：§背景与目标 / §明确不做 / §备选与取舍 是这场改动的判断依据；
> §接口与数据形状 是参考型小节（执行者与机器查考），人审可跳过；
> §已知限制 / §实际交付 是留给后来人的。
```

**参考型小节排到末尾**。`接口与数据形状` 属这类：它是给执行者与机器的签名契约，不是给人读的散文，夹在中间会把人挡在门口。

| 小节 | 写什么 | 不适用时 |
|---|---|---|
| **一句话方案** | 这个改动是什么。读者合上文档能复述出来才算合格。**必须实质**——"实现完成""按计划交付"这类等于没写 | 不可省 |
| **背景与目标** | **为什么做 + 做成什么样**：问题现状（现在是什么样、不改会怎样）、预期结果（做成后谁看到什么不同）、关键约束。**已有设计来源时写承接关系**：源路径 + 继承它哪些结论 + 本次增量/修正 | 不可省 |
| **做法** | 机制**怎么运作**。不是文件清单，不是执行步骤。判据：**每个机制段落 ≤ 6 句，且不出现文件路径清单与符号名清单**——出现了就说明写成了执行步骤，那属于计划的任务块。**不重复背景里的动机**——需要时写成指针（"见 §背景与目标"或"见 `docs/x.md`"） | 不可省 |
| **备选与取舍** | 考虑过的其他做法 + 为什么没选。只有一种做法时写"无备选"+理由 | 不可省 |
| **接口与数据形状** | **参考型**：对外接口签名、数据结构、事件与表形状。**精确到实现者不用再做设计决策**——这个精度是给执行者的，不是给人读的，所以排到末尾 | 可写「无（<理由>）」 |
| **明确不做** | 本次范围外的事 + 为什么排除。防的是"以后有人以为它做了" | 不可省 |
| **实际交付** | **实际交付了什么**：交付物清单（文件/接口/表/脚本/文档）、与计划的偏离及原因、遗留项。起草时写「无（尚未实现——回写时补齐）」是合法的，**收尾时还那样会被拦**（见「回写」） | 起草期可写「无（尚未实现…）」，收尾前必须回写 |
| **已知限制** | 已知的不足、边界条件、失效场景。**最值钱的一节**——写代码的人会走，限制不会 | 可写「无」 |
| **验收标准** | 怎么算做完了，逐条可判定 | 不可省 |
| **决策摘要** | 全部 `D-NN` 的合并视图（见下） | 不可省 |

小节标题必须逐字一致（二级标题 `##`）。**标题在但正文空着会被拦**；十节里两节允许写「无（理由）」，其余空着就是没写。

**「背景与目标」是"为什么"的唯一归属**：这一节写动机与目标，做法节只写怎么运作，计划的 `### 背景与目标` 只写承接、增量与指针。三处不要互相抄——抄了就会有两份真源，改一份忘一份，读者不知道信哪个。需要重复时写成指针。

### 承接已有设计时怎么写

本次改动如果建在既有文档之上（用户给的方案、项目里的既有设计、上一个工作流的产出）：

- **背景与目标**里写明：承接哪份（路径）、继承它的哪些结论、本次增量/修正了什么。**不要重述它已经说过的东西**——那些内容留在源文档里，这里只写指针
- 术语、字段名、表名、接口名**逐字沿用**源文档，不要另起近义名
- 本文档仍要**自包含到能独立读懂**：读者不该被迫去翻源文档才能理解本次改动做了什么。所以"指针"用在不重复上，不用在省略关键结论上

## 决策摘要：决策的唯一长期视图

这一节是"决策不许只留在报告或账本里"的落点，有一条机械校验：

**计划决策表里的每一个 `D-NN` 都必须在这里出现**，否则 `check` 报 ERROR。

**和计划决策表的分工**（两处出现同一个编号是有意的，不要试图合并成一份）：

| | 计划里的决策表 | 本文档的决策摘要 |
|---|---|---|
| 作用 | **需求的锚点**：每个 `D-NN` 必须被至少一个任务引用，`check` 靠它拦范围缩减 | **长期记录**：计划收尾后消失，决策靠它活下来 |
| 状态 | 一次工作流 | 进版本库，半年后还有人读 |
| 写法 | 一行一句话即可（机器要的是编号与来源列） | 可以展开：背景、被否的方案、代价 |

**两者口径不一致时以本文档为准**（计划是一次性的，本文档是留存版），并顺手把计划改齐。计划那个「来源」列不是形式——标 `用户` 的和标 `agent` 的在这里要能分辨，否则回看时不知道哪些是用户拍过的板。

用和计划一致的列，便于对照：

```markdown
| ID | 决策 | 来源 | 理由 |
|----|------|------|------|
| D-01 | 编排 loop 放浏览器端，不进 edge function | 用户 | 要求 1；同时避开 edge 墙钟与网关超时 |
| D-07 | 写操作两段式：draft 不写库、confirm 才写 | agent | 写库不可逆，upsert 会覆盖已有记录 |
```

**运行期新增的决策也写在这里**，编号接着往下排（`D-16`、`D-17`…）。分三种去向：

| 这类决策 | 去哪 | 要不要重新审批 |
|---|---|---|
| 执行期新发现的技术选择、边界裁定 | **只进设计文档**（+ 账本裁决区记"谁在什么时候拍的板"） | 不要——审批绑定计划内容指纹，改计划会让它失效 |
| 改变了**任务范围或验收标准** | **回填计划的决策表**（并落在任务上） | **要**——这是用户批准过的东西被改了，`slice`/`record` 会自动拒绝，重新走计划门 |
| 纯运行时操作取舍（顺序、重试、超时） | 只进账本裁决区 | 不要 |

**账本裁决区 ≠ 决策摘要**：前者是"运行时谁拍了什么板、错的代价是什么"的时间线，后者是"结论长什么样"的合并视图。两者都要有，含混地把裁决当成设计记录，收尾后就没了。

## 篇幅：决策记录，不是过程记录

**一条决策一行加理由。** 会话里当场否掉的方案给一行（名字 + 否决理由），不要复活成一整节重新论证。

| 原则 | 从哪来 |
|---|---|
| 决策记录而非过程记录；被否掉的方案一行带过 | gstack：文档是 decision record 不是 transcript |
| 不重复计划已有内容，只写"怎么做"和"为什么选 X 不选 Y" | OpenSpec：proposal 管 why 和 what，design 管 how；只重复就退化成指针 |
| 接口与数据形状要精确到实现者零设计决策 | gstack：代码只在消除歧义时写，"schema 和 API 形状要写，随手贴的实现片段不要" |
| 不适用的小节写「无（理由）」，不要凑字 | 本 skill：给诚实的省略留出口 |

**没有字数上限**——多出来的长度必须来自"真的还有话要说"（已知限制、取舍、接口细节），不是来自把模板填满。

## 不写什么

- **不写执行流水账**：跑过哪些命令、哪一轮审查发现了什么、谁先写的谁后改的——那是任务报告和 git log 的事。
- **不写会被代码取代的内容**：完整实现、整段测试、逐行算法。写了必然过期，而且读者会以为它可信。
- **不写没有依据的断言**：验证范围之外的行为（"线上一定没问题"）、没实测过的性能、没核实的部署状态。要么标条件句并写清"须核实"，要么不写。这一条是有教训的——一次真实回写里，**四处失实陈述全部靠人工审查才发现**（`grep` 级验收只能证明字符串存在）。
- **不留占位符**：`TODO` / 待补 / TBD 会被 `check` 拦。**确实可以推迟的未知**有合法写法：`**未知**：<是什么> — 待 <条件> 确定 — 不影响 <做法/接口/验收/任务拆分>`。判据是"它会改变做法、接口、验收或任务拆分吗"——会，就现在问用户，别留成未知（见 `plan-format.md`「真正可推迟的未知」）。

## 相对计划的地位

计划是**实现期的契约**（任务、依赖、验收、门），设计文档是**实现后的解释**（是什么、为什么、边界在哪）。两者冲突时：

- 计划与文档不一致 → 以**代码**为准，两个都要改：文档回写对齐实现，计划按需修正（改计划要重新审批）。
- 文档描述了计划里没有的东西 → 先判断它是不是"实际做出来的"。是就补进文档并说明；不是就从文档里删掉——**文档不许描述没做的事**。
- **实现偏离了文档里的决策**（不是文档写错，是实现改了口径）→ **不要默认改文档迁就实现**。先判断哪个是对的：实现对了就改文档并在「决策摘要」里说明口径为什么变；实现错了就改实现。裁定结论必须留痕（改文档说明 / 回填计划重新审批 / 记进「已知限制」）——**悄悄把文档改成实现的样子，等于抹掉了这次偏离**。

修改计划时**不必同步改设计文档**（回写是 E 轮末尾一次性的事）；但改了**方案**影响设计本身时，要顺手把设计文档的对应小节改掉，否则回写时会发现整节都要重写。
