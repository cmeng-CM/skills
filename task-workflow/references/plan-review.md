# 计划语义审查

`check` 全绿之后、计划门之前，对「已批准的设计文档 + 计划」做一次**目标倒推**的语义审查。

## 为什么需要（`check` 不够）

`check` 是机械的：它能证明"每个决策编号都被某个任务引用了""字段都填了""没有占位符"。**它能证明的东西不等于计划是对的。**

它能证明的都抓不到这些：

| 这类问题 | 为什么 `check` 抓不到 |
|---|---|
| 一条决策被引用，但它承诺的行为没有任务承载 | `check` 只比集合：`D-NN` 出现在某任务的「决策」字段就算承载。真实案例：设计文档写明"确认后写入 `dma_assessments`"，而承载它的任务工具清单里只有"分析 / 生成草稿 / 确认工单"三个动作，**没有"保存分析结果"** |
| 任务是缩水版（"先做静态的，动态后续再接"） | 文字看起来完全合理，只有对照决策原文才知道砍了多少 |
| 「预期」写的是实现细节而不是可观察结果 | "用了 jose 库""函数写好了"格式完全合法 |
| 计划与设计文档口径矛盾 | 两边各自自洽，只有并排读才发现 |
| 依赖顺序看着对、实际会互相踩 | 文件重叠是 WARNING，语义冲突它看不出来 |

**这类缺口要靠人/模型读一遍才能发现**，而且**自审会软化**：写计划的人读自己的计划，会把"我心里想过的"当成"纸上写了的"（GSD 的 plan-checker 为此专门写了警告：审查者会给 blocker 降级成 warning 以避免和规划者冲突）。所以这一步**必须派独立 subagent**，不能自己过一遍了事。

## 谁做、什么时候做

| 项 | 要求 |
|---|---|
| 时机 | `check` 零 ERROR 之后，**计划门之前**（此时设计文档也已起草完） |
| 执行者 | **独立只读 subagent**，没参与写计划与设计文档 |
| 输入 | 计划的全文、设计文档全文、**承接来源文档的相关小节**（背景与目标里声明的路径） |
| 成本 | 只读、一次派发。不需要写任何文件 |
| 产出 | 分级问题清单（BLOCKER / WARNING）+ 需要用户拍板的问题 |

派发时**不要在 prompt 里预判 findings**（"不要报 X""这个我们已经知道了"）——那是给审查者省事，等于让它放水。

## 三个维度

### 维度一：覆盖（目标倒推）

**先别看任务清单。** 顺序是：从「背景与目标」的预期结果和决策表出发 → 列出"目标达成必须为真的事" → 再回计划里找谁承载它。

- **每条决策的完整行为都有承载吗？** 逐个决策问："这条决策承诺了几件事？每件事在哪个任务里？"——**引用编号不算承载**，要指出具体的任务动作
- **「明确不做」有没有被偷偷做？**（反向越界：说了不做却排了任务）
- **所有任务的「预期」加起来，能不能推出「背景与目标」里的预期结果？**（漏一环就是目标达不成）
- **缩水语言扫描**：`先做简版` / `暂时静态` / `后续再接` / `先 hardcode 跑通` / `这轮先不管` / `小范围实现`。每命中一处，回去对照决策原文——**砍了就报 BLOCKER**（GSD 把这条定为 always blocker：它是最阴险的失败模式，计划"看起来合规"，因为决策编号确实在）

### 维度二：正确（可执行性）

- 每个任务的 `做法` / `预期` / `验收` / `失败信号` 四件：**换一个执行者拿这个片段，不问问题能做完吗？** 不能就报
- **「预期」是否可观察**：是外部能看到的行为/产物，还是实现细节？
- **「预期」和「验收」是否分离**：预期=应该看到什么，验收=用什么命令/检查证明。只有验收没有预期的，报出来
- **接口逐字一致**：后面任务 `consumes` 的名字，必须和前面任务 `produces` 的**逐字**相同（含类型）
- **验收可判定**："跑通""合理""正常"不算可判定

### 维度三：一致（与已批准物）

- **计划 ↔ 设计文档**：做法、接口、边界口径有没有互相矛盾的地方
- **承接来源**：背景与目标声明承接了哪些文档——**去读那些文档的相关小节**，检查计划有没有违反它已经定下的结论（这是最容易被跳过、也最容易出事的一维）
- **术语/字段名/表名/接口名**是否与源文档、代码**逐字一致**（近义名 = 未来漂移的起点）
- **决策来源**：`check` 只会列出"来源不是『用户』"的决策，但不会判断它们该不该问。这里要判断：凡是属于**输入容错 / 输出格式取值 / 范围边界 / 兼容性影响**四类的，来源不是「用户」就报（该问没问）

## 输出格式

```markdown
## 判定
BLOCKER <n> 条 / WARNING <m> 条

## 问题
| # | 维度 | 严重度 | 依据 | 问题 | 建议 |
|---|------|--------|------|------|------|
| 1 | 覆盖 | BLOCKER | plan.md:T5「接口」+ 设计文档「实际交付」 | 决策 D-08 承诺"确认后落库"，T5 的产物清单里没有保存动作 | 在 T5 或新任务里明确 `confirm_dma` 工具与它的落库函数 |

## 需要用户拍板的问题
- <只在确实需要用户决定时才列；没有就写"无">
```

**每条问题必须给依据**：计划行号（`T5` + 字段名）或文档小节名。引不出依据的判断不写进报告——那是猜测。

## 纪律

- **不报纯风格问题**（措辞、排序、命名偏好）——噪音会让人忽略真问题
- **没核对的地方写"未核对"并说明原因**，不要写"看起来没问题"。**声称核对过但拿不出依据，比诚实地说"没核对"更糟**
- **不因为计划写得详细就降低标准**：详细 ≠ 正确
- **不替用户拍板**四类敏感决策——发现了就列为"需要用户拍板的问题"
- 审查结论**不写文件**（这是只读审查），直接附在计划门的呈现里

## 处理

| 结果 | 动作 |
|---|---|
| 有 BLOCKER | 改计划或设计文档 → 重跑 `check` → **重跑本审查**（只核改动涉及的部分）→ 才可呈报计划门 |
| 只有 WARNING | 连同结论一起呈给用户，由用户在计划门决定接受或修正 |
| 零发现 | 在计划门呈现里写明"已做语义审查，未发现问题" |

改了计划就会让计划审批失效（内容指纹变了）——这一步发生在**审批之前**，所以不额外产生一次重新审批。
