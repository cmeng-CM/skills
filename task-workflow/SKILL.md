# Task Workflow

把需求变成 `<project>/.workflow/<slug>/` 下的计划与账本，逐任务派 subagent 执行，最后用可执行的外部证据验证到通过。计划与进度落在磁盘上，所以上下文被压缩或清空后仍能精确接续。

引擎脚本在**本 skill 目录**下（即本 SKILL.md 所在目录的 `scripts/workflow.py`，下文记作 `$W`）。各客户端通过软链指向同一份文件，所以从任意客户端的 skills 目录取到的都是同一个脚本。安装后可用 `python3 ~/.agents/skills/task-workflow/scripts/workflow.py` 直接调用。

所有状态操作都走 `$W`——不要手改计划里的状态字段和账本表格。

**守卫：**

- **没有计划不执行。** 执行轮的前置条件是一份通过了 `check` 的 plan.md。直接开干等于放弃这套机制的全部价值。
- **没有外部证据不算完成。** 模型自述"做完了"不是证据。跑验证命令、看退出码、对内容指纹——这才算。
- **提交是任务的一部分，推送不是。** 每个任务（或批次）完成即**自动提交**，不逐次问用户；**分批、分阶段**——别把几个任务攒成一次提交（审查范围与中断恢复都依赖它）。**push / merge / rebase / 发布等远端动作必须停下来问用户**，自动的只有本地提交。
- **计划是唯一的任务来源。** 不在计划里的工作不开工；发现该做的事，先写进计划再执行。
- **边界。** 本 skill 自包含：只做「需求 → 计划 → 执行 → 验证」，需求有歧义时由它自己一次一个问题澄清（见 P1 第 1 步），**不转交、不探测别的 skill 在不在**。理解陌生项目、把产出写回别处都不是本 skill 的事——账本本身就能跨会话恢复，所以**也不需要另做交接文档**。
- **设计文档独立于状态控制。** 计划、账本、事件与报告活在 `.workflow/`（自忽略，保留用于恢复与历史收尾），所以设计记录必须另有一份、**落在项目仓库里**：机制、取舍、接口、边界、限制、决策。没有它，"这次改动是什么"在工作流结束后就无从追溯。见 `references/design-doc.md`。
- **方案只写一遍。** 声明了设计文档时，方案的正文归它（「一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做」五节），计划的 `## 方案` 只留承接、增量与指针，方案审批的指纹也绑在设计文档那五节上。写两遍就会改一处忘一处，读者不知道信哪个。
- **十节是工作流的形状，不是对方案的要求。** 从外面承接一份方案时，**对齐是工作流的动作，不是用户的义务**——只动标题、不动内容；不能对齐（文档有外部格式约束、要送评审、被别人大量引用）就另起一份写增量，**绝不要求用户改自己的文档来迎合模板**。机制该去适配文档，不是反过来。
- **gated 的门审的是判断，不是执行细节。** 方案门和计划门给人看的是散文、边界与用户拍过的板；任务的执行字段（`做法`/`预期`/`接口`/`验收`/`失败信号`）不进门的呈现。execution 不呈现、不等待，但同样要做计划语义审查。走过场的审批比没有审批更糟——它留下一个"已批准"的假象。
- **判断和决策不许留在报告里。** 报告只装证据（命令、产物、偏离、阻塞）；技术选择与裁定必须上浮到设计文档，改变了范围/验收的才回填计划并重新审批。`.workflow/` 不入版本库，长期判断不能只留在其中。
- **收尾之后不由本 skill 决定。** 工作流跑到验证通过、报完账本就结束。要不要把产出写回别处（项目契约、长期记忆、知识目录、周报），由用户自己判断——**本 skill 不代判、不探测、不代办**。

- **工作流与审批门是两件事。** 进入工作流是为了留下计划、执行、验证和回溯证据；审批门只在工作流产生新的范围、方案、取舍或用户契约判断时出现。明确规格、范围和验收且没有新增判断的工作，可以走 execution 模式，不停方案/计划门；但仍须 `check`、独立审查、终审、`verify` 和 `close`。
- **execution 不是按体量开的快路径。** 不得因为文件少、任务少、看起来简单就自行免门；必须有明确的规格/范围/验收依据，并记录为什么没有新增用户判断。不确定就走 gated。
- **阶段边界必须停，等用户明确答复。** gated 计划写完必停；gated 方案这一步只在"方案是工作流内新做出来的"时才停——**用户进入工作流之前就定稿的方案没有待审内容**，那一步换成记锁（见第 5 步情形一）。execution 模式没有这两次人工等待，但不代表省略计划质量检查。
- **没有答复不等于可以继续。** 用户没回答就停住并报告，把问题留在那里等——不要用"没收到答复"当默许
- **但阶段内部不要停。** 执行轮里能自己拍板的事自己拍板并记账，不为每个小决定打断用户
- **只读的活可以并行，写操作一律串行。** 调研、多路审查、排查多个独立失败——这些不写文件，放心并行，等待时间直接除以 N。改文件的实现者一次只派一个（写面没隔离，见 `references/dispatch-protocol.md`）

**反模式（明确不要做的事）：**

- 不要在需求还有歧义时硬写方案——那是"计划会乱"的直接原因
- **不要在已有设计来源时从零写一份薄方案**——该做的是承接它、只补缺口（见 P1 第 3 步）。重写一份薄的，此后没人知道哪份是准的
- 不要在方案门/计划门处"呈现完就顺手开始做"——呈现和开工在同一口气里完成，等于没有门
- **不要跳过计划语义审查**——`check` 全绿只证明"引用齐、字段全"，不证明计划是对的（见 P2 第 9 步）
- 不要用"用户没回答"当作默许继续——那是绕过门，不是通过门
- 不要把整个 plan.md 塞给执行者——用 `slice` 抽单任务片段
- 不要让实现者自己审查自己的代码
- 不要在审查 prompt 里写"不要报 X"，那是预判
- **不要并行派发多个实现者**——它们会改同一个工作树（**但只读 agent 并行是允许且鼓励的**）
- 不要把同型机械改动拆成一文件一任务，也不要逐个派——合成一个任务或一批
- 不要让控制器（你自己）动手修代码——写和审必须解耦
- 不要在**执行阶段内部**停下来问"要不要继续"——能自己拍板的事自己拍板并记账
- 不要在验证红灯时说"基本完成了"
- 不要在计划里留任何占位符（TBD / TODO / 待补）——`check` 会拦，但别浪费那一轮
- **不要把设计文档写进 `.workflow/`**——那是自忽略目录，状态记录虽保留，长期设计仍须入库
- **不要把技术判断、裁定留在任务报告或账本里**——不许只活到工作流结束
- **不要在 `verify` 之后才回写设计文档**——指纹失配，`close` 会拒绝收尾
- **不要为了让它过 `check` 去改用户的文档**——标题对齐是工作流的动作；对不齐就另起一份写增量，不要动别人已定稿的结论与结构
- **不要让同一份方案写两遍**——声明了设计文档时，正文在文档那五节，计划只留承接、增量与指针
- **不要把任务块的执行字段端到门上**（`做法`/`预期`/`接口`/`验收`/`失败信号`）——那是给执行者的逐字指令，端上去只会让人挑措辞，门就变成了橡皮章

## Working Protocol

### 门：轮次路由

先判定该走哪一轮，判据是状态文件而不是对话记忆：

```bash
$W status          # 报告阶段与任务状态；无 slug 时要求只有一个活跃工作流
```

| 用户的话 / 观察到的状态 | 轮次 |
|---|---|
| 要新做一件事，且没有对应工作流、没有明确规格 | **P 轮 · gated**（方案 → 计划） |
| 用户已给出明确规格/范围/验收，要求直接落地，且没有新增判断 | **P 轮 · execution**（计划 → 执行，不停审批门） |
| 要修一个 bug（有症状、能复现） | **P 轮 · bug 路径**（`init --bug`，专用补偿控制） |
| 方案写好了、等用户看 | **P 轮 · gated 停在方案门** |
| 计划写好了、等用户看 | **P 轮 · gated 停在计划门** |
| 有 execution 工作流，还有未完成任务 | **E 轮 · execution**（执行，不走审批门） |
| 有 gated 工作流，还有未完成任务 | **E 轮 · gated**（执行前需两道门） |
| 全部任务 complete、尚未 closed | **V 轮**（验证、补证或等待必验人工） |
| status 为 closed，只问状态 | 报告历史收尾，不因无关提交重验 |
| closed 后明确要求修补原目标 | `reopen --reason --by --work`，补齐新增任务后回 P/E；原修补请求即授权 |
| 提出不同的新目标 | `init <新 slug> --from <原 slug>`；不强行 close 仍待验的旧工作流 |
| 明确说"验证一下" | **V 轮** |
| 明确说"执行 T3" | **E 轮**（只做 T3） |
| "看看进度" | 只读，报告后停 |
| "计划改一下" | **P 轮**（改计划、重跑 check 和语义审查；gated 重新审批，execution 若产生新判断先 `gate` 升级） |
| 用户对方案的答复（"可以"/"换个做法"） | **P 轮**：记审批，或按反馈改方案重新呈现 |
| 用户对计划的答复 | **P 轮**：记审批后进 E 轮，或改计划重新呈现 |

### 两套"停"的规则，不要混

- **gated 的阶段边界必须停，等用户明确答复。** 方案写完停一次，计划写完停一次。**"没收到答复"不等于"可以继续"**——没有答复就停住并报告，把问题留在那里等。
- **execution 不在这两处停，但仍必须先写出完整计划并通过 `check`。** 它省的是人工审阅等待，不是计划、审查、验证或收尾。
- **阶段内部不停。** 任一路径的执行轮里能自己拍板的运行时细节自己拍板并记账，不为每个小决定打断用户。逐任务的审查由 subagent 做，不找用户。

前一条是**判断门**，第二条是**已明确规格下的执行路径**，后一条是**自主推进**。历史上两边的失败都真实发生过：门不闭合会导致"计划乱、内容不全"（没人拦），而阶段内频繁停会让人守着屏幕（有会话在一个本可自己拍板的问题上停了 9 小时）。**该硬的是新判断的边界，不是所有工作的等待。**

**上下文被清空后的恢复**：不要相信自己对这个工作的回忆。先跑 `status`，对齐 `plan.md`、旧 `ledger.md`、`events.jsonl`（存在时）、输出 receipt/报告与 `git log`。新验证、人工结论和生命周期以事件为准；账本新事件区只是呈现。账本的审批模式元数据先告诉你这是 gated、execution 还是 bug；gated 再看 `## 审批` 段，execution 不把空审批表误判成漏记。

多个活跃工作流且用户没指明是哪个时，列出来让用户选，不要猜。

### P 轮：需求 → 计划（按审批模式分流）

进入 P 轮先判定审批模式：

- **gated**：本次仍需由工作流产生或确认范围、方案、取舍、兼容性、数据/安全边界或用户可见契约判断；按 P1 → 方案门 → P2 → 计划门执行。
- **execution**：用户已经给出明确规格、范围、实现规则和验收，本次没有新增用户判断；仍按 P1/P2 生成计划、做 `check` 和独立语义审查，但不在方案门、计划门停下来，也不调用 `approve`。创建时必须显式使用 `$W init --execution --execution-reason`，不能由 agent 按任务大小自行推断。

execution 仍需读项目约定、承接已有设计、确定设计文档归属、写决策与任务、检查验证覆盖；省的是人工等待，不是计划质量、审查、验证和回溯。

#### P1 · 需求 → 方案（gated 才有方案审阅门）

**第 1 步 · 判需求是否够清楚，不清楚就澄清。**

出现以下任一条，就是**不清楚**，先澄清再写方案：

- 同一句话能合理理解成两种不同的东西
- 目标里有无法定量的形容词（"优化一下""更流畅""好用一点"）
- 用户没明说、但会改变计划结构的关键决策（技术栈、范围边界、兼容性要求）
- 打算写「决策」表时，发现有决策根本写不出来——说明需求本身没定

**澄清由本 skill 自己做**（不转交、不探测别的 skill 在不在），做法固定：

- **一次只问一个问题**，等回答再问下一个。一次抛五个会让人无从答起——那正是"计划会乱"的源头
- **每个问题附上你的推荐答案**，让用户确认或纠正，不要让他从零作答
- **事实自己查，决策问用户**：能从代码、文档、文件系统里查到的不问；但选择权在用户的必须抛给他。**哪些决策必须问、哪些可以自己定，第 7 步有判据**（不是所有决策都问）
- **问题能一句话说清之前，不给方案**——用户口中的"解法"往往不是真问题
- **答案要落账**：澄清得到的每个结论先记下来，第 7 步写「决策」表时落成 `D-NN` 行、**来源记 `用户`**——那张表的可信度全靠这里的答案是真的从用户那儿问来的

需求本来清楚就直接进第 2 步，**别为了走流程而走流程**。反过来，**有歧义时硬写方案是"计划会乱"的直接原因**。

**第 2 步 · 拿项目约定和验证命令。**

直接读项目根的 `AGENTS.md` / `CLAUDE.md` / `README.md`，从里面取两样东西：

1. 项目用什么测试/构建命令 —— V 轮的验证命令来源
2. 项目有哪些必须遵守的约定 —— 会进计划的全局约束

读不到就**问用户一次**，答案写进 plan.md 的验证命令块，之后每次验证都用它。**绝不猜默认值**——宁可标 `未声明`，也不要写一个想当然的 `npm test`。

**第 3 步 · 承接已有设计（有来源时不能跳过）。**

写方案之前先查：这次改动是不是建在既有文档之上——用户给的路径、项目 `docs/` 下的既有方案与设计文档、前一个工作流留下的设计记录。

**先问一句再判**：用户嘴上说"按这个方案做"的时候，确认那份方案**是不是覆盖本次全部范围**——它是"这次改动的方案"，还是"更大的路线图里关于这次的那一段"？这一问决定下面走哪条路，问错两条都会错：要么抄一遍产生两份真源，要么把总纲当成本次设计文档、范围失控。

**有来源时，先判一件事：源文档的范围，和本次工作流的范围相等吗？** 这一步决定设计文档是谁的。

- **相等**（它就是这次改动的方案）→ **外来来源**：不另起文档，把 `**设计文档**:` 直接指向它。**不要抄一遍**——抄一遍就产生两份真源，而且实测会丢东西（一次真实承接里 12 条决策丢了 6 条理由，源文档归档后再也查不到"当时为什么这么定"）。对它做的四个动作见 `references/design-doc.md`「外来来源」一节。
- **更大或是别人的**（例如一份 P0–P5 的总体方案、本次只做 P0）→ **自生来源**：另起一份写本次增量，源文档保持不动。

**判完范围，四步读法照走**（两条路都要走；外来来源要读得更细，它是你要锁的正文）：

1. **列清单**：哪些文档讲的是同一个模块/同一件事（判据是内容，不是文件名像不像）
2. **过滤读**：先看目录、决策摘要、小节标题——别一上来把整份大文档拉进上下文，那会挤掉真正要做的事
3. **决策前完整读**：决定"哪些已经定了、哪些要改"之前，把相关小节**完整读一遍**。只读摘要会漏掉约束、边界和已否决的方案，于是把定过的事重新讨论一遍
4. **归位**：已定过的结论**不重写**——自生来源只写增量与修正，承接关系写进 `### 背景与目标`（源路径 + 继承什么 + 本次增量是什么）。术语、字段名、表名、接口名**逐字沿用**源文档，不要另起近义名

**走了哪条要在方案门或计划门的呈现里说明**——判错要能被看见。

**没有来源也要把"没有"写清楚**：背景与目标写问题现状与预期结果即可，不必强凑承接关系。反过来，**已有来源却从零写一份薄方案**是本 skill 明确要防的失败（此后没人知道哪份是准的）。

**第 4 步 · 建工作流骨架，定方案的载体，写方案。**

```bash
# gated（默认）
$W init <slug> --goal "<一句话目标>"

# execution（只有规格、范围、规则和验收已明确且没有新增用户判断时）
$W init <slug> --execution --execution-reason "<规格/范围/验收来源，以及为何没有新增用户判断>" --goal "<一句话目标>"
```

先定**方案的正文写在哪**——计划头部的 `**设计文档**` 必填，它同时决定了这件事：

```
**设计文档**: docs/<模块>方案.md     ← 方案正文写在它里面（格式 3 起）
**设计文档**: 无 — <理由>            ← 方案四段写在计划的 `## 方案`
```

**命中任一条就必须写一份，不能声明「无」**：跨模块改动或引入新架构模式 / 新增外部依赖或数据模型实质变化 / 涉及安全·性能·迁移复杂度 / 需要先定技术决策才能开工。其余情况可以写「无 — <理由>」，但理由要站得住（`check` 会把「无」作为警告在计划门上呈现，用户看得见）。

**方案只写一遍**。声明了设计文档时，四段的正文写进它的「一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做」五节，计划的 `## 方案` 只留承接关系、本次增量与指针；**方案门审的就是设计文档那五节，方案审批的指纹也绑在它们上面**。声明「无」时，四段写在计划里。写两遍的代价是改一处忘一处，读者不知道信哪个。

`背景与目标` 写为什么做与预期结果（承接关系也在这一节）；`做法` 写**机制怎么运作**，不是文件清单，也不是执行步骤，**不重复动机**——重复就会有两份真源。篇幅**随任务规模伸缩**：小改动 2-3 句话就够。gated 的方案门不因任务小而省；execution 是否无门看的是规格、范围、规则和验收是否已明确且没有新增判断，不看任务大小。十节骨架与每节要求见 `references/design-doc.md`。

**第 5 步 · 🚧 方案门（gated 才执行）。**

**execution 不进入这道人工门**：它仍起草方案承载位、写决策和做语义检查，但用户已经给定规格且没有新增判断，所以不暂停、不调用 `approve`。gated 才继续按下面三种情形判定方案门形态：

**情形一 · 外来来源（无门，只记锁）。** 源文档就是这次改动的方案，由用户在进入工作流之前定稿并看过，**没有待审内容**。这里只做一个动作：确认结构对齐已做完（见 `references/design-doc.md`「外来来源」）→ 记指纹与依据。

```bash
$W approve <slug> 方案 --by "承接自 <源文档路径>，用户于 <日期> 定稿并授权按此执行"
```

**这不是"agent 绕过门"。** 门的职责是让人审新做出来的东西，这里没有新东西可审；守卫里"不得自行绕过门"禁的是**替你拍板**，不禁止把**你已经拍过的板**记成基线。但依据必须写清承接自哪份、什么时候定的——那是以后追溯"当时锁的是哪一版"的唯一线索。

**情形二 · 自生来源（审阅形态）。** 方案是在工作流内起草的，呈现方案正文（一句话方案 / 背景与目标 / 明确不做 / 备选与取舍，最多再加一段做法）+ 决策表里**来源为 `用户`** 的条目。人要回答：方向对吗、取舍接受吗、边界划得对吗。

```bash
$W approve <slug> 方案 --by "<用户的原话>"
```

**情形三 · 方案被改动（变更门）。** 五节一改，指纹失效，必须重过门。**这时只呈现 diff**——改了什么、为什么、影响哪些任务；不要重念全文。**用户自己在别处编辑了那份文档也算变更**（那是有意识的行为，不是异常），正确反应是停下来给他看 diff，不是报错、也不是自动重批。

**三种情形下，人都不需要审的**：字段齐不齐、依赖成不成环、验证覆盖对不对得上、每步能不能执行——那四件事分别由 `check`、独立语义审查、逐任务审查与整体终审承担，在这里再让人看一遍，只会把人推成橡皮章。

用户说要改，就改方案再呈现一次。**不要在没有答复的情况下继续写计划**，也不要把呈现和开工放在同一口气里完成——那等于没有门。

#### P2 · 方案 → 计划

**第 6 步 · 补齐设计文档（或已声明「无」，无需动作）。**

设计文档是**计划之外进入版本库的长期设计记录**（计划/账本/报告在自忽略的 `.workflow/`，收尾后仍保留，但不能代替入库的设计记录）。路径在第 4 步已经声明、四条"必须写一份"的判据也在那里判过；gated 在方案门之后、execution 在计划检查和语义审查之前，都要把它写全。

**声明了路径的**：方案的五个小节早在第 4 步就起草完、并已过方案门，现在补齐其余小节——`决策摘要` 与 `验收标准` 此时能写；`接口与数据形状` 要**精确到执行者不用再做设计决策**（那是它做判断的依据，缺了它执行者只能自己发明），可以现在写全，也可以先写关键签名；`已知限制` 与 `实际交付` 往往要等实现把东西做出来——**那是回写的事**（E 轮末尾），别在这里编。`实际交付` 起草时写「无（尚未实现——回写时补齐）」是合法的，收尾前必须换成真的清单。

**方案那五节不要再动**：它们是刚批准过的东西，改动会让方案审批失效（这是正确行为，只是别在收尾阶段才发现——回写也只动接口/限制/交付/决策摘要那几节）。

十节骨架、小节顺序（参考型小节排末尾）、每节要求、承接与回写规则见 `references/design-doc.md`。`check` 会核对：文件存在、十节齐全、无空节、无占位符、`决策摘要` 覆盖全部 `D-NN`。

**第 7 步 · 写任务与决策。**

- **决策表**：把讨论中敲定的每个决策编号 `D-01`…，并标注**来源**（`用户` / `agent`）。这张表是需求的锚点，后面每个任务都要引用它——漏一个都会被 `check` 拦下
- **决策的来源不是形式**：属于「**输入容错**（遇到非法输入是报错还是跳过）、**输出格式取值**（字段名、精度、单位）、**范围边界**（做什么不做什么）、**兼容性影响**（是否破坏既有行为）」这四类的决策，**必须停下来问用户一次**，不能自行决定后只记进表里。其余细节可以自行决定并标 `agent`。判据是"这个选择会直接影响用户看到的行为吗"——会，就问
- **任务**：垂直切片（每个任务穿过它需要的全部层，不要"先 DB 阶段再 API 阶段"）；**一个任务 = 一次派发能做完、有自己的验收、值得一次独立审查的交付单元**——"2-5 分钟"约束的是 `做法` 里的步骤（2-8 步），不是任务本身；单任务不超过 5 个文件
- **同型机械改动合成一个任务**：改常量、改字段名、同样的调用替换重复在多处时，那是**一个任务**（可覆盖多个文件），不是一文件一任务。判据是"这次改动需要自己的判断、自己的测试、自己的审查面吗"——不需要就合并。拆成三个任务 = 六次派发（实现者+审查者各三次），合成一个只要两次，**而审查、验证、覆盖审计一样不少**。这不是按体量开快路径，是省掉纯重复的流程
- **每个任务十个字段都要填**。四个判定性字段各管一件事，别写混：`做法`（这一步具体做什么：动作+关键取值+边界，判据是"换个执行者不追问就能做完"）→ `预期`（做完后应观察到什么，必须是**外部可观察**的，不是"实现完成"这类实现细节）→ `验收`（用什么命令/检查证明）→ `失败信号`（什么现象说明没做对）。没有失败信号的验收标准等于没写
- **写 `## 验证覆盖`**：每条决策都要说明"用什么证明它对"，并**显式列出不验证的部分**。验证范围不写出来就是隐式的、无法审查——而没验证的东西才是风险所在
- **接口字段写精确签名**：执行者只看得到自己那一个任务，`接口` 是它了解邻居任务用什么的唯一渠道
- **用户可见的改动要带上文档任务**：这次改动如果改变了用户可见的命令、选项、输出或行为，计划里要有一个更新 README/用法文档的任务；决定不更新时，把它作为一条决策写清理由。漏掉文档不会让测试变红，所以它只能靠计划兜住

**第 8 步 · 检查计划，必须过。**

```bash
$W check      # 有 ERROR 时任何路径都不得进执行轮；gated 还不得申请审批
```

`check` 会查：依赖引用是否存在、有没有循环依赖、必填字段（格式 2 起还有 `做法`/`预期`）、审批模式是否合法、决策是否都有任务承载（范围缩减检测）、决策来源、占位符、规模、验证命令是否声明、方案的 `背景与目标` 是否在，以及**设计文档**（声明了没有、文件在不在、十节齐不齐、`决策摘要` 有没有覆盖全部 `D-NN`——决策不许只留在报告里）。execution 和 gated 都必须零 ERROR；只有 gated 还需要随后申请审批。

根据反馈修计划，直到零 ERROR。这一步不能跳过——**计划里的洞，到执行轮会变成返工，代价高一个数量级。**

**第 9 步 · 计划语义审查（`check` 之后、计划门之前）。**

`check` 是机械的：它能证明"每个决策编号都被引用了""字段都填了"，**证明不了计划是对的**。派一个**独立只读 subagent**，按 `references/plan-review.md` 做目标倒推审查，三个维度：

- **覆盖**：两条都要核。① 每条决策的**完整行为**都有任务承载吗（引用 `D-NN` 不算承载，要指出具体任务动作）；② **决策里点名的每个落点**都在任务里有对应吗——**决策里出现的每个名词（文件、配置项、标识符）都要能指到承载它的任务**。②是有实测教训的：一条决策写"把 X 一并收尾"，而 X 在工程里有两处同义落点，任务只改了其中一处，`check` 全绿、覆盖审计报无缺口，最后是整体终审才发现的。另核有没有缩水语言（"先做简版""暂时静态""后续再接"）
- **正确**：换一个执行者拿任务片段，不追问能做完吗；`预期` 是否可观察；接口 `consumes`/`produces` 是否逐字一致
- **一致**：计划与设计文档口径有没有矛盾；**去读背景与目标声明的承接来源**，检查有没有违反它已定的结论；四类敏感决策的来源是不是真的问过用户

- **有 BLOCKER**：改计划或设计文档 → 重跑 `check` → 重跑审查（只核改动涉及的部分）→ 才可呈报计划门
- **只有 WARNING**：连同结论一起呈给用户
- 审查结论**不写文件**，附在计划门的呈现里

**为什么必须独立派发**：写计划的人自己读会自动补全——心里想过的会被当成纸上写了的。真实案例：设计文档写明"确认后落库"，承载它的任务清单里却没有保存动作，而决策编号齐全、`check` 全绿。

**第 10 步 · 🚧 计划门（gated 才执行）。**

execution 在第 9 步语义审查无 BLOCKER 后直接进入执行轮，不呈现、不等待、不调用 `approve`；gated 才把计划**连同第 9 步的语义审查结论**一起呈现给用户，**停下来等明确答复**。呈现的只有这些：

- 目标（`Goal`）与方案的指针——方案正文在设计文档里、已过方案门，这里不必重念
- 决策表里**来源为 `用户`** 的条目
- 阶段名与任务名清单（`### Phase …` 与 `#### T<n> <名称>` 的标题，**不展开任务块正文**）
- 验证覆盖的概要：每条决策用什么证明、显式不验证的是什么
- 第 9 步语义审查的结论（BLOCKER / WARNING）

**不呈现**任务的 `做法` / `预期` / `接口` / `验收` / `失败信号`——那五个字段是写给执行者的逐字指令（`slice` 抽出来派发用的），不是给人做判断的材料。把它们端上桌，人只会挑措辞。

**在这个门上，人要回答的是**：范围对不对、有没有漏的大块、有没有把说好不做的事又做进去、遗留项接受吗。**人不需要审的**：字段齐不齐、依赖成不成环、验证覆盖对不对得上、每步能不能执行——前两类是 `check` 的活，第三类是 `verify` 与覆盖审计的活，第四类是独立语义审查与整体终审的活。人在这里把这些再看一遍，只会把门变成橡皮章；而**走过场的审批比没有审批更糟，它留下一个"已批准"的假象**。

**这道门不因方案走了外来来源而省。** 方案是用户定过的，"方案怎么拆成任务"却是新做的功课——用户没见过这一步，范围判断在这里仍是必要的判断。方案门削掉的是"重审已经谈过的方向"，不是"审新做出来的东西"。

```bash
$W approve <slug> 计划 --by "<用户的原话>"
```

**gated 的两道审批是机器强制的**：`slice` 和 `record`（也就是派发任务和记录完成）都会检查审批是否存在，以及**方案/计划是否在审批之后被改动过**。批准后偷改计划 → 审批自动失效 → 必须重新审批。execution 由同一入口识别为无门模式，但不能因此跳过 `check`。

**变更后重过门时，只呈现 diff。** 批准之后改方案或计划（执行中发现要扩范围、换做法、加任务，或者你自己去编辑了那份设计文档），审批会自动失效、必须重过门——**这个时刻才是真正需要人判断的时刻**。此时不要重念全文，呈现三样就够：**改了什么、为什么改、影响哪些决策与任务**。门第一次出现时已经把基线锁过，重过门的意义只在于"这次变化接不接受"。

**门与独立审查的分工写死**：门负责**范围与取舍**（做什么、不做什么、边界在哪、遗留项接不接受）；**覆盖的有效性归独立审查**——第 9 步的语义审查与最后的整体终审，不是门的活。这条分界是有实测依据的：一次真实工作流里 `check` 全绿、覆盖审计报无缺口，但一条决策承诺的落点里有两处同义位置只改了一处，最后是整体终审发现的——**机械校验会漏，补它的是独立审查，不是让人在门上再看一遍**。

**没有答复时的正确行为**：停住，把"正在等用户对方案的答复"作为状态报告出来，不要用"用户没回答"当作默许继续。用户明确说"直接做，不用给我看"时，用 `--by "用户说：直接做，不用给我看"` 把用户的话记成审批依据——**是用户绕过门，不是你自己绕过**。

### execution 路径（不走审批门，但仍走完整工作流）

execution 不是 bug 的别名，也不是按规模开的快路径。只有用户已经给出明确规格、范围、实现规则和验收结果，且本次没有新增方案、取舍、兼容性、数据、安全、性能或用户可见契约判断时，才可以在 `init` 时显式选择：

```bash
$W init <slug> --execution --execution-reason "按用户给定规格落地；范围、规则和验收已明确，没有新增用户判断"
```

它仍然必须经过：

- 完整 `plan.md` 与 `check`；
- 独立计划语义审查；
- 每个任务的独立实现审查与阶段 Checkpoint；
- 整体终审、设计文档回写、验证覆盖审计、`verify` 和 `close`。

它只省两次人工等待和对应的 `approve` 指纹门，不省质量控制。**不确定就走 gated**；不得因为文件少、任务少、截图里列了多条、或“看起来简单”自行选 execution。

执行中出现以下任一情况，立即停止相关派发并升级：要改变方案或范围、任务验收，改变公开接口/默认行为/兼容性，涉及数据/安全/性能边界，或原规格出现多个合理解释：

```bash
$W gate <slug> --reason "<新增判断及其影响>"
```

升级后只呈现这次变化的 diff；`slice`/`record` 会重新要求方案门和计划门。不能手改 `**审批模式**`，也不能把新判断留在报告里继续走 execution。

### bug 路径（免两道门，但另有三项强制）

bug 的"需求"是一个**症状**而不是规格，没有可审的方案——要做的事已经被症状决定了大半。所以 bug 工作流**免两道审批门**。

```bash
$W init <slug> --bug --goal "<症状>"
```

补偿控制是**三项强制**，它们替代门起的作用：

| 强制项 | 为什么 |
|---|---|
| `## 复现`——可复现的最小步骤或命令 | 没有可复现的失败，就无法证明修好了。**修之前先确认它确实失败** |
| `## 根因`——说清为什么错 | 说不清根因就只是在让症状消失，换个输入就复现 |
| **回归测试**——验证覆盖表里必须有一行标为回归测试 | 修复不带回归测试，同一个 bug 会回来，而且回来时没人记得修过 |

`check` 会拦空节和缺失的回归测试；`verify` 会核对回归测试**真实存在**；`close` 照旧要求验证通过。

**验证比常规更严**：复现用例必须从失败变为通过 **+ 全量测试不回归**（修复最容易打破别处，特别要检查是否改动了共享函数或默认值）。

**不夹带无关改动**——顺手重构是 bug 修复最常见的坏味道。要重构就单独开一个工作流。

**期望行为要确认一次**：有时"bug 报告"本身有歧义——用户觉得是 bug，其实是有意行为。所以开工前用一句轻确认："当前行为是 X，期望行为是 Y，是吗？" 这不是审批门，是确认对问题的理解。

**升级条件**：复现不出来 / 根因不明 / 需要改 3 处以上或跨模块 / 涉及数据正确性、安全、并发 / 发现要改的是一段设计 —— 任一命中就改走 gated 路径（此时它实际是"探索 + 改造"，不是"修复"）。

### E 轮：逐任务执行

```bash
$W next                    # 依赖图算出的可执行任务（不是线性从头做）；会提示哪些可合并
$W slice <slug> T3         # 抽出 T3 的派发片段
$W slice <slug> T3 T4 T5   # 合并成一批：同型机械改动才这么做（见下）
```

**同型机械改动的逃生通道**：如果计划里已经有几个同型的小任务（改常量、改字段名、加日志），**不要逐个派**——`slice` 给多个任务，一次派发、一次审查、一次 `record`。引擎会先挡掉三类不该合并的情况：批次内含相互依赖、有任务已完成或被阻塞、超过 4 个任务。**判据是任务形态不是数量**——需要自己写测试、自己的判断、自己的审查面的任务必须单独派。详见 `references/dispatch-protocol.md`。

派发、报告契约、四态分诊、fix loop、裁决规则**全部按 `references/dispatch-protocol.md` 执行**。这里只列每轮的固定动作：

1. `next` 拿到可执行任务
2. **记录 base commit**（`git rev-parse --short HEAD`）——它就是本任务提交范围的起点，`slice` 生成的片段里也会带上这个值
3. `slice` 生成片段，派给 subagent（片段里的**提交契约**要求它做完自己提交：只 stage 自己的文件、提交信息 `T<N>: <任务名>`、不 push）
4. 子 agent 回来（≤15 行 + 报告文件，含提交范围 `<base7>..<head7>`）
5. **派第二个 subagent 独立审查**（双判决：规格符合 + 代码质量）
6. 有问题走 fix loop（修复也要提交，范围会自然延伸）；通过则记账：

```bash
$W record <slug> T3 --commits <base7>..<head7> --verdict clean
```

7. **阶段末核对 Checkpoint**：`record` 的输出里出现 ▸ 提醒时（说明本阶段任务已全部完成），**推进下一阶段之前逐条核对本阶段的 `**Checkpoint**` 是否成立**，核对结论记进账本「裁决」区。引擎只提醒、不校验——"检查点成立没成立"要人判，所以这一步在规程里，不在机械校验里
8. 回到第 1 步

**提交由实现者做，不是控制器做**：它有上下文、知道改了哪些文件；而且中断时工作不会丢在未提交状态。控制器只校验范围（`record` 会查 sha 是否真实存在、base 是否为 head 的祖先、范围是否为空）。**确实无需改动的任务**（核实后不用动）要把理由写进 `--note`，否则空范围会被拦。

**自动提交 ≠ 自动推送。** 本地提交每个任务都做，不需要问；`push` / `merge` / `rebase` / 发布必须在用户明确要求后单独做——它们在下面这四类里。

**裁决不停机。** 需要拍板的事自己定并记进账本：

```bash
$W record <slug> T3 --note "<决定> — <理由> — <错的代价>"
```

只有四类事必须停下来问用户：不可逆/破坏性操作、安全敏感动作、工作区之外的副作用（merge/push/发布）、计划坏到每条路都是猜。

**裁决要归位，不能只进账本。** 执行期做出的判断按三种去向处理，别让它只活在账本里（账本在 `.workflow/`，不进入长期版本记录）：

| 这类判断 | 去哪 | 重新审批吗 |
|---|---|---|
| 新的技术选择、边界裁定 | **设计文档的「决策摘要」**（编号接着 `D-NN`）+ 账本裁决区记时限与代价 | 不要 |
| 改变了任务范围或验收标准 | **回填计划的决策表**并落在任务上 | **要**——审批会因内容变更自动失效 |
| 纯运行时操作取舍（顺序、重试、超时） | 只进账本裁决区 | 不要 |

### E 轮收束：整体终审（不可跳过）

所有任务都 `complete` 之后、进入 V 轮之前，做**一次覆盖整段改动范围的终审**。

**为什么逐任务审查不够**：每个任务单独看都对，合起来仍可能有问题——跨任务的接口理解不一致、两个任务用不同方式解决了同一个问题、后一个任务悄悄削弱了前一个任务的保证、整体契约与设计不符。这类问题只有把全部改动放在一起看才现形。

**终审协议**（细节见 `references/dispatch-protocol.md`）：

1. **范围**：从工作流的第一个提交到当前 HEAD 的完整 diff，不是单个任务
2. **模型**：用**当前可用的最强模型**——这是唯一一处刻意升档的地方，因为它是发版门前最后一道关
3. **审查者**：必须是**没有参与过任何实现、也没有做过任务级审查**的独立 subagent
4. **产出**：一个明确判定 `Ready to merge: Yes | No`，外加 Critical / Important / Minor 分级的问题列表
5. **修复**：有 Critical 或 Important 时，派**一个**修复 subagent 带完整问题清单去修（不是每个问题一个 fixer），修完重跑验证。**只有一波修复**——再来一轮就说明问题不在实现而在计划或设计，停下来重新想
6. **Minor 不进修复循环**：逐条裁定，写明"修 / 留作后续 / 不修"，记进账本裁决区

**终审同时做两件事**（同一个 agent、同一份报告，不额外开一轮）：

- **设计文档回写**：把 `接口与数据形状`、`已知限制`、**`实际交付`** 按**实际实现**补齐，核对已有小节是否与代码相符。终审者逐节比对，产出两份清单——「文档与实现不符」（含失实陈述与漏记）和**「实现偏离了文档里的决策」**（这一栏不要默认改文档迁就实现：先判断哪个对，裁定结论留痕）。**`grep` 级验收抓不出失实陈述，只有逐节比对能抓**
- **决策上浮**：把这一路产生的判断从报告和账本里捞出来，按上面那张表归位

**`实际交付` 是这一波必须补上的**：它是"当时到底改了什么"的唯一长期记录（交付物清单 + 与计划的偏离及原因 + 遗留项）。留成起草时的「无（尚未实现…）」会让 `close` 直接拒绝收尾。

判据一句话：**如果这个工作流明天被删掉，哪些结论是你希望六个月后还能读到的？** 那些就是必须写进设计文档的。

**回写必须在 `verify` 之前完成**——验证记录绑定的是整个工作树的指纹，验证之后再改文档会让指纹失配，`close` 会拒绝收尾。

**改完文档要重跑 `check`**：十节齐不齐、决策摘要有没有覆盖全部 `D-NN`，引擎会替你核一遍。

终审判 `No` 且修复波次用完之后仍不过，就不是继续修的问题了——回到 P 轮重新审视计划，把裁决记账。

### V 轮：验证、补证与人工验收

进入 V 轮先读 [`references/verification.md`](references/verification.md)，按条目类型选外部证据，核对具体产物；代码、声明与实际交付物不能混同。

1. 设计文档与计划验收先定稿，再 `verify <slug>`。读取命令 `exit_code` 和整体 `passed`，不把命令成功当作完成。
2. 必验人工项待确认时报告“实现完成，等待人工验收”；先用 `acceptance` 展示 ID、具体步骤与预期。用户可一次明确确认清单中的多项，`confirm` 为每项记录原答复和来源；部分确认只记录部分，“继续”不算验收。
3. 必验证据 unknown/missing 时保持待核实，先检查已有结果和引用，用 `evidence` 关联同周期、同工作树、同验收要求的最近一次验证；不因格式问题盲目重跑，也不把待核实直接叫实现失败。
4. 只有确认是实现缺口才追加任务、回 E 轮。取消/改必验要求须有明确用户依据；用逐项 `waive` 记录豁免或按审批模式更新计划，不能自行改成可选。
5. 只有全部必验项通过或获明确豁免，最近计划命令成功、绑定有效、输出与完整引用链未损坏，才可 `close`。泛人工确认不能覆盖自动失败。

**遇到失败或旧工作流恢复**：按 [`references/verification.md`](references/verification.md) 的状态分流和失败表处理。该文件同时规定保守失效、只补证不重跑、无命令边界和 close/reopen 兼容；不得凭旧 Markdown PASS 拼造新证据。

## Exit Criteria

P 轮完成需满足（gated 路径）：

- [ ] **审批模式**已明确为 `gated`；老计划没有该字段时按 gated 处理
- [ ] **方案的载体已定**：`**设计文档**` 已声明（项目仓库内的路径，或 `无 — <理由>`；命中四条判据的必须写一份）
- [ ] 方案的五段（一句话方案 / 背景与目标 / 做法 / 备选与取舍 / 明确不做）都已写、无占位符——声明了设计文档时在设计文档里，声明「无」时在计划的 `## 方案`
- [ ] 有设计来源时，承接关系已写明（源路径 + 继承什么 + 本次增量）
- [ ] 方案已呈现给用户，**得到明确答复**，并以 `approve <slug> 方案 --by` 记账
- [ ] 方案门的呈现是散文与用户决策，没有把任务块的执行指令端上去
- [ ] 声明了路径的：其余小节已补齐，十节齐全、无空节、无占位符，`决策摘要` 已覆盖全部 `D-NN`
- [ ] `$W check` 零 ERROR
- [ ] **计划语义审查已做（独立只读 subagent），BLOCKER 为零**；残留 WARNING 已随计划一起呈报用户
- [ ] 每个任务都有 `做法` / `预期` / `验收` / `失败信号` 四个字段，且都可判定、可观察
- [ ] 每个决策 `D-NN` 都至少被一个任务引用（无范围缩减）
- [ ] 四类敏感决策的来源都是 `用户`，不是 `agent` 自行决定
- [ ] `## 验证覆盖` 已填：每条决策都有验证手段，**且显式列出了不验证的部分**
- [ ] 验证命令已声明，或明确标为 `未声明`
- [ ] 计划门的呈现只含目标、用户决策、阶段与任务名、验证覆盖概要、语义审查结论——**不含任务块的五个执行字段**
- [ ] 计划超过 8 个任务时，决策表里有一条显式接受超限的取舍记录（或已拆成多个工作流）
- [ ] 计划已呈现给用户，**得到明确答复**，并以 `approve <slug> 计划 --by` 记账

**execution 路径**的 P 轮完成需满足：

- [ ] `**审批模式**: execution`，并有 `**审批模式依据**`，说明规格/范围/规则/验收来源和没有新增判断的理由
- [ ] 方案承载位、承接关系、设计文档归属与决策表仍已写全；不能因为不走门而把方案和决策省掉
- [ ] `$W check` 零 ERROR，独立计划语义审查 BLOCKER 为零
- [ ] 每个任务都有可执行的 `做法` / `预期` / `验收` / `失败信号`，每个决策都有任务承载和验证覆盖
- [ ] 不调用 `approve`，不伪造“用户已批准”；计划审查无 BLOCKER 后直接进入 E 轮
- [ ] 发现新的范围、方案、取舍、契约或安全/数据边界判断时，先停止派发并运行 `$W gate <slug> --reason ...`

**bug 路径**（免两道门）的 P 轮完成需满足：

- [ ] `## 复现` 有可复现的最小步骤，且**修之前确认过它确实失败**
- [ ] `## 根因` 说清了为什么错
- [ ] 验证覆盖表里有明确标为**回归测试**的一行
- [ ] 验证命令已声明（bug 工作流不允许 `未声明`）
- [ ] `**设计文档**` 已声明（bug 通常写 `无 — <理由>`，但**不能空着**）
- [ ] 上述各项之外，与通用 P 轮相同（`check` 零 ERROR、任务字段齐全、决策被承载）

E 轮完成需满足：

- [ ] 每个完成的任务在账本里有对应行，含**校验过的**提交范围（sha 真实存在、范围非空）
- [ ] **改动是分阶段提交的**：没有把多个任务攒成一次提交
- [ ] **没有 push / merge / rebase / 发布**（除非用户明确要求并有记账）
- [ ] 每个任务都经过了独立审查（审查者非实现者）
- [ ] **整段改动经过了整体终审，且判定为 `Ready to merge: Yes`**（或修复波次后转 Yes）
- [ ] **设计文档已按实际实现回写**：`接口与数据形状` / `已知限制` / **`实际交付`** 三节都已按实现补齐，终审的「文档与实现不符」清单已逐条处理（改文档或说明）
- [ ] **「实现偏离了文档里的决策」已逐条裁定**（改实现 / 改文档并说明口径变化 / 记入已知限制），没有把文档悄悄改成实现的样子
- [ ] **执行期新增的判断已上浮**：进设计文档决策摘要、或回填计划（并重新审批）、或裁定不采纳并记理由
- [ ] 所有裁决已记账（不是只存在于对话里）
- [ ] `$W next` 报"没有可执行的任务"

V 轮完成需满足：

- [ ] 条目按对应外部手段验证，设计文档在验证前回写；不能用本仓库 diff 代替外部状态
- [ ] 当前周期的计划命令成功，运行前后稳定，工作树与验收绑定有效；无命令须满足明确人工验收边界
- [ ] 必验自动化无 unknown/missing，原输出和全部已采纳引用的摘要完整
- [ ] 必验人工逐项通过；允许明确清单一次答复、逐项记录，未选项保持 pending
- [ ] 可选项事先声明；豁免指向具体项并有用户答复、理由和来源，不能豁免命令失败
- [ ] `$W close <slug>` 成功，保存本周期快照；记录保留，历史 close 不覆盖

## Exit Protocol

**收尾用 `close` 记账，它同时是门**：

```bash
$W close <slug> --next-step "<给用户的下一步建议>"
```

`close` 汇总当前周期的任务、设计文档、验证绑定、引用链和逐项验收。`--manual-confirmed` 不再放行活跃工作流，旧人工授权应通过 `confirm` 如实逐项登记；无命令不等于空验收可过。详细拒绝条件见验证 reference。

成功后汇总裁决、报告验证与人工/豁免证据、给出设计文档路径；保留 `.workflow/<slug>/` 中的计划、事件、旧账本、receipt 和报告。重复 close 不再记一条；后续修补按路由显式 reopen，保留旧结论。

**本 skill 的职责到报告为止。** 不改代码、不写长期记忆、不更新项目契约。**收尾之后做什么由用户自己判断**——包括是否把产出写回别处；那是用户的决定，本 skill 不代判、不探测、不代办。

**报告要求**：给文件路径和可点的锚点，不要复述长内容；不要把"没有验证的推测"写成结论。

**未完成就要中断时**：说明当前任务、已完成到哪一步，并给出一条可直接粘贴的恢复指令——`先运行 status <slug>，读 plan.md、ledger.md、events.jsonl 与关联证据，从 <任务或待验项> 继续`。**`reports/` 保留不动**：那是任务执行细节的重要依据。计划、旧账本、事件与输出/报告共同支持跨会话恢复；要不要额外生成交接文档，同样由用户判断。
