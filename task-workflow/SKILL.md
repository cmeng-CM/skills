# Task Workflow

把需求变成 `<project>/.workflow/<slug>/` 下的计划与账本，逐任务派 subagent 执行，最后用可执行的外部证据验证到通过。计划与进度落在磁盘上，所以上下文被压缩或清空后仍能精确接续。

引擎脚本在**本 skill 目录**下（即本 SKILL.md 所在目录的 `scripts/workflow.py`，下文记作 `$W`）。各客户端通过软链指向同一份文件，所以从任意客户端的 skills 目录取到的都是同一个脚本。安装后可用 `python3 ~/.agents/skills/task-workflow/scripts/workflow.py` 直接调用。

所有状态操作都走 `$W`——不要手改计划里的状态字段和账本表格。

**守卫：**

- **没有计划不执行。** 执行轮的前置条件是一份通过了 `check` 的 plan.md。直接开干等于放弃这套机制的全部价值。
- **没有外部证据不算完成。** 模型自述"做完了"不是证据。跑验证命令、看退出码、对内容指纹——这才算。
- **计划是唯一的任务来源。** 不在计划里的工作不开工；发现该做的事，先写进计划再执行。
- **边界。** 需求本身有歧义 → 交给 `delve`；理解陌生项目 → `project-learning`；换人接手 → `session-handoff`。本 skill 不越界。
- **收尾之后不由本 skill 决定。** 工作流跑到验证通过、报完账本就结束。要不要把产出写回别处（项目契约、长期记忆、知识目录、周报），由用户自己判断——**本 skill 不代判、不探测、不代办**。

- **阶段边界必须停，等用户明确答复。** 方案写完停一次，计划写完停一次。这是审阅门，不因任务小而省
- **没有答复不等于可以继续。** 用户没回答就停住并报告，把问题留在那里等——不要用"没收到答复"当默许
- **但阶段内部不要停。** 执行轮里能自己拍板的事自己拍板并记账，不为每个小决定打断用户
- **只读的活可以并行，写操作一律串行。** 调研、多路审查、排查多个独立失败——这些不写文件，放心并行，等待时间直接除以 N。改文件的实现者一次只派一个（写面没隔离，见 `references/dispatch-protocol.md`）

**反模式（明确不要做的事）：**

- 不要在需求还有歧义时硬写方案——那是"计划会乱"的直接原因
- 不要在方案门/计划门处"呈现完就顺手开始做"——呈现和开工在同一口气里完成，等于没有门
- 不要用"用户没回答"当作默许继续——那是绕过门，不是通过门
- 不要把整个 plan.md 塞给执行者——用 `slice` 抽单任务片段
- 不要让实现者自己审查自己的代码
- 不要在审查 prompt 里写"不要报 X"，那是预判
- **不要并行派发多个实现者**——它们会改同一个工作树（**但只读 agent 并行是允许且鼓励的**）
- 不要把同型机械改动拆成一文件一任务，也不要逐个派——合成一个任务或一批
- 不要让控制器（你自己）动手修代码——写和审必须解耦
- 不要在**执行阶段内部**停下来问"要不要继续"——能自己拍板的事自己拍板并记账
- 不要在验证红灯时说"基本完成了"
- 不要在计划里留任何占位符（TBD / TODO / 待补）——`check` 会拦，但别浪费那一轮

## Working Protocol

### 门：轮次路由

先判定该走哪一轮，判据是状态文件而不是对话记忆：

```bash
$W status          # 报告阶段与任务状态；无 slug 时要求只有一个活跃工作流
```

| 用户的话 / 观察到的状态 | 轮次 |
|---|---|
| 要新做一件事，且没有对应工作流 | **P 轮**（方案 → 计划） |
| 要修一个 bug（有症状、能复现） | **P 轮 · bug 路径**（`init --bug`，免两道门） |
| 方案写好了、等用户看 | **P 轮 · 停在方案门** |
| 计划写好了、等用户看 | **P 轮 · 停在计划门** |
| 有活跃工作流，还有未完成任务 | **E 轮**（执行） |
| 全部任务 complete | **V 轮**（验证） |
| 明确说"验证一下" | **V 轮** |
| 明确说"执行 T3" | **E 轮**（只做 T3） |
| "看看进度" | 只读，报告后停 |
| "计划改一下" | **P 轮**（改计划，改完重跑 check 并**重新审批**） |
| 用户对方案的答复（"可以"/"换个做法"） | **P 轮**：记审批，或按反馈改方案重新呈现 |
| 用户对计划的答复 | **P 轮**：记审批后进 E 轮，或改计划重新呈现 |

### 两套"停"的规则，不要混

这是最容易搞错的一处：

- **阶段边界必须停，等用户明确答复。** 方案写完停一次，计划写完停一次。**"没收到答复"不等于"可以继续"**——没有答复就停住并报告，把问题留在那里等。
- **阶段内部不停。** 执行轮里能自己拍板的事自己拍板并记账，不要为每个小决定打断用户。逐任务的审查由 subagent 做，不找用户。

前一条是**审阅门**，后一条是**自主推进**。历史上两边的失败都真实发生过：门不闭合会导致"计划乱、内容不全"（没人拦），而阶段内频繁停会让人守着屏幕（有会话在一个本可自己拍板的问题上停了 9 小时）。**该硬的是边界，不是内部。**

**上下文被清空后的恢复**：不要相信自己对这个工作的回忆。`status` + 读 `<project>/.workflow/<slug>/ledger.md` + `git log` 三者对齐后再动手。账本的 `## 审批` 段会告诉你哪道门已经过了。

多个活跃工作流且用户没指明是哪个时，列出来让用户选，不要猜。

### P 轮：需求 → 方案 → 计划（两道审阅门）

P 轮分两段，**每段末尾都是一道必须停下来等用户答复的门**。

#### P1 · 需求 → 方案

**第 1 步 · 判需求是否够清楚。**

不清楚就交给 `delve`（见 `references/integrations.md` 的判据与降级路径）。**不要在有歧义时硬写方案。**

**第 2 步 · 拿项目约定和验证命令。**

先直接读项目根的 `AGENTS.md` / `CLAUDE.md` / `README.md`。读得到验证命令就不要调 `codebase-onboarding`。拿不到就**问用户**，不要猜一个默认值。

**第 3 步 · 建工作流骨架，写 `## 方案`。**

```bash
$W init <slug> --goal "<一句话目标>"
```

按 `references/plan-format.md` 填 `plan.md` 的 `## 方案` 一节——三段：**做法**、**备选与取舍**、**明确不做**。

篇幅**随任务规模伸缩**：小改动 2-3 句话就够，大改动才写成一节。但方案这一步本身不因任务小而省——省的是字数，不是这道门。

**第 4 步 · 🚧 方案门。**

把方案呈现给用户，**停下来等明确答复**。得到答复后：

```bash
$W approve <slug> 方案 --by "<用户的原话>"
```

用户说要改，就改方案再呈现一次。**不要在没有答复的情况下继续写计划。**

#### P2 · 方案 → 计划

**第 5 步 · 写任务与决策。**

- **决策表**：把讨论中敲定的每个决策编号 `D-01`…，并标注**来源**（`用户` / `agent`）。这张表是需求的锚点，后面每个任务都要引用它——漏一个都会被 `check` 拦下
- **决策的来源不是形式**：属于「**输入容错**（遇到非法输入是报错还是跳过）、**输出格式取值**（字段名、精度、单位）、**范围边界**（做什么不做什么）、**兼容性影响**（是否破坏既有行为）」这四类的决策，**必须停下来问用户一次**，不能自行决定后只记进表里。其余细节可以自行决定并标 `agent`。判据是"这个选择会直接影响用户看到的行为吗"——会，就问
- **任务**：垂直切片（每个任务穿过它需要的全部层，不要"先 DB 阶段再 API 阶段"）、每任务 2-5 分钟、单任务不超过 5 个文件
- **同型机械改动合成一个任务**：改常量、改字段名、同样的调用替换重复在多处时，那是**一个任务**（可覆盖多个文件），不是一文件一任务。判据是"这次改动需要自己的判断、自己的测试、自己的审查面吗"——不需要就合并。拆成三个任务 = 六次派发（实现者+审查者各三次），合成一个只要两次，**而审查、验证、覆盖审计一样不少**。这不是按体量开快路径，是省掉纯重复的流程
- **每个任务八个字段都要填**，尤其 `验收`（必须可判定）和 `失败信号`（必须有可观察的反面）。没有失败信号的验收标准等于没写
- **写 `## 验证覆盖`**：每条决策都要说明"用什么证明它对"，并**显式列出不验证的部分**。验证范围不写出来就是隐式的、无法审查——而没验证的东西才是风险所在
- **接口字段写精确签名**：执行者只看得到自己那一个任务，`接口` 是它了解邻居任务用什么的唯一渠道
- **用户可见的改动要带上文档任务**：这次改动如果改变了用户可见的命令、选项、输出或行为，计划里要有一个更新 README/用法文档的任务；决定不更新时，把它作为一条决策写清理由。漏掉文档不会让测试变红，所以它只能靠计划兜住

**第 6 步 · 检查计划，必须过。**

```bash
$W check      # 有 ERROR 时不得进执行轮，也不得申请审批
```

`check` 会查：依赖引用是否存在、有没有循环依赖、必填字段、决策是否都有任务承载（范围缩减检测）、决策来源、占位符、规模、验证命令是否声明。

根据反馈修计划，直到零 ERROR。这一步不能跳过——**计划里的洞，到执行轮会变成返工，代价高一个数量级。**

**第 7 步 · 🚧 计划门。**

把计划呈现给用户，**停下来等明确答复**。得到答复后：

```bash
$W approve <slug> 计划 --by "<用户的原话>"
```

**这两道审批是机器强制的**：`slice` 和 `record`（也就是派发任务和记录完成）都会检查审批是否存在、以及**方案/计划是否在审批之后被改动过**。批准后偷改计划 → 审批自动失效 → 必须重新审批。这条不是靠自觉。

**没有答复时的正确行为**：停住，把"正在等用户对方案的答复"作为状态报告出来，不要用"用户没回答"当作默许继续。用户明确说"直接做，不用给我看"时，用 `--by "用户说：直接做，不用给我看"` 把用户的话记成审批依据——**是用户绕过门，不是你自己绕过**。

### bug 路径（免两道门，但另有三项强制）

bug 的"需求"是一个**症状**而不是规格，没有可审的方案——要做的事已经被症状决定了大半。所以 bug 工作流**免两道审批门**。

```bash
$W init <slug> --bug --goal "<症状>"
```

补偿控制是**三项强制**，它们替代门起的作用：

| 强制项 | 为什么 |
|---|---|
| `## 复现`——可复现的最小步骤或命令 | 没有可复现的失败，就无法证明修好了。**修之前先确认它确实失败** |
| `## 根因`——说清为什么错 | 说不清根因就只是在让症状消失，换个输入就复现 |
| **回归测试**——验证覆盖表里必须有一行标为回归测试 | 修复不带回归测试，同一个 bug 会回来，而且回来时没人记得修过 |

`check` 会拦空节和缺失的回归测试；`verify` 会核对回归测试**真实存在**；`close` 照旧要求验证通过。

**验证比常规更严**：复现用例必须从失败变为通过 **+ 全量测试不回归**（修复最容易打破别处，特别要检查是否改动了共享函数或默认值）。

**不夹带无关改动**——顺手重构是 bug 修复最常见的坏味道。要重构就单独开一个工作流。

**期望行为要确认一次**：有时"bug 报告"本身有歧义——用户觉得是 bug，其实是有意行为。所以开工前用一句轻确认："当前行为是 X，期望行为是 Y，是吗？" 这不是审批门，是确认对问题的理解。

**升级条件**：复现不出来 / 根因不明 / 需要改 3 处以上或跨模块 / 涉及数据正确性、安全、并发 / 发现要改的是一段设计 —— 任一命中就改走完整路径（此时它实际是"探索 + 改造"，不是"修复"）。

### E 轮：逐任务执行

```bash
$W next                    # 依赖图算出的可执行任务（不是线性从头做）；会提示哪些可合并
$W slice <slug> T3         # 抽出 T3 的派发片段
$W slice <slug> T3 T4 T5   # 合并成一批：同型机械改动才这么做（见下）
```

**同型机械改动的逃生通道**：如果计划里已经有几个同型的小任务（改常量、改字段名、加日志），**不要逐个派**——`slice` 给多个任务，一次派发、一次审查、一次 `record`。引擎会先挡掉三类不该合并的情况：批次内含相互依赖、有任务已完成或被阻塞、超过 4 个任务。**判据是任务形态不是数量**——需要自己写测试、自己的判断、自己的审查面的任务必须单独派。详见 `references/dispatch-protocol.md`。

派发、报告契约、四态分诊、fix loop、裁决规则**全部按 `references/dispatch-protocol.md` 执行**。这里只列每轮的固定动作：

1. `next` 拿到可执行任务
2. **记录 base commit**（`git rev-parse --short HEAD`）
3. `slice` 生成片段，派给 subagent
4. 子 agent 回来（≤15 行 + 报告文件）
5. **派第二个 subagent 独立审查**（双判决：规格符合 + 代码质量）
6. 有问题走 fix loop；通过则记账：

```bash
$W record <slug> T3 --commits <base7>..<head7> --verdict clean
```

7. 回到第 1 步

**裁决不停机。** 需要拍板的事自己定并记进账本：

```bash
$W record <slug> T3 --note "<决定> — <理由> — <错的代价>"
```

只有四类事必须停下来问用户：不可逆/破坏性操作、安全敏感动作、工作区之外的副作用（merge/push/发布）、计划坏到每条路都是猜。

### E 轮收束：整体终审（不可跳过）

所有任务都 `complete` 之后、进入 V 轮之前，做**一次覆盖整段改动范围的终审**。

**为什么逐任务审查不够**：每个任务单独看都对，合起来仍可能有问题——跨任务的接口理解不一致、两个任务用不同方式解决了同一个问题、后一个任务悄悄削弱了前一个任务的保证、整体契约与设计不符。这类问题只有把全部改动放在一起看才现形。

**终审协议**（细节见 `references/dispatch-protocol.md`）：

1. **范围**：从工作流的第一个提交到当前 HEAD 的完整 diff，不是单个任务
2. **模型**：用**当前可用的最强模型**——这是唯一一处刻意升档的地方，因为它是发版门前最后一道关
3. **审查者**：必须是**没有参与过任何实现、也没有做过任务级审查**的独立 subagent
4. **产出**：一个明确判定 `Ready to merge: Yes | No`，外加 Critical / Important / Minor 分级的问题列表
5. **修复**：有 Critical 或 Important 时，派**一个**修复 subagent 带完整问题清单去修（不是每个问题一个 fixer），修完重跑验证。**只有一波修复**——再来一轮就说明问题不在实现而在计划或设计，停下来重新想
6. **Minor 不进修复循环**：逐条裁定，写明"修 / 留作后续 / 不修"，记进账本裁决区

终审判 `No` 且修复波次用完之后仍不过，就不是继续修的问题了——回到 P 轮重新审视计划，把裁决记账。

### V 轮：验证到通过

**第 1 步 · 先分类，再判断。**

在判断任何一条是否完成之前，**先把计划里的条目分成四类**——因为 `git diff` 对后三类是**结构性不可见**的，不分类就会把没做的事判成做完了：

| 类别 | 判定手段 |
|---|---|
| `DIFF-VERIFIABLE` | 看 diff 与测试 |
| `CROSS-REPO` | 要去看**另一个仓库**的状态，本仓库 diff 证明不了 |
| `EXTERNAL-STATE` | 要去看外部系统（部署状态、线上配置、第三方后台） |
| `CONTENT-SHAPE` | 要检查产物的**形态**（文件真的存在吗、内容结构对吗） |

**第 2 步 · 路径具体化规则。**

计划条目里写了具体路径的，**必须**用存在性判定：

```bash
[ -f <path> ] && echo DONE || echo "NOT DONE"
```

写了路径就不允许标"无法验证"——"我不想检查"不等于"够不到"。

**第 3 步 · 诚实规则。**

**"处理交付物的代码"不等于交付物本身。** 发一个 markdown 提取库，不等于发出了那个 markdown 文件。不要把"相关代码上线了"当作"这一项完成了"。

**第 4 步 · 跑验证命令并留证。**

```bash
$W verify <slug>            # 用 plan 里声明的命令
```

引擎会记录命令、退出码、当时提交、时间戳和**工作树内容指纹**。指纹由「提交 + 未提交改动 + 未跟踪文件内容」共同决定：之后改了代码、提交了新内容、或新增了文件，指纹都会变，之前那次验证不再算数——这防的是"验证通过后又悄悄改了东西"。反过来，改回原样指纹会复原，所以同内容不会被误判成失效。

**第 5 步 · 审计验证覆盖（这一步不能省）。**

`verify` 会同时核对 `## 验证覆盖` 表：**标自动化的条目，它真的去检查声称的产物是否存在**（文件在不在、文件里有没有那个测试）。对不上就是**覆盖缺口**。

为什么必须有这一步：前面几步只能判断"我要求的都做到了吗"，**判断不了"验证范围本身够不够"**。覆盖表加上"不验证的部分"，才把范围变成可审查的东西。而**声称验证了却拿不出证据，比诚实地说"这个没验证"更糟**——所以：

| 情况 | 处理 |
|---|---|
| 覆盖缺口（声称的产物不存在） | **必须补上，或把它移进「不验证的部分」并说明理由**。有缺口时 `close` 会拒绝收尾 |
| 标`人工`的条目 | **逐项**向用户确认，**不给"一次性确认全部"的选项** |
| 「不验证的部分」里的条目 | 呈现给用户过目——那是本次明确接受的风险 |

**第 6 步 · 未通过的处理。**

把缺口写成**新任务追加回 plan.md**（带 `依赖` 和 `决策` 引用），重跑 `check`，回到 E 轮。重复直到验证通过——**这是"重复直到收敛"的闭环，不是一次性的检查。**

**第 7 步 · 判通过。**

判 `passed` 的条件：**验证命令退出码为 0 + 无覆盖缺口 + 所有人工验证项已逐项确认。** 只要还有未确认的人工项，就不能判通过——符号存在但行为未验证的，不计入通过。

### 失败分支（触发条件 → 一线修复 → 仍失败兜底）

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| `$W status` 报没有工作流 | 用户想新做一件事 → 走 P 轮；用户以为有 → 检查是否在错误的目录下（引擎按 `.git` 定位项目根） | 确认路径后仍无 → 按新任务走 P 轮，不试图从对话里重建旧计划 |
| `slice`/`record` 报"方案/计划尚未审批" | 把该阶段呈现给用户并**等答复**，拿到答复后用 `approve` 记账 | 用户暂时不在 → **停住并报告"正在等用户对 X 的答复"**，不要当作默许继续 |
| `slice` 报"审批已失效"（内容被改过） | 说明改了什么、为什么改，重新呈现给用户并重新审批 | 用户认为不该改 → 把改动回退到已审批的版本，或确认后按新版本重新审批 |
| 方案被用户打回要求换做法 | 改 `## 方案` 后重新呈现，**重新走方案门**（方案审批会自动失效） | 改了几轮仍谈不拢 → 说明需求本身没定清楚，回到第 1 步交 `delve` 澄清 |
| `check` 报"决策没有出现在验证覆盖里" | 给每条决策补上验证手段，或把它移进「不验证的部分」并说明理由 | 某条决策确实无法验证 → 移进不验证清单并列明风险，**不要在覆盖表里凑一个假的** |
| `check` 持续报同一个 ERROR | 读该条 ERROR 的具体指向，改计划对应位置 | 仍不通过 → 说明计划结构本身有问题，考虑拆成多个工作流 |
| `verify` 报覆盖缺口（声称的产物不存在） | 补上那个测试，或把它移进「不验证的部分」并说明理由 | 缺口是要修的工作 → 写成新任务追加回 plan.md，回 E 轮 |
| 想合并的几个任务被守卫拒绝（含依赖/已完成/超 4 个） | 按提示逐个派发，或拆成两批 | 含依赖说明它们是顺序工作 → 逐个派，别硬合 |
| 批次派发后审查发现只有其中一个任务有问题 | 修复只针对那个任务，重审限定在它的改动范围 | 若批次里多数任务都有问题 → 说明这批不是同型改动，改回逐个派发 |
| 有多个活跃工作流，用户没指明 | `$W status` 列出全部，让用户选 | 用户不确定 → 逐个展示 goal 和进度帮他判断，不要猜 |
| 验证命令未声明 | 问用户一次，写进 plan.md 的验证命令块 | 用户也给不出 → 标 `未声明`，V 轮走逐项人工确认，**不判自动通过**。bug 工作流不允许未声明 |
| bug 修着发现要改设计 | 停下改走完整路径（新开工作流，把已查清的复现与根因带过去） | 说不清是 bug 还是改造 → 按完整路径走——多走一道门的代价远小于漏审 |
| 子 agent 连续 5 轮修不好 | 控制器裁决并记账 | 计划本身错了 → 改 plan.md 后重跑 `check`，**并因内容变更重新审批**，再带裁决重派 |
| 验证红但任务都标了 complete | 用缺口任务追加回计划，回到 E 轮 | 反复红 → 检查验收标准是否本身不可判定，改标准而不是改结论 |
| 执行中发现工作流外的新问题 | 记进计划的决策区或新任务，**不在计划外开工** | 与当前目标无关 → 记进账本交给收尾，不扩大本次范围 |

## Exit Criteria

P 轮完成需满足：

- [ ] `## 方案` 的三段（做法 / 备选与取舍 / 明确不做）都已填写，无占位符
- [ ] 方案已呈现给用户，**得到明确答复**，并以 `approve <slug> 方案 --by` 记账
- [ ] `$W check` 零 ERROR
- [ ] 每个任务都有 `验收` 和 `失败信号` 两个字段，且都可判定
- [ ] 每个决策 `D-NN` 都至少被一个任务引用（无范围缩减）
- [ ] 四类敏感决策的来源都是 `用户`，不是 `agent` 自行决定
- [ ] `## 验证覆盖` 已填：每条决策都有验证手段，**且显式列出了不验证的部分**
- [ ] 验证命令已声明，或明确标为 `未声明`
- [ ] 计划已呈现给用户，**得到明确答复**，并以 `approve <slug> 计划 --by` 记账

**bug 路径**（免两道门）的 P 轮完成需满足：

- [ ] `## 复现` 有可复现的最小步骤，且**修之前确认过它确实失败**
- [ ] `## 根因` 说清了为什么错
- [ ] 验证覆盖表里有明确标为**回归测试**的一行
- [ ] 验证命令已声明（bug 工作流不允许 `未声明`）
- [ ] 上述各项之外，与通用 P 轮相同（`check` 零 ERROR、任务字段齐全、决策被承载）

E 轮完成需满足：

- [ ] 每个完成的任务在账本里有对应行，含提交范围
- [ ] 每个任务都经过了独立审查（审查者非实现者）
- [ ] **整段改动经过了整体终审，且判定为 `Ready to merge: Yes`**（或修复波次后转 Yes）
- [ ] 所有裁决已记账（不是只存在于对话里）
- [ ] `$W next` 报"没有可执行的任务"

V 轮完成需满足：

- [ ] 计划条目已按四类分类，`CROSS-REPO` / `EXTERNAL-STATE` / `CONTENT-SHAPE` 的项都用了对应的检查手段
- [ ] 写了路径的条目都用存在性判定过
- [ ] 验证命令已执行，退出码为 0，且当前工作树指纹与验证时一致
- [ ] **验证覆盖已审计：每条自动化条目声称的产物都真实存在（无覆盖缺口）**
- [ ] **「不验证的部分」已呈现给用户过目**（那是本次明确接受的风险）
- [ ] 标`人工`的条目已**逐项**确认（无打包确认）
- [ ] 没有遗留的未确认人工项
- [ ] **`$W close` 已执行成功**（它会拒绝在未验证、指纹不符、或有覆盖缺口时收尾）

## Exit Protocol

**收尾用 `close` 记账，它同时是门**：

```bash
$W close <slug> --next-step "<给用户的下一步建议>"
```

`close` 会在四种情况下拒绝执行——还有未完成任务、账本里没有验证记录、最近一次验证的指纹与当前工作树不符、存在验证覆盖缺口。这几道门把"没有验证不得声称完成"钉在收尾这个边界上。确实无法自动化验证的任务，用 `--manual-confirmed "<谁确认了什么>"` 记录人工确认，同样落账本，**不存在静默通过的口子**。

`close` 成功之后按顺序做两件事：

1. **汇总账本**——把 `## 裁决` 表里的所有行呈现给用户。随工作区消失的裁决等于秘密做的决定。
2. **报告验证证据**——验证命令、退出码、指纹，以及每条计划条目落在哪一类、用什么手段确认的。

**本 skill 的职责到报告为止。** 不改代码、不写长期记忆、不更新项目契约。**收尾之后做什么由用户自己判断**——包括是否把产出写回别处；那是用户的决定，本 skill 不代判、不探测、不代办。

**报告要求**：给文件路径和可点的锚点，不要复述长内容；不要把"没有验证的推测"写成结论。

**未完成就要中断时**：说明当前任务、已完成到哪一步，并给出一条可直接粘贴的恢复指令——`读 .workflow/<slug>/ledger.md 和 plan.md，从 <任务> 继续`。账本自己就能跨会话恢复；要不要额外生成交接文档，同样由用户判断。
