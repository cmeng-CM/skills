# Delivery Plan

把明确的设计依据转成可交接、可审阅的实施安排，让人能理解路径，让 AI 能据此执行并反馈问题。独立使用即可完成生成、审阅或调整；执行流程可以复用同一规范。

## Working Protocol

### 1. 识别模式，按需读取资源

过渡期仅在用户明确点名、本项目明确选择 delivery 体系或 delivery 编排明确委派时使用；普通规划意图不自动替代原有入口。用户选择单独规划不等于授权完整编排。

先承接用户指定材料和已经确认的讨论，确认本次是生成、仅审阅还是调整。不要为走流程重问已确认内容。

读取本 skill 自带的[交付约定](references/delivery-contract.md)，确定工作目录、输入输出与版本记录。独立使用不要求先有独立设计文件、编排器或 `.workflow`；组合使用时承接调用方给定的范围和目录。

| 模式 | 读取资源 | 产物 |
| --- | --- | --- |
| 生成计划 | [准备规则](references/preparation.md)、[规划规范](references/plan-standard.md)、[文档骨架](assets/plan-template.md) | 覆盖全局、当前工作足够细化的计划 |
| 仅审阅 | 规划规范、[审阅方法](references/review.md)及被审阅材料 | 有证据、影响范围和修订建议的问题清单 |
| 调整或细化 | 准备规则中的基线与调整要求、规范中受影响部分、审阅方法 | 一致的有效正文、ID 映射及变更影响记录 |
| 成文自检 | 审阅方法；文档已保存且 Python 3 可用时运行 [check_plan.py](scripts/check_plan.py) | 语义检查结果、机械检查结果与未检查范围 |

只加载当前模式需要的资源。需要理解任务卡、联合验证或决策记录的实际写法时，再看[完整示例](references/example-plan.md)。示例是虚构应用，不能把其中路径、命令、平台能力或确认状态带入真实项目。

### 2. 检查依据，解决当前缺口

- 不强制先有独立技术方案；明确的小改动可以在计划内记录设计依据。技术机制和验收仍须足够明确。
- 查验相关代码、测试与项目规则，区分已存在、计划新增、推断和待核实。按任务需要定位，不扫描无关目录。
- 已确认决定连同理由、前提、适用范围一起承接；关键决策的判断来源和确认状态分开记录。
- 影响当前规划的设计选择逐项沟通，给出事实、影响、选项与推荐。未决问题明确阻塞范围；可继续规划不受影响部分。
- 规划活动不授予执行、测试、发布或修改执行状态的权限。只审阅时不擅自改写；写入范围与已有授权保持一致。

### 3. 编制、审阅或调整

按规划规范覆盖七章语义，默认使用统一骨架。小改动可以合并表达；七章的必要信息不省略，也不按项目大小维护多套标准。

采用“全局完整规划、分阶段细化”，小改动一次写完整。未来阶段至少明确成果、设计依据、主要依赖、验收归属和细化触发条件；当前阶段必须补齐执行所需材料与步骤。细化状态与实施、验证状态分别记录。

任务按交付边界拆分，不按固定分钟数、文件数或独立测试次数拆分。任务必须有验收归属，可以由验证组统一提供证据。同组前置产物已实现且满足明确的可接入条件即可继续；必须先通过的门禁仍有效。组间启动条件按声明判断，阶段不自动形成屏障。

实施按交付任务组织，独立实现审查按风险和集成边界组织，验证按验收要求组织，三者不要求一一对应。按规范第 5 章声明审查覆盖、提前门禁、整体验收与整体审查；不能以实施者自检替代独立审查。

图表按信息关系选择：范围、覆盖、状态和条件用表格；分支、并行和门禁用依赖图配条件；复杂控制分支用流程图；交互可精确引用设计时序图。步骤保持有序动作，不用图代替执行细节。

调整时保留稳定 ID、旧新映射和变更依据，核查受影响依赖、覆盖及证据；改变关键设计、契约或验收时先反馈并确认。不得通过改写计划绕过设计约束。不要把自检、用户确认、代码实现和验收通过混为一种状态。

### 4. 自检与交付

按审阅方法检查设计承接、任务可交接性、联合依赖、验证充分性和变更边界。修正已定事项的遗漏；新增设计选择返回讨论。检查脚本只提供有限的机械证据，所有未覆盖的结构与语义仍需审阅。

已有执行流程时，承接其明确的上下文、产物路径、已有确认与记录入口；不要求 `.workflow` 目录或任何特定引擎。格式或约束与交付约定冲突时说明具体影响，先确定处理方式。执行流程特有的字段由接入方补充，不改变本规范的七章语义。本 skill 只维护计划定义、细化与变更影响，不自行串联其他交付能力，也不接管运行状态或宣布整体交付完成。

组合使用仍交付可读 Markdown，由编排器读正文并形成绑定版本的准入快照；独立使用者不需要生成编排 JSON。计划中的作者、自检、确认与当前可交接范围必须如实，不能以结构检查成功替代语义接纳。

## Exit Criteria

- [ ] 输入、代码基线、范围、已有决定及其确认依据可识别；设计缺口和阻塞范围明确。
- [ ] 已知交付与验收覆盖完整；当前工作可交接，后续阶段的细化范围和触发条件清楚。
- [ ] 产物可接入、验证门禁、设计条件与资源交接分别说明；联合依赖无环。
- [ ] 验证组、整体验收及有效证据复用有明确安排，未机械要求逐任务独立验证。
- [ ] 独立审查覆盖、提前门禁及整体审查有明确安排，联合依赖包含这些条件且不自锁。
- [ ] 实施、验证、细化、计划确认等状态区分；没有虚构执行结果、确认凭据或成功证据。
- [ ] 语义审阅完成，机械检查结果及未检查范围如实交代；调整保留 ID、历史和影响关系。
- [ ] 正式产物、依据、适用版本与未解决事项已按交付约定留存；对话交付或保存受阻时如实说明。

## Exit Protocol

生成或调整时交付正文或实际保存路径，说明计划状态、当前可细化范围、阻塞、检查结论及其局限。仅审阅时按审阅方法输出发现与核实范围，不未经授权改写。

正式活动按交付约定留存产物与阻塞；用户明确只讨论、只在对话交付或不写文件时遵从其范围，并说明尚未形成落盘产物。新建正式计划默认保存到项目内 `docs/delivery/YYYY-MM-DD-主题/plan.md`；同一目标继续沿用原工作目录，已有明确指定的计划原位调整。实际计划不保存到 skill 目录。源文档与实际执行记录保持各自权威，不在计划中制造第二份实时状态。

维护本 skill 时使用 [behavior-cases.json](tests/behavior-cases.json) 验证真实行为；脚本测试命令为 `python3 -B -m unittest discover -s <skill目录>/tests -p 'test_*.py' -v`。日常规划不加载测试文件；测试用例存在不等于行为已通过验证。
