# Project Learning

帮助用户真正学会一个项目：产出以**系统如何运行**为骨架的认知地图与模块精讲，并作为陪读者随用户下钻逐步加深，直到用户能在脑中重建这个项目的运行模型。产物是给学习者的讲解与阅读路径，不是审计报告。

## Working Protocol

本 skill 是一个跨会话的学习循环，每次调用先判断处于哪一轮：

```text
<project>/.context/project-learning/00-map.md 不存在 -> 首轮：建图
00-map.md 已存在                               -> 续学：读取学习状态，按用户指令下钻 / 答疑 / 校验
用户要求"考我 / 我复述你看对不对"               -> 校验轮（任何时刻可进入）
```

### 首轮：建立全局地图

1. **确认对象与落点**。确认分析对象（整个项目或指定部分）；确认一次产物目录（默认 `<project>/.context/project-learning/`），用户已指定或授权过则不再问。若项目过大，选择最能代表系统运行方式的主线建图，并在地图中写明未覆盖范围。

2. **以运行结构组织认知，而不是以设计原则组织**。地图的骨架是系统怎么转：启动与装配 → 输入如何进入 → 核心执行流程 → 输出/副作用 → 状态与持久化 → 失败与恢复。设计取舍（为什么这么设计、牺牲了什么）作为各环节的"为什么"融入叙述，不单独成章。这样组织是因为学习者的心智模型是沿数据和控制流生长的，不是沿原则清单生长的。

3. **至少一条端到端主线 trace**。选系统最典型的一次完整运行（如"用户发一条消息之后发生了什么"），从入口到落盘逐步讲，每步格式固定为"一句人话说明这步发生了什么和为什么 +（file:line）"。这是全图中最值钱的部分——没有它，地图只是组件清单。

4. **绘制运行图**。用嵌入式 Mermaid 画帮助建立心智模型的图（典型：主线时序图、状态/生命周期图、组件与数据流向图）。每张图必须降低一项真实认知成本；图种按问题选择，不为配图而配图。

5. **给出下钻菜单**。列出值得下钻的模块，按学习价值排序，每项一句话说明"这里面有什么值得学的"（如"会话生命周期——generation/lease 失效协议是并发一致性的核心"）。菜单是主动规划的学习纵深，不是等用户自己发现。

6. **建立术语表**。收词标准以读者为准，不以"是否项目自造"为准：项目私有概念（lease、ledger 这类不查代码无从知晓的词）**和**正文承重的行业黑话、借用隐喻（transcript、overlay、capabilities、栅栏/fencing 这类），都在地图开头集中一行一释义。判定测试：这个词删掉正文就讲不通，且不能假定读者认识——两条都满足就收。正文可以放心使用这些词，读者卡住时有地方查——这是控制正文解释负担的前提。

7. **建立学习状态区**。地图开头维护：已下钻模块（链接到 modules/ 文件）、待下钻菜单、遗留疑问。这是跨会话续学的入口。

写入 `00-map.md`，结构：

```text
<project>/.context/project-learning/
|-- 00-map.md          # 学习状态 + 术语表 + 运行模型 + 主线 trace + 下钻菜单
`-- modules/           # 每轮下钻一个文件
```

### 下钻轮：模块精讲

用户从菜单选择或自由指定模块后：

1. **精讲机制**：该模块解决什么问题（没有它哪里会坏）、机制如何运转（组件、状态、控制流、关键数据结构）、与全局地图的接口关系。深度以"读完能预测该模块在典型场景与异常场景下的行为"为准。

2. **给出代码阅读路径**：面向用户后续精读的导航——"先读 X（file:line）建立骨架，再沿 Y trace 一次典型调用，注意 Z 处的状态转换/易误解点"。这是讲解与自学之间的桥，不可省略。

3. **附自检问题**：3-5 个"读完应能回答"的问题，检验的是机制理解（"为什么这里要递增 generation"），不是名词记忆。

4. **回写**：写入 `modules/<模块名>.md`；更新 `00-map.md` 的学习状态（该模块标记已下钻并链接）；若下钻发现的证据推翻了地图层结论，先修正地图再继续。

### 校验轮：按需考核与复述校正

用户说"考我"时：用自检问题或新构造的场景题提问，逐题等用户作答后再对照代码给出讲评。用户复述理解时：对照代码逐点确认或纠正，纠正必须指向具体代码位置说明实际行为，不笼统说"不对"。校验结果中的薄弱点记入地图的遗留疑问。

### 展现形式（所有产物适用）

学习文档的第一敌人是"读不下去"。密集的代码索引和成片的长文都会让读者中途放弃，因此：

- **锚点是注脚，不是主语**。叙述用领域语言写清"发生了什么、为什么需要这步、没有它哪里会坏"，代码标识符与行号一律放句末括号；禁止"方法名 → 方法名"的裸调用链充当正文叙述。
- **锚点删除测试**（可判定）：把段落里全部代码标识符与行号删掉，剩余文字必须仍然通顺且有信息量；不通过就说明这段是索引不是讲解，重写。
- **深度分层**：运行模型章节 = 人话叙事、每环节只锚关键入口；trace = 每步一句人话 +（锚点）；逐方法的精细调用链只出现在下钻模块文件，且优先收进折叠块。
- **按信息形状选形式**，文字只留给非它不可的内容：
  - 因果、动机、取舍 → 短段落，一段只讲一件事
  - 并列可枚举的事实（组件职责、状态字段、错误分类、方案对比）→ 表格
  - 多对象协作、流程、状态变迁、生命周期 → Mermaid 图
  - 过程步骤 → 有序清单
  - 机制的最小核心代码（如失效协议的关键十行）→ 带注释的代码摘录，胜过三段转述
  - 项目私有名词 → 地图开头的术语表
  - 必须保留但打断主线的细节 → `<details>` 折叠块
- **文字预算**：任何章节连续纯文字不超过 4-5 段，超过就换形式、拆分或删减。宁可标注"此处未展开、可下钻"，也不写一节没人读完的长文。

### 写作纪律（保证内容不失真的内部约束，不是交付物）

- README、架构文档、注释是作者意图的候选，不是事实；讲解的最终依据是当前代码、配置、数据定义与测试。两者冲突时按代码讲，并顺带指出文档已过时。
- 关键判断给出 `file:line` 供跳转验证，但锚点写法必须遵循"注脚不是主语"。
- 静态推演与已核实事实分开：没运行过的行为不写成"已验证"，拿不准就标注"推断"，无法判断就写"未知"，不猜测填空。
- 不用目录名、类名、技术栈名代替机制解释；不把"灵活、可扩展"等形容词当作解释。
- 图不能比证据更确定；关键节点与连线可回溯到正文。
- 以静态分析为主，不主动要求搭建运行环境；用户想跑起来验证时提供跑法建议即可。

## Exit Criteria

**首轮**：`00-map.md` 包含学习状态区、术语表、以运行结构组织的模型叙述、至少一条带 file:line 的端到端主线 trace、按学习价值排序的下钻菜单；一个没读过代码的读者**不翻代码**读完后，能用自己的话说出"这个系统从输入到输出是怎么转的"。

**下钻轮**：`modules/<模块名>.md` 包含机制精讲、带锚点的阅读路径、自检问题；`00-map.md` 的学习状态已同步更新。

**所有产物**：任取一段正文都通过锚点删除测试；正文没有裸调用链；表格、图、代码摘录、折叠块按信息形状使用，无连续超过 4-5 段的纯文字。

**校验轮**：每个考题/复述点都有明确的对错讲评及代码依据；薄弱点已记入地图遗留疑问。

## Exit Protocol

每轮结束：对话中给出本轮产物文件路径、一句话概括本轮新增了什么认知，然后给出续学建议（"下一个最值得下钻的是 X，因为……"），等用户决定方向。不在对话中复制长文，不生成自评式总结。
