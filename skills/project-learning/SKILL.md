description: Quickly build a layered mental model of an unfamiliar software project — a memorizable structural skeleton and core concept model first, then a runtime narrative with an end-to-end trace — then accompany the user through module-by-module deep dives. Use when the user wants to learn or onboard onto a new project, build a holistic view of it ("学一下这个项目"、"建立全貌"、"整体架构是什么"), understand how it works internally, read its source code with guidance, trace how a request/message/event flows through the system, or continue a previous learning session ("继续学"、"下钻某模块"、"带我读源码"). Also use when the user asks to be quizzed on or to verify their understanding of a project being studied. Do not use for bug fixing, feature work, code navigation without a learning goal, or post-learning tasks such as implementing changes or evaluating whether to adopt the project.

# Project Learning

帮助用户快速学会一个新项目：首轮产出分层认知文档——先给一份 10 分钟能读完、合上能背下骨架的**结构 + 概念**速览层，再给**运行主线**的深读层——并作为陪读者随用户下钻逐步加深，直到用户能在脑中重建这个项目的模型。产物是给学习者的讲解与阅读路径，不是审计报告。学完之后的动手改码、选型评估不是本 skill 的职责。

## Working Protocol

本 skill 是一个跨会话的学习循环，每次调用先判断处于哪一轮：

```text
<project>/.context/project-learning/11-map.md 不存在 -> 首轮：建图
  （若 10-overview.md 已存在而 11-map.md 尚未生成，说明首轮中断：续写，不重头再来）
11-map.md 已存在                               -> 续学：读取学习状态，按用户指令下钻 / 答疑 / 校验
用户要求"考我 / 我复述你看对不对"               -> 校验轮（任何时刻可进入）
```

### 第 0 步：探测 codegraph（首轮开工前必做）

判断目标项目是否已有 codegraph 索引：项目根目录存在 `.codegraph/`，或 `codegraph status` 正常返回。

- **有索引**：后续结构清点、符号定位、调用关系分析优先走 codegraph——`files` 拿目录结构与文件元数据，`query` 定位符号，`node`/`callers`/`callees` 看一个符号的上下游，`explore` 一次拿一个区域的相关符号与调用路径。它能替代大量目录列举、文本搜索与逐文件翻找，显著缩短建图时间。但 codegraph 是索引不是事实源：用它**定位**，最终叙述与锚点仍以读到的源码为准。
- **无索引**：不使用，纯静态分析（目录列举、行数统计、文本搜索、读文件）。**不要主动 `codegraph init`**——那会向项目写入上百 MB 的 `.codegraph/`，除非用户明确要求。

### 首轮：建立分层地图

1. **确认对象与落点**。确认分析对象（整个项目或指定部分）；确认产物目录（默认 `<project>/.context/project-learning/`），用户已指定或授权过则不再问。

2. **先摸版图，再写任何叙述**。做一次结构清点：包/目录划分、每块规模（文件数、行数）、依赖方向（谁 import 谁）、入口点。codegraph 可用时以 `files` 起步。同时做一次**能力盘点**：扫入口命令、内置工具/扩展/插件目录、配置面，得到「这个项目能干什么」的清单——只看依赖图会漏掉以扩展、插件形态实现的内置能力，这是防遗漏的关键一步。两份清单是后面所有层的地基：结构地图由前者直接产出，能力清单进速览，概念模型和主线 trace 从它们出发去读码确认。中小项目（约几万行以内）穷尽到目录级；大型项目到模块/包级，并在地图中显式写明未覆盖范围。

3. **写 `10-overview.md`——骨架层**。10 分钟能读完、可独立阅读、合上文档还能凭记忆重画的那一层：

   - **速览**（半页）：一句话定位（项目是什么、给谁解决什么问题）、技术栈、入口点清单、规模数字、能力清单（第 2 步盘点的产物，5-8 条——基于代码的功能盘点，回答"能干什么"，不是定位话术）、一张总览图。
   - **结构地图**（全貌的核心）：完整组件清单表，每行「组件 | 职责一句话 | 关键实体 | 代码位置 | 规模」，配一张依赖方向图（Mermaid）。关键实体是该组件 3-5 个主要导出符号，让结构表兼任代码导航索引——从包名一跳到类名；codegraph 可用时用 `query` 逐包生成。读者要能拿这张表回答"任何一个话题落在哪块代码"。
   - **概念模型**：核心领域抽象（名词）之间的关系图（Mermaid）+ 概念表（概念 | 职责边界 | 谁持有/调用它）。这层回答"这个项目的基本词汇是什么、谁跟谁打交道"。原「术语表」降为本节附录，只收概念表覆盖不到、正文又承重的词；有单一明确代码位置的词带上锚点，让术语表兼任索引。
   - **验收（可判定）**：合上文件，读者能凭记忆重画出「组件 + 依赖方向」骨架和概念关系图。画不出来就是这层没做好，重做——宁可表格再瘦，不可骨架不牢。

4. **写 `11-map.md`——运行层 + 学习状态**：

   - **学习状态区**：已下钻模块（链接到 modules/ 文件）、待下钻菜单、遗留疑问。跨会话续学的入口。
   - **运行模型**：以运行结构组织——启动与装配 → 输入如何进入 → 核心执行流程 → 输出/副作用 → 状态与持久化 → 失败与恢复。设计取舍（为什么这么设计、牺牲了什么）作为各环节的"为什么"融入叙述，不单独成章。注意它只是三个认知层之一，不是全图核心：每环节只锚关键入口，机制细节留给下钻轮。
   - **端到端主线 trace**：至少一条，选系统最典型的一次完整运行（如"用户发一条消息之后发生了什么"），从入口到落盘逐步讲，每步固定为「一句人话说明发生了什么和为什么 +（file:line）」。**主线由第 2 步的结构发现决定**——选穿过组件最多、最能把结构表串起来的那条路，不要先验拍脑袋。
   - **下钻菜单**：列出值得下钻的模块，按学习价值排序，每项一句话说明"这里面有什么值得学的"。菜单是主动规划的学习纵深，不是等用户自己发现。

   绘图规则：用嵌入式 Mermaid 画真正降低认知成本的图（典型：主线时序图、组件与数据流向图、状态/生命周期图），图种按问题选，不为配图而配图。可交互成品图（opt-in）：仅当用户主动要求把「主线 trace」或「模块依赖」画成可交互、能点开看 file:line 的成品时，调用 `archify` skill 生成自包含 HTML，存到 `.context/project-learning/diagrams/` 并在文中链接；默认用 Mermaid 内嵌保底。

产物目录结构：

```text
<project>/.context/project-learning/
|-- 10-overview.md   # 骨架层：速览 + 结构地图 + 概念模型（可独立阅读）
|-- 11-map.md        # 运行层：运行模型 + 主线 trace + 学习状态 + 下钻菜单
`-- modules/         # 每轮下钻一个文件
```

### 下钻轮：模块精讲

用户从菜单选择或自由指定模块后：

1. **先列公开面**：该模块核心类/入口的公开 API 与事件清单，每个一句话——读者先知道"这个模块对外暴露什么"，再读机制。
2. **精讲机制**：该模块解决什么问题（没有它哪里会坏）、机制如何运转（组件、状态、控制流、关键数据结构）、与全局地图的接口关系。深度以"读完能预测该模块在典型场景与异常场景下的行为"为准。枚举型内容（事件、钩子、配置项）给**完整目录**而非抽样——目录本身就是这类模块的核心知识，大目录要分组；模块内有 N 个并行实现（provider 适配器、存储后端）给跨实现的**支撑矩阵**，暴露多条使用路径（SDK/RPC/子进程）给「路径 → 适用场景」**选型表**。
3. **给出代码阅读路径**：面向用户后续精读的导航——"先读 X（file:line）建立骨架，再沿 Y trace 一次典型调用，注意 Z 处的状态转换/易误解点"。这是讲解与自学之间的桥，不可省略。
4. **附自检问题**：检验的是机制理解，不是名词记忆。数量跟随机制数而非固定配额——每个核心机制或设计取舍至少一问（典型 3-6 个）；不为凑数出弱题，也不为守数砍检验。
5. **回写**：写入 `modules/<模块名>.md`，页尾以「关键数据结构 recap 表」（概念 | 类型/接口 | 锚点）收束，让精讲页兼任速查卡；更新 `11-map.md` 的学习状态（该模块标记已下钻并链接）；若下钻发现的证据推翻了地图层结论，先修正地图再继续。

### 校验轮：按需考核与复述校正

用户说"考我"时：用自检问题或新构造的场景题提问，逐题等用户作答后再对照代码给出讲评。用户复述理解时：对照代码逐点确认或纠正，纠正必须指向具体代码位置说明实际行为，不笼统说"不对"。校验结果中的薄弱点记入地图的遗留疑问。

### 展现形式（所有产物适用）

学习文档的第一敌人是"读不下去"。密集的代码索引和成片的长文都会让读者中途放弃，因此：

- **锚点是注脚，不是主语**。叙述用领域语言写清"发生了什么、为什么需要这步、没有它哪里会坏"，代码标识符与行号一律放句末括号；禁止"方法名 → 方法名"的裸调用链充当正文叙述。
- **锚点删除测试**（可判定）：把段落里全部代码标识符与行号删掉，剩余文字必须仍然通顺且有信息量；不通过就说明这段是索引不是讲解，重写。
- **深度分层**：overview 层以表格与图为主——结构表、概念表、两张图就是该层的全部记忆物，正文文字只做粘合，不锚代码细节；运行模型章节 = 人话叙事、每环节只锚关键入口；trace = 每步一句人话 +（锚点）；逐方法的精细调用链只出现在下钻模块文件，且优先收进折叠块。
- **按信息形状选形式**，文字只留给非它不可的内容：
  - 因果、动机、取舍 → 短段落，一段只讲一件事
  - 并列可枚举的事实（组件职责、状态字段、错误分类、方案对比）→ 表格
  - 多对象协作、流程、状态变迁、生命周期 → Mermaid 图
  - 过程步骤 → 有序清单
  - 机制的最小核心代码（如失效协议的关键十行）→ 带注释的代码摘录，胜过三段转述
  - 项目私有名词 → 概念模型层（或其术语附录）
  - 必须保留但打断主线的细节 → `<details>` 折叠块
- **文字预算**：任何章节连续纯文字不超过 4-5 段，超过就换形式、拆分或删减。宁可标注"此处未展开、可下钻"，也不写一节没人读完的长文。

### 写作纪律（保证内容不失真的内部约束，不是交付物）

- README、架构文档、注释是作者意图的候选，不是事实；讲解的最终依据是当前代码、配置、数据定义与测试。两者冲突时按代码讲，并顺带指出文档已过时。codegraph 同理——它是索引，用来加速定位与关系发现，结论以源码为准。
- 关键判断给出 `file:line` 供跳转验证，但锚点写法必须遵循"注脚不是主语"。
- 静态推演与已核实事实分开：没运行过的行为不写成"已验证"，拿不准就标注"推断"，无法判断就写"未知"，不猜测填空。
- 不用目录名、类名、技术栈名代替机制解释；不把"灵活、可扩展"等形容词当作解释。
- 图不能比证据更确定；关键节点与连线可回溯到正文。
- 以静态分析为主，不主动要求搭建运行环境；用户想跑起来验证时提供跑法建议即可。

## Exit Criteria

**首轮**：两个文件齐备。`10-overview.md` 通过"合上重画"测试——读者不翻代码能重画结构骨架（组件 + 依赖方向）与概念关系图，能说出这个项目由哪几块组成、核心概念是什么；`11-map.md` 包含学习状态区、以运行结构组织且锚点稀疏的模型叙述、至少一条带 file:line 的端到端主线 trace、按学习价值排序的下钻菜单——读者读完能用自己的话说出"这个系统从输入到输出是怎么转的"。

**下钻轮**：`modules/<模块名>.md` 包含机制精讲、带锚点的阅读路径、自检问题；`11-map.md` 的学习状态已同步更新。

**所有产物**：任取一段正文都通过锚点删除测试；正文没有裸调用链；表格、图、代码摘录、折叠块按信息形状使用，无连续超过 4-5 段的纯文字。

**校验轮**：每个考题/复述点都有明确的对错讲评及代码依据；薄弱点已记入地图遗留疑问。

## Exit Protocol

每轮结束：对话中给出本轮产物文件路径、一句话概括本轮新增了什么认知，然后给出续学建议（"下一个最值得下钻的是 X，因为……"），等用户决定方向。不在对话中复制长文，不生成自评式总结。
