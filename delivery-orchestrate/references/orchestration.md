# 编排操作与质量协议

## 进入、续接和目录

用户只调用一个能力时，不组织其他能力。完整流程由用户或项目明确选择，已有工作继续所属体系；同一目标不能由旧 workflow 与新编排同时控制。存在多个候选工作目录时按真实目标核对，不能按名字相似合并。

默认目录为 `docs/delivery/创建日期-主题/`，日期不随会话改变。design.md 和 plan.md 维护规范性定义；implementation、review、verification 目录保存带序号的实际活动报告；evidence 保存原始证据；index 只导航；runtime 的状态由脚本独占维护。只生成实际发生的材料。

独立活动可以接入同目标编排，先核对依据、版本和权限，保留原文件。更大范围的上游设计精确引用，不复制成当前目标的第二份设计。

## 路线与质量门禁

| 当前输入 | 先做什么 | 进入下一步的条件 |
| --- | --- | --- |
| 只有需求且机制未定 | design | 目标、关键机制、契约和验收足够明确，重要未决范围已处理 |
| 有适用设计或明确小需求 | plan | 当前任务可交接，全局覆盖与审查/验收安排完整 |
| 有可执行计划 | implement | 依赖和授权满足，范围及版本可识别 |
| 已有实现 | review / verify | 补足真实要求映射、作者与版本，再按标准检查 |
| 有失败或变化 | 对应能力定向返回 | 问题、影响、处理与新的依据均可追溯 |

已有源文档的确认须保留原文、条件和范围。用户“认可”只对应当时明确提出的事项；模型提出不等于未获批准，也不因来自旧实现就算已确认。一般代码局部组织无需逐项批准，重要方案变化按实际授权处理。

plan 不要求每项任务独立运行同一套测试；审查组与验证组可交叉覆盖。提前审查适用于关键契约被下游消费、错误广泛传播、不可逆影响或现有控制不足。整体审查可与最后一组兼任，但必须覆盖所有交付和跨组关系。

引擎 `next` 只反映已接纳的依赖，不证明自然语言的客观接入条件成立。实施者和编排器必须核对实际产物、版本、限制与语义条件，再执行。引擎无法表达的条件不能静默省略，应在准入时声明必要前置或阻塞，并在报告保留理由。

## 委派与身份

根据质量选择主 agent 或子 agent，避免固定“简单主做、复杂子做”。判断上下文掌握、所需工具、专注度、历史结果和可核验性。任务边界明确且文件不冲突时可以并行；共享文件或必要依赖按实际顺序协调。

委派保留原始要求和明确产物路径，子 agent 写自己的报告。编排器直接核对真实变更和证据，再接纳结果；不能仅转述“已完成”。需要沟通新决定时带事实、原约束、方案与影响，已有授权下可继续不受影响工作。

一个任务多个实现者都要如实登记，审查排除全部相关实现者及其上下文。独立者同样需要原始要求和产品上下文；独立不意味着盲审到不知道需求。仅更换名字或角色标签无效。

## 准入记录与检查

编排器先完成语义核对，再准备 JSON。schema、契约和参数按 runtime-api；所有来源路径相对项目根，摘录必须确实存在。来源来自外部会话时，将真实原文与来源说明留在工作目录，不编造当事人确认。

报告和证据的最少存在性检查不能证明结论正确：报告要回答要求、实际行为、证据与限制。检查器发现结构错误时修正真实遗漏，不能降低标准使检查变绿。未知或待验与失败不同，不能混写。

配置变化后默认拒绝旧准入，重新核对受影响对象。需要复用未变结果时显式说明理由与范围，由引擎核对可验证条件；新版本正文不能借旧批准自动放行。仍有效证据可复用，不因换人或换会话机械重跑。

## 命令证据与人工项

正式自动验收用引擎 `run` 执行计划中声明的 argv，以项目根为工作目录，无隐式 shell。需要 shell 时必须在计划中明确命令与权限。诊断命令是定位证据，不能替换必验命令。

记录实际退出结果、完整输出及前后范围快照。失败/超时保留，重试使用新操作 ID；同一 ID 重试用于恢复同一个操作，不用于强行覆盖失败。若执行改了产品，先处理变化再对正确版本验证。

退出码 0 后，验证者仍需按标准判断并写报告。UI、安装包、跨仓库或外部服务验收需要直接检查实际对象，源代码和本地 diff 不能替代。无法访问对象时记录 unknown，不凭经验写通过。

人工项应列清单、操作、预期结果，由真实用户逐项确认；允许一条答复明确覆盖多项，但未确认项仍未完成。提供具体来源与摘录，脚本只核对引用，编排者对来源真实性负责。

## 问题和修复

| 问题性质 | 返回环节 | 对原证据的处理 |
| --- | --- | --- |
| 实现违反既定要求 | implement | 修复后复审及验证受影响范围 |
| 缺任务、错误依赖或验收安排 | plan | 更新映射并核对受影响结果 |
| 机制不成立、契约需改变 | design，再核对 plan | 保留原结论，说明新确认与失效范围 |
| 证据不足或环境不可用 | verify 或环境准备 | unknown不写成实现失败，不制造通过 |

记录稳定问题标识、触发条件、影响、严重度、阻断性及实际处置。已解决问题复发时，遵循引擎实际身份规则新增问题并关联原问题，不篡改旧历史。修复结论应有新版本和验证依据，不是作者一句“修好了”。

同类失败连续两轮没有新事实或改善时，停止原样循环，重新诊断、缩小复现或安排更适合的 agent；记录策略变化。可在原授权内持续解决，但不能因为超轮数自动接受风险或宣布完成。

## 本地提交与收尾

独立调用默认不提交；完整编排按任务拆分和交付边界安排本地提交。用户和项目具体规则优先，不 push。提交前查看当前工作区、暂存区及明确路径，保留原有修改；不要用全仓库暂存把不相关文件带入。

提交可以作为阶段快照，不代表最终质量通过。审查、验证绑定实际文件内容，后续提交若只改变提交标识而文件不变，不应人为使证据失效。若提交过程会改文件或生成产物，按实际范围重新检查。

close 前核对来源当前、全任务实施、独立整体审查、所有必验、问题处置与实际交付说明。首版 limited 只豁免允许例外且已实证失败的验收；实施和审查仍须通过。未知/过期证据和不可豁免条件不进入例外。

关闭后不写入新的活动结果，先 reopen。状态损坏、对象缺失或版本不支持时保留现场，报告恢复需要；不删除 runtime 后重建一个伪装成功的流程。最终报告真实状态、证据、剩余限制和需用户查看的重大选择。
