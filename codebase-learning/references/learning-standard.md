# 学习材料规范

本文件是三阶段内容、格式与证据要求的真源。必需的是信息覆盖，允许按主题复杂度合并或细分章节。模板只提供骨架；生成后替换全部占位内容，移除作者提示。

## 通用规则

### 连贯结构与视觉表达

- 阶段一、二共同构成项目总览；阶段三每个已选主题使用独立指南。模块、机制和符号命名保持一致，使用文内与文档间链接连接相关内容。
- 按用户语言写作，默认中文，保留源码标识符和必要原名。新概念先解释含义，再用于分析；术语密集时补局部术语表。
- 文字解释原因与因果，图表达结构、交互或状态，表承载导航和比较。段落之间要形成解释链，不能用密集短句、表格或概念清单代替原理讲解。
- 每个阶段都包含下文规定的图表。图表附近说明读法、关键观察点和结论；一张图聚焦一个层级或过程，复杂主题拆总图与局部图。
- 优先使用 Markdown 表格与 Mermaid：结构／数据流用 flowchart，参与者交互用 sequenceDiagram，生命周期用 stateDiagram-v2。环境无法渲染时提供清晰的文本图及图例，并说明呈现限制；不能只交付无法阅读的图源码或删除视觉内容。
- 图中节点使用真实模块或机制，连线标明调用、事件、数据传递、共享状态等语义；流程图与源码路线保持一致。学习先后关系单独标注，不与运行关系混淆。
- 不为统一版式凑图数、优缺点数或章节长度。简单关系可复用一张图承担相关作用，复杂内容分节，确保每项必需信息仍可定位。

### 源码与证据

- 每份材料记录项目、分析范围与实际源码基线。Git 项目记录可识别的提交或标签及相关工作区差异；其他来源记录版本标识或来源、日期与限制。
- 源码链接必须来自实际读取的文件和符号；行号是辅助定位，须与当前基线对应。远程仓库优先使用明确版本的链接，本地材料采用从文档位置可解析的相对路径并注明符号；对话中按宿主支持提供可点击位置。
- 作者动机引用实际读过的设计文档、注释、提交或讨论。实现事实引用实现／测试位置；分析推断使用“据此推测”“在这些条件下”等局部说明。无需逐句打标签，但不能模糊关键结论的证据层次。
- README、生成式 wiki 和既有学习材料用于建立线索；关键实现结论要核对当前源码。文档与源码有冲突时写清版本、证据与未解决处。
- 不从模块名、导入关系、注释或一个成功例子直接推导全部运行语义。按关键判断需要追查真实调用、状态写入、配置开关和异常分支。
- 测试源码说明它声明的预期与覆盖场景，不证明测试已执行或所有行为正确。性能、可靠性等经验结论需要相应测量；未运行时明确是静态分析或待实测。
- 无法核实的内容列出具体缺口及其影响。目录完整不等于机制已覆盖；不能宣称已经读完所有代码或掌握所有机制，除非存在相应范围与证据。

## 阶段一：项目地图

目标：用户能说明项目存在的理由、整体如何运行，并找到下一步阅读入口。以下内容按顺序组织。

| 部分 | 必需信息 | 呈现方式 |
| --- | --- | --- |
| 阅读定位 | 项目、版本、分析范围、读完应理解什么 | 简短信息栏与导读 |
| 项目解决的问题 | 用户与场景、问题、总体思路、能力边界 | 简短说明＋问题与能力对应表 |
| 核心设计思想 | 理解系统的关键概念／设计选择、体现位置与依据 | 分项连贯讲解，关联模块及源码 |
| 系统结构 | 主要模块、职责边界、输入输出、交互与依赖 | 系统结构图＋模块职责表 |
| 典型运行过程 | 一个真实代表场景，从输入到结果，数据与控制权如何流转 | 流程图或时序图＋步骤说明 |
| 源码导航与缺口 | 关键入口、相关测试／文档、阅读目的、未核实处 | 源码导航表＋缺口说明 |

**视觉必需项：系统结构图、典型运行过程图、模块／源码导航表。** 模块职责与源码导航可以合为一张表，但要覆盖两者信息。

模块导航建议列：模块、职责与边界、主要输入输出、源码入口。源码路线建议列：顺序、模块／入口、文件与关键符号、重点观察问题。复杂表可拆分，不能把整段说明塞进过宽的单元格。

核心设计思想有证据才能归纳；无法确认作者理念时，说明实现呈现的特征与推断范围，不强凑固定数量。代表场景各主要步骤须能落到实际入口或符号，不能使用通用架构图冒充当前项目。

部署结构、外部依赖、运行模式和领域背景在影响整体理解时展开。本阶段内部机制讲到能够连接全局，完整运行细节与取舍留给选定主题。

## 阶段二：模块学习建议

目标：用户能比较学习价值并选择模块、机制或跨模块问题。与阶段一保存在同一份总览中，沿用模块划分。

### 1. 模块学习建议总表（必需）

| 字段 | 必需内容 |
| --- | --- |
| 模块 | 与项目地图同名，链接到相应说明 |
| 重点机制与学习问题 | 具体机制以及学完应能回答的问题 |
| 学习价值 | 体现的设计思想、通用原理或项目特色 |
| 前置知识 | 必要概念或其他模块的基础理解 |
| 建议优先级与理由 | 建议优先、按兴趣深入或暂缓，以及依据 |

覆盖地图中已识别的主要模块。可以暂缓的模块也说明理由；复杂模块在表后补主题列表，简单模块用一行。尚未检查的候选机制要标明待核查，不能用推测填满清单。

学习问题须能指导实际阅读。例如“状态由谁持有，何时持久化，中断后怎样恢复，对一致性有什么影响”，比“了解状态管理”更具体。建议依据关键路径、设计代表性和知识依赖，不仅依据代码量或个人偏好。

### 2. 推荐学习路线（必需）

简单关系用有序路线，分支或多个前置条件用学习依赖图，附推荐理由。明确区分：

| 关系 | 表达要求 |
| --- | --- |
| 必要前置 | 缺少哪个概念将妨碍理解目标机制 |
| 推荐顺序 | 采用该顺序能怎样建立认识 |
| 可独立学习 | 可以直接选择，必要背景可在指南开头补充 |

用户可以跨过推荐顺序。不要把一个模块的必要背景扩大成必须先完整学习另一个模块。

### 3. 选择入口（必需）

结尾说明用户可选择模块、其中的机制，或横跨模块的问题。对跨模块问题列出涉及部分，后续以问题组织同一份指南。

**视觉必需项：模块学习建议表。** 学习依赖复杂时增加图，不重复放一张没有新增解释作用的系统结构图。

本阶段解释到足以支持选择；交付后等待选择。对话摘要给出推荐起点及理由，不提前自动深挖全部模块。

## 阶段三：模块深度学习指南

目标：配合源码独立阅读，能够解释、推演和评价所选范围的机制。整份材料按五个部分组织，主体按机制展开。

| 部分 | 必需内容 | 形式 |
| --- | --- | --- |
| 学习导读 | 对象、基线与范围、核心问题、必要前置知识 | 简短导读＋信息表 |
| 模块全貌 | 职责边界、输入输出、上下游、内部关键机制及关系 | 机制关系图＋机制清单 |
| 逐项机制解析 | 下文六组问题，覆盖范围内关键机制 | 讲解＋必要的过程图、源码摘录和比较表 |
| 贯通场景与源码路线 | 串起机制的完整场景、读取源码的顺序与关注点 | 流程图或时序图＋源码阅读路线表 |
| 理解收束 | 核心设计结论、适用边界、未确定事项、继续研究的问题 | 简短总结，必要时用边界表 |

### 每个关键机制的必需内容

| 内容 | 要回答的问题 |
| --- | --- |
| 问题与必要性 | 解决什么问题，缺少它会发生什么？用具体情境说明 |
| 基本原理 | 依靠什么思想工作，需要什么前提？区分通用原理与项目选择 |
| 实际运行方式 | 谁触发、谁参与，数据／状态／控制权如何变化，结果怎样产生？关联实现 |
| 关键约束与边界 | 什么条件必须成立，哪些异常或变化会影响结果？ |
| 设计取舍 | 收益、代价、局限、成立条件、有意义的替代方案与适用情境是什么？ |
| 源码观察点 | 到哪里看、观察什么、哪些实现印证解释？ |

六组信息须覆盖，但不要求每个小机制机械拆成六个标题。解释从问题到原理再到实现，图和代码出现在相关讲解附近；关键约束适用时覆盖状态、并发、生命周期、失败、取消、重试和恢复。确实不适用的分支可省略，重要但未核实的行为必须保留为缺口。

机制清单至少区分已分析和待核实；范围过大时先给完整主题结构，再与用户确定本轮展开边界，不静默删掉难点或宣称穷尽。

### 必需的图表与阅读导航

- **机制图**：解释核心关系或行为，并由贯通场景展示机制如何合作。静态关系、交互与状态变化选用对应图；简单主题允许同一张图承担两者作用，复杂主题拆图。
- **源码阅读路线表**：顺序、阅读目的、文件与关键符号、重点观察问题、对应机制。覆盖支撑解释的入口、核心处理、关键边界；测试能帮助理解时加入路线。
- **设计取舍表**：设计选择、解决的问题／收益、代价与局限、成立条件、替代方案及何时值得考虑。可按机制分表，也可合并，必须明确归属，不能用空泛的“性能好、扩展性强”代替分析。

比较以真实问题和约束为基础。没有足够证据评价作者动机或实际收益时标明未定，不为凑备选方案虚构可行性。指出可能的缺陷或技术债时给证据和影响，不仅依据代码风格下判断。

源码摘录是按需内容，保留支撑机制的关键类型、语句或状态转换，说明关注点和必要上下文。省略部分要可辨认；示意伪代码明确标注，不能伪装成仓库原文。

### 深度与继续讨论

读完应能解释机制如何工作、为何在这些约束下选择它、何时可能出问题，并按路线进入源码核对。对话摘要给出主要认识、指南链接、源码起点与尚未解决的问题。

用户提问后定点补查，将有效新结论更新到原有章节及关联图表。情境推演、自测、运行实验和代码练习是可选学习方式，不是获取完整解释的前置门槛，也不能替代必需的原理与取舍讲解。
