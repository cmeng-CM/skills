# Session Handoff

在同一项目内，把"干到哪、接下来干什么、踩过什么坑"落成 `.handoffs/` 下的链式 Markdown 文件，让新会话或新 agent 无需全量历史即可精确接续。两个模式：CREATE（写交接）与 RESUME（读交接）。

**守卫：**
- **不许自由发挥。** handoff 文档只能由本 skill 按本协议产出。脱离协议的"类 handoff 总结"看似正确，但缺链式追踪、缺客观锚点、缺新鲜度概念，会污染 `.handoffs/` 目录。
- **写给读者，不写给作者。** 读者是下一个对本次对话一无所知的 agent，每写一个字段都先想"它看到这个能直接行动吗"。
- **边界。** 本 skill 只做"同一项目内、给下一个 agent 接续干活"的交接。用户要的是跨工具迁移卡（粘贴到另一个 AI 工具里继续）、或给分享链接用的对话总结 → 本 skill 不管，直接说明不做这两类即可。

**反模式（明确不要做的事）：**

- 不要把架构全景、代码常识、容易重新发现的事实塞进 handoff——那是 AGENTS.md / codebase-onboarding 的职责，塞进去只会稀释关键信息
- 不要留 `[TODO]` 占位符——空章节写"无"，占位符会被误认为待办
- 不要擅自修改 `.gitignore`、`CLAUDE.md` 等项目文件——只提示，改动权在用户
- 不要在 RESUME 结尾问"要不要我继续"——恢复的目的就是继续干活，直接干
- 不要默认读整条父链——最新一份通常足够，父链只在涉及早期决策时按需读
- 不要为凑齐八个字段硬编内容——空章节是 feature，硬凑是噪声

## Working Protocol

### Step 0: 模式判定

- 用户要保存/暂停/交接 → 走 CREATE
- 用户要继续/resume/粘贴了 resume 指令 → 走 RESUME
- 用户在问"handoff 是什么"、想手动编辑已有 handoff 文件 → 不执行流程，先回答或确认意图
- 完成大量工作后用户没有提交接 → 只说一句建议（"进展较多，可以说'交接一下'生成 handoff"），不擅自生成

### CREATE 流程

**1. 客观锚点先行。** 先跑 git 拿事实，再写主观总结——防止凭回忆编造状态：

```bash
git branch --show-current
git rev-parse --short HEAD
git log --oneline -5
git status -s
git diff --stat
```

**2. 链式判定（双层，确定父链与 seq）：**

- **Tier A（确定性）**：用户开场粘贴了 resume 指令并指明了父文件 → 读该文件头部，继承其 chain，seq = 父 seq + 1。
- **Tier B（启发式）**：否则在 `.handoffs/` 里找同分支或同任务标签的最新文件。**匹配到只是候选，不是延续的证据**——读候选文件的"待办/下一步"章节比对：当前会话的工作是它的直接后续 → 续链（seq+1，prev 指向它）；🔴 **CHECKPOINT：不明确或不相关时，列出候选文件并等待用户确认，默认开新链（seq=1，prev 为空）**。
- 都不匹配 → 新链（seq=1）。chain 名取任务短 slug（如 `auth-refactor`）。

**3. 按 `references/handoff-template.md` 填八个字段。** 取舍原则：

- **失败方案与坑优先级最高**——这是重新发现成本最高的信息，写不清等于白交接。
- **只装两类信息**："重新发现成本高"的（决策理由、坑、未回答问题）和"未完成"的（进行中、待办、下一步）。架构全景、代码常识、容易重新发现的事实**不写**——那是 AGENTS.md / codebase-onboarding 的职责。
- **空章节是 feature。** 一次修 bug 的会话可能只有状态+下一步，不硬凑完整模板；但不许留 `[TODO]` 占位符。

**4. 写文件。** 路径 `.handoffs/<YYYYMMDD-HHmm>_<task-slug>.md`（时间戳前缀保证按文件名排序即时间序），头部五元组：`chain / seq / prev / branch / base_commit`（当前 HEAD 短 SHA，供 RESUME 做新鲜度检查）。

**5. gitignore 提示。** 检查目标项目 `.gitignore` 是否包含 `.handoffs/`；没有则提示用户加一行——handoff 定位是个人续命卡，默认不入库。**只提示，不擅自改。**

### RESUME 流程

**1. 定位文件。** `ls .handoffs/`；用户指明了文件就直接用。存在多条链时按序路由：**先按当前 git 分支过滤 → 取时间最新**；🔴 **CHECKPOINT：同分支有多条活跃链或意图不明时，列出候选（chain/seq/时间/一句话状态）并等待用户选择**，不擅自猜。

**2. 新鲜度检查（不可跳过）。** 读文件头部的 `base_commit`，对比当前状态：

```bash
git log --oneline <base_commit>..HEAD
git diff --stat <base_commit>..HEAD
git status -s
```

- 0 commit 且工作区干净 → **FRESH**，直接使用；
- ≤5 commits → **轻微过期**，把"handoff 之后发生了什么"作为事实附在摘要后一并呈现；
- \>5 commits、或当前分支与 handoff 的 branch 已分叉 → **过期**。🔴 **CHECKPOINT：明确告知用户并等待选择——人工核对后继续 / 干完当前阶段后重建 handoff；在用户选择前不许按旧"下一步"执行。**

**3. 按需读父链。** 文件有 `prev` 且当前任务涉及早期决策背景时才读父文件；通常最新一份足够，不要默认把整条链读进来。

**4. 接续执行。** 展示状态摘要（当前状态 / 进行中 / 下一步）。🔴 **CHECKPOINT：若 handoff 记录了上任 agent 提出但未获回答的问题，必须原样重问用户并等待回答后再动手**；否则不说"要不要我继续"，直接开始执行下一步——恢复上下文的目的就是继续干活。

### 失败分支（触发条件 → 一线修复 → 仍失败兜底）

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| RESUME 时 `.handoffs/` 不存在或为空 | 明确告知"本项目还没有 handoff 记录"，终止流程，不编造内容 | 用户坚持要恢复 → 改用 `git log` 等客观信息口头重建上下文，或直接用 CREATE 生成第一份 |
| 用户指明的 handoff 文件不存在 | 终止，向用户核实路径或分支是否正确，不擅自猜用别的文件 | 核实无果 → 列出 `.handoffs/` 现有文件让用户重选 |
| CREATE 时 git 命令失败（非 git 仓库） | 跳过客观锚点，该节标注"非 git 项目，无锚点" | `base_commit` 写 null，并在报告中声明：后续 RESUME 方无法做新鲜度检查 |
| 链式判定时读取候选文件失败 | 按无候选处理，开新链 seq=1 | 在新文件中注明"链式判定失败，可能存在未关联的历史 handoff" |

## Exit Criteria

CREATE 满足以下全部条件才算完成：

- [ ] 文件已写入 `.handoffs/`，头部含 chain / seq / prev / branch / base_commit 五元组
- [ ] "当前状态""待办/下一步"两节非空；其余章节允许留空，但全文无 `[TODO]` 占位符
- [ ] 客观锚点（分支、commit、变更文件）来自实际 git 输出，不是凭记忆写的
- [ ] 坑与失败方案已尽力挖掘——如果本轮确实没有，写"无"而不是省略该节
- [ ] `.handoffs/` 不在 `.gitignore` 时已提示用户（未擅自修改）

RESUME 满足以下全部条件才算完成：

- [ ] 已做新鲜度检查并向用户报告级别（FRESH / 轻微过期 / 过期）
- [ ] 上任未回答的问题已原样重问（如存在）
- [ ] 已展示状态摘要，且已直接开始执行下一步或把第一个具体动作摆出来

## Exit Protocol

**CREATE：**
1. 报告：文件路径 + 链位置（`chain: xxx, seq n, prev: yyy`）+ 一句话概括捕获了什么
2. 给出可直接粘贴进新会话的 resume 指令：`读取 .handoffs/<文件名> 并继续 <任务>`
3. 结束，不替用户决定下一步做什么

**RESUME：**
新鲜度报告 + 状态摘要呈现后，本 skill 的职责即完成，立即让位于实际任务——后续动作由 handoff 里"下一步"驱动，不再以本 skill 的名义继续。

**可选：会话开始自动提示。** 如果用户希望新会话自动发现未完成的交接，建议他在目标项目的 `CLAUDE.md` / `AGENTS.md` 自行加一行：`会话开始时若 .handoffs/ 目录存在且含近期文件，提示用户是否接续。` 由用户决定是否添加，本 skill 不自动写入。
